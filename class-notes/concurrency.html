이번 주제는 동시성(concurrency)입니다. 프로그램이 하는 일의 상당 부분은 계산이 아니라 기다림입니다. 웹 페이지가 내려오기를, 파일이 읽히기를, 사용자가 입력하기를 기다립니다. 기다리는 동안 다른 일을 하게 만들면 같은 일을 훨씬 짧은 시간에 끝낼 수 있습니다. 먼저 threading으로 스레드를 만들어 기다림을 겹치고, 여러 스레드가 같은 값을 바꿀 때 생기는 경쟁 조건과 Lock을 봅니다. 이어서 queue.Queue로 일을 나누는 생산자-소비자 패턴, 스레드 관리를 대신해 주는 concurrent.futures, 스레드 하나로 여러 기다림을 다루는 asyncio를 차례로 익히고, 마지막으로 asyncio TCP 에코 서버를 만듭니다. 실습 페이지는 threads, race_lock, producer_consumer, thread_pool, asyncio_basics, echo_server입니다.

동시성이란: 기다림을 겹치기

카페의 바리스타

바리스타 한 명이 커피 세 잔을 주문받았다고 해 봅시다. 커피 머신이 한 잔을 내리는 1분 동안 옆에 서서 기다렸다가 다음 잔을 시작하면 3분이 걸립니다. 첫 잔을 머신에 올려 두고 두 번째, 세 번째 잔도 바로 올려 두면 약 1분이면 됩니다. 바리스타는 여전히 한 명이고 손도 두 개뿐입니다. 달라진 것은 기다리는 시간을 겹쳤다는 것뿐입니다. 이것이 동시성입니다.

바리스타가 세 명이면 세 사람이 정말로 동시에 손을 움직입니다. 이것은 병렬성(parallelism)입니다. 동시성은 여러 일을 번갈아 진행하며 함께 다루는 것이고, 병렬성은 여러 일을 같은 순간에 실제로 실행하는 것입니다. 병렬로 실행하려면 CPU 코어가 여러 개 있어야 합니다.

I/O 작업과 CPU 작업

어떤 일이 빨라질 수 있는지는 그 일이 무엇을 하며 시간을 보내는지에 달려 있습니다.

종류시간을 쓰는 곳예스레드·asyncio로
I/O 작업(I/O-bound)네트워크, 디스크, 사용자 등 바깥을 기다림다운로드, 데이터베이스 질의, 서버의 클라이언트 응답기다림이 겹쳐서 빨라진다
CPU 작업(CPU-bound)계산소수 세기, 이미지 처리, 큰 행렬 곱코어가 하나면 빨라지지 않는다

이 실습에서는 진짜 네트워크 대신 time.sleep으로 기다림을 흉내 냅니다. 잠든 스레드는 CPU를 쓰지 않으므로 실제 I/O 대기와 같은 성질을 가집니다.

이 가상 머신에 대해

브라우저 안의 가상 머신에는 CPU 코어가 하나뿐이고, 에뮬레이션이라 실제 PC보다 훨씬 느립니다. os.cpu_count()가 1을 돌려줍니다. 그래서 기다림을 겹치는 예제는 PC와 똑같이 빨라지지만, 계산만 하는 일은 스레드로 나누든 프로세스로 나누든 빨라지지 않습니다. 코어가 여러 개인 PC에서 무엇이 달라지는지는 아래 CPU 작업 절에서 설명합니다.

threading: 스레드 만들기

스레드란

스레드는 한 프로그램(프로세스) 안에서 따로 진행되는 실행 흐름입니다. 프로그램은 메인 스레드 하나로 시작합니다. 새 스레드를 만들면 같은 메모리(같은 변수, 같은 객체)를 함께 보면서 각자 자기 함수를 실행합니다. 한 스레드가 time.sleep이나 네트워크 읽기로 기다리는 동안 다른 스레드가 실행됩니다.

Thread, start, join

threading.Thread(target=함수, args=(인자,))로 스레드 객체를 만들고, start()로 출발시키며, join()으로 끝나기를 기다립니다. threads 예제의 핵심 부분입니다.

import threading
import time

def download(name):
    print(f"  start {name}")
    time.sleep(1.0)             # waiting: this thread sleeps, the CPU is free
    print(f"  done  {name}")

threads = [threading.Thread(target=download, args=(name,)) for name in FILES]
for t in threads:
    t.start()                   # starts running download(name) in the background
for t in threads:
    t.join()                    # waits until that thread has finished

시작과 기다림을 두 개의 반복문으로 나눈 것이 중요합니다. 한 반복문 안에서 start() 바로 뒤에 join()을 하면 첫 스레드가 끝날 때까지 두 번째 스레드를 시작하지 않으므로 결국 하나씩 실행하는 것과 같아집니다. 모두 출발시킨 다음에 모두 기다립니다.

시간 재기: time.perf_counter

경과 시간은 time.perf_counter()로 잽니다. 이 함수의 값 자체에는 의미가 없고, 두 번 부른 값의 차가 그 사이에 흐른 초입니다. 시계를 바꿔도 영향을 받지 않아 측정용으로 알맞습니다. 측정값은 실행마다 조금씩 다르므로 예제에서는 round()로 반올림해 "about 1 s"처럼 출력합니다.

start = time.perf_counter()
func()
elapsed = time.perf_counter() - start
print(f"about {round(elapsed)} s")
sequential: about 3 s
threaded: about 1 s

스레드 쪽에서는 start 세 줄이 먼저 나오고 done 세 줄이 뒤따릅니다. 어느 스레드가 먼저 출력하는지는 운영체제가 정하므로 순서가 실행마다 달라질 수 있습니다. 여러 스레드의 출력 순서에 기대는 코드를 쓰면 안 됩니다.

스레드에서 결과 받기

스레드가 실행한 함수의 return 값은 버려집니다. 결과가 필요하면 모든 스레드가 볼 수 있는 딕셔너리나 리스트에 넣고, join()으로 모두 끝난 뒤에 읽습니다. start() 직후에 읽으면 아직 비어 있습니다. 결과를 돌려받는 더 편한 방법은 아래 concurrent.futures입니다.

results = {}

def work(name, seconds):
    time.sleep(seconds)
    results[name] = seconds      # each thread writes its own key

# ... start all, then join all ...
print(results)

join을 하지 않으면

join()이 없으면 메인 스레드는 스레드가 끝나기를 기다리지 않고 바로 다음 줄로 갑니다. 그래도 프로그램이 일을 끝내기 전에 사라지지는 않습니다. 파이썬은 데몬이 아닌 스레드가 모두 끝나야 프로세스를 끝내기 때문입니다. Thread(..., daemon=True)로 만든 데몬 스레드는 메인 스레드가 끝나면 함께 중단됩니다. 결과를 써야 하는 지점에서는 반드시 join()합니다.

공유 상태와 경쟁 조건

사라지는 입금

스레드는 메모리를 함께 쓰기 때문에 편리하지만, 바로 그 점이 위험합니다. race_lock 예제에서 스레드 네 개가 하나의 balance에 1000번씩 1을 더합니다. 결과는 4000이어야 합니다.

def deposit(times):
    global balance
    for _ in range(times):
        current = balance          # 1. read
        time.sleep(0)              # 2. pause: another thread may run now
        balance = current + 1      # 3. write back (maybe a stale value)
without lock: expected 4000, got 1001
lost updates: 2999

두 스레드 A와 B가 번갈아 실행되면 이런 일이 생깁니다.

순서스레드 A스레드 Bbalance
1current = balance (10)10
2current = balance (10)10
3balance = 1111
4balance = 1111

입금은 두 번 했는데 값은 1만 늘었습니다. B는 A가 쓰기 전의 낡은 값을 읽었기 때문입니다. 결과가 스레드의 실행 순서에 따라 달라지는 상황을 경쟁 조건(race condition)이라고 합니다. 오류 메시지가 없고, 어떤 실행에서는 우연히 맞기도 해서 찾기 어려운 버그입니다. 예제의 time.sleep(0)은 읽기와 쓰기 사이에서 일부러 차례를 넘겨 이 문제를 매번 드러나게 합니다.

한 줄이어도 안전하지 않다

counter += 1은 한 줄이지만 한 동작이 아닙니다. dis.dis로 바이트코드를 보면 읽기, 더하기, 쓰기로 나뉘어 있습니다.

LOAD_GLOBAL              0 (counter)
LOAD_SMALL_INT           1
BINARY_OP               13 (+=)
STORE_GLOBAL             0 (counter)

실습 가상 머신에서 sleep 없이 counter += 1만 40만 번 하면 대개 400000이 정확히 나옵니다. 지금의 CPython이 이런 짧은 코드 중간에서 스레드를 바꾸는 일이 드물기 때문입니다. 하지만 이것은 구현의 우연이지 언어의 약속이 아닙니다. 버전이 바뀌거나, 코드가 조금 길어지거나, GIL이 없는 빌드에서 여러 코어로 실행하면 틀린 값이 나올 수 있습니다. 결과가 맞게 나왔다는 것은 안전하다는 증거가 아닙니다.

threading.Lock

Lock(잠금)은 한 번에 한 스레드만 가질 수 있는 열쇠입니다. with lock: 블록에 들어갈 때 열쇠를 얻고(acquire) 나올 때 돌려줍니다(release). 다른 스레드가 열쇠를 갖고 있으면 돌려받을 때까지 기다립니다. 블록 안에서 예외가 나도 with가 열쇠를 돌려주므로 acquire()와 release()를 직접 부르는 것보다 안전합니다.

lock = threading.Lock()

def deposit(times):
    global balance
    for _ in range(times):
        with lock:                 # only one thread at a time in here
            current = balance
            time.sleep(0)
            balance = current + 1
with lock: expected 4000, got 4000
correct

잠금으로 감싸는 부분(임계 구역)은 공유 값을 읽고 바꾸는 최소한으로 합니다. 잠금 안에서 오래 기다리면 다른 스레드가 모두 멈춰 스레드를 쓴 의미가 없어집니다.

교착 상태

Lock은 이미 열쇠를 가진 스레드도 다시 얻을 수 없습니다. 같은 스레드가 with lock: 안에서 다시 lock을 얻으려 하면 자기 자신을 영원히 기다립니다. 두 스레드가 서로 상대의 잠금을 기다리는 경우도 마찬가지입니다. 이를 교착 상태(deadlock)라고 합니다. 예제에서는 lock.acquire(timeout=1)로 1초만 기다려 False를 확인합니다. 같은 스레드가 여러 번 얻어야 하는 경우에는 threading.RLock을 씁니다. 잠금을 여러 개 쓴다면 모든 스레드가 같은 순서로 얻도록 합니다.

queue.Queue: 생산자와 소비자

일을 나누는 가장 안전한 방법

공유 변수를 잠금으로 지키는 대신, 스레드끼리 메시지를 주고받게 하면 실수할 여지가 줄어듭니다. queue.Queue는 여러 스레드가 동시에 써도 안전한 줄(FIFO)입니다. 일을 만드는 쪽(생산자)은 put()으로 넣고, 일을 처리하는 쪽(소비자)은 get()으로 꺼냅니다. 큐 안에서 잠금을 알아서 처리합니다.

메서드하는 일
q.put(item)넣는다. maxsize가 차 있으면 자리가 날 때까지 기다린다
q.get()가장 먼저 넣은 것을 꺼낸다. 비어 있으면 들어올 때까지 기다린다
q.get(timeout=1)1초까지만 기다리고, 그래도 없으면 queue.Empty
q.put_nowait(item)기다리지 않는다. 가득 차 있으면 queue.Full
q.qsize()지금 들어 있는 개수(다른 스레드 때문에 곧 바뀔 수 있다)

웨이터와 요리사

producer_consumer의 kitchen.py에서는 웨이터 스레드가 주문을 큐에 넣고, 요리사 스레드 두 개가 하나씩 꺼내 0.5초씩 요리합니다.

orders = queue.Queue(maxsize=3)   # the counter holds at most 3 tickets

def waiter():
    for dish in ORDERS:
        orders.put(dish)              # blocks while the counter is full
    for _ in range(COOKS):
        orders.put(None)              # one stop signal per cook

def cook(name):
    while True:
        dish = orders.get()           # blocks until there is an order
        if dish is None:
            break
        time.sleep(COOK_TIME)
        served.put((dish, name))

요리사는 while True로 계속 주문을 꺼내므로, 일이 끝났다는 것을 알려 줄 방법이 필요합니다. 여기서는 요리사 수만큼 None을 넣고, None을 꺼낸 요리사는 반복을 끝냅니다. 이런 특별한 값을 센티널(sentinel)이라고 합니다. 센티널을 하나만 넣으면 요리사 하나만 끝나고 나머지는 get()에서 영원히 기다려 프로그램이 끝나지 않습니다.

maxsize=3은 큐의 크기를 제한합니다. 생산자가 소비자보다 빠를 때 메모리에 일이 끝없이 쌓이지 않도록 생산자를 잠시 세우는 역할(배압, backpressure)을 합니다. 실행해 보면 웨이터가 주문 다섯 개를 넣은 뒤 요리가 하나 끝날 때까지 멈추는 것을 볼 수 있습니다.

served 6 dishes: bibimbap, japchae, kimbap, mandu, ramen, tteokbokki
2 cooks: about 1.5 s (one cook would need 3.0 s)

요리사를 셋으로 늘리면 about 1.0 s입니다. 소비자 수만 바꾸면 되고 생산자 코드는 그대로입니다. 결과 목록을 sorted()로 정렬해 출력하는 이유는 어느 요리가 먼저 끝나는지가 실행마다 다를 수 있기 때문입니다. 큐에는 task_done()과 join()으로 "넣은 일이 모두 처리될 때까지 기다리기"를 하는 방법도 있습니다.

concurrent.futures: 스레드 풀

ThreadPoolExecutor와 map

스레드를 만들고, 출발시키고, 기다리고, 결과를 모으는 일은 매번 비슷합니다. concurrent.futures.ThreadPoolExecutor는 일꾼 스레드 몇 개를 미리 만들어 두고(풀), 맡긴 일을 나눠 처리한 뒤 결과를 돌려줍니다. with 블록을 나갈 때 모든 일이 끝나기를 기다리고 스레드를 정리합니다.

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=3) as pool:
    for result in pool.map(fetch, PAGES):
        print("  got", result)

pool.map(함수, 입력들)은 내장 map처럼 쓰지만 여러 스레드에서 실행합니다. 결과는 입력 순서대로 나옵니다. 1.5초 걸리는 home이 첫 입력이면, 0.5초 만에 끝난 news도 home이 끝날 때까지 기다렸다가 두 번째로 나옵니다. 함수의 return 값을 그대로 받을 수 있으니 공유 딕셔너리가 필요 없습니다.

submit, Future, as_completed

pool.submit(함수, 인자)는 일 하나를 맡기고 곧바로 Future를 돌려줍니다. Future는 나중에 나올 결과의 영수증입니다. future.result()는 결과가 나올 때까지 기다렸다가 돌려줍니다. as_completed(futures)는 Future들을 끝난 순서대로 하나씩 내줍니다. 먼저 끝난 결과부터 처리하고 싶을 때 씁니다.

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(fetch, page) for page in PAGES]
    for future in as_completed(futures):
        print("  got", future.result())
map: results in the order of the inputs
  got home.html
  got news.html
  got about.html
submit + as_completed: results in the order they finish
  got news.html
  got about.html
  got home.html
total: about 3 s (one by one: 6 s)

작업 안의 예외

일꾼 스레드에서 예외가 나도 그 자리에서는 아무것도 보이지 않습니다. 예외는 Future 안에 보관되었다가 future.result()를 부를 때 다시 발생합니다. 그래서 result() 호출을 try로 감쌉니다. result()를 한 번도 부르지 않으면 예외가 조용히 사라지므로 주의합니다.

for n, future in zip(range(1, 5), futures):
    try:
        print(n, "->", future.result())
    except ValueError as error:
        print(n, "-> error:", error)

max_workers

max_workers는 동시에 일하는 스레드 수입니다. 1이면 하나씩 하는 것과 같고, 일의 개수보다 많아도 더 빨라지지 않습니다. 기다림이 대부분인 일이라면 수십 개까지 늘려도 괜찮지만, 상대 서버에 너무 많은 요청을 한꺼번에 보내지 않도록 적당히 제한하는 것이 예의입니다.

CPU 작업, GIL, 프로세스

계산은 왜 빨라지지 않는가

cpu_pool.py는 소수를 세는 계산만 하는 일을 네 조각으로 나눠 하나씩, 스레드 풀로, 프로세스 풀로 각각 실행합니다. 이 가상 머신에서의 결과입니다(초 단위 숫자는 실행마다 다릅니다).

CPU cores: 1
one by one 1862 primes  0.7 s
threads    1862 primes  0.7 s
processes  1862 primes  3.3 s
threads: about the same as one by one
processes: slower than one by one

코어가 하나이면 계산은 한 번에 하나만 할 수 있습니다. 스레드든 프로세스든 번갈아 실행할 뿐 전체 계산량은 그대로입니다. 프로세스 쪽은 새 파이썬 프로세스를 띄우고 데이터를 주고받는 비용까지 더해져 오히려 느립니다.

GIL

코어가 여러 개인 PC에서도 보통의 CPython에서는 스레드로 계산을 나눠도 빨라지지 않습니다. GIL(Global Interpreter Lock)이라는 잠금 때문에 한 프로세스 안에서 파이썬 코드를 실행하는 스레드는 한순간에 하나뿐이기 때문입니다. 대신 스레드가 time.sleep, 파일 읽기, 소켓 읽기처럼 기다리는 동안에는 GIL을 내려놓으므로 I/O 작업은 스레드로 잘 겹쳐집니다. 파이썬 3.13부터는 GIL이 없는 별도 빌드(free-threaded build)도 있어 스레드가 여러 코어에서 함께 계산할 수 있지만, 아직 기본 설치는 GIL이 있는 빌드입니다. 이 가상 머신의 파이썬도 GIL이 켜져 있습니다.

ProcessPoolExecutor

여러 코어로 계산을 나누는 표준적인 방법은 프로세스입니다. 프로세스마다 자기 인터프리터와 자기 GIL을 가지므로 코어 수만큼 동시에 계산할 수 있습니다. ProcessPoolExecutor는 ThreadPoolExecutor와 사용법이 같습니다.

from concurrent.futures import ProcessPoolExecutor

def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        total = sum(pool.map(count_primes, CHUNKS))

if __name__ == "__main__":   # required: worker processes import this file
    main()

몇 가지 차이가 있습니다. 일꾼 프로세스는 이 파일을 import해서 count_primes를 찾으므로 if __name__ == "__main__": 가드가 반드시 필요하고, 코드가 파일에 있어야 합니다(python3 -로 표준 입력에 넣은 코드는 import할 수 없어 오류가 납니다). 인자와 결과는 프로세스 사이를 복사되어 오가므로 pickle로 바꿀 수 있는 값이어야 하고, 크면 그만큼 느립니다. 프로세스끼리는 메모리를 공유하지 않으므로 전역 변수를 바꿔도 다른 프로세스에는 보이지 않습니다. 코어가 여러 개인 PC에서 일이 충분히 크면(조각마다 적어도 수십 밀리초 이상) 프로세스 풀이 하나씩보다 코어 수에 가까운 배수만큼 빨라집니다. 일이 너무 작으면 PC에서도 프로세스를 띄우는 비용이 더 큽니다.

1코어(이 가상 머신)여러 코어 PC
I/O 작업 + 스레드/asyncio빨라진다빨라진다
CPU 작업 + 스레드그대로그대로(GIL). free-threaded 빌드에서는 빨라질 수 있다
CPU 작업 + 프로세스오히려 느려진다일이 크면 빨라진다

asyncio: 스레드 하나로 기다림 겹치기

코루틴과 이벤트 루프

스레드는 운영체제가 언제든 바꿔 실행하므로 경쟁 조건을 늘 조심해야 합니다. asyncio는 다른 방식을 씁니다. 스레드는 하나이고, 함수가 스스로 "여기서 기다린다"고 밝힌 지점(await)에서만 다른 일로 넘어갑니다. async def로 정의한 함수를 코루틴 함수라고 하고, 코루틴들을 번갈아 실행하는 관리자를 이벤트 루프라고 합니다. asyncio.run(main())이 이벤트 루프를 시작하고 main()이 끝날 때까지 돌립니다.

import asyncio

async def brew(drink, seconds):
    print(f"  start {drink}")
    await asyncio.sleep(seconds)     # pause here; other coroutines run meanwhile
    print(f"  done  {drink}")
    return f"{drink} ({seconds} s)"

async def together():
    return await asyncio.gather(brew("coffee", 1), brew("tea", 1), brew("cocoa", 1))

asyncio.run(together())

await를 하나씩 vs gather

await brew(...)를 세 번 차례로 쓰면 하나가 끝나야 다음을 시작하므로 3초가 걸립니다. asyncio.gather(...)에 코루틴 여러 개를 넘기면 모두 함께 진행하고, 모두 끝나면 결과를 넘긴 순서대로 리스트로 돌려줍니다. asyncio_basics의 출력입니다.

one after another: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 3 s
gather: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 1 s

create_task와 시간 제한

asyncio.create_task(코루틴)은 코루틴을 이벤트 루프에 바로 올리고 Task를 돌려줍니다. 만든 쪽은 기다리지 않고 계속 진행하다가, 필요할 때 await task로 결과를 받습니다. 응답이 오지 않을 수 있는 기다림에는 async with asyncio.timeout(초):로 시간 제한을 둡니다. 제한 시간이 지나면 기다리던 작업이 취소되고 TimeoutError가 납니다.

task = asyncio.create_task(slow())
try:
    async with asyncio.timeout(0.5):
        await task
except TimeoutError:
    print("gave up after 0.5 s, task cancelled:", task.cancelled())

asyncio의 두 가지 함정

첫째, await를 잊으면 아무 일도 일어나지 않습니다. 코루틴 함수를 부르기만 하면 몸체는 실행되지 않고 coroutine 객체만 생깁니다. 이런 코루틴은 나중에 RuntimeWarning: coroutine 'hello' was never awaited 경고로 드러납니다.

둘째, 코루틴 안에서 time.sleep()처럼 기다리는 일반 함수를 부르면 이벤트 루프 전체가 멈춥니다. await 지점이 없으니 다른 코루틴으로 넘어갈 기회가 없습니다. 예제에서 gather로 묶어도 bad는 about 3 s, asyncio.sleep을 쓴 good은 about 1 s입니다. 코루틴 안에서는 asyncio.sleep, asyncio.open_connection처럼 await할 수 있는 함수를 씁니다. 어쩔 수 없이 기다리는 일반 함수를 불러야 한다면 await asyncio.to_thread(함수, 인자)로 별도 스레드에서 실행합니다.

asyncio TCP 에코 서버

서버: start_server

asyncio가 가장 빛나는 곳은 많은 연결을 동시에 다루는 네트워크 서버입니다. 클라이언트 대부분은 대부분의 시간 동안 조용하므로, 스레드 하나가 이 연결 저 연결을 오가며 도착한 데이터만 처리하면 됩니다. echo_server의 echo_server.py는 받은 줄을 대문자로 돌려주는 서버입니다.

async def handle(reader, writer):
    """Called once per connection; echoes each line back in capitals."""
    while True:
        line = await reader.readline()        # b"" when the client hangs up
        if not line:
            break
        writer.write(line.upper())
        await writer.drain()
    writer.close()
    await writer.wait_closed()

server = await asyncio.start_server(handle, "127.0.0.1", 8765)

asyncio.start_server는 연결이 하나 들어올 때마다 handle 코루틴을 새로 시작하고, 읽기용 reader와 쓰기용 writer를 넘깁니다. reader.readline()은 줄 하나가 올 때까지 기다리며, 상대가 연결을 끊으면 빈 바이트열 b""을 돌려줍니다. writer.write()는 보낼 데이터를 버퍼에 넣기만 하고, await writer.drain()이 실제로 보낼 수 있을 때까지 기다립니다. 소켓으로 오가는 것은 문자열이 아니라 바이트이므로 encode()와 decode()로 바꿉니다.

클라이언트: open_connection

reader, writer = await asyncio.open_connection("127.0.0.1", port)
writer.write(b"hi\n")
await writer.drain()
reply = await reader.readline()

예제를 인자 없이 실행하면 한 스크립트 안에서 서버를 열고 클라이언트 세 개를 gather로 함께 돌립니다. 포트로 0을 주면 운영체제가 빈 포트를 골라 주므로 다른 프로그램과 부딪히지 않습니다. 각 클라이언트는 메시지 사이에 0.5초씩 쉬지만, 그동안 서버는 다른 클라이언트에 답합니다. 스레드 하나로 세 연결을 함께 처리하는 것입니다.

client got: ['MINA: HI', 'MINA: BYE']
client got: ['JUN: HELLO', 'JUN: SEE YOU']
client got: ['SORA: HEY', 'SORA: LATER']

따로 띄운 서버

python3 echo_server.py serve &는 서버만 8765번 포트에서 백그라운드로 실행하고, 다른 프로세스인 echo_client.py가 접속합니다. 127.0.0.1은 자기 자신을 가리키는 주소(루프백)라 같은 컴퓨터 안에서만 연결됩니다. 이 서버는 클라이언트 두 명을 받거나 30초가 지나면 스스로 끝납니다. 연습용 서버에 종료 조건을 넣어 두면 잊고 켜 둔 프로세스가 포트를 차지하는 일이 없습니다. 서버가 끝난 뒤 접속하면 ConnectionRefusedError가 나는데, 클라이언트는 이를 잡아 client: no server on 127.0.0.1:8765를 출력합니다.

무엇을 고를까

도구알맞은 일주의할 점
threading.Thread기다림이 있는 일 몇 개를 겹치기공유 값은 Lock으로. 결과 받기가 번거롭다
queue.Queue만드는 쪽과 처리하는 쪽이 나뉜 흐름소비자에게 정지 신호를 보낸다
ThreadPoolExecutor같은 함수를 여러 입력에 실행하는 I/O 작업예외는 result()에서 나온다
asyncio연결이 아주 많은 네트워크 프로그램모든 기다림이 await여야 한다
ProcessPoolExecutor여러 코어에서 큰 계산__main__ 가드, 복사 비용, 코어가 하나면 이득 없음

대부분의 경우 직접 Thread를 다루기보다 ThreadPoolExecutor가 간단하고 안전합니다. 이미 asyncio로 된 라이브러리(웹 프레임워크, 네트워크 클라이언트)를 쓴다면 asyncio를 따릅니다. 계산이 느리다면 먼저 알고리즘과 자료 구조를 개선하고, 그다음에 프로세스를 생각합니다.

흔한 실수

  • target=f(x): 함수를 그 자리에서 호출해 버립니다. target=f, args=(x,)로 씁니다. 인자가 하나일 때 args=(x)는 튜플이 아니므로 쉼표를 붙여 (x,)로 씁니다.
  • 반복문 안에서 start() 직후 join(): 하나씩 실행하는 것과 같아집니다. 모두 시작한 뒤 모두 기다립니다.
  • join() 전에 결과 읽기: 아직 비어 있거나 일부만 있습니다.
  • "테스트할 때는 맞았다": 경쟁 조건은 가끔만 나타납니다. 여러 스레드가 바꾸는 값은 Lock으로 지키거나 Queue로 주고받습니다.
  • 잠금 안에서 오래 기다리기, 같은 Lock을 두 번 얻기: 느려지거나 교착 상태가 됩니다.
  • 소비자에게 정지 신호를 보내지 않기: get()이 영원히 기다려 프로그램이 끝나지 않습니다.
  • future.result()를 부르지 않기: 작업 안의 예외가 조용히 사라집니다.
  • await 잊기, 코루틴 안의 time.sleep: 실행되지 않거나 이벤트 루프 전체가 멈춥니다.
  • 계산을 스레드로 빠르게 하려 하기: GIL 때문에 빨라지지 않습니다. 코어가 여러 개라면 프로세스를 씁니다.
  • 출력 순서나 정확한 시간에 기대기: 실행마다 달라집니다. 결과는 정렬하거나 넘긴 순서로 모으고, 시간은 대략으로 봅니다.

정리

  • 동시성은 기다림을 겹치는 것이고, 병렬성은 여러 코어에서 실제로 동시에 실행하는 것입니다.
  • Thread(target=..., args=...), start(), join()으로 I/O 대기를 겹치면 3초 걸리던 일이 1초가 됩니다.
  • 공유 값을 읽고-바꾸고-쓰는 코드는 경쟁 조건을 만듭니다. with lock:으로 한 번에 한 스레드만 실행하게 합니다.
  • queue.Queue는 스레드끼리 일을 안전하게 주고받는 통로입니다. 센티널로 끝을 알립니다.
  • ThreadPoolExecutor의 map은 입력 순서, as_completed는 끝난 순서로 결과를 줍니다.
  • asyncio는 스레드 하나에서 await 지점마다 코루틴을 바꿔 가며 기다림을 겹칩니다. gather로 함께 기다립니다.
  • 계산만 하는 일은 코어가 하나인 이 가상 머신에서 빨라지지 않습니다. 여러 코어 PC에서는 프로세스로 나눕니다.
