This topic is concurrency. Much of what programs do is not computing but waiting: for a web page to arrive, for a file to be read, for the user to type. If a program does something else while it waits, the same work can finish in far less time. First we use threading to create threads and overlap waits, and look at the race conditions that appear when several threads change the same value, and at Lock. Then we cover the producer/consumer pattern with queue.Queue, concurrent.futures, which manages threads for you, and asyncio, which handles many waits on a single thread. Finally we build an asyncio TCP echo server. The practice pages are threads, race_lock, producer_consumer, thread_pool, asyncio_basics and echo_server.

What concurrency is: overlapping waits

The barista

Say a barista takes an order for three coffees. If they stand by the machine for the minute it takes to brew one cup and only then start the next, it takes three minutes. If they put the first cup on, then the second and third right away, it takes about one minute. There is still one barista with two hands. The only change is that the waiting times overlap. That is concurrency.

With three baristas, three people really move their hands at the same time. That is parallelism. Concurrency means dealing with several tasks at once by taking turns; parallelism means actually running several tasks at the same instant. Running in parallel needs several CPU cores.

I/O-bound and CPU-bound work

Whether a task can get faster depends on what it spends its time on.

KindTime goes intoExamplesWith threads or asyncio
I/O-boundwaiting for the outside world: network, disk, the userdownloads, database queries, a server answering clientsthe waits overlap, so it gets faster
CPU-boundcomputingcounting primes, image processing, big matrix productsno faster on one core

In this lab, time.sleep stands in for a real network wait. A sleeping thread does not use the CPU, so it behaves just like a real I/O wait.

About this virtual machine

The virtual machine in your browser has one CPU core, and because it is emulated it is much slower than a real PC. os.cpu_count() returns 1. Examples that overlap waits therefore speed up exactly as they would on a PC, but pure computation does not get faster whether you split it into threads or processes. The section on CPU-bound work below explains what changes on a PC with several cores.

threading: creating threads

What a thread is

A thread is a separate flow of execution inside one program (process). A program starts with a single main thread. New threads see the same memory (the same variables, the same objects) while each runs its own function. While one thread waits in time.sleep or a network read, other threads run.

Thread, start, join

threading.Thread(target=function, args=(argument,)) creates a thread object, start() sets it going and join() waits for it to finish. Here is the heart of the threads example.

import threading
import time

def download(name):
    print(f"  start {name}")
    time.sleep(1.0)             # waiting: this thread sleeps, the CPU is free
    print(f"  done  {name}")

threads = [threading.Thread(target=download, args=(name,)) for name in FILES]
for t in threads:
    t.start()                   # starts running download(name) in the background
for t in threads:
    t.join()                    # waits until that thread has finished

Splitting the starting and the waiting into two loops matters. If you call join() right after start() in the same loop, the second thread does not start until the first has finished, which is the same as running them one by one. Start them all, then wait for them all.

Measuring time: time.perf_counter

Measure elapsed time with time.perf_counter(). Its value by itself means nothing; the difference between two calls is the number of seconds in between. It is not affected by changes to the clock, which makes it right for measurements. Measurements vary a little from run to run, so the examples round them with round() and print things like "about 1 s".

start = time.perf_counter()
func()
elapsed = time.perf_counter() - start
print(f"about {round(elapsed)} s")
sequential: about 3 s
threaded: about 1 s

In the threaded run the three start lines come first, followed by the three done lines. Which thread prints first is up to the operating system, so the order can change between runs. Never write code that depends on the order in which threads print.

Getting results out of a thread

The return value of a thread's function is thrown away. If you need results, put them in a dictionary or list that all threads can see, and read it after join() has confirmed they are all done. Right after start() it is still empty. concurrent.futures, below, is the more convenient way to get results back.

results = {}

def work(name, seconds):
    time.sleep(seconds)
    results[name] = seconds      # each thread writes its own key

# ... start all, then join all ...
print(results)

Without join

Without join(), the main thread does not wait for the threads and moves straight on. The program still does not vanish before the work is done, because Python ends the process only when every non-daemon thread has finished. A daemon thread, created with Thread(..., daemon=True), is stopped when the main thread ends. Wherever you need the results, always join() first.

Shared state and race conditions

Disappearing deposits

Threads share memory, which is convenient, and that is exactly what makes them dangerous. In the race_lock example, four threads each add 1 to a single balance 1000 times. The result should be 4000.

def deposit(times):
    global balance
    for _ in range(times):
        current = balance          # 1. read
        time.sleep(0)              # 2. pause: another thread may run now
        balance = current + 1      # 3. write back (maybe a stale value)
without lock: expected 4000, got 1001
lost updates: 2999

When two threads A and B take turns, this happens:

StepThread AThread Bbalance
1current = balance (10)10
2current = balance (10)10
3balance = 1111
4balance = 1111

Two deposits were made but the value went up by only 1, because B read the old value before A wrote. When the result depends on the order in which threads happen to run, that is a race condition. There is no error message, and some runs happen to come out right, which makes these bugs hard to find. The time.sleep(0) in the example deliberately hands over the turn between the read and the write so that the problem shows up every time.

One line is not safe either

counter += 1 is one line but not one action. Looking at the bytecode with dis.dis shows it split into a read, an add and a write.

LOAD_GLOBAL              0 (counter)
LOAD_SMALL_INT           1
BINARY_OP               13 (+=)
STORE_GLOBAL             0 (counter)

On the lab machine, doing plain counter += 1 400,000 times with no sleep usually gives exactly 400000, because today's CPython rarely switches threads in the middle of such short code. But that is an accident of the implementation, not a promise of the language. A different version, slightly longer code, or a build without the GIL running on several cores can give a wrong value. A correct result is not proof that the code is safe.

threading.Lock

A Lock is a key that only one thread can hold at a time. Entering a with lock: block takes the key (acquire) and leaving it gives the key back (release). If another thread holds the key, you wait until it is returned. Even if an exception happens inside the block, with gives the key back, so it is safer than calling acquire() and release() yourself.

lock = threading.Lock()

def deposit(times):
    global balance
    for _ in range(times):
        with lock:                 # only one thread at a time in here
            current = balance
            time.sleep(0)
            balance = current + 1
with lock: expected 4000, got 4000
correct

Keep the part inside the lock (the critical section) down to the minimum that reads and changes the shared value. If you wait for a long time inside the lock, every other thread stops too and the threads gain you nothing.

Deadlock

A Lock cannot be taken again even by the thread that already holds it. If a thread inside with lock: tries to take lock again, it waits for itself forever. The same happens when two threads each wait for the other's lock. This is called a deadlock. The example uses lock.acquire(timeout=1) to wait for just one second and see False. When the same thread needs to take a lock several times, use threading.RLock. If you use several locks, make every thread take them in the same order.

queue.Queue: producers and consumers

The safest way to share work

Instead of guarding shared variables with locks, have threads pass messages to each other; there is less room for mistakes. A queue.Queue is a first-in, first-out line that many threads can use at the same time safely. The side that creates work (the producer) puts items in with put(), and the side that handles it (the consumer) takes them out with get(). The queue does the locking itself.

MethodWhat it does
q.put(item)adds an item; if maxsize is reached, waits until there is room

q.get(timeout=1)waits at most 1 second, then raises queue.Empty
q.put_nowait(item)does not wait; raises queue.Full if the queue is full
q.qsize()how many items are in it right now (other threads may change that at any moment)

The waiter and the cooks

In kitchen.py from producer_consumer, a waiter thread puts orders into a queue, and two cook threads take them out one at a time and cook each for 0.5 seconds.

orders = queue.Queue(maxsize=3)   # the counter holds at most 3 tickets

def waiter():
    for dish in ORDERS:
        orders.put(dish)              # blocks while the counter is full
    for _ in range(COOKS):
        orders.put(None)              # one stop signal per cook

def cook(name):
    while True:
        dish = orders.get()           # blocks until there is an order
        if dish is None:
            break
        time.sleep(COOK_TIME)
        served.put((dish, name))

The cooks keep taking orders in a while True loop, so they need some way to learn that the work is over. Here the waiter puts one None per cook, and a cook who takes out None leaves the loop. A special value like this is called a sentinel. With only one sentinel, only one cook would stop; the other would wait in get() forever and the program would never end.

maxsize=3 limits the size of the queue. When the producer is faster than the consumers, it pauses the producer so that work does not pile up in memory without end (backpressure). When you run it, you can see the waiter stop after five orders until a dish is finished.

served 6 dishes: bibimbap, japchae, kimbap, mandu, ramen, tteokbokki
2 cooks: about 1.5 s (one cook would need 3.0 s)

With three cooks it takes about 1.0 s. Only the number of consumers changes; the producer code stays the same. The list of results is printed with sorted() because which dish finishes first can change from run to run. Queues also offer task_done() and join() for "wait until everything that was put in has been handled".

concurrent.futures: thread pools

ThreadPoolExecutor and map

Creating threads, starting them, waiting for them and collecting results looks much the same every time. concurrent.futures.ThreadPoolExecutor keeps a few worker threads ready (a pool), shares out the jobs you give it and hands back the results. Leaving the with block waits for all jobs to finish and cleans up the threads.

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=3) as pool:
    for result in pool.map(fetch, PAGES):
        print("  got", result)

pool.map(function, inputs) is used like the built-in map but runs in several threads. Results come out in the order of the inputs. If home, which takes 1.5 seconds, is the first input, then news, done after 0.5 seconds, still waits for home and comes out second. You get the function's return value directly, so no shared dictionary is needed.

submit, Future, as_completed

pool.submit(function, argument) hands over one job and immediately returns a Future, a receipt for a result that will come later. future.result() waits for the result and returns it. as_completed(futures) yields the futures one by one in the order they finish. Use it when you want to handle whichever result is ready first.

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(fetch, page) for page in PAGES]
    for future in as_completed(futures):
        print("  got", future.result())
map: results in the order of the inputs
  got home.html
  got news.html
  got about.html
submit + as_completed: results in the order they finish
  got news.html
  got about.html
  got home.html
total: about 3 s (one by one: 6 s)

Exceptions inside jobs

When a worker thread raises an exception, nothing shows at that moment. The exception is stored in the Future and raised again when you call future.result(), which is why that call is wrapped in try. If you never call result(), the exception disappears silently, so watch out.

for n, future in zip(range(1, 5), futures):
    try:
        print(n, "->", future.result())
    except ValueError as error:
        print(n, "-> error:", error)

max_workers

max_workers is the number of threads working at once. With 1 it is the same as one by one, and more workers than jobs does not help. For work that is mostly waiting, even dozens of workers are fine, but it is polite to keep the number reasonable so you do not hit someone else's server with too many requests at once.

CPU-bound work, the GIL and processes

Why computation does not get faster

cpu_pool.py splits a pure computation, counting primes, into four chunks and runs them one by one, in a thread pool and in a process pool. Here is the result on this virtual machine (the seconds change from run to run).

CPU cores: 1
one by one 1862 primes  0.7 s
threads    1862 primes  0.7 s
processes  1862 primes  3.3 s
threads: about the same as one by one
processes: slower than one by one

With one core, only one computation can run at a time. Threads and processes just take turns, and the total amount of computing stays the same. The processes are even slower, because starting new Python processes and passing data to and from them adds its own cost.

The GIL

Even on a PC with several cores, splitting computation across threads does not speed it up in standard CPython. A lock called the GIL (Global Interpreter Lock) means that only one thread in a process runs Python code at any moment. Threads do release the GIL while they wait, in time.sleep, file reads or socket reads, which is why I/O-bound work overlaps well in threads. Since Python 3.13 there is also a separate free-threaded build without the GIL, in which threads can compute together on several cores, but the default install is still the build with the GIL. The Python in this virtual machine has the GIL enabled too.

ProcessPoolExecutor

The standard way to spread computation over several cores is processes. Each process has its own interpreter and its own GIL, so as many can compute at once as there are cores. ProcessPoolExecutor is used just like ThreadPoolExecutor.

from concurrent.futures import ProcessPoolExecutor

def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        total = sum(pool.map(count_primes, CHUNKS))

if __name__ == "__main__":   # required: worker processes import this file
    main()

There are some differences. The worker processes import this file to find count_primes, so the if __name__ == "__main__": guard is required and the code has to live in a file (code fed through standard input with python3 - cannot be imported, so it fails). Arguments and results are copied between processes, so they must be values that pickle can convert, and big ones are slow to send. Processes do not share memory, so changing a global variable in one is invisible to the others. On a PC with several cores and a big enough job (at least tens of milliseconds per chunk), a process pool runs faster than one by one by a factor close to the number of cores. If the job is too small, starting the processes costs more than it saves, even on a PC.

One core (this virtual machine)PC with several cores

asyncio: overlapping waits on one thread

Coroutines and the event loop

The operating system can switch threads at any moment, so with threads you always have to watch for race conditions. asyncio works differently. There is one thread, and it moves on to other work only at the points where a function itself says "I am waiting here" (await). A function defined with async def is a coroutine function, and the manager that runs coroutines in turn is the event loop. asyncio.run(main()) starts the event loop and runs it until main() finishes.

import asyncio

async def brew(drink, seconds):
    print(f"  start {drink}")
    await asyncio.sleep(seconds)     # pause here; other coroutines run meanwhile
    print(f"  done  {drink}")
    return f"{drink} ({seconds} s)"

async def together():
    return await asyncio.gather(brew("coffee", 1), brew("tea", 1), brew("cocoa", 1))

asyncio.run(together())

Awaiting one at a time vs gather

Writing await brew(...) three times in a row starts each one only after the previous one has finished, so it takes 3 seconds. Passing several coroutines to asyncio.gather(...) runs them all together, and when they are all done it returns their results as a list in the order you passed them. Here is the output of asyncio_basics.

one after another: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 3 s
gather: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 1 s

create_task and time limits

asyncio.create_task(coroutine) puts the coroutine on the event loop right away and returns a Task. The caller carries on without waiting and later gets the result with await task when it needs it. Give waits that might never get an answer a time limit with async with asyncio.timeout(seconds):. When the time is up, the awaited work is cancelled and TimeoutError is raised.

task = asyncio.create_task(slow())
try:
    async with asyncio.timeout(0.5):
        await task
except TimeoutError:
    print("gave up after 0.5 s, task cancelled:", task.cancelled())

Two asyncio traps

First, if you forget await, nothing happens. Just calling a coroutine function does not run its body; it only creates a coroutine object. Such a coroutine shows up later as the warning RuntimeWarning: coroutine 'hello' was never awaited.

Second, calling an ordinary function that waits, such as time.sleep(), inside a coroutine stops the whole event loop. There is no await point, so there is no chance to switch to another coroutine. In the example, even under gather, bad takes about 3 s while good, which uses asyncio.sleep, takes about 1 s. Inside coroutines, use awaitable functions such as asyncio.sleep and asyncio.open_connection. If you really must call an ordinary function that waits, run it in a separate thread with await asyncio.to_thread(function, argument).

An asyncio TCP echo server

The server: start_server

asyncio shines brightest in network servers that handle many connections at once. Most clients are quiet most of the time, so one thread can move from connection to connection, handling only the data that has arrived. echo_server.py in echo_server is a server that sends each line it receives back in capitals.

async def handle(reader, writer):
    """Called once per connection; echoes each line back in capitals."""
    while True:
        line = await reader.readline()        # b"" when the client hangs up
        if not line:
            break
        writer.write(line.upper())
        await writer.drain()
    writer.close()
    await writer.wait_closed()

server = await asyncio.start_server(handle, "127.0.0.1", 8765)

asyncio.start_server starts a new handle coroutine for every connection that comes in and passes it a reader for reading and a writer for writing. reader.readline() waits until a line arrives, and returns the empty bytes b"" when the other side hangs up. writer.write() only puts the data in a buffer; await writer.drain() waits until it can actually be sent. What travels over a socket is bytes, not strings, so convert with encode() and decode().

The client: open_connection

reader, writer = await asyncio.open_connection("127.0.0.1", port)
writer.write(b"hi\n")
await writer.drain()
reply = await reader.readline()

Run without arguments, the example opens the server and runs three clients together with gather, all in one script. Port 0 lets the operating system pick a free port, so it cannot clash with other programs. Each client rests half a second between messages, and meanwhile the server answers the other clients: one thread handling three connections together.

client got: ['MINA: HI', 'MINA: BYE']
client got: ['JUN: HELLO', 'JUN: SEE YOU']
client got: ['SORA: HEY', 'SORA: LATER']

A server in its own process

python3 echo_server.py serve & runs only the server, in the background on port 8765, and echo_client.py, a separate process, connects to it. 127.0.0.1 is the address that means "this machine" (loopback), so only programs on the same computer can connect. This server stops by itself after two clients or 30 seconds. Giving a practice server a way to end means a forgotten process never sits on the port. Connecting after the server has ended raises ConnectionRefusedError; the client catches it and prints client: no server on 127.0.0.1:8765.

Most of the time a ThreadPoolExecutor is simpler and safer than handling Thread yourself. If you already use libraries built on asyncio (web frameworks, network clients), go with asyncio. If a computation is slow, first improve the algorithm and data structures, and only then think about processes.

Common mistakes

  • target=f(x): calls the function right there. Write target=f, args=(x,). With a single argument, args=(x) is not a tuple; add the comma: (x,).
  • join() right after start() in the loop: the same as running one by one. Start them all, then wait for them all.
  • Reading results before join(): they are still empty or incomplete.
  • "It was right when I tested it": race conditions show up only sometimes. Guard values that several threads change with a Lock, or pass them through a Queue.
  • Waiting a long time inside a lock, taking the same Lock twice: things slow down or deadlock.
  • Not sending the consumers a stop signal: get() waits forever and the program never ends.
  • Never calling future.result(): exceptions inside jobs vanish silently.
  • Forgetting await, time.sleep inside a coroutine: the code does not run, or the whole event loop stops.
  • Trying to speed up computation with threads: the GIL prevents it. With several cores, use processes.
  • Relying on output order or exact timings: they change from run to run. Sort results or collect them in the order you submitted them, and treat times as approximate.

Summary

  • Concurrency is overlapping waits; parallelism is actually running at the same time on several cores.
  • Overlapping I/O waits with Thread(target=..., args=...), start() and join() turns a 3-second job into a 1-second one.
  • Code that reads, changes and writes a shared value creates race conditions. with lock: lets only one thread run it at a time.
  • queue.Queue is a safe channel for passing work between threads; a sentinel signals the end.
  • ThreadPoolExecutor's map gives results in input order, as_completed in the order they finish.
  • asyncio overlaps waits on one thread by switching coroutines at every await; gather waits for them together.
  • Pure computation does not get faster on this one-core virtual machine. On a multi-core PC, split it across processes.
