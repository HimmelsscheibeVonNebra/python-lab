Data that must outlive the program goes into files. This chapter covers three tools for working with files, together with the error handling you always need alongside them. First we build paths and look around folders with pathlib, and compare the modes for opening and closing files with open() and with. Then we use try/except to keep a program running when a file is missing or its contents are wrong, and learn to signal errors with raise and exception classes of our own. Finally we build a game save file with json, and a robust importer that skips bad lines with the csv module. The examples are paths, file_modes, exceptions, custom_errors, json_save and csv_import.

Paths and pathlib

Path Objects

A file's location is written as a path such as notes/todo.txt. You can handle paths as plain strings, but with the standard library's pathlib.Path, joining, splitting and checking a path each take a single method. Paths are joined with the division sign /. Gluing "/" onto strings by hand easily drops a slash or doubles one; the / operator rules that out.

from pathlib import Path

p = Path("notes") / "archive" / "old.txt"
print(p)              # notes/archive/old.txt
print(p.name)         # old.txt
print(p.stem)         # old
print(p.suffix)       # .txt
print(p.parent)       # notes/archive
print(p.with_suffix(".bak"))   # notes/archive/old.bak

Methods that change a name, such as with_suffix, only build a new Path; they do not touch the file on disk. A Path is a value that says "where". What actually creates or deletes files are methods such as write_text, mkdir and unlink.

Relative Paths and the Current Folder

A path that does not start with / is relative: it is interpreted from the folder the program was started in (Path.cwd()). If you cd to another folder in the shell and run the same program, Path("notes") points somewhere else. The example pages here cd into each example's folder before running commands, so relative paths work as intended. The home folder is Path.home() (/home/student in this virtual machine).

Looking Around a Folder: iterdir, glob, rglob

iterdir() returns everything directly inside a folder; glob(pattern) returns only the names that match a pattern. * means "any characters, any number of them", so "*.txt" is any name ending in .txt. rglob searches every subfolder as well. The order is not fixed, so sort with sorted() before showing the results.

folder = Path("notes")
for p in sorted(folder.iterdir()):
    kind = "dir " if p.is_dir() else "file"
    print(kind, p.name)

for p in sorted(folder.glob("*.txt")):     # .txt directly in notes
    print(p.name)

for p in sorted(folder.rglob("*.txt")):    # subfolders too
    print(p)                               # notes/archive/old.txt ...

read_text and write_text

Read a short text file all at once with read_text() and write one all at once with write_text(). write_text creates the file if it does not exist and otherwise erases it and writes it anew. To split the text into lines, use splitlines(): you get a list without the \n at the end of each line.

out = Path("notes/hello.txt")
out.write_text("안녕하세요\nHello\n", encoding="utf-8")   # 12 (characters)
text = out.read_text(encoding="utf-8")
print(text.splitlines())                  # ['안녕하세요', 'Hello']
print(len(out.read_bytes()))              # 22 (bytes)

Why Always encoding="utf-8"

A disk stores bytes, not characters. The rule that turns characters into bytes is an encoding, and today's standard is UTF-8. In UTF-8 an English letter takes 1 byte and a Korean character 3 bytes, so the 12 characters above become 22 bytes. If you leave out encoding, Python uses the operating system's default, which differs from computer to computer (older Korean Windows uses cp949). That is why a Korean file that reads fine on your computer can raise UnicodeDecodeError or show garbled characters on another. Make a habit of writing encoding="utf-8" every time you open a text file.

Check and Create: exists and mkdir

Checking with exists() first keeps the program from stopping while reading a missing file. Folders are created with mkdir(): parents=True creates the in-between folders as well, and exist_ok=True means no error if the folder already exists. With both options it is safe to run any number of times.

p = Path("notes/nope.txt")
if p.exists():
    print(p.read_text(encoding="utf-8"))
else:
    print(p, "does not exist, skipping")

Path("notes/out/2026").mkdir(parents=True, exist_ok=True)

open() and with

File Objects and Modes

read_text/write_text handle a whole file at once. To read a little at a time, add to the end of an existing file, or process a large file line by line, get a file object with open(). The second argument, the mode, decides how the file is opened.

ModeMeaningIf the file is missingIf the file exists
"r" (default)readFileNotFoundErrorreads from the start
"w"writecreates iterases everything, then writes
"a"appendcreates itwrites after the end
"x"create a new file (exclusive)creates itFileExistsError

Adding b to the mode ("rb", "wb") gives binary mode, which reads and writes bytes instead of characters; no encoding is used then. It is for files that are not text, such as images or archives.

The mode to be most careful with is "w". The moment the file is opened, its old contents are gone, even before you write anything. For a file that collects records, use "a"; for a file that must never be overwritten, use "x".

with Closes the File

A file you opened must be closed when you are done. Until it is closed, what you wrote may not be fully on disk yet, and there is a limit on how many files one program can have open. You can call f.close() yourself, but if an error happens in between, the program never reaches the close() line. The with statement closes the file the moment the block ends, whether it ends normally or because of an error.

# closing by hand: an error in the middle skips close()
f = open("diary.txt", encoding="utf-8")
text = f.read()
f.close()

# with: always closed when the block ends
with open("diary.txt", encoding="utf-8") as f:
    text = f.read()
print(f.closed)     # True

Trying to read a closed file gives ValueError: I/O operation on closed file. Finish the file work inside the with block, and outside it use the value you read (text).

Ways to Read

A file object remembers how far it has read: readlines() after a readline() no longer has the first line. for line in f reads one line at a time without loading the whole file into memory, so it works even for very large files. Each line ends in \n, so remove it with strip() or rstrip() before comparing or printing.

Ways to Write

f.write(s) writes exactly the string you give it and adds no newline. print(..., file=f) writes to the file with the same rules as printing to the screen (separated by spaces, a newline at the end). f.writelines(list) writes the strings of a list one after another; there too, the newlines are up to you.

with open("log.txt", "w", encoding="utf-8") as f:
    f.write("a")
    f.write("b\n")                      # 'ab\n'  (a and b on one line)
    print("c", "d", sep=",", file=f)    # 'c,d\n'
    f.writelines(["e\n", "f\n"])

Exceptions: Dealing with Errors

Exceptions and Tracebacks

When a program hits a situation in which it cannot go on, Python raises an exception. int("ten") raises ValueError, opening a missing file raises FileNotFoundError, and dividing by zero raises ZeroDivisionError. If nobody handles the exception, the program stops right there and prints a traceback.

Mina: 84.0
Traceback (most recent call last):
  File "/home/student/files/exceptions/report.py", line 13, in <module>
    report("Joon", [])
    ~~~~~~^^^^^^^^^^^^
  File "/home/student/files/exceptions/report.py", line 9, in report
    print(f"{name}: {average(scores):.1f}")
                     ~~~~~~~^^^^^^^^
  File "/home/student/files/exceptions/report.py", line 5, in average
    return sum(scores) / len(scores)
           ~~~~~~~~~~~~^~~~~~~~~~~~~
ZeroDivisionError: division by zero

Read a traceback from the bottom up.

  1. The last line: the kind of exception and its message. It tells you what went wrong (ZeroDivisionError: division by zero).
  2. The File line just above: where the exception actually happened (line 5 of average, where len(scores) is 0).
  3. The lines above that: the chain of calls that led there. report("Joon", []) on line 13 called average by way of line 9. Line 13, which passes an empty list, may well be the place to fix.

Recent versions of Python point at the failing part of each line with ~~~^^^ marks (since 3.11) and use colours in the terminal (since 3.13). Anything printed before the traceback (here Mina: 84.0) stays on screen, and code after the exception (Sora's report) never runs.

try and except

Put the code that may raise an exception in a try block, and what to do when that exception happens in an except block. If an exception is raised inside try, the rest of the block is skipped and control jumps to the matching except; after that, execution continues after the whole try statement.

text = "ten"
try:
    n = int(text)
    print("got", n)          # skipped when an exception is raised
except ValueError as e:
    print("not a number:", e)
print("program goes on")

as e puts the exception object in a variable. Printing it shows the message, and depending on the kind it carries more information, such as e.filename on a FileNotFoundError or the missing key on a KeyError.

Catch Only What You Expect

One try can have several except blocks; only the first one that matches, from the top, runs. Exceptions that get the same treatment can be grouped in a tuple: except (ValueError, ZeroDivisionError):. A bare except: or except Exception: swallows every error, quietly hiding even a NameError from a typo. The rule is: catch the exceptions you expect by name, and let unexpected errors show up as tracebacks.

else and finally

The else block runs only when the try raised no exception. Moving the success code out of try into else leaves only the lines that can really fail in try, which makes it clear which line's error you mean to catch. The finally block always runs last, on success or failure, even while a return is leaving the function. It is the place for clean-up work.

def to_int(text):
    try:
        n = int(text)
    except ValueError:
        print("except")
        return None
    else:
        print("else")
        return n
    finally:
        print("finally")

to_int("42")    # else, finally
to_int("abc")   # except, finally
SituationOrder
no exceptionall of try → else → finally
caught exceptiontry (up to the error) → matching except → finally
uncaught exceptiontry (up to the error) → finally → passed outward (traceback)

with open(...) closing the file works on the same principle as this finally.

Code Walk-through: calc.py

calc.py in the exceptions example divides two numbers for each input line. Input is read line by line with for line in sys.stdin, just like a file. The key point is that the try sits inside the loop: when one line fails, only that line is skipped and the loop moves on. With the try outside the loop, the first failure would end the whole loop.

for number, line in enumerate(sys.stdin, start=1):
    try:
        a_text, b_text = line.split()   # ValueError: not two pieces
        a = int(a_text)                 # ValueError: not a whole number
        b = int(b_text)
        result = a / b                  # ZeroDivisionError
    except ValueError as e:
        print(f"line {number}: skipped, {e}")
    except ZeroDivisionError:
        print(f"line {number}: skipped, cannot divide by zero")
    else:
        print(f"line {number}: {a} / {b} = {result:g}")

Feeding in printf '10 4\n7 0\nten 2\n9\n8 2\n' gives two successful lines and three skipped ones. 9, a single number, fails while unpacking with ValueError: not enough values to unpack; it is the same kind as int("ten"), so the same except handles it.

Check First, or Try First

There are two ways to prepare for a missing file: check first with if p.exists(): (Look Before You Leap), or just call open() and catch FileNotFoundError (Easier to Ask Forgiveness than Permission). Python code usually takes the second route: another program could delete the file between the check and the use, and failures that are hard to check in advance, such as a missing permission or broken contents, are handled the same way. For dicts, a method with a default such as prices.get("mango", 0) is often simpler still.

Raising Exceptions: raise and Your Own Exceptions

raise

When a function you wrote receives a value it cannot handle, do not return some odd value; raise an exception with raise. Then the caller cannot carry on as if nothing happened, and it is the caller who decides whether to handle it. For a bad value, ValueError is the usual choice.

def withdraw(self, amount):
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    ...

A bare raise inside an except block re-raises the exception you just caught, unchanged. Use it when you only want to log something and leave the handling to the code further up.

Exception Classes of Your Own

Exceptions are classes too; inherit from Exception to make a new one. Give each module one parent exception (BankError) and put the specific ones under it: the caller can then catch narrowly with except InsufficientFunds, or catch all of the module's errors at once with except BankError. Storing values as attributes in __init__ lets the code that catches the exception use the information without picking apart the message string.

class BankError(Exception):
    """Base class for every error this module raises."""

class InsufficientFunds(BankError):
    def __init__(self, balance, amount):
        super().__init__(f"balance {balance}, tried to withdraw {amount}")
        self.balance = balance
        self.amount = amount
try:
    left = account.withdraw(20000)
except InsufficientFunds as e:
    print("short by", e.amount - e.balance)    # 13000

Exceptions form a hierarchy, and except catches the class it names plus all of its subclasses. FileNotFoundError and FileExistsError are subclasses of OSError, and json.JSONDecodeError is a subclass of ValueError. So with several except blocks, put the specific ones on top and the broad ones below: a broad one on top would catch everything before the lines below get a chance.

Exception Chaining: raise ... from

config.py in the custom_errors example reads a port number from a settings file. It can fail for several reasons (no file: FileNotFoundError; not a number: ValueError; out of range), but the caller does not need to know all of them. So the low-level exceptions are caught and re-raised as a single ConfigError. Adding from e links the original exception to the new one's __cause__.

def read_port(path):
    try:
        with open(path, encoding="utf-8") as f:
            text = f.read().strip()
        port = int(text)
    except FileNotFoundError as e:
        raise ConfigError(f"{path}: file not found") from e
    except ValueError as e:
        raise ConfigError(f"{path}: port must be a number, got {text!r}") from e
    if not 1 <= port <= 65535:
        raise ConfigError(f"{path}: port {port} is outside 1-65535")
    return port

If nobody catches this ConfigError, you get two tracebacks: the cause (ValueError) on top, then The above exception was the direct cause of the following exception:, and the final error (ConfigError) at the bottom. The cause is not hidden, so while debugging you can see what went wrong in the first place. When there is no need to show the cause, cut the link with raise ... from None (BadRow in csv_import does this).

JSON: Storing Data as Text

What Is JSON?

JSON (JavaScript Object Notation) is a format for writing structures such as dicts and lists as text. People can read it, and almost every language and web service can exchange it, so it is everywhere: settings files, save files, web API responses. It looks like a Python dict, but the rules are stricter: strings must use double quotes, object keys must be strings, and no comma may follow the last item.

Code Walk-through: save.py

save.py in the json_save example keeps a game record in save.json: each run reads it, changes it and writes it back. The heart of it is that the load function handles both ways reading can fail. On the very first run there is no file (FileNotFoundError), and if the power goes off while saving, the file may be only half written (JSONDecodeError). Either way, the game starts fresh.

def load():
    try:
        with open(SAVE, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        print("no save file yet: new game")
    except json.JSONDecodeError as e:
        print(f"{SAVE} is broken ({e.msg}, line {e.lineno} column {e.colno}): new game")
    return new_game()

def save(data):
    with open(SAVE, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)

The defaults come from a function, new_game(), that builds a fresh dict each time, rather than from a constant dict. Returning the constant itself would make several places share its history list, so a score added in one place could show up in another. JSONDecodeError says where the file is broken with lineno and colno; showing that to the user helps when fixing the file by hand.

CSV: A Robust Importer

The csv Module Instead of split(",")

You can split a CSV line yourself with strip().split(","), but it breaks as soon as a value contains a comma. CSV wraps such values in double quotes, as in "Kim, Jiwoo", and split knows nothing about quotes. The standard library's csv module knows the quoting and line-break rules.

'"Kim, Jiwoo",math,88'.split(",")
# ['"Kim', ' Jiwoo"', 'math', '88']     broken into four pieces

DictReader and DictWriter

csv.DictReader uses the first line (the header) as keys and gives one dict for each of the other lines. You read row["score"] instead of row[2], so the code still works if the columns are reordered. All values are strings, so numbers need int(). When a line's field count differs from the header, this is what you get:

  • Too few fields: the missing key's value is None ({'name': '지우', 'subject': 'math', 'score': None}).
  • Too many fields: the extra values go into a list under the key None ({..., None: ['extra']}).
  • A field that is present but empty: the empty string ''.

csv.DictWriter goes the other way and writes dicts as lines. Set the column order with fieldnames, then write the header with writeheader() and the rows with writerows(). Values containing commas are quoted automatically. Open CSV files with newline="", both for reading and writing: it leaves line-break handling to the csv module. Without it, depending on the operating system, blank lines can appear between rows or line breaks inside quotes can break.

Code Walk-through: importer.py

Real data nearly always has bad lines mixed in. One bad line should not make you give up the whole import, and it should not be dropped silently either. importer.py in the csv_import example collects the good lines and reports the bad ones with their line numbers and reasons. The work is split in two: parse(row) checks one line and either returns a clean dict or raises BadRow, and main calls parse for every line and catches BadRow.

class BadRow(Exception):
    """A row we cannot use; the message says why."""

def parse(row):
    if None in row:
        raise BadRow(f"extra fields {row[None]}")
    if row["score"] is None:
        raise BadRow("missing score column")
    name = row["name"].strip()
    if not name:
        raise BadRow("empty name")
    try:
        score = int(row["score"])
    except ValueError:
        raise BadRow(f"score is not a whole number: {row['score']!r}") from None
    if not 0 <= score <= 100:
        raise BadRow(f"score {score} is outside 0-100")
    return {"name": name, "subject": row["subject"], "score": score}

Whatever the reason, parse reports it as one kind of exception, BadRow, so main needs only one except. The ValueError from int() is also re-raised as BadRow; since the message already says everything about the cause, from None cuts the link.

try:
    with open(path, encoding="utf-8", newline="") as f:
        reader = csv.DictReader(f)
        for row in reader:
            try:
                good.append(parse(row))
            except BadRow as e:
                bad += 1
                print(f"line {reader.line_num}: skipped, {e}")
except FileNotFoundError:
    print(f"error: {path} not found")
    return 1

There are two layers of try. The inner one sits inside the loop and handles one line's failure; the outer one handles the file itself being missing. reader.line_num is the file's line number read so far (the header is 1), so it matches the numbers from cat -n scores.csv. If the file is missing, main returns 1 and sys.exit(main(...)) uses it as the exit code, keeping the shell's convention that 0 means success and anything else means failure.

Common Mistakes

  • Opening an existing file with "w". Its contents vanish the moment it opens. To add, use "a"; if it must not be overwritten, use "x".
  • Leaving out encoding. A Korean file that works on your computer turns into garbage on another. Always write encoding="utf-8" for text files.
  • Forgetting the \n at the end of a line. In for line in f, line ends in \n, so line == "5000" is false; strip() before comparing. In the other direction, write() adds no \n.
  • Reading a file outside its with block. It is already closed: ValueError: I/O operation on closed file.
  • Catching everything with except:. It swallows typos (NameError) and even Ctrl+C, so bugs hide. Catch the exceptions you expect, by name.
  • Putting too much code in try. It blurs which line's error you mean to catch, and it also catches the same kind of error from lines you did not expect. Move the success code into else.
  • Catching an exception and doing nothing (except ValueError: pass). Data disappears silently. If you skip something, say what and why.
  • Single quotes or a trailing comma in JSON. {'a': 1} and [1, 2,] are not JSON. Do not write it by hand; produce it with json.dump.
  • Forgetting that CSV values are strings. row["score"] > 90 is a TypeError. Convert with int(), and handle the case where the conversion fails.

Check Quiz

  1. What are the suffix and parent of Path("data") / "2026" / "a.csv"? .csv and data/2026.
  2. Which mode adds one line to the end of an existing log file? "a".
  3. What happens to the file if an exception is raised inside a with block? It is closed as the block is left.
  4. When does the else block run? Only when the try raised no exception.
  5. Does finally run even when there is a return? Yes, just before the function ends.
  6. Does except BankError catch InsufficientFunds? Yes, because it is a subclass.
  7. In raise ConfigError(...) from e, where does e end up? In the new exception's __cause__; it is also shown in the traceback.
  8. What does loads give back for json.dumps((1, 2))? Not a tuple but the list [1, 2].
  9. In DictReader, what is the missing value of a line with too few fields? None.

Summary

Build paths with Path and join them with /. Open files with with open(..., encoding="utf-8"), finish the work inside the block, and pick the mode (r, w, a, x) that fits the job. Put work that can fail in try, catch only the exceptions you expect by name, and report values your function cannot handle with raise. Store structured data with json and tables with csv, and when reading, always consider that the file may be missing or broken. Run the steps on each example page, then deliberately break the input and see how the program reacts.
