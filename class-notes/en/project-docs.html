In this lesson you write the four design documents for your project: Requirement, Feature, Function and UML. The four documents do not describe different programs; they look at the same program from four directions. The requirement answers what must hold, the feature what the user sees, the function what the code promises, and UML how they connect. Today's shared example is the study logger from earlier in this chapter. On the lab pages you run study_logger_skeleton, a skeleton with only contracts, and study_logger_f1, which implements F1, and carry out the documents' checks yourself.

The class is 120 minutes with a 10-minute break in the middle. The first half covers three documents (requirement, feature, function), the second half UML and traceability, followed by a 46-minute lab in which you write the four documents for your own project.

Project guidance and document scope

The project uses only Python 3 and the standard library. Data is kept in a file and results are reported on the screen. Every project is checked on the same three points:

  • Does it refuse bad input?
  • Does it survive a missing file?
  • Is the file left unchanged after a failure?

The design covers the problem, the feature scope, the module structure and the data format. The four documents introduced today are a guide; the actual submission items and weights follow the syllabus.

The role of the four documents

DocumentQuestion it answersWhat it contains

DOC 2 · FeatureWhat does the user do?How to use it, and the results the user can observe
DOC 3 · FunctionWhich Python function does it?Inputs, return value and failure, as a contract

Linking requirements to implementation

A requirement is a condition to satisfy, and a feature is what the user does to satisfy it. A function is the code's promise, and a check decides whether that promise holds. UML sits under feature and function and shows the structure and flow that connect them.

Rule: use the same ID in every document. Then you can follow one requirement all the way to its code and its check.

Shared example: the study logger

There are three basic features: log one entry, reload the file, and show weekly totals per course. The result report prints one line per course, largest first, or, if the entry could not be saved, "Not saved" with the reason. Its duties are to refuse bad input, leave the file unchanged on failure, and survive a missing file.

$ python3 main.py
Date (YYYY-MM-DD): 2026-11-10
Course: python
Minutes: 90
Saved.
python   180 min
stats     45 min

Minutes are a value the student types in. Timing sessions with a clock is an extension.

DOC 1 · Requirement: the specification

The requirement document states what must hold, for whom, and how far. Each line must be something you can judge pass or fail.

  • Purpose and scope: who has what problem, what the program solves, and where it stops.
  • Requirement items: an ID, the statement, a priority (Must, Should, Could) and a check.
  • Functional requirements: log an entry, apply the input rules, report totals, keep the data.
  • Constraints: standard library only, input checked, file unchanged on failure.

Write only one condition per line. A check must be something a classmate can do at the keyboard.

Requirement example

IDStatementPriorityCheck
REQ-01Save one entry with a date, a course and positive minutesMustEnter 2026-11-10, python, 90 → one new row in study.csv
REQ-02Reject minutes that are not a positive whole numberMust-30 → Not saved, file unchanged
REQ-03Show weekly totals per course, largest firstMustpython 90 + 90, stats 45 → python 180 printed first
REQ-04Keep entries between runsMustRun twice; the second run counts the first run's entry

Every requirement carries an observable check. No check, no requirement. The statement says what, not how: no function names and no file formats. The check must be something a classmate can try at the keyboard in a minute. The Must requirements are the MVP; Should and Could wait until the MVP runs. These checks become the implementation stage's test_logic.py, and the testing stage's test list.

On the lab page study_logger_f1 you can carry out the checks for REQ-01 and REQ-02 exactly as written. Entering 2026-11-10, python, 90 adds one line to study.csv, and entering -30 prints Not saved and leaves the line count the same.

Matching requirements to checks

Give each requirement sentence an input condition and an observable result.

  • Input condition: exactly what is typed, or what the file holds before the run.
  • Observed result: what is printed, and what the file contains after the run.

A check that only works if its author stands beside you and explains it is not a check yet.

DOC 2 · Feature: the user-facing specification

The feature document describes the program as the user meets it: the command, the questions (prompts), and the results that come back.

FEAT-xx  <name>              basic | extension
purpose  one sentence
usage    command, prompts, allowed values
flow     step 1 ... step n, the normal path
result   what the user sees on success
errors   each failure and its message
serves   REQ-xx, REQ-yy
  • Identification: feature ID, name, purpose, and whether it is a basic feature or an extension.
  • How to use: the command, the prompts, the allowed values, the preconditions.
  • Behavior and result: the normal flow and the output the user checks.
  • Exceptions and links: bad input, failures, and the requirement IDs this feature serves.

Feature example: logging one entry

FEAT-01  Log one entry                     basic
purpose  record one study session
usage    python3 main.py, then three prompts:
         date YYYY-MM-DD, course, minutes > 0
flow     check input -> build record
         -> append one row to data/study.csv
result   "Saved."
errors   bad minutes or empty course:
         "Not saved: <reason>", file unchanged
         data/ missing: report it, write nothing
serves   REQ-01, REQ-02, REQ-04

The usage line is what you will actually type in the demo. Write it so that a stranger could follow it. List errors one by one, each with its message; a single line saying "handles errors" is not an error entry. The serves line is the traceability link back to the requirements.

A feature's normal path and error path

Define what the user sees on both the good day and the bad day. Both belong in the feature sheet.

  • Normal path: four steps, each with something the user can observe.
  • Input error: a sentence with the reason is printed, and nothing is written to the file.
  • File error: the cause is reported, nothing is left half-written, and the program ends cleanly.

DOC 3 · Function: Python function design

One function, one contract. The design document from your design stage already has the fields.

make_record(date: str, course: str,
            minutes_text: str) -> dict
module   logic.py       called by main()
I/O      none           pure   yes
returns  {"date", "course", "minutes": int}
fails    ValueError: empty course, or
         minutes not a whole number above 0
  • Signature: name, parameters with types, return type.
  • Inputs and results: allowed values and units, what success returns, and how failure shows.
  • Where it runs: which module it is in and who calls it, and whether it uses the keyboard, a file, or neither.
  • Failure and resources: whether it raises an exception or returns None, and who opens and closes the file.

Function example: make_record()

Write the contract in the docstring and the body under it, then add one call that shows the promise is kept.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))
python 90

The input is three strings from input(). Trimming and lower-casing the course happens here and only here. main() calls this function before anything is written. It returns one dict, with minutes as an int. On failure it raises ValueError with a reason, and main prints Not saved and writes nothing. The real implementation is in logic.py of study_logger_f1 (with the minutes check split out into parse_minutes()), and you can run the same call on the lab page.

Decomposing into functions

Six functions, six single responsibilities, named with the verb test from "From Proposal to Design".

FunctionContract
parse_minutes()minutes string → positive int, or ValueError
make_record()date, course, minutes → one record dict
append_record()one record → one row in data/study.csv
load_records()file → list of records, [] if the file is missing
weekly_totals()list of records → {course: minutes}

Two rule functions, two file functions, one report function, and main(), which calls them. Every name is a verb plus a noun, and each line of the table above is one row of the contract table. If you need "and" to describe a function, split it before you write the contract.

This table turned into code is study_logger_skeleton. Every function has a name and a docstring, but the bodies are raise NotImplementedError or TODO. It runs (Loaded 0 records), but it does not satisfy the requirements yet.

Functions and modules: who does what

Once main() has asked the user, each module answers only one kind of question. None of them asks the user anything.

  • main.py asks, calls and prints. It holds no rules.
  • logic.py holds the rules and never touches the keyboard or the disk.
  • storage.py is the only module that opens data/study.csv.
  • report.py turns results into lines.

DOC 4 · UML: choosing a diagram by purpose

You do not need every diagram. Pick the one that answers your reader's question.

Reader's questionDiagram
Who uses it, and for what?Use case
Which file imports which?Module (component) diagram
In what order do the calls happen?Sequence diagram
What happens to one entry?State (or activity) diagram

The arrows in a module diagram point one way only. An activity diagram shows the steps, including the error branches.

Use case example

Draw the user and the goals the system offers: goals, not functions. There is one actor, the student, and the system boundary is the study logger. There are three goals: log an entry, review weekly totals, and find earlier entries again. Function names do not appear here; the order of calls belongs in the sequence diagram.

Sequence example: one run

Draw one run of the normal path, with time flowing from top to bottom. Every arrow is a call from your contract table. main() calls logic first, so nothing is written before the record is valid. Each return arrow carries one data shape: a record, a list of records, a totals dict, or a list of lines. Draw the failure path (ValueError) as a separate branch or as a second, shorter diagram.

State example: one entry

Four states and one dead end; each transition is a function from the table. Typed → checked by make_record() → saved by append_record() → counted by weekly_totals(). An empty course or bad minutes ends in rejected: "Not saved" is printed and nothing is written. A file error after the check is also reported, and no half-written file is left behind.

Traceability across documents

Write the requirement ID in the feature, the function, the diagram and the test, and nothing gets lost. For example, REQ-02 says what must hold (minutes that are not positive are rejected). FEAT-01 shows it to the user, parse_minutes() enforces it, the state diagram draws it, and TEST-02 proves it. A grader, or you near the end of the project, can follow this chain in either direction.

Document review and demo preparation

Ask five questions before you say the documents are done.

  1. Scope: are basic features and extensions separated, and is the MVP boundary visible?
  2. Done: can each requirement be judged pass/fail by its check?
  3. Consistency: do the feature sheet, the function contracts and the UML flow agree with each other?
  4. Data checks: have you covered bad input, a missing file, the header row and "file unchanged on failure"?
  5. Reproduction: are the setup, the run command, one normal scenario and one error scenario written down?

Lab: your four documents

In 46 minutes, write four short documents for your own project, using one ID scheme.

  • A. Requirements, 12 minutes
  • B. The feature sheet for F1, 10 minutes
  • C. Function contracts, 10 minutes
  • D. One UML diagram, 10 minutes
  • Last 4 minutes: swap with a classmate and follow one REQ ID through all four documents.

Submission and the next stage

Submit the four documents today. Keep the REQ and FEAT IDs as they are; these IDs go into your commit messages, test names and README.

The next stage moves from design to running code: you make F1 work end to end on a feature branch. Bring a laptop on which your repository is cloned, git status is clean and python3 main.py runs. This web lab has no git, so do the branch and commit work on your real PC; here you only check that the code runs and passes its checks.

Rule: the Must scope is frozen. A new idea becomes a Should or Could line, not a new Must requirement.
