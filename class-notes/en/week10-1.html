Last week's proposal decided what the program will do. This session decides how. It is the time to draw the program on paper before you type it. The session has three acts and a lab. In Act 1 (decompose), stories become features and features become functions. In Act 2 (contracts), every function promises its inputs, output and failures. In Act 3 (modules and data), you settle on one file per job and one shape per kind of data. In the final lab, each of you writes a design document and reviews it with a classmate.

The examples are study_logger, the finished study-time logger, and refactor_lab, a practice in splitting an expense tracker that crams everything into one function. The slide paths examples/study_logger/ and labs/session1/refactor_lab.py are ~/week10/examples/session1/study_logger/ and ~/week10/starter/session1/refactor_lab.py in this web lab.

Where we are in the project

In Week 9 you made a proposal with a problem, user stories, Must features and acceptance criteria. Week 11 needs an MVP in which the Must features run end to end. Week 10 is the bridge between them: a design document today, a Git repository next session. Rule: the Must scope freezes at the end of this week, and new ideas go to Should or Could.

Check your proposal first

Design is built on the proposal, so cracks in the proposal spread. Spend five minutes checking:

  • At most 3 Must features, each one sentence.
  • Each Must feature has a pass/fail acceptance criterion.
  • Your data file has a name, columns and types.
  • Your Won't list has at least two items.

A criterion like "entering -30 minutes prints a warning and the file is unchanged" is excellent. It becomes a test in Week 12 as it is.

The 200-line main.py

Every project starts as one file, and the problem is that most stay that way. To test the totals you must type at the keyboard every time, a change to the printing breaks the arithmetic, and by Week 14 neither you nor the grader can find anything. The cure is not more code but a plan for where code lives.

Design means making decisions on paper. A box on paper takes a minute to move; the same change in code costs an evening. There are four things to decide. Which functions exist, and what is each one's single job? What does each function take and return, and what does it do with bad input? Which file holds each function? What does one record of data look like, in memory and on disk? Your design document becomes the Week 11 checklist: each time you implement one contract, you tick one box.

Act 1 · Decompose: from stories to functions

Big problems are small problems standing in a line. A story says why, a feature says what, and a function says how.

Story, feature, function

  • Story: As a student, I want to log study time by course, so that I can review my week.
  • Feature: F1 accepts date, course and positive minutes and saves valid entries.
  • Function: one verb, one job, testable alone.

Aim for 2–4 functions per Must feature.

The verb test

Read the feature sentence aloud and the verbs become functions. "F1: accept date, course and minutes; check the minutes; save valid entries."

F1 accept, check and save one entry
  -> read_entry()     asks the user       I/O
  -> make_record()    checks and builds   logic
  -> append_record()  writes the file     I/O

Verbs become functions, and nouns (date, course, minutes, record) become data. Name functions verb_noun, like make_record, not record_stuff. If a function name needs "and", it is two functions.

Input, processing, output

Every feature is a pipeline. Input is what arrives from the keyboard or a file, processing is the rules and calculations on that input, and output is what goes to the screen or a file. Processing is where the bugs live, and where the marks are. Draw the picture before you write code.

Trap: one function does everything

def run():
    date = input("Date: ")
    course = input("Course: ").strip().lower()
    minutes = int(input("Minutes: "))
    if minutes <= 0:
        print("Not saved")
        return
    with open("study.csv", "a") as f:
        f.write(f"{date},{course},{minutes}\n")
    totals = {}
    for line in open("study.csv"):
        d, c, m = line.strip().split(",")
        totals[c] = totals.get(c, 0) + int(m)
    print(totals)

run()

This code works only until the second day of use. To test the totals you have to type three answers every time, and if the CSV has a header row, on the next run int() meets 'minutes' and stops with ValueError: invalid literal for int() with base 10: 'minutes'. Reading the code alone, would you have found this bug?

Split by job

def parse_minutes(text):
    minutes = int(text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return minutes

def weekly_totals(records):
    totals = {}
    for r in records:
        c = r["course"]
        totals[c] = totals.get(c, 0) + r["minutes"]
    return totals

rows = [{"course": "python", "minutes": 90},
        {"course": "stats", "minutes": 45}]
print(weekly_totals(rows))   # {'python': 90, 'stats': 45}

The rules are the same, but now they live in functions with no input(), print() or open(). parse_minutes checks one value and weekly_totals adds up a list of records. Neither knows where the data comes from or goes to, so you can call them with any data you like.

Test without typing

assert parse_minutes("90") == 90
for bad in ["-30", "0", "abc"]:
    try:
        parse_minutes(bad)
        print("accepted", bad)
    except ValueError:
        pass
print("All checks passed.")

Logic functions can be checked in one second, as often as you like. Each assert is one acceptance criterion from your proposal. No keyboard, no files, no waiting, so rerun the checks after every change. Week 9's "entering -30 prints a warning" has now become check code. study_logger's test_logic.py is exactly this kind of file; run it with python3 test_logic.py in study_logger.

Act 2 · Contracts: promises between functions

"Give me this and I give you that, or I tell you why not." A contract is decided before the function body is written, and it is the part of your design that a grader can check line by line.

Anatomy of a contract

  • Name: a verb that says what you get back
  • Arguments: names and types
  • Return value: one type, always the same type
  • Failure: what happens with bad input

If you cannot fill in all four fields, the function is not designed yet.

Write the contract in the docstring

def parse_minutes(text):
    """Return text as a positive int of minutes.

    Raises ValueError if text is not a whole
    number or is not above 0.
    """
    minutes = int(text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return minutes

print(parse_minutes("45"))
print(parse_minutes.__doc__.splitlines()[0])

The docstring is the contract, stored right beside the code it describes. The first line says what the function returns; after that, write what makes it fail and how. In VS Code, hovering over a call shows the docstring (in the web lab, print __doc__ to check it). Write the docstring first; the body is filled in during Week 11. The output is 45 and Return text as a positive int of minutes.

Choose one failure style

def find_minutes(totals, course):
    """Return the minutes, or None if absent."""
    return totals.get(course)

totals = {"python": 90}
print(find_minutes(totals, "python"))   # 90
print(find_minutes(totals, "art"))      # None

Bad input will arrive. Decide on paper how each function deals with it.

  • raise ValueError: the input breaks a rule. The caller must react.
  • return None: "nothing found" is a normal answer.
  • print inside the function: avoid. The caller cannot react and tests cannot see it.

Trap: a function that sometimes returns an int and sometimes the string "error" breaks every piece of calling code.

Logic raises, main talks

for typed in ["90", "-30", "abc"]:
    try:
        minutes = parse_minutes(typed)
    except ValueError as error:
        print("Not saved:", error)
    else:
        print("Saved", minutes)
Saved 90
Not saved: minutes must be positive
Not saved: invalid literal for int() with base 10: 'abc'

The rule lives in logic; the message for the user lives at the edge. parse_minutes only raises and never prints. The caller catches ValueError and decides what the user sees. That is why the same parse_minutes works in a menu, a test and a chart script. In the third step of study_logger, entering -30 and abc gives the same two messages and the file does not change (study_logger's message adds got -30).

Keep I/O at the edges

Put a pure core in the middle and a thin shell of input and output around it. The core is logic.py: same input, same output, every time. The shell is main.py, storage.py and report.py, which talk to the keyboard, disk and screen. The core never calls input(), print() or open(). Bugs in the core show up in tests; bugs in the shell show up in the demo. In Week 12 you test the core with asserts and the shell by running it once.

main() reads like a table of contents

def main():
    date = input("Date (YYYY-MM-DD): ")
    course = input("Course: ")
    minutes = input("Minutes: ")
    try:
        record = make_record(date, course, minutes)

main() only calls; it does not calculate. Each line is a step from the design (ask, build, save, total, show), and reading main() tells the whole story in about ten lines. If main() grows past 20 lines, a function is missing. This is study_logger's main.py as it is. In the second step of study_logger, running it with input prints Saved. and the totals per course.

Act 3 · Modules and data: where things live

One file per responsibility, one shape per kind of data. A module is just a .py file you import, and your design decides which function goes in which file.

One responsibility per file

  • main.py runs the program: ask, call, show.
  • logic.py holds the rules. No I/O at all.
  • storage.py is the only file that opens data files.
  • report.py turns results into lines of text.

Rule: imports point one way only. logic.py imports none of your other files.

Importing your own files

from logic import make_record, weekly_totals
from report import format_totals

rows = [make_record("2026-10-24", "python", "90"),
        make_record("2026-10-25", "Stats", "45")]
for line in format_totals(weekly_totals(rows)):
    print(line)
python    90 min
stats     45 min

A file in the same folder is a module, and its name is the file name without .py. from logic import weekly_totals loads logic.py once. Import only the names you need and avoid import *. Run python3 from the project folder so that Python can find the files. The sixth step of study_logger runs this code; you can also see make_record store "Stats" as stats.

Run it or import it

def format_totals(totals):
    return [f"{c:<8}{m:>4} min"
            for c, m in totals.items()]

if __name__ == "__main__":
    print(format_totals({"python": 90}))

if __name__ == "__main__": separates "run this file" from "lend me your functions". If you run it with python3 report.py, the block runs and prints ['python 90 min']; if another file does import report, the block is skipped. Use it for a quick self-check at the bottom of a module. (study_logger's report.py has no such block, so you can add one yourself and try it.)

Two import traps

Both cause confusing errors far from the real cause.

  • Never name a file after a library, such as csv.py or random.py. Your csv.py hides the real module and you get AttributeError: module 'csv' has no attribute 'DictReader'.
  • Never let two of your modules import each other. One of them would see a half-built module.

If the error remains after renaming the file, delete __pycache__. The last step of study_logger creates a csv.py in a temporary folder to reproduce the first trap.

Three shapes of data

  • One record: a dict with fixed keys.
  • All records: a list of dicts, in file order, duplicates allowed.
  • A summary: a dict from key to result, one entry per key.

Decide the shapes now, because every function's contract mentions them. Predict: why a list for the records but a dict for the totals? (Records have an order and the same course can appear many times, but the totals need exactly one value per course.)

From file to records

import csv

with open("data/study.csv", newline="") as f:
    rows = list(csv.DictReader(f))
print(rows[0]["course"], repr(rows[0]["minutes"]))
for r in rows:
    r["minutes"] = int(r["minutes"])
print(sum(r["minutes"] for r in rows))
python '90'
135

csv.DictReader turns each row into a dict using the header as keys, but every value arrives as a str. Convert numbers only once, right after loading, in storage.py, so that every other function can trust the types from then on. Trap: "90" + "45" is "9045". Convert before you add. In the seventh step of study_logger, adding without converting really gives 9045.

C: design review (5 minutes)

Swap documents, not code, with one classmate. Can every Must feature be traced to named functions? Is logic.py free of input(), print() and open()? Does every contract state its failure behavior? Could you write an assert for each logic function right now? Give one strength and one concern, then revise your own document. This is review only; do not share functions, files or code.

Five ways to ruin a design

  • Function names that are nouns: data(), stuff(), process().
  • Contracts with no failure behavior.
  • print() and input() inside logic functions.
  • One utils.py that holds everything.
  • Designing Won't features "just in case".
