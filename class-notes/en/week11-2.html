In this session we follow one project from the user's problem all the way to a web report that passes its checks. The topic is Korean stock market analysis. Using the previous close and today's close of five stocks in a fictional classroom CSV, we calculate the daily percentage change, compare by market, and produce an HTML report. The session runs in four acts: define the task with requirements and features (ACT 1), trace and prove the promises with function contracts and tests (ACT 2), draw the structure in UML (ACT 3), and build the MVP and open the web report (ACT 4). The finished version is korea_market_mvp, and at the end you practice refactoring that does not change behavior with tidy_lab.

Scenario: Minji reviews the market

After the market closes, Minji wants to compare a few stocks.

  • SC-01: prepare a CSV, generate the report and compare markets. She generates the report for ALL, then regenerates it for KOSPI, and checks the reference date, the daily change ranking and the sample summary.
  • SC-02: reject bad input.
  • SC-03: generate a valid empty report.

Scope and data honesty

A snapshot sample is useful when its limits are visible. All supplied prices and volumes are fictional classroom data: a single date, two market labels, five example stocks. The Mean is the equal-weight average of the changes in the selected sample. It is neither a KOSPI/KOSDAQ index return nor a live market feed.

The input contract

Define the data before writing the loop.

date,code,name,market,previous_close,close,volume
2026-11-05,005930,삼성전자,KOSPI,70000,71400,1000000
  • A UTF-8 CSV; an optional BOM is accepted. The header must match exactly, including order.
  • The six-digit stock code stays text: 005930 must keep its leading zeros.
  • previous_close is the previous trading day's close (KRW) and close is the snapshot close (KRW), both positive integers. volume is the number of shares traded, a nonnegative integer.
  • There is one date, and codes must be unique. Both closes use the same price basis.

ACT 1 · Requirements and features

Requirement: observable conditions

Each REQ in the Requirement sheet links to SC IDs and has a check.

  • REQ-01: read a valid CSV and preserve stock codes.
  • REQ-02: reject invalid values, duplicate codes and mixed dates.
  • REQ-03: calculate, filter and sort daily percentage changes. For example, previous_close=70000 and close=71400 gives +2%. Choosing KOSPI yields only KOSPI rows. The order is by change, descending; ties are broken by code, ascending.
  • REQ-04: count up, down and flat, and calculate a sample mean.
  • REQ-05: show the date, market, source, units, summary and table in HTML.
  • REQ-06: report file and data errors, and preserve the old HTML on failure.

The output and the failure policy are part of the product too. A header-only CSV produces a valid empty report (count 0, mean N/A). A missing CSV file is an error, not a successful empty report.

MVP cut: Must, Should, Could

Ship the complete CSV → analysis → HTML path first.

  • Must: validated input, analysis, static HTML, clear error handling.
  • Should: a clickable market filter in the browser.
  • Could: API data, history, moving averages, charts, publishing.

Do not add a new Must until the existing acceptance checks pass.

ACT 2 · Functions and tests

Contracts before bodies

Keep the values and failure rules that cross module boundaries consistent.

Quote = {date, code, name, market,
         previous_close: int, close: int,
         volume: int}
Analyzed row = Quote + {change_pct: float}
Summary = {count, up, down, flat, mean}
  • FUNC-01 parse_row(row): strings → a typed quote. ValueError on invalid fields.
  • FUNC-02 load_quotes(path): CSV → list. A missing file raises OSError.
  • FUNC-04 analyze(quotes, market): validated list → freshly made, sorted rows.
  • FUNC-05 summarize(rows): counts and mean. If empty, the mean is None.

Implement the smallest rule

Compute with full precision and round only in the report. The formula is (close − previous_close) / previous_close × 100. Reject a zero or negative price before dividing. A rise, a fall and a flat price are separate checks.

def change_pct(previous_close, close):
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    difference = close - previous_close
    return difference / previous_close * 100

assert change_pct(70000, 71400) == 2.0
assert change_pct(200000, 198000) == -1.0
assert change_pct(100, 100) == 0.0
print("Daily change checks passed.")

Modules: keep I/O at the edges

The module diagram tells us where each responsibility lives.

  • main: arguments, orchestration, messages and exit codes.
  • storage: CSV reads and atomic HTML writes. It imports parse_row.
  • logic: validation and analysis. report: escaped HTML strings.

Neither logic nor report opens files or asks the user questions.

Actor, goals and call order

Choose the diagram that answers the reader's question.

  • Component: which module depends on which.
  • Sequence: the calls made during one successful run.
  • Activity: the normal path and the branches that stop on error.

Sequence: one successful run

Every call name appears in the function contract table. main → load_quotes → parse_row for each row. main → analyze → summarize → render_html. main → write_html. Success is reported only after the replacement has finished. The browser opens the generated file after Python finishes.

Activity: stop before replacing output

Validate first, then render, and only then commit the output file. Bad input ends with a reason and exit code 1. A complete new file replaces the old file in one step. A valid empty input follows the successful report path. The full Mermaid diagrams are in project-spec.md.

Prototype a complete path first

A fake function makes the whole pipeline runnable before every rule exists.

def load_quotes(path):

def render_html(rows):

Start with one known quote and a tiny HTML table. Keep the planned names and return types. Replace the fakes one at a time: rules, CSV, HTML, output. In the final MVP there must be no fake on any Must-feature path.

CSV to validated quotes

Convert text only once, and keep the code as a string.

import csv, io
source = ("code,previous_close,close\n"
          "005930,70000,71400\n")
row = next(csv.DictReader(io.StringIO(source)))
print(row["code"], type(row["code"]).__name__)
difference = (int(row["close"])
              - int(row["previous_close"]))
print(difference)
005930 str
1400

csv.DictReader reads every field as a string. Check that the header is exact before trusting any row. parse_row validates and converts the prices and volume. Validate every row, even those outside the selected market.

Filter, sort and summarize

Keep calculations independent of HTML. Reject mixed dates and duplicate codes before filtering. Return new dicts and leave the loaded quotes unchanged. Sort on the unrounded change, then by stock code for equal values. If there are no rows, the mean is None, which the view turns into N/A.

ALL order from the supplied fictional CSV:
247540  +3.00%
005930  +2.00%
035420  +0.00%
000660  -1.00%
035900  -2.00%
mean    +0.40% (sample, equal weight)

HTML is a view of the result

Formatting changes only the presentation; it must not change the calculation. render_html returns a string, and storage does the writing. Use html.escape for stock names and other external text. Show the sign and the number as well as color. Include the date, the source, a fictional-data label and the units.

from html import escape
name = "<b>Example</b>"
change = 2.0
print(escape(name))
print(f"{change:+.2f}%")
&lt;b&gt;Example&lt;/b&gt;
+2.00%

main: assemble the program

The top-level function coordinates the contracts.

quotes = load_quotes(args.input)
rows = analyze(quotes, args.market)
summary = summarize(rows)
html = render_html(rows, summary, market, day)
write_html(args.output, html)
# Only now print Generated ...

argparse takes --input, --output and --market. Data and file errors are caught at the user-facing boundary (main). Prepare all results before calling write_html. The exit codes are 0 for success, 1 for data or I/O failure, and 2 for CLI misuse.

Refactor with evidence

Keep the behavior identical while improving the structure. Run all 12 checks before and after each move. Rename vague variables to quote, rows and summary. Keep FIELDS and MARKETS in one place. Extract the HTML formatting into a function, but leave the numbers, order and messages as they are.

Feature commit:  add KOSPI filtering
Refactor commit: extract render_html
Fix commit:      preserve leading zero in stock code

These three are different kinds of change and need different evidence. The evidence for a refactoring is "same checks, same results". tidy_lab is the file for this practice. To hard-to-read code whose checks all PASS, apply renaming, constant extraction (the 2000 ml goal), pulling a duplicated line into a function, and guard clauses, one at a time, running it each time to check that the six PASS lines stay the same.
