The goal of this session is to extend one feature while keeping the MVP reliable. The deliverable is one feature plus tests that demonstrate its behaviour, and you check that the previous report is preserved when something fails. Work in your own repository or in a copy of the example. In the first half, short experiments (Activities A–D) check input validation and failure handling; in the second half, using a minimum-volume filter as the example, you go through the feature contract, a failing test, the implementation, a demo and a code review. Run the experiments in korea_market_mvp and playground.

The CSV input boundary

CSV cells arrive as strings. Check the schema and required fields first, and pass only validated, converted values to the analysis function.

Stock codes stay text

int("005930")  # 5930

Leading zeros are part of a stock code. Convert only the prices and volumes used in calculations to integers.

Conversion and valid values

int("-1")  # -1

Even if conversion succeeds, reject a negative volume. Prices must be greater than 0, and volume must be 0 or more.

Row rules and snapshot rules

ScopeRule
One rowReal date, valid price and volume ranges
Whole inputOne date, unique stock codes

Whether whitespace is normalized is also part of the input contract. In the MVP, parse_row handles the row rules and analyze handles the whole-input rules. In korea_market_mvp you can see a row with volume -1 rejected by parse_row, and a duplicate code on a row that the filter would drop rejected by analyze.

The minimum-volume type contract

Accept only nonnegative int values; reject bool, strings and floats. Distinguish a value passed in a direct function call from a value converted from a CLI string.

def validate_min_volume(value):
    if type(value) is not int or value < 0:
        raise ValueError("min_volume must be a nonnegative integer")
    return value

isinstance(True, int) is True, so bool has to be handled explicitly. Here type(value) is not int rejects bool as well.

Where exceptions are raised and where they are handled

Rule functions raise ValueError for contract violations. The storage module passes file and decoding failures on to its caller. The CLI converts expected failures into a user message and an exit code. Handle exceptions where the program can make a useful decision, and keep unexpected programming errors visible during development.

Failure disguised as empty data

try:
    quotes = load_quotes(path)
except Exception:
    quotes = []

Written like this, missing files and programming errors both look like valid empty input.

Failure and valid empty results

InputExpected behavior
Missing CSVFail, preserve the old report
Valid header-only CSVSucceed, generate an empty report

A completely empty (zero-byte) file is different from a header-only file.

The existing CLI handler

except (OSError, ValueError, UnicodeError) as error:
    print(f"Report not generated: {error}")
    return 1

Include the information needed to investigate the cause, such as the CSV row number, in the message.

Check the state of the output file as well as the message.

Before and after replacing the report

Read and validate all input, then write the complete new HTML to a temporary file in the output folder. Keep the old report until validation and writing finish. When writing is done, replace the destination file with os.replace; if replacement fails, remove the temporary file. This protects the old result from handled failures before the replacement; it does not guarantee durability if the power is cut.

New feature: minimum volume

The user goal is to compare only stocks whose volume meets a chosen minimum.

analyze(quotes, market, min_volume=0)

With the default 0, existing two-argument calls keep their results. Duplicate codes and mixed dates are rejected across the whole input first. Apply the market and minimum-volume conditions together, and keep the change-descending, code-ascending order and the unchanged input.

Second half: from feature contract to implementation

During the break, choose one feature to extend in your own project. The second half starts with its contract and a failing test.

Writing the feature contract

Open labs/session2/project-review.md, link a requirement ID to the function you will change, and briefly state the accepted inputs and the successful and error results. The review sheet has an example plan for TEST-13 to TEST-18 (volumes 99/100/101, threshold 0, wrong types, all excluded, hidden duplicate and mixed dates, market and volume applied together).

Failure evidence before implementation

Add a test for the new behaviour first, run it on the old code and check that it fails for the expected reason. Record the input, the expected result and the actual failure.

Implementation (20 minutes)

Validate the new parameter, then apply the filter. Keep whole-snapshot validation before filtering. Do not change the original input.

New tests and regression tests

Run the new cases and the complete existing suite. Check the default 0 and existing two-argument calls. If something fails, reproduce the input and narrow down the cause.

To try this on this virtual machine, make a copy with cp -r ~/week11/examples/korea_market_mvp ~/my_mvp, edit logic.py and test_market.py with nano, then run python3 -m unittest -v. The copy disappears when you reboot, so copy your result files to /mnt/host and download them.

Demonstrating the result

Generate a normal report and an empty report with the existing main entry point, and prepare a test that demonstrates the new function's behaviour. If there is no CLI wiring, demonstrate the report and the function tests separately. Do not claim that extending the function automatically applies to the CLI report.

  • 30 seconds: the user explains the market, the number of stocks and the ranking in the normal report.
  • 30 seconds: the user says whether the empty report's message is sufficient.

Record one observed issue or one confirmed acceptance criterion and link it to the demonstration field in project-review.md. Make sure all tests in the final submission pass.

Code review

Find a counterexample (15 minutes)

Compare the diff with the contract and the test plan, and look for one counterexample among boundaries, errors and empty results. If you have no partner, review your own diff with the same questions.

Concrete feedback

Input: ______
Expected / actual result: ______ / ______
Supporting function or test: ______

Also check failure propagation, preservation of the old output, and naming and separation of responsibilities. The reviewer does not overwrite the change directly but leaves feedback with a concrete input and expected result.

Applying feedback and rechecking

Revise the code based on the feedback and rerun the affected tests. For feedback you do not apply, record the reason, and keep the review feedback and the revision result in the submission form.

Evidence for the PR and submission

  • The problem, the user-visible change and the requirement ID.
  • The changed function, the exact checking commands and the actual results.
  • If GitHub is hard to use, submit a local diff and the review record.

Submit the feature code, the tests, the review record and the traceability documents. Open the PR from the repository on your real PC. There are two exit questions: what specific fault does your test catch? Why must a duplicate code be rejected even when the filter would hide it?
