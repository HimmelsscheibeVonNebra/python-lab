이번 시간부터 16주차까지는 한 학생이 하나의 프로그램을 스스로 기획하고 개발하는 개인 기말 프로젝트를 진행합니다. 오늘은 프로젝트의 규칙과 평가 방식, 주제를 고르는 기준, 막연한 바람을 검사 가능한 요구사항으로 바꾸는 방법, 그리고 개인 작업 계획을 다룹니다. 수업이 끝나면 프로필, 주제 워크시트, 제안서 v0 세 문서를 제출합니다.

개인 소유와 완료의 정의

한 학생이 한 프로젝트를 제출합니다. 기획, 구현, 데이터, 테스트, 문서, 시연을 모두 스스로 책임지고, 자신의 저장소에 진행 상황을 기록합니다. 조언과 동료 피드백으로 결정을 다듬을 수는 있지만 구현은 본인의 몫입니다. 구현을 공유하거나 개발 작업을 나누어 맡으면 개인 프로젝트가 아닙니다. 제출한 모든 함수와 설계 결정을 설명할 수 있어야 합니다.

프로젝트는 다음을 갖추었을 때 완료입니다.

  1. 저장소의 안내대로 새 환경에서 실행되는 프로그램
  2. 목적, 설치, 사용법, 한계를 설명하는 README
  3. 16주차의 믿을 수 있는 개인 라이브 시연

2. 주제 고르기

개인 주제를 위한 세 가지 테스트

  1. 관심 테스트: 나 또는 내가 아는 누군가가 실제로 그 프로그램을 필요로 한다.
  2. 파이썬 테스트: 핵심 부분이 지금까지 배운 논리와 데이터 기술로 해결된다.
  3. MVP 마감 테스트: 11주차까지 혼자서 최소 버전을 실행할 수 있다.

하나가 실패하면 범위를 좁히고, 둘이 실패하면 다른 주제를 고릅니다. 가용 시간에는 테스트와 문서 작업 시간도 포함해야 합니다.

작을수록 좋다: MVP 사다리

MVP(최소 기능 제품)는 쓸모 있는 일 하나를 처음부터 끝까지 해내는 가장 작은 프로그램입니다.

수준아이디어
너무 큼로그인, 피드, 추천이 있는 피트니스 앱
여전히 큼차트와 목표가 있는 운동 기록기
MVPworkout.csv에 세트를 추가하고 주간 요약 차트를 출력
너무 작음숫자 하나를 출력하는 스크립트(사용자도 결정도 없음)

먼저 MVP를 만들고 그다음에 올라갑니다. 추가 기능은 12–13주차의 일입니다.

주제 목록

데이터 프로젝트(pandas, matplotlib, 5–7주차): 과목별 공부 시간을 기록하고 주간 막대 차트를 그리는 공부 시간 기록기, 두 도시의 CSV로 최저·평균·최고 기온 선을 그리는 날씨 비교, expenses.csv로 카테고리 원그래프와 월별 추세를 보는 개인 가계부, 학식 메뉴·도서관 이용 시간·시험 기간 수요 같은 캠퍼스 데이터. 데이터는 이미 있거나 며칠 안에 손으로 모을 수 있어야 합니다.

도구와 게임(함수, 클래스, 파일, 3–7주차): CSV 단어장과 퀴즈 모드·오답 복습이 있는 단어 카드, 한 판을 클래스 하나로 만드는 Wordle 스타일 단어 게임, 추가·삭제·검색 후 파일에 저장하는 재고 관리, 비밀번호 생성기와 강도 검사기, 교사가 문제를 내고 학생이 풀며 점수가 저장되는 퀴즈 빌더. 게임이라면 시연할 수 있는 분명한 "한 판"이 있어야 합니다.

일상 도우미(딕셔너리, 클래스, 예외): 과목·강의실·시간 충돌을 경고하는 시간표 검사기, 여행 비용과 각자의 정산 금액을 계산하는 비용 분할기, 주간 메뉴와 CSV 장보기 목록을 만드는 레시피 플래너, 마감일·우선순위·지연 목록이 있는 개인 할 일 관리. 개발자는 한 명이어도 프로그램 사용자는 여러 명일 수 있습니다.

3. 요구사항 분석

요구사항은 검사할 수 있어야 한다

요구사항이 아닌 것요구사항
"보고서가 빠르다""10,000행에 대해 요약이 1초 안에 출력된다"
"쓰기 쉽다""처음 쓰는 사용자가 설명서 없이 명령 하나로 항목을 기록할 수 있다"
"잘못된 입력을 처리한다""음수 금액을 입력하면 경고가 나오고 아무것도 저장되지 않는다"

기능 요구사항은 프로그램이 무엇을 하는지, 비기능 요구사항은 얼마나 잘 하는지(속도, 안전성, 가독성)를 말합니다. 시험 방법을 떠올릴 수 없다면 아직 요구사항이 아닙니다.

사용자 스토리

형식은 "___로서, 나는 ___을 원한다, 그래야 ___할 수 있다(As a ___, I want ___, so that ___)"입니다.

스토리평가
학생으로서, 나는 과목별 공부 시간을 기록하고 싶다. 그래야 한 주를 돌아볼 수 있다.사용자, 행동, 이유가 분명함
사용자로서, 나는 기능을 원한다. 그래야 무언가를 할 수 있다.너무 막연함
나는 클래스를 쓰고 싶다.기술 선택이지 사용자의 필요가 아님

스토리를 3–5개 쓰고, 각각을 번호 붙은 기능에 연결합니다.

스토리에서 기능으로

ID기능사용하는 수업 내용
F1날짜, 과목, 양수인 분을 입력입력, 조건문, 예외
F2study.csv에 저장하고 다시 읽기파일, CSV, 형 변환
F3과목별 주간 합계 출력딕셔너리와 반복문

잘못된 분 입력을 거부하는 것은 F1의 수용 기준에 포함됩니다. 첫 동작 버전에 꼭 필요한 기능은 무엇일지 예측해 봅니다.

MoSCoW 우선순위

우선순위의미공부 시간 기록기
Must핵심 시연에 반드시 필요F1 올바른 입력, F2 저장, F3 합계
Should중요하지만 필수는 아님F4 차트

MVP는 Must 기능으로 만들고 11주차까지 실행되게 합니다. 개인 프로젝트에서는 Must 기능을 최대 3개로 하고, 각각 검사 가능한 결과를 가져야 합니다. 입력 검증과 오류 처리는 해당 기능 안에 포함합니다.

범위의 경계

v1에 포함v1에서 제외(어디로 갔는지)
기록, 저장, 주간 합계로그인 / Won't
차트 하나, CSV 하나데이터베이스 / Won't
콘솔 인터페이스웹 페이지 / 이번 학기 Won't

제외 목록은 결정의 기록입니다. 평가자는 무엇을 왜 뺐는지 묻습니다. "Won't"는 실패가 아니라 계획입니다.

데이터 설계: 네 가지 질문

  1. 프로그램이 어떤 데이터를 읽고 쓰는가?
  2. 누가 만드는가: 사용자, 나, 기존 공개 자료?
  3. 형식과 자료형은: 파일 이름, 열, 값의 규칙?
  4. 얼마나 많은가: 직접 확인한 작은 표본부터 시작한다.
study.csv: date,course,minutes

통합은 나중에 하더라도 데이터 형식은 지금 정해 둡니다. study_logger_criteria의 첫 단계에서 이 표본 파일이 실제 프로그램의 데이터로 쓰이는 것을 볼 수 있습니다.

수용 기준

Must 기능마다 통과/실패를 가르는 문장이 적어도 하나 있어야 합니다.

기능수용 기준
F1 항목 기록2026-10-24, python, 90을 입력하면 study.csv에 한 행이 추가된다
F1 잘못된 입력-30분을 입력하면 경고가 나오고 파일은 바뀌지 않는다
F3 합계위 표본 주에 대해 python 90, stats 45가 출력된다

이 문장들은 12주차에 거의 그대로 테스트 케이스가 됩니다. study_logger_criteria에서 -30을 넣으면 Not saved 경고가 나오고 파일 줄 수가 그대로인지, 올바른 입력은 한 행을 추가하는지, 그리고 같은 기준을 assert로 적은 test_logic.py가 통과하는지 차례로 확인할 수 있습니다.

요구사항 체크리스트

  • 사용자, 행동, 이유가 있는 사용자 스토리 3–5개
  • 모든 스토리가 번호 붙은 기능에 연결됨
  • 모든 기능에 Must / Should / Could / Won't 표시
  • 개인 MVP의 Must 기능은 최대 3개
  • Must 기능마다 수용 기준이 적어도 하나
  • 필요한 곳에 잘못된 입력에 대한 동작 명시
  • 열과 자료형이 정해진 데이터 파일 이름
  • 범위 제외 결정을 글로 기록

5. 실습: 나의 주제 (20분)

프로젝트 프로필 작성 (3분)

project-profile.md에 이름과 학번, 가제, 주간 진행 점검 시간과 코딩 시간대, 현재 강점과 복습이 필요한 기술을 적습니다. 모든 개발 책임은 스스로 맡습니다.

개인 브레인스토밍 (5분)

  1. 자신의 한 주에서 겪는 문제를 적어도 6개 적는다.
  2. 판단하기 전에 먼저 아이디어를 쏟아낸다.
  3. 각 아이디어를 사용자 한 명과 쓸모 있는 행동 하나로 바꾼다.
  4. 모든 아이디어를 자신의 워크시트에 남긴다.

점수표로 비교하기 (5분)

기준012
사용자 필요분명한 사용자 없음쓸 수도 있음분명하고 반복되는 필요
파이썬 적합성대부분 낯섦새로운 작업이 일부배운 기술을 사용

후보 주제 세 개에 0–2점을 매깁니다. 실현 가능성이 0이면 총점이 높아도 그 주제는 고를 수 없습니다. 동점이면 범위가 더 작고 데이터를 구하기 쉬운 쪽을 고릅니다.

선택한 아이디어의 범위 정하기 (7분)

  • 한 문장 목표: "___을 위해, 내 프로그램은 ___함으로써 ___을 돕는다."
  • 한 줄씩, 최대 3개의 Must 기능
  • 범위 밖 항목 최소 2개
  • 이름 붙인 데이터 출처 또는 직접 만들 수 있는 작은 표본
  • 대비책: 11주차 MVP가 위험해지면 무엇을 뺄 것인가?

정한 주제는 교수자에게 개인적으로 보고합니다.

동료 피드백과 1분 발표

5분 동안 한 명의 동료와 초안을 교환해 세 가지를 확인합니다. 읽는 사람이 목표를 한 문장으로 다시 말할 수 있는가? 각 Must 기능은 검사 가능한가? 한 학생이 11주차까지 그 범위를 끝낼 수 있는가? 장점 두 가지와 우려 한 가지를 전하고, 피드백을 받은 뒤 자신의 제안서를 고칩니다. 검토만 하며 구현을 나누거나 공동 제출물을 만들지 않습니다.

이어서 자원자 두 명이 1분씩 사용자의 문제, Must 기능, 관찰 가능한 시연 결과 하나를 발표합니다. 듣는 사람은 뺄 기능 하나와 그 이유를 제안합니다. 시간이 부족하면 발표 내용을 글 한 단락으로 보냅니다.

흔한 실수

  • 사용자 목표 대신 기술 이름을 쓴다.
  • 개발자 여러 명이 필요한 범위.
  • 데이터 확보를 구현 단계까지 미룬다.
  • 테스트나 문서 작업 시간을 남겨 두지 않는다.
  • 막연한 설명으로 채운 제안서.

7. 정리

확인 질문

  1. 요구사항을 검사 가능하게 만드는 것은? 분명한 통과/실패 결과.
  2. MVP에는 무엇이 들어가나? Must 기능만, 이번 개인 계획에서는 최대 3개.
  3. Won't 항목을 왜 적나? 범위 결정을 기록하고 근거를 대기 위해.
  4. 데이터 설계는 무엇에 답하나? 무엇을, 누가, 어떤 형식으로, 얼마나.
  5. 공동 개발이 허용되나? 아니다. 각 프로젝트는 개인이 구현한다.

제출과 다음 주 준비

프로필, 주제 워크시트, 제안서 v0를 LMS로 제출합니다. 10주차 전에 자신의 제안서를 다시 읽고 범위 결정을 설명할 수 있게 준비합니다. 10주차에는 함수 분해, 모듈, 데이터 설계, 개인 Git 작업 흐름을 다룹니다. git --version이 실행되는 노트북을 가져와야 합니다(이 웹 실습 환경에는 git이 없습니다).
