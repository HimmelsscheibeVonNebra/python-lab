이번 시간에는 프로젝트의 설계 문서 네 가지를 씁니다. 요구사항(Requirement), 기능(Feature), 함수(Function), UML입니다. 네 문서는 서로 다른 프로그램을 설명하는 것이 아니라 같은 프로그램을 네 방향에서 봅니다. 요구사항은 무엇이 성립해야 하는지, 기능은 사용자가 무엇을 보는지, 함수는 코드가 무엇을 약속하는지, UML은 그것들이 어떻게 연결되는지를 답합니다. 오늘의 공통 예제는 9·10주차에 다룬 공부 기록기(study logger)이고, 실습 페이지에서는 계약만 있는 뼈대 study_logger_skeleton과 F1이 구현된 study_logger_f1을 실행하며 문서의 검사(check)를 직접 해 봅니다.

수업은 120분이며 중간에 10분 휴식이 있습니다. 전반에 문서 세 개(요구사항·기능·함수), 후반에 UML과 추적성, 그리고 46분 동안 자기 프로젝트의 네 문서를 쓰는 실습을 합니다.

프로젝트 안내와 문서의 범위

프로젝트는 Python 3와 표준 라이브러리만 사용합니다. 데이터는 파일에 보관하고 결과는 화면에 보고합니다. 모든 프로젝트가 공통으로 확인받는 점은 세 가지입니다.

  • 잘못된 입력을 거절하는가
  • 파일이 없을 때 견디는가
  • 실패한 뒤에도 파일이 바뀌지 않고 그대로인가

설계 문서는 문제, 기능 범위, 모듈 구조, 데이터 형식을 다룹니다. 오늘 소개하는 네 문서는 길잡이이며, 실제 제출 항목과 배점은 강의계획서를 따릅니다.

네 문서의 역할

요구사항과 구현의 연결

요구사항은 만족해야 할 조건이고, 기능은 그 조건을 만족시키기 위해 사용자가 하는 일입니다. 함수는 코드의 약속이고, 검사(check)는 그 약속이 지켜지는지를 판정합니다. UML은 기능과 함수 아래에서 둘을 잇는 구조와 흐름을 보여 줍니다.

규칙: 모든 문서에서 같은 ID를 씁니다. 그래야 요구사항 하나를 그 코드와 검사까지 따라갈 수 있습니다.

공통 예제: 공부 기록기

기본 기능은 세 가지입니다. 한 건 기록하기, 파일 다시 읽기, 과목별 주간 합계 보여 주기. 결과 보고는 과목마다 한 줄씩 큰 값부터 출력하거나, 저장하지 못했으면 이유와 함께 "Not saved"를 출력합니다. 지켜야 할 의무는 잘못된 입력 거절, 실패 시 파일 보존, 파일이 없어도 견디기입니다.

$ python3 main.py
Date (YYYY-MM-DD): 2026-11-10
Course: python
Minutes: 90
Saved.
python   180 min
stats     45 min

분(minutes)은 학생이 직접 입력하는 값입니다. 시계로 시간을 재는 것은 확장 기능입니다.

DOC 1 · 요구사항: 명세

요구사항 문서는 무엇이 성립해야 하는지, 누구를 위해, 어디까지인지를 적습니다. 각 줄은 합격 또는 불합격으로 판정할 수 있어야 합니다.

  • 목적과 범위: 누가 어떤 문제를 겪는지, 프로그램이 무엇을 해결하고 어디서 멈추는지.
  • 요구사항 항목: ID, 문장, 우선순위(Must, Should, Could), 검사.
  • 기능 요구사항: 한 건 기록, 입력 규칙 적용, 합계 보고, 데이터 보관.
  • 제약: 표준 라이브러리만 사용, 입력 검사, 실패 시 파일 불변.

한 줄에는 조건 하나만 씁니다. 검사는 같은 반 친구가 키보드 앞에서 할 수 있는 것이어야 합니다.

요구사항 예

ID문장우선순위검사
REQ-01날짜, 과목, 양수 분으로 한 건을 저장한다Must2026-11-10, python, 90 입력 → study.csv에 새 행 하나
REQ-02양의 정수가 아닌 분은 거절한다Must-30 → Not saved, 파일 불변
REQ-03과목별 주간 합계를 큰 값부터 보여 준다Mustpython 90 + 90, stats 45 → python 180이 먼저 출력
REQ-04실행과 실행 사이에 기록을 유지한다Must두 번 실행하면 두 번째 실행이 첫 번째 기록을 센다

모든 요구사항에는 관찰할 수 있는 검사가 붙습니다. 검사가 없으면 요구사항이 아닙니다. 문장은 무엇을 말하고 어떻게는 말하지 않습니다. 함수 이름이나 파일 형식은 쓰지 않습니다. 검사는 친구가 1분 안에 키보드로 해 볼 수 있어야 합니다. Must 요구사항이 MVP이며, Should와 Could는 MVP가 돌아간 뒤로 미룹니다. 이 검사들은 다음 차시의 test_logic.py가 되고, 12주차의 테스트 목록이 됩니다.

실습 페이지 study_logger_f1에서 REQ-01과 REQ-02의 검사를 그대로 해 볼 수 있습니다. 2026-11-10, python, 90을 넣으면 study.csv의 줄 수가 하나 늘고, -30을 넣으면 Not saved와 함께 줄 수가 그대로입니다.

요구사항과 검사 맞추기

요구사항 문장마다 입력 조건과 관찰 가능한 결과를 붙입니다.

  • 입력 조건: 정확히 무엇을 입력하는지, 또는 실행 전에 파일에 무엇이 들어 있는지.
  • 관찰 결과: 무엇이 출력되는지, 그리고 실행 뒤 파일에 무엇이 들어 있는지.

작성자가 옆에서 설명해 줘야 할 수 있는 검사는 아직 검사가 아닙니다.

DOC 2 · 기능: 사용자 관점의 명세

기능 문서는 사용자가 만나는 프로그램을 적습니다. 명령, 질문(프롬프트), 그리고 돌아오는 결과입니다.

FEAT-xx  <name>              basic | extension
purpose  one sentence
usage    command, prompts, allowed values
flow     step 1 ... step n, the normal path
result   what the user sees on success
errors   each failure and its message
serves   REQ-xx, REQ-yy
  • 식별: 기능 ID, 이름, 목적, 기본 기능인지 확장 기능인지.
  • 사용 방법: 명령, 프롬프트, 허용되는 값, 사전 조건.
  • 동작과 결과: 정상 흐름과 사용자가 확인하는 출력.
  • 예외와 연결: 잘못된 입력, 실패, 그리고 이 기능이 충족하는 요구사항 ID.

기능 예: 한 건 기록하기

FEAT-01  Log one entry                     basic
purpose  record one study session
usage    python3 main.py, then three prompts:
         date YYYY-MM-DD, course, minutes > 0
flow     check input -> build record
         -> append one row to data/study.csv
result   "Saved."
errors   bad minutes or empty course:
         "Not saved: <reason>", file unchanged
         data/ missing: report it, write nothing
serves   REQ-01, REQ-02, REQ-04

usage 줄은 시연에서 실제로 입력할 내용입니다. 처음 보는 사람도 따라 할 수 있게 씁니다. 오류는 하나씩, 각각의 메시지와 함께 나열합니다. "오류를 처리한다"는 한 줄은 오류 항목이 아닙니다. serves 줄은 요구사항으로 돌아가는 추적 연결입니다.

정상 경로와 오류 경로

좋은 날과 나쁜 날에 사용자가 무엇을 보는지 모두 정의합니다. 둘 다 기능 명세에 들어갑니다.

  • 정상 경로: 네 단계, 각 단계마다 사용자가 관찰할 수 있는 것이 있습니다.
  • 입력 오류: 이유를 담은 문장이 나오고 파일에는 아무것도 쓰지 않습니다.
  • 파일 오류: 원인을 알리고, 반쯤 쓴 파일을 남기지 않으며, 프로그램은 깔끔하게 끝납니다.

DOC 3 · 함수: 파이썬 함수 설계

함수 하나에 계약 하나입니다. 10주차 설계 문서에 이미 항목이 있습니다.

make_record(date: str, course: str,
            minutes_text: str) -> dict
module   logic.py       called by main()
I/O      none           pure   yes
returns  {"date", "course", "minutes": int}
fails    ValueError: empty course, or
         minutes not a whole number above 0
  • 시그니처: 이름, 자료형이 붙은 매개변수, 반환 자료형.
  • 입력과 결과: 허용되는 값과 단위, 성공하면 무엇을 반환하는지, 실패는 어떻게 드러나는지.
  • 실행 위치: 어느 모듈에 있고 누가 호출하는지, 키보드나 파일에 접근하는지 아니면 둘 다 하지 않는지.
  • 실패와 자원: 예외를 던지는지 None을 반환하는지, 파일은 누가 열고 닫는지.

함수 예: make_record()

계약은 docstring에, 본문은 그 아래에 씁니다. 그리고 약속이 지켜지는 것을 보여 주는 호출 하나를 붙입니다.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))
python 90

입력은 input()에서 온 문자열 세 개입니다. 과목의 공백 제거와 소문자 변환은 여기에서만 합니다. 이 함수는 무엇이든 쓰기 전에 main()이 호출합니다. 반환값은 dict 하나이고 minutes는 int입니다. 실패하면 이유를 담은 ValueError를 던지고, main은 Not saved를 출력하고 아무것도 쓰지 않습니다. study_logger_f1의 logic.py에 실제 구현이 있으며(분 검사는 parse_minutes()로 분리), 실습 페이지에서 같은 호출을 실행할 수 있습니다.

함수로 나누기

여섯 함수, 여섯 개의 단일 책임입니다. 10주차의 동사 테스트로 이름을 붙입니다.

함수계약
parse_minutes()분 문자열 → 양의 int, 아니면 ValueError
make_record()날짜, 과목, 분 → 기록 dict 하나
append_record()기록 하나 → data/study.csv에 한 행
load_records()파일 → 기록 목록, 파일이 없으면 []
weekly_totals()기록 목록 → {과목: 분}
format_totals()합계 → 줄 목록, 큰 값부터

규칙 함수 둘, 파일 함수 둘, 보고 함수 하나, 그리고 이들을 호출하는 main()입니다. 이름은 모두 동사+명사이고, 위 표의 한 줄이 계약 표의 한 행입니다. 함수를 설명하는 데 "그리고"가 필요하다면, 계약을 쓰기 전에 나눕니다.

이 표가 코드가 된 모습이 study_logger_skeleton입니다. 모든 함수가 이름과 docstring을 갖추었지만 본문은 raise NotImplementedError나 TODO입니다. 실행하면 동작은 하지만(Loaded 0 records) 요구사항은 아직 만족하지 못합니다.

함수와 모듈: 누가 무엇을 하는가

main()이 사용자에게 묻고 나면, 각 모듈은 한 종류의 질문에만 답합니다. 그중 어느 모듈도 사용자에게 무언가를 묻지 않습니다.

  • main.py는 묻고, 호출하고, 출력합니다. 규칙은 갖지 않습니다.
  • logic.py는 규칙을 갖고, 키보드나 디스크를 절대 건드리지 않습니다.
  • storage.py는 data/study.csv를 여는 유일한 모듈입니다.
  • report.py는 결과를 줄로 바꿉니다.

DOC 4 · UML: 목적에 따라 다이어그램 고르기

모든 다이어그램이 필요하지는 않습니다. 읽는 사람의 질문에 답하는 다이어그램 하나를 고릅니다.

읽는 사람의 질문다이어그램
누가 무엇을 위해 쓰는가?유스케이스
어느 파일이 어느 파일을 import하는가?모듈(컴포넌트) 다이어그램
호출은 어떤 순서로 일어나는가?시퀀스 다이어그램
기록 하나에 무슨 일이 일어나는가?상태(또는 활동) 다이어그램

모듈 다이어그램의 화살표는 한 방향만 가리킵니다. 활동 다이어그램은 오류 분기를 포함한 단계를 보여 줍니다.

유스케이스 예

사용자와, 시스템이 제공하는 목표를 그립니다. 함수가 아니라 목표입니다. 행위자(actor)는 학생 한 명이고, 시스템 경계는 공부 기록기입니다. 목표는 세 가지입니다. 한 건 기록하기, 주간 합계 보기, 예전 기록 다시 찾기. 함수 이름은 여기에 나오지 않습니다. 호출 순서는 시퀀스 다이어그램의 몫입니다.

시퀀스 예: 한 번의 실행

정상 경로의 한 번 실행을, 시간이 위에서 아래로 흐르게 그립니다. 모든 화살표는 계약 표에 있는 호출입니다. main()은 logic을 먼저 호출하므로, 기록이 유효해지기 전에는 아무것도 쓰이지 않습니다. 돌아오는 화살표마다 데이터 모양 하나를 나릅니다. 기록, 기록 목록, 합계 dict, 줄 목록입니다. 실패 경로(ValueError)는 별도의 분기로 그리거나, 더 짧은 두 번째 다이어그램으로 그립니다.

상태 예: 기록 하나

상태 넷과 막다른 길 하나입니다. 각 전이는 표에 있는 함수입니다. 입력됨(typed) → make_record()가 검사함(checked) → append_record()가 저장함(saved) → weekly_totals()가 셈(counted). 빈 과목이나 잘못된 분이면 거절됨(rejected)으로 끝나고 "Not saved"가 나오며 아무것도 쓰이지 않습니다. 검사를 통과한 뒤에 파일 오류가 나도 보고하고, 반쯤 쓴 파일은 남기지 않습니다.

문서 간 추적성

요구사항 ID를 기능, 함수, 다이어그램, 테스트에 모두 적으면 아무것도 잃어버리지 않습니다. 예를 들어 REQ-02는 무엇이 성립해야 하는지(양수가 아닌 분은 거절)를 말합니다. FEAT-01은 그것을 사용자에게 보여 주고, parse_minutes()가 강제하고, 상태 다이어그램이 그리고, TEST-02가 증명합니다. 채점자나 14주차의 내가 이 사슬을 어느 방향으로든 따라갈 수 있습니다.

문서 검토와 시연 준비

문서를 끝냈다고 말하기 전에 다섯 가지를 묻습니다.

  1. 범위: 기본 기능과 확장 기능이 나뉘어 있고, MVP의 경계선이 보이는가?
  2. 완료: 각 요구사항을 그 검사로 합격/불합격 판정할 수 있는가?
  3. 일관성: 기능 명세, 함수 계약, UML 흐름이 서로 맞는가?
  4. 데이터 검사: 잘못된 입력, 파일 없음, 헤더 행, "실패 시 파일 불변"을 다루었는가?

작성한 네 문서는 오늘 제출합니다. REQ와 FEAT ID는 그대로 유지합니다. 이 ID들은 커밋 메시지, 테스트 이름, README에 들어갑니다.

다음 차시는 설계에서 실행되는 코드로 넘어갑니다. F1이 기능 브랜치에서 처음부터 끝까지 동작하게 만듭니다. 저장소가 클론되어 있고 git status가 깨끗하며 python3 main.py가 실행되는 노트북을 가져옵니다. 이 웹 실습에는 git이 없으므로, 브랜치·커밋 작업은 실제 PC에서 하고 여기서는 코드 실행과 검사만 확인합니다.

규칙: Must 범위는 동결합니다. 새 아이디어는 새 Must 요구사항이 아니라 Should나 Could 줄이 됩니다.

참고: GitHub 홈페이지 만들기 안내

11주차에는 별도 자료로 Intel Mac용과 Windows용 "Your GitHub Homepage" 안내가 함께 배포되었습니다. 실제 PC에서 따라 하는 복사·붙여넣기 실습으로, 터미널(Mac은 Terminal, Windows는 PowerShell)에서 Git과 GitHub CLI(gh)를 설치하고(Mac은 Homebrew, Windows는 WinGet), gh auth login으로 로그인한 뒤 사용자이름.github.io 저장소를 만들거나 클론합니다. Antigravity IDE의 에이전트에게 index.html과 style.css로 된 학생 홈페이지(About Me, My Python Project, Contact)를 만들게 하고, 로컬에서 미리 본 뒤 git add, git commit, git push하고 GitHub Pages를 main 브랜치의 루트(/)로 켭니다. 설치가 막히는 컴퓨터를 위해 브라우저에서 저장소를 만들고 index.html과 빈 .nojekyll을 직접 추가한 다음 Settings → Pages에서 배포하는 경로도 안내되어 있습니다. 이 과정은 네트워크와 git이 필요하므로 이 웹 실습의 가상 머신에서는 할 수 없고, 실제 PC에서 진행합니다.
