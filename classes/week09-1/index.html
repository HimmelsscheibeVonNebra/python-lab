1. State and object identity

Week 7 recap: class, object and instance

In a = BankAccount("Minsu", 1000) and b = BankAccount("Jisu", 500), BankAccount is the class that defines how an account behaves, and a and b refer to two separate account objects. Both objects are instances of BankAccount. An object is already an instance the moment it is created, so there is no extra step that turns an object into an instance.

class SimpleAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

account = SimpleAccount("Minsu", 1000)

__init__ initializes the newly created instance. self receives that instance, and owner and balance receive the other arguments. This minimal example has no validation; the main model we look at later adds it.

Attributes store state, and methods describe operations on the object. After account.deposit(200), account.balance becomes 1200.

Class variables and instance variables

class LabelledAccount:
    bank_name = "Python Bank"
    def __init__(self, owner):
        self.owner = owner

a = LabelledAccount("Minsu")
b = LabelledAccount("Jisu")
LabelledAccount.bank_name = "Campus Bank"
print(a.bank_name, b.bank_name)   # Campus Bank Campus Bank

bank_name belongs to the class, while each instance has its own owner. If you change the class's value, every instance sees the new value. But if you assign through an instance, as in a.bank_name = ..., the class variable does not change; instead a new instance attribute with the same name is created on a only. You can check both cases in turn in week7_review.

Calling a method and self

a.deposit(200)
BankAccount.deposit(a, 200)

Both forms pass a as self. To deposit only once, run only one of them. self is a conventional parameter name, not a Python keyword, and the method reads and changes the instance through self. The same deposit method only changes the object passed as self, so even after a.deposit(200), b's balance stays 500.

Assignment creates another reference

a = BankAccount("Minsu", 1000)
alias = a
alias.withdraw(300)
print(a.get_balance())   # 700
print(alias is a)        # True

Assignment only binds another name to the existing object; it does not construct a second BankAccount. Conversely, calling the class twice with the same values creates two separate objects. Even if their attributes look the same, their identity differs, so a is b is False, and withdrawing from a leaves b at 1000.

Predict: after c = a and accounts = [a, b], what are c.get_balance() and b.get_balance() once you run accounts[0].withdraw(200)? What changes if you then replace accounts[0] with b? Running identity gives 800 and 500, and even after the list slot is replaced, c is still 800. The list slot now points to a different object; the object itself did not change.

2. Valid state and method contracts

The balance invariant

An invariant is a rule that must hold right after construction and after every public operation. The account rules in this session are:

  • The balance is a nonnegative integer in the smallest currency unit.
  • Deposits and withdrawals accept positive integers only.
  • A rejected operation changes nothing.
  • The internal _balance changes only through the account's methods.

Question to think about: if amount is negative and balance -= amount runs as is, which rule is broken?

Validate during initialization

class BankAccount:
    def __init__(self, owner, balance=0):
        if not isinstance(owner, str) or not owner.strip():
            raise ValueError("owner must be nonblank text")
        if type(balance) is not int or balance < 0:
            raise ValueError("balance must be a nonnegative integer")
        self.owner = owner.strip()
        self._balance = balance

If invalid starting data comes in, an exception is raised before construction finishes, so an account with an invalid balance is never created at all. The caller can catch the exception, as below, and explain the error or ask for another value. If construction ends with an exception, the assignment account = ... does not happen either.

try:
    account = BankAccount("Minsu", -100)
except ValueError as error:
    print(error)

There is a reason the code uses type(balance) is not int rather than isinstance(balance, int). In Python, bool is a subclass of int, so isinstance(True, int) is True. This lesson's integer policy does not accept True as an amount, so the check requires exactly int. In validation you can see that a blank name, a negative balance and a True balance are all rejected, and that deposits of 0, -10, 1.5, "10" and True all return False.

Deposits and withdrawals that preserve the rules

def deposit(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    self._balance += amount
    return True

def withdraw(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    if amount > self._balance:
        return False
    self._balance -= amount
    return True

False means "rejected and nothing changed"; True means "the balance changed by amount". The key is to validate before mutating state. A withdrawal has two kinds of failure, an invalid amount and insufficient funds, and both leave the balance unchanged. Withdrawing exactly the balance is allowed.

Encapsulation and public access

def get_balance(self):
    return self._balance

get_balance shows the result without changing the balance. The leading underscore is an internal-use convention, so Python does not prevent account._balance = -100. Team code should respect the documented public interface. In the second step of state_checks you can see -100 actually getting in.

Small checks for method contracts

a = BankAccount("Minsu", 1000)
assert a.withdraw(1200) is False
assert a.get_balance() == 1000
assert a.withdraw(1000) is True
assert a.get_balance() == 0

Check both the success/failure return value and the resulting state. assert is for checks during development; validate user input with conditionals or exceptions.

3. Objects that collaborate

The key sentence of this section is "AccountBook has accounts; SavingsAccount is an account."

Composition: an AccountBook holds accounts

class AccountBook:
    def __init__(self):
        self._accounts = []

    def add_account(self, account):
        if account in self._accounts:
            return False
        self._accounts.append(account)
        return True

Each AccountBook instance gets its own list, and that list stores references to account objects. Adding the same account again returns False.

The shared mutable class-attribute trap

class BadBook:
    accounts = []

first = BadBook()
second = BadBook()
first.accounts.append("Minsu")
print(second.accounts)   # ["Minsu"]

If a list is a class attribute, every instance shares that one list. Mutable state that each book should have for itself must be created inside __init__ as self._accounts. shared_state compares the two approaches.

Delegate to each account

def total_balance(self):
    total = 0
    for account in self._accounts:
        total += account.get_balance()
    return total

def report(self):
    rows = []
    for account in self._accounts:
        rows.append((account.owner, account.account_type(),
                     account.get_balance()))
    return rows

AccountBook coordinates accounts through their public methods. It does not need to read account._balance directly. The total of an empty book is 0. report returns result data instead of printing, so the caller can decide whether to print it or save it. It must not return the mutable internal account list itself.

Changes remain visible through references

a = BankAccount("Minsu", 1000)
book = AccountBook()
book.add_account(a)
a.withdraw(300)
print(book.total_balance())   # 700

book and a refer to the same account object, and the book recalculates the total from the current account state every time. A separately created empty AccountBook still has total 0. In composition you can also see that the report() result (a list of tuples) taken before the withdrawal still says 1000, and only a fresh call shows 700.

Inheritance: a specialized account

class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, bonus=100):
        super().__init__(owner, balance)
        if type(bonus) is not int or bonus <= 0:
            raise ValueError("bonus must be a positive integer")
        self.bonus = bonus

    def add_bonus(self):
        return self.deposit(self.bonus)

The subclass reuses the base account's validation rules through super().__init__ and adds one operation (add_bonus). add_bonus also calls the inherited deposit, so it keeps the same rules.

Overriding one public operation

class BankAccount:
    def account_type(self):
        return "Standard"

class SavingsAccount(BankAccount):
    def account_type(self):
        return "Savings"

A shared method name provides behavior that fits each type. SavingsAccount still supports all of get_balance, deposit and withdraw, so one piece of calling code can use the same operations on different accounts.

accounts = [BankAccount("Minsu", 700),
            SavingsAccount("Jisu", 600, 100)]
for account in accounts:
    print(account.owner, account.account_type(), account.get_balance())
# Minsu Standard 700
# Jisu Savings 600

In inheritance, check that receiving the bonus twice gives 700, and look at the output of this loop.

Inheritance and composition

RelationshipExampleResponsibility
Is an account (is-a)SavingsAccount inherits BankAccountPreserve the account contract and extend behavior
Has accounts (has-a)AccountBook stores account referencesCoordinate a collection of accounts

AccountBook should not inherit BankAccount just to reuse get_balance, because a book is not an account. Also, when no object state is needed, a dictionary and functions may be enough.

Checkpoint

a = BankAccount("Minsu", 1000)
b = SavingsAccount("Jisu", 500, 100)
book = AccountBook()
book.add_account(a)
book.add_account(b)
a.withdraw(300)
b.add_bonus()
print(book.total_balance())

The total is 700 + 600 = 1300. If you then call a.withdraw(900), it is rejected for insufficient funds and the total stays the same. full_demo prints this whole process.

1. 상태와 객체의 정체성

7주차 복습: 클래스, 객체, 인스턴스

a = BankAccount("Minsu", 1000), b = BankAccount("Jisu", 500)에서 BankAccount는 계좌가 어떻게 동작하는지 정의하는 클래스이고, a와 b는 서로 다른 두 계좌 객체를 가리킵니다. 두 객체는 모두 BankAccount의 인스턴스입니다. 객체는 만들어진 순간 이미 인스턴스이므로, 객체를 인스턴스로 바꾸는 별도의 단계는 없습니다.

        self.balance = balance

BankAccount.deposit(a, 200)

두 형태는 모두 a를 self로 넘깁니다. 입금을 한 번만 하려면 둘 중 하나만 실행해야 합니다. self는 관례적인 매개변수 이름이지 파이썬 키워드가 아니며, 메서드는 self를 통해 그 인스턴스를 읽고 바꿉니다. 같은 deposit 메서드라도 self로 넘어온 객체만 바꾸므로, a.deposit(200) 후에도 b의 잔액은 500 그대로입니다.

대입은 참조를 하나 더 만든다

a = BankAccount("Minsu", 1000)
alias = a
alias.withdraw(300)
print(a.get_balance())   # 700
print(alias is a)        # True

대입은 이미 있는 객체에 이름을 하나 더 붙일 뿐, 두 번째 BankAccount를 만들지 않습니다. 반대로 같은 값으로 클래스를 두 번 호출하면 별개의 객체 두 개가 생깁니다. 속성 값이 같아 보여도 정체성(identity)은 다르므로 a is b는 False이고, a에서 출금해도 b는 1000 그대로입니다.

예측 문제: c = a, accounts = [a, b]로 만든 뒤 accounts[0].withdraw(200)을 하면 c.get_balance()와 b.get_balance()는 무엇일까요? 그 뒤 accounts[0]을 b로 바꾸면 무엇이 달라질까요? identity를 실행하면 800, 500이 나오고, 리스트 칸을 바꾼 뒤에도 c는 여전히 800입니다. 리스트의 칸이 다른 객체를 가리키게 되었을 뿐 객체 자체가 바뀐 것은 아니기 때문입니다.

2. 올바른 상태와 메서드 계약

잔액 불변식

불변식(invariant)은 생성 직후와 모든 공개 동작 뒤에 항상 성립해야 하는 규칙입니다. 이 수업의 계좌 규칙은 다음과 같습니다.

  • 잔액은 가장 작은 화폐 단위의 0 이상 정수다.
  • 입금과 출금은 양의 정수만 받는다.
  • 거부된 동작은 아무것도 바꾸지 않는다.
  • 내부의 _balance는 계좌의 메서드를 통해서만 바뀐다.

생각해 볼 질문: amount가 음수일 때 balance -= amount를 그대로 실행하면 어떤 규칙이 깨질까요?

생성할 때 검증하기

class BankAccount:
    def __init__(self, owner, balance=0):
        if not isinstance(owner, str) or not owner.strip():
            raise ValueError("owner must be nonblank text")
        if type(balance) is not int or balance < 0:
            raise ValueError("balance must be a nonnegative integer")
        self.owner = owner.strip()
        self._balance = balance

잘못된 초기값이 들어오면 생성이 끝나기 전에 예외가 발생합니다. 그래서 잘못된 잔액을 가진 계좌는 아예 만들어지지 않습니다. 호출하는 쪽에서는 다음처럼 예외를 잡아 설명하거나 다른 값을 다시 요청할 수 있습니다. 생성이 예외로 끝나면 account = ... 대입도 일어나지 않습니다.

try:
    account = BankAccount("Minsu", -100)
except ValueError as error:
    print(error)

여기서 isinstance(balance, int)가 아니라 type(balance) is not int를 쓴 이유가 있습니다. 파이썬의 bool은 int의 하위 클래스라서 isinstance(True, int)가 True입니다. 이 수업의 정수 정책에서는 True를 금액으로 받지 않으므로 정확히 int인지 검사합니다. validation에서 공백 이름, 음수 잔액, True 잔액이 모두 거부되고, 0, -10, 1.5, "10", True 입금이 모두 False인 것을 확인합니다.

규칙을 지키는 입금과 출금

def deposit(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    self._balance += amount
    return True

def withdraw(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    if amount > self._balance:
        return False
    self._balance -= amount
    return True

False는 "거부되었고 아무것도 바뀌지 않았다", True는 "잔액이 amount만큼 바뀌었다"는 뜻입니다. 핵심은 상태를 바꾸기 전에 먼저 검증하는 것입니다. 출금에는 잘못된 금액과 잔액 부족이라는 두 종류의 실패가 있으며, 둘 다 잔액을 그대로 둡니다. 잔액과 정확히 같은 금액을 출금하는 것은 허용됩니다.

상태 추적

동작 (시작 1000)반환값이후 잔액
deposit(200)True1200
withdraw(500)True700
withdraw(900)False700
withdraw(-50)False700
withdraw(700)True0

반환값과 새 상태를 항상 함께 읽어야 합니다. state_checks가 이 표를 그대로 출력합니다.

캡슐화와 공개 접근

def get_balance(self):
    return self._balance

get_balance는 잔액을 바꾸지 않고 결과만 보여 줍니다. 앞의 밑줄은 내부용이라는 관례이므로, 파이썬은 account._balance = -100을 막지 않습니다. 팀 코드에서는 문서로 정한 공개 인터페이스를 존중해야 합니다. state_checks의 두 번째 단계에서 실제로 -100이 들어가는 것을 볼 수 있습니다.

메서드 계약을 확인하는 작은 검사

a = BankAccount("Minsu", 1000)
assert a.withdraw(1200) is False
assert a.get_balance() == 1000
assert a.withdraw(1000) is True
assert a.get_balance() == 0

성공/실패 반환값과 그 결과 상태를 모두 검사합니다. assert는 개발 중 확인용이고, 사용자 입력 검증은 조건문이나 예외로 해야 합니다.

3. 함께 일하는 객체

이 절의 핵심 문장은 "AccountBook은 계좌들을 가지고 있다(has), SavingsAccount는 계좌이다(is)"입니다.

합성: AccountBook이 계좌를 담는다

class AccountBook:
    def __init__(self):
        self._accounts = []

    def add_account(self, account):
        if account in self._accounts:
            return False
        self._accounts.append(account)
        return True

AccountBook 인스턴스마다 자기 리스트가 따로 생기고, 그 리스트에는 계좌 객체에 대한 참조가 저장됩니다. 같은 계좌를 다시 추가하면 False를 돌려줍니다.

변경 가능한 클래스 속성의 함정

class BadBook:
    accounts = []

first = BadBook()
second = BadBook()
first.accounts.append("Minsu")
print(second.accounts)   # ["Minsu"]

리스트를 클래스 속성으로 두면 모든 인스턴스가 리스트 하나를 함께 씁니다. 장부마다 따로 가져야 하는 변경 가능한 상태는 __init__ 안에서 self._accounts로 만들어야 합니다. shared_state에서 두 방식을 비교합니다.

각 계좌에 일을 맡기기

def total_balance(self):
    total = 0
    for account in self._accounts:
        total += account.get_balance()
    return total

def report(self):
    rows = []
    for account in self._accounts:
        rows.append((account.owner, account.account_type(),
                     account.get_balance()))
    return rows

AccountBook은 계좌의 공개 메서드를 통해 계좌들을 조정합니다. account._balance를 직접 읽을 필요가 없습니다. 빈 장부의 합계는 0입니다. report는 출력하지 않고 결과 데이터를 돌려주므로, 호출한 쪽이 출력할지 저장할지 정할 수 있습니다. 이때 내부의 변경 가능한 계좌 리스트를 그대로 돌려주면 안 됩니다.

참조를 통해 변화가 보인다

a = BankAccount("Minsu", 1000)
book = AccountBook()
book.add_account(a)
a.withdraw(300)
print(book.total_balance())   # 700

book과 a는 같은 계좌 객체를 가리키고, 장부는 합계를 현재 계좌 상태로부터 매번 다시 계산합니다. 따로 만든 빈 AccountBook의 합계는 여전히 0입니다. composition에서는 출금 전에 받아 둔 report() 결과(튜플 목록)는 1000 그대로이고, 다시 호출한 결과만 700으로 바뀌는 것도 확인할 수 있습니다.

상속: 특화된 계좌

class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, bonus=100):
        super().__init__(owner, balance)
        if type(bonus) is not int or bonus <= 0:
            raise ValueError("bonus must be a positive integer")
        self.bonus = bonus

    def add_bonus(self):
        return self.deposit(self.bonus)

하위 클래스는 super().__init__으로 기반 계좌의 검증 규칙을 재사용하고, 동작 하나(add_bonus)를 추가합니다. add_bonus도 물려받은 deposit을 호출하므로 같은 규칙을 지킵니다.

공개 동작 하나를 재정의하기

class BankAccount:
    def account_type(self):
        return "Standard"

class SavingsAccount(BankAccount):
    def account_type(self):
        return "Savings"

같은 메서드 이름이 종류에 맞는 동작을 제공합니다. SavingsAccount는 여전히 get_balance, deposit, withdraw를 모두 지원합니다. 그래서 하나의 호출 코드가 서로 다른 계좌에 같은 동작을 쓸 수 있습니다.

accounts = [BankAccount("Minsu", 700),
            SavingsAccount("Jisu", 600, 100)]
for account in accounts:
    print(account.owner, account.account_type(), account.get_balance())
# Minsu Standard 700
# Jisu Savings 600

inheritance에서 보너스를 두 번 받아 700이 되는 것과 이 반복문의 출력을 확인합니다.

상속과 합성 비교

관계예책임
계좌이다 (is-a)SavingsAccount가 BankAccount를 상속계좌의 계약을 지키며 동작을 확장
계좌를 가진다 (has-a)AccountBook이 계좌 참조를 저장계좌 모음을 조정

get_balance를 재사용하겠다고 AccountBook이 BankAccount를 상속해서는 안 됩니다. 장부는 계좌가 아니기 때문입니다. 또한 객체 상태가 필요 없다면 딕셔너리와 함수만으로도 충분할 수 있습니다.

체크포인트

a = BankAccount("Minsu", 1000)
b = SavingsAccount("Jisu", 500, 100)
book = AccountBook()
book.add_account(a)
book.add_account(b)
a.withdraw(300)
b.add_bonus()
print(book.total_balance())

합계는 700 + 600 = 1300입니다. 이어서 a.withdraw(900)을 호출하면 잔액 부족으로 거부되어 합계는 그대로입니다. full_demo가 이 과정 전체를 출력합니다.
