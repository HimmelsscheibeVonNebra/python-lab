From this session through Week 16, you work on a solo term project in which each student plans and develops one program independently. Today covers the project rules and grading, the criteria for choosing a topic, how to turn vague wishes into testable requirements, and your personal work plan. At the end of the session you submit three documents: a profile, a topic worksheet and proposal v0.

This session is not about writing code, so there is no separate example to run. Instead, the Week 10 example that actually implements the "study-time logger" the slides keep using as an example is linked at study_logger_criteria. You can see for yourself how the data format and acceptance criteria written in a proposal are judged pass/fail from the program's results.

Individual ownership and the definition of done

One student submits one project. You are responsible for all of the planning, implementation, data, tests, documentation and demo, and you record your progress in your own repository. Advice and peer feedback can refine your decisions, but the implementation is yours. A shared implementation or divided development work is not a solo project. You must be able to explain every function and design decision you submit.

The project is done when it has:

  1. A program that runs in a fresh environment by following the repository's instructions
  2. A README explaining its purpose, setup, usage and limitations
  3. A reliable individual live demo in Week 16
  4. Clear explanations of your implementation and design choices

Features are frozen in Week 14 and rehearsed in Week 15.

2. Choosing a topic

Three tests for a solo topic

  1. Care test: you or someone you know actually needs the program.
  2. Python test: its core can be solved with the logic and data skills you have learned so far.
  3. MVP deadline test: you can run a minimal version on your own by Week 11.

If one test fails, narrow the scope; if two fail, choose another topic. Your available time must include time for testing and documentation.

Small is beautiful: the MVP ladder

An MVP (minimum viable product) is the smallest program that does one useful thing end to end.

LevelIdea
Too bigA fitness app with login, feed and recommendations
Still bigA workout tracker with charts and goals
MVPAppend sets to workout.csv and print a weekly summary chart
Too smallA script that prints one number (no user, no decision)

Build the MVP first, then climb. Extras are Week 12–13 work.

Topic catalog

Data projects (pandas, matplotlib, Weeks 5–7): a study-time logger that records study time per course and draws a weekly bar chart; a weather comparison that plots min/mean/max temperature lines from two cities' CSVs; a personal finance tracker that shows a category pie chart and monthly trend from expenses.csv; campus data such as cafeteria menus, library hours or exam-period demand. The data must already exist or be collectable by hand within a few days.

Tools and games (functions, classes, files, Weeks 3–7): vocabulary flashcards with a CSV word list, quiz mode and wrong-answer review; a Wordle-style word game with one class per round; an inventory manager that adds, removes and searches items and saves them to a file; a password generator and strength checker; a quiz builder where teachers write questions, students play and scores are saved. A game needs a clear "one round" you can demo.

Everyday helpers (dictionaries, classes, exceptions): a timetable checker that warns about course, room and time conflicts; an expense splitter that calculates trip costs and each person's settlement amount; a recipe planner that makes a weekly menu and a CSV shopping list; a personal task planner with deadlines, priorities and an overdue list. Even with one developer, a program can have several users.

3. Requirements analysis

A requirement is testable

Not a requirementRequirement
"The report is fast""The summary prints in under 1 second for 10,000 rows"
"Easy to use""A new user can log an entry with one command and no manual"
"Handles bad input""Entering a negative amount shows a warning and nothing is saved"

Functional requirements say what the program does; non-functional requirements say how well it does it (speed, safety, readability). If you cannot imagine a test for it, it is not a requirement yet.

User stories

The format is "As a ___, I want ___, so that ___."

StoryQuality
As a student, I want to log study time by course so that I can review my week.Clear user, action and reason
As a user, I want features so that I can do things.Too vague
I want to use classes.A technical choice, not a user need

Write 3–5 stories and connect each to numbered features.

From stories to features

IDFeatureCourse skills
F1Enter date, course and positive minutesInput, conditions, exceptions
F2Save and reload study.csvFiles, CSV, type conversion
F3Show weekly totals by courseDictionaries and loops
F4Draw a weekly bar chartmatplotlib

Rejecting invalid minutes is part of F1's acceptance criteria. Predict which features are essential for the first working version.

MoSCoW prioritization

PriorityMeaningStudy logger
MustRequired for the core demoF1 valid input, F2 persistence, F3 totals
ShouldImportant but not essentialF4 chart
CouldAdd only if time remainsCourse colors
Won'tExplicitly outside this projectLogin, mobile app, database

Build the MVP from the Must features and have it running by Week 11. In a solo project, have at most 3 Must features, each with a testable result. Input validation and error handling belong inside the relevant feature.

The scope border

In v1Out of v1 (and where it went)
Log, save, weekly totalsLogin / Won't
One chart, one CSVDatabase / Won't
Console interfaceWeb page / Won't this term

The Out list is a decision record. Reviewers will ask what you cut and why. "Won't" is a plan, not a failure.

Data design: four questions

  1. What data does the program read and write?
  2. Who creates it: the user, you, or an existing public source?
  3. What format and types: file names, columns and value rules?
  4. How much: start with a small sample you have checked yourself.
study.csv: date,course,minutes
2026-10-24,python,90
2026-10-25,stats,45

Specify the data format now, even if integration happens later. In the first step of study_logger_criteria you can see this sample file used as the data of a real program.

Acceptance criteria

Each Must feature needs at least one statement that decides pass or fail.

FeatureAcceptance criterion
F1 log entryEntering 2026-10-24, python, 90 appends one row to study.csv
F1 bad inputEntering -30 minutes prints a warning and the file is unchanged
F3 totalsFor the sample week above, python 90 and stats 45 are printed

These lines become Week 12 test cases almost word for word. In study_logger_criteria you can check in turn that entering -30 shows the Not saved warning and leaves the file's line count unchanged, that valid input adds one row, and that test_logic.py, which writes the same criteria as asserts, passes.

Requirements checklist

  • 3–5 user stories naming a user, action and reason
  • Every story connected to numbered features
  • Every feature labeled Must / Should / Could / Won't
  • At most 3 Must features for the solo MVP
  • At least one acceptance criterion per Must feature
  • Invalid-input behavior specified where relevant
  • Named data files with columns and types
  • Out-of-scope decisions written down

5. Lab: your topic (20 minutes)

Set up your project profile (3 minutes)

In project-profile.md, write your name and student ID, a working title, your weekly progress-review time and coding blocks, and your current strengths and the skill you need to review. You will take on all development responsibilities yourself.

Individual brainstorming (5 minutes)

  1. Write at least 6 problems from your own week.
  2. Generate ideas before judging them.
  3. Turn each idea into one user and one useful action.
  4. Keep all ideas in your own worksheet.

Compare ideas with a scorecard (5 minutes)

Criterion012
User needNo clear userPossible useClear recurring need
Python fitMostly unfamiliarSome new workUses learned skills
MVP feasibilityCannot finish aloneScope uncertainRuns by Week 11

Score three candidate topics from 0 to 2. If feasibility is 0, you cannot choose that topic, however high its total. For a tie, choose the one with the smaller scope and more accessible data.

Scope your chosen idea (7 minutes)

  • One-sentence goal: "For ___, my program helps ___ by ___."
  • At most 3 Must features, one line each
  • At least 2 out-of-scope items
  • A named data source or a small sample you can create yourself
  • A fallback: what will you cut if the Week 11 MVP is at risk?

Report your chosen topic individually to the instructor.

6. Lab: solo proposal v0 (25 minutes)

Draft the eight parts (18 minutes)

PartsMinutes
1–2. Problem and user3
3–4. Features and scope6
5–6. Data and skills4
7. Milestones and work schedule3
8. Risks2

Attempt every part, and give each unresolved decision a date for follow-up.

Peer feedback and one-minute pitch

For 5 minutes, exchange drafts with one classmate and check three things. Can the reader restate the goal in one sentence? Is each Must feature testable? Can one student finish the scope by Week 11? Give two strengths and one concern, and revise your own proposal after receiving feedback. This is review only: do not split the implementation or create a joint submission.

Next, two volunteers each give a one-minute pitch: the user's problem, the Must features and one observable demo result. Listeners suggest one feature to cut and explain why. If time is short, send your pitch as a written paragraph.

Common mistakes

  • A technology name instead of a user goal.
  • Scope that needs several developers.
  • Data access postponed until implementation.
  • No time reserved for tests or documentation.
  • A proposal filled with vague descriptions.

7. Review

Check questions

  1. What makes a requirement testable? A clear pass/fail result.
  2. What goes into the MVP? Must features only, at most 3 for this solo plan.
  3. Why write Won't items? To record and defend scope decisions.
  4. What does data design answer? What, who, format and amount.
  5. Is joint development allowed? No. Each project is implemented individually.

Submit and prepare for next week

Submit your profile, topic worksheet and proposal v0 via the LMS. Before Week 10, reread your proposal and be ready to explain your scope decisions. 데이터 프로젝트(pandas, matplotlib, 5–7주차): 과목별 공부 시간을 기록하고 주간 막대 차트를 그리는 공부 시간 기록기, 두 도시의 CSV로 최저·평균·최고 기온 선을 그리는 날씨 비교, expenses.csv로 카테고리 원그래프와 월별 추세를 보는 개인 가계부, 학식 메뉴·도서관 이용 시간·시험 기간 수요 같은 캠퍼스 데이터. 데이터는 이미 있거나 며칠 안에 손으로 모을 수 있어야 합니다.

도구와 게임(함수, 클래스, 파일, 3–7주차): CSV 단어장과 퀴즈 모드·오답 복습이 있는 단어 카드, 한 판을 클래스 하나로 만드는 Wordle 스타일 단어 게임, 추가·삭제·검색 후 파일에 저장하는 재고 관리, 비밀번호 생성기와 강도 검사기, 교사가 문제를 내고 학생이 풀며 점수가 저장되는 퀴즈 빌더. 게임이라면 시연할 수 있는 분명한 "한 판"이 있어야 합니다.

일상 도우미(딕셔너리, 클래스, 예외): 과목·강의실·시간 충돌을 경고하는 시간표 검사기, 여행 비용과 각자의 정산 금액을 계산하는 비용 분할기, 주간 메뉴와 CSV 장보기 목록을 만드는 레시피 플래너, 마감일·우선순위·지연 목록이 있는 개인 할 일 관리. 개발자는 한 명이어도 프로그램 사용자는 여러 명일 수 있습니다.

3. 요구사항 분석

요구사항은 검사할 수 있어야 한다

요구사항이 아닌 것요구사항

"쓰기 쉽다""처음 쓰는 사용자가 설명서 없이 명령 하나로 항목을 기록할 수 있다"

기능 요구사항은 프로그램이 무엇을 하는지, 비기능 요구사항은 얼마나 잘 하는지(속도, 안전성, 가독성)를 말합니다. 시험 방법을 떠올릴 수 없다면 아직 요구사항이 아닙니다.

사용자 스토리

형식은 "___로서, 나는 ___을 원한다, 그래야 ___할 수 있다(As a ___, I want ___, so that ___)"입니다.

스토리평가

사용자로서, 나는 기능을 원한다. 그래야 무언가를 할 수 있다.너무 막연함
나는 클래스를 쓰고 싶다.기술 선택이지 사용자의 필요가 아님

스토리를 3–5개 쓰고, 각각을 번호 붙은 기능에 연결합니다.

MoSCoW 우선순위

우선순위의미공부 시간 기록기

MVP는 Must 기능으로 만들고 11주차까지 실행되게 합니다. 개인 프로젝트에서는 Must 기능을 최대 3개로 하고, 각각 검사 가능한 결과를 가져야 합니다. 입력 검증과 오류 처리는 해당 기능 안에 포함합니다.

동료 피드백과 1분 발표

5분 동안 한 명의 동료와 초안을 교환해 세 가지를 확인합니다. 읽는 사람이 목표를 한 문장으로 다시 말할 수 있는가? 각 Must 기능은 검사 가능한가? 한 학생이 11주차까지 그 범위를 끝낼 수 있는가? 장점 두 가지와 우려 한 가지를 전하고, 피드백을 받은 뒤 자신의 제안서를 고칩니다. 검토만 하며 구현을 나누거나 공동 제출물을 만들지 않습니다.

이어서 자원자 두 명이 1분씩 사용자의 문제, Must 기능, 관찰 가능한 시연 결과 하나를 발표합니다. 듣는 사람은 뺄 기능 하나와 그 이유를 제안합니다. 시간이 부족하면 발표 내용을 글 한 단락으로 보냅니다.

흔한 실수

  • 사용자 목표 대신 기술 이름을 쓴다.
  • 개발자 여러 명이 필요한 범위.
  • 데이터 확보를 구현 단계까지 미룬다.
  • 테스트나 문서 작업 시간을 남겨 두지 않는다.
  • 막연한 설명으로 채운 제안서.
