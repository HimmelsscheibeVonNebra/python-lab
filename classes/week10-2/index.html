Why Git when you work alone?

Even if nobody else edits your code, Git earns its place.

  • An undo button for the whole project.
  • Proof of process: Git workflow is part of a 20% component.
  • A main branch that always runs, ready for the demo.
  • You can continue your work on any computer.

Trap: a single commit called "final" in Week 15 proves nothing.

Four places your code lives

Every Git command moves changes between these four places.

  1. Working folder: the files you edit in VS Code.
  2. Staging area: the changes you picked for the next commit.
  3. Local repository: every commit, inside the hidden .git folder.
  4. GitHub: a copy of the repository online.

Act 1 · Commit: save points with a message

We review Week 8 in ten minutes (init, status, add, commit, log, diff, push), then cover .gitignore, which keeps junk out, and the habits that earn points.

Once per computer: who are you?

git config --global user.name "Jiwoo Park"
git config --global user.email "jiwoo@example.com"
git config --global init.defaultBranch main
git config user.name

Git signs every commit with a name and an email. Set them once per laptop, using the email of your GitHub account. Always name the first branch of a new project main. The last command prints the name you set (Jiwoo Park) to check the result.

Start the repository

mkdir study-logger
cd study-logger
git init
git status
Initialized empty Git repository in .../study-logger/.git/
On branch main
No commits yet
Untracked files:
  .gitignore
  README.md
  main.py

Run git init once per project, inside the project folder. It creates the hidden .git folder, but nothing is saved yet. git status tells you what Git sees, so run it constantly. Predict: the folder also holds __pycache__, so why is it not in the list? The answer is .gitignore, in the next section.

.gitignore: what never goes in

# Python
__pycache__/
*.pyc
.venv/

# Editors and operating systems
.vscode/
.DS_Store

# Secrets: never commit these
.env
*.key

It is a text file of patterns, and files that match a pattern are invisible to Git. Python rebuilds generated files (__pycache__, .pyc), each computer makes its own virtual environment (.venv), and system junk (.DS_Store, Thumbs.db) is not needed. Never, ever include secrets (.env, keys, passwords). Trap: a password you pushed once is public even if you delete it later. You must change the password.

In starter_repo, running python3 main.py creates a new __pycache__ folder, which you can see with ls -a. The starter-repo's .gitignore uses exactly these patterns to hide that folder from Git.

add, then commit

git add .
git commit -m "Add project skeleton"
git status
[main (root-commit) c4f930b] Add project skeleton
 3 files changed, 5 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 README.md
 create mode 100644 main.py
On branch main
nothing to commit, working tree clean

add picks the changes and commit saves them with a message. git add . stages everything that is not ignored, and git commit -m saves one snapshot with a sentence. After the commit, the working tree is clean.

A commit message is a sentence

The grader reads your log. Make it read like a diary of decisions.

Messages that prove nothingMessages that tell a story
updateAdd load_records stub
asdfReject negative minutes in parse_minutes
final final2Show weekly totals sorted by minutes

Start with a verb in the imperative (Add, Fix, Reject, Rename) and say what changed in about 50 characters. Put one logical change in each commit. Commit when a small step works, and before you try something risky.

See what changed: diff and log

git diff
git commit -am "Print the week in the banner"
git log --oneline
@@ -1 +1,2 @@
 print("Study logger")
+print("Week 10 skeleton")
[main 71b8a6e] Print the week in the banner
 1 file changed, 1 insertion(+)
71b8a6e Print the week in the banner
c4f930b Add project skeleton

Before you commit, look; after you commit, check. git diff shows unstaged changes line by line: + is an added line, - a removed line, and @@ the location. git commit -am stages tracked files and commits them in one move. git log --oneline shows one line per commit, newest first. Trap: -a skips new files. A newly created storage.py still needs git add.

The last step of starter_repo changes one line of report.py and compares before and after with diff -u. Its output format (---, +++, @@, and -/+ lines) is the same as git diff, so it is good reading practice.

Put it on GitHub

git remote add origin \
  https://github.com/jiwoo-park/study-logger.git
git push -u origin main
To https://github.com/jiwoo-park/study-logger.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

On github.com, create a repository with New repository, but leave it empty, with no README or .gitignore. Public or private is fine; if it is private, add the instructor as a collaborator. Connect the remote only once, use push -u the first time, and plain git push after that.

Two push errors you will meet

! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com/...'

remote: Support for password authentication was removed on August 13, 2021.
fatal: Authentication failed

Both are common on the first day, and both have a short fix. Rejected: you ticked "Add a README" on GitHub, so GitHub has a commit your laptop does not. Run git pull --rebase origin main, then push again. Authentication failed: GitHub does not accept account passwords on the command line. Sign in through VS Code (Source Control, Publish) or use gh auth login.

Act 2 · Branch: a safe place to try

main always runs; new work happens next door. Make one branch per feature and merge it when it works. Then we look at what conflicts look like and how to end them.

Why branch when you are alone?

A branch is a second line of commits that main does not see until you merge. main stays demo-ready at every moment. Each Must feature gets its own short-lived branch. A failed experiment is just one deleted branch, not a broken project. The graph shows the grader exactly how each feature was built.

Create a branch and work on it

git switch -c feature/save-records
git add storage.py
git commit -m "Add load_records stub"
ls
Switched to a new branch 'feature/save-records'
[feature/save-records d05376a] Add load_records stub
 1 file changed, 2 insertions(+)
 create mode 100644 storage.py
README.md  __pycache__  main.py  storage.py

switch -c creates the branch and moves you onto it. Commits now land on feature/save-records, not main, and the new file storage.py exists on this branch.

Where did storage.py go?

git switch main
ls
Switched to branch 'main'
README.md  __pycache__  main.py

git switch changes the files in your folder to match the branch. storage.py is safe inside a commit on the feature branch, and main has not seen it yet. That is the point. Predict: what will ls show after git switch feature/save-records?

Merge: bring the work home

git merge feature/save-records
git branch -d feature/save-records
git log --oneline --graph
Updating 71b8a6e..d05376a
Fast-forward
 storage.py | 2 ++
Deleted branch feature/save-records (was d05376a).
* d05376a Add load_records stub
* 71b8a6e Print the week in the banner
* c4f930b Add project skeleton

When the feature works, merge it from main. If main had no new commits, this is a fast-forward: main just moves up. Delete the merged branch; its commits stay in main. log --graph draws the history.

Branch names and habits

git branch
  feature/report-title
* main

A good branch name is a to-do item: feature/save-records, fix/negative-minutes. One feature per branch, merged within days. git branch lists the branches, and * marks the current one. Commit before you switch branches. Make a habit of checking the branch name shown in the bottom-left corner of VS Code before you type.

When two edits collide

git merge feature/report-title
git status --short
cat report.py
CONFLICT (content): Merge conflict in report.py
Automatic merge failed; fix conflicts and then commit the result.
UU report.py
<<<<<<< HEAD
TITLE = "Minutes per course"
=======
TITLE = "Study time this week"
>>>>>>> feature/report-title

The same line was changed differently on two branches: main changed TITLE to "Minutes per course" and feature/report-title changed it to "Study time this week". Git will not guess; it stops and marks the file. UU means unmerged. From <<<<<<< HEAD to ======= is the current branch's (main's) content, and below it, up to >>>>>>>, is the content of the branch being merged in.

Resolve in three moves

git add report.py
git commit -m "Merge report title: keep both ideas"
git log --oneline --graph
*   f84e248 Merge report title: keep both ideas
|\
| * dd6fc23 Rename report title
* | b7d071f Clarify report title
|/
* 7846ed1 Add report title

A conflict is a question, and you answer it by editing the file. First, keep the line you want and delete all three marker lines. Second, git add the file to say "answered". Third, git commit to finish the merge. VS Code shows Accept Current, Accept Incoming and Accept Both buttons above each conflict.

Practice: make a conflict on purpose (7 minutes)

mkdir conflict-practice && cd conflict-practice
git init
echo "Hello" > title.txt
git add title.txt && git commit -m "Add title"
git switch -c feature/greeting
echo "Hello, class" > title.txt
git commit -am "Greet the class"
git switch main
echo "Hi" > title.txt
git commit -am "Shorten the title"
git merge feature/greeting

Do this in a scratch folder, not in your project. Make a repository with title.txt and commit it, change the line on a branch and commit, then change the same line differently on main and commit. Then merge, resolve, add and commit, and check with git log --oneline --graph. (This practice also needs git, so do it on your own PC.)

Act 3 · Pull request: review your own work

A pull request (PR) is a merge with a conversation attached. It lives on GitHub, between your branch and main, and it is where you explain, check and get feedback.

Why a pull request in a solo project?

Even if nobody needs to approve it, a PR is the best record of your work. The description says what changed and why, in your own words. The Files changed tab makes you read your own diff. The instructor can comment on a specific line of your code. Each feature becomes one link that ties together branch, commits, review and merge.

Push the branch, open the PR

git switch -c feature/append-record
git add storage.py
git commit -m "Add append_record with header"
git push -u origin feature/append-record
remote: Create a pull request for
remote: 'feature/append-record' on GitHub:
remote: https://github.com/jiwoo-park/
remote: study-logger/pull/new/feature/append-record
 * [new branch]      feature/append-record

This time we do not merge on the laptop. We push the branch and let GitHub merge. Set base to main and compare to your feature branch. Write the title like a commit message, saying what the feature does, and fill the description with the following four headings.

A PR description that earns points

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: the change, linked to a feature ID.
  • Why: the contract or acceptance criterion from your design document.
  • How I checked: the command you ran and what it printed.
  • Not in this PR: what is left for the next branch.

Two minutes to write, and a whole feature is explained. The contract of the example append_record ("write the header only when the file is newly created") is implemented in Session 1's study_logger storage.py.

The self-review checklist

Read the Files changed tab as if a stranger wrote the code.

  • python3 main.py still runs from a fresh terminal.
  • Every new function matches its contract and docstring.
  • No leftover debug print() or commented-out experiments.
  • No ignored files (__pycache__, .venv, .env) slipped in.
  • Only one feature in this PR.

If you find a problem, fix it on the same branch and push again. The PR updates automatically.

Merge, then sync your laptop

git switch main
git pull
git branch -d feature/append-record
Updating d05376a..e2a91c4
Fast-forward
 storage.py | 9 +++++++++
Deleted branch feature/append-record (was 5a0c7e1).

On GitHub, click Merge pull request, then Delete branch. Your laptop does not know until you pull. On the laptop, go back to main, pull and delete the local branch, then start the next feature branch from the updated main. Trap: skip git pull and your next branch starts from the old main.

The weekly loop

One loop per Must feature: pull, branch, commit a few times, push, pull request, merge, pull. Weeks 11–13 are three or four loops. Small loops finish; giant branches rot. The grader sees this rhythm in your history.

Step 2: the feature branch (12 minutes)

# A stub: final name, full contract, no body yet
def make_record(date, course, minutes_text):
    """Return one record dict.

    Raises ValueError if course is empty
    or minutes is not positive.
    """
    raise NotImplementedError("make_record")

Turn your design document into stubs. Create a branch with git switch -c feature/skeleton, rename the stub functions to the names in your design document, and copy each contract into its docstring. Leave the bodies as TODO. Commit at least twice with real messages, check that python3 main.py still runs, and push the branch. The starter-repo's logic.parse_value is exactly this kind of stub: it has a contract but its body is raise NotImplementedError, and since main.py does not call it yet, the program still runs.

지난 시간에는 프로그램을 그렸습니다. 이번 시간에는 그 프로그램에 집과 역사를 줍니다. 프로젝트 점수의 5분의 1(설계와 Git 작업 흐름 20%)은 커밋이 들려주는 이야기에서 나옵니다. 세 막과 실습으로 진행합니다. 1막 커밋에서는 메시지가 달린 저장 지점을 만들고 GitHub에 사본을 올립니다. 2막 브랜치에서는 main을 깨뜨리지 않고 새 작업을 시도합니다. 3막 풀 리퀘스트에서는 내 작업이 합쳐지기 전에 스스로 검토합니다. 실습에서는 자신의 저장소, 첫 기능 브랜치, 첫 병합된 풀 리퀘스트를 만듭니다.

이 웹 실습 환경에 대해: 이 페이지의 가상 머신에는 git, 네트워크, 브라우저가 없습니다. 따라서 이 차시의 모든 git 명령과 GitHub 작업은 git --version이 동작하는 자신의 PC에서 해야 합니다. 여기서는 실습의 출발점인 starter-repo의 구성(모듈, README, .gitignore)과 실행 결과를 starter_repo에서 확인하고, git diff가 보여 주는 변경 형식을 diff -u로 미리 읽어 봅니다. 슬라이드의 labs/session2/starter-repo/는 이 환경에서 ~/week10/starter/session2/starter-repo/입니다.

혼자 작업하는데 왜 Git인가?

아무도 내 코드를 고치지 않아도 Git은 제 몫을 합니다.

  • 프로젝트 전체에 대한 되돌리기 버튼.
  • 과정의 증거: Git 작업 흐름은 20% 항목의 일부다.
  • 언제나 실행되어 시연에 바로 쓸 수 있는 main 브랜치.
  • 어느 컴퓨터에서든 이어서 작업할 수 있다.

함정: 15주차에 "final"이라는 커밋 하나만 있으면 아무것도 증명하지 못합니다.

코드가 사는 네 장소

모든 Git 명령은 변경을 다음 네 장소 사이에서 옮깁니다.

  1. 작업 폴더: VS Code에서 편집하는 파일들.
  2. 스테이징 영역: 다음 커밋에 넣으려고 골라 둔 변경.
  3. 로컬 저장소: 숨김 폴더 .git 안에 있는 모든 커밋.
  4. GitHub: 온라인에 있는 저장소의 사본.

1막 · 커밋: 메시지가 달린 저장 지점

8주차 내용을 10분 만에 복습하고(init, status, add, commit, log, diff, push), 쓸모없는 파일을 막는 .gitignore와 점수를 얻는 습관을 다룹니다.

컴퓨터마다 한 번: 나는 누구인가?

git config --global user.name "Jiwoo Park"
git config --global user.email "jiwoo@example.com"
git config --global init.defaultBranch main
git config user.name

Git은 모든 커밋에 이름과 이메일을 서명합니다. 노트북마다 한 번 설정하고, 이메일은 GitHub 계정의 것을 씁니다. 새 프로젝트의 첫 브랜치 이름은 항상 main으로 합니다. 마지막 명령은 설정한 이름(Jiwoo Park)을 출력해 결과를 확인합니다.

저장소 시작하기

mkdir study-logger
cd study-logger
git init
git status
Initialized empty Git repository in .../study-logger/.git/
On branch main
No commits yet
Untracked files:
  .gitignore
  README.md
  main.py

프로젝트 폴더 안에서 프로젝트당 한 번 git init을 실행합니다. 숨김 폴더 .git이 만들어지지만 아직 아무것도 저장되지 않았습니다. git status는 Git이 무엇을 보고 있는지 알려 주므로 수시로 실행합니다. 예측 질문: 폴더에는 __pycache__도 있는데 왜 목록에 없을까요? 답은 다음 절의 .gitignore입니다.

.gitignore: 절대 넣지 않는 것

# Python
__pycache__/
*.pyc
.venv/

# Editors and operating systems
.vscode/
.DS_Store

# Secrets: never commit these
.env
*.key

패턴을 적은 텍스트 파일이며, 패턴에 맞는 파일은 Git에게 보이지 않습니다. 생성 파일(__pycache__, .pyc)은 파이썬이 다시 만들고, 가상 환경(.venv)은 컴퓨터마다 따로 만들며, 시스템 찌꺼기(.DS_Store, Thumbs.db)는 필요 없습니다. 비밀 정보(.env, 키, 비밀번호)는 절대로 넣지 않습니다. 함정: 한 번 push한 비밀번호는 나중에 지워도 공개된 것입니다. 비밀번호를 바꿔야 합니다.

starter_repo에서 python3 main.py를 실행하면 __pycache__ 폴더가 새로 생기는 것을 ls -a로 볼 수 있습니다. starter-repo의 .gitignore가 바로 이 패턴들로 그 폴더를 Git에서 숨깁니다.

add 다음에 commit

git add .
git commit -m "Add project skeleton"
git status
[main (root-commit) c4f930b] Add project skeleton
 3 files changed, 5 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 README.md
 create mode 100644 main.py
On branch main
nothing to commit, working tree clean

add는 변경을 고르고, commit은 메시지와 함께 저장합니다. git add .은 무시되지 않은 모든 것을 스테이징하고, git commit -m은 문장 하나와 함께 스냅숏 하나를 저장합니다. 커밋 후에는 작업 트리가 깨끗해집니다.

커밋 메시지는 문장이다

평가자는 로그를 읽습니다. 결정의 일기처럼 읽히게 합니다.

아무것도 증명하지 못하는 메시지이야기를 들려주는 메시지
updateAdd load_records stub
asdfReject negative minutes in parse_minutes
final final2Show weekly totals sorted by minutes

명령형 동사(Add, Fix, Reject, Rename)로 시작하고, 무엇이 바뀌었는지 약 50자로 씁니다. 커밋 하나에는 논리적 변경 하나만 담습니다. 작은 단계가 동작할 때, 그리고 위험한 시도를 하기 전에 커밋합니다.

무엇이 바뀌었나: diff와 log

git diff
git commit -am "Print the week in the banner"
git log --oneline
@@ -1 +1,2 @@
 print("Study logger")
+print("Week 10 skeleton")
[main 71b8a6e] Print the week in the banner
 1 file changed, 1 insertion(+)
71b8a6e Print the week in the banner
c4f930b Add project skeleton

커밋하기 전에 보고, 커밋한 뒤에 확인합니다. git diff는 스테이징하지 않은 변경을 줄 단위로 보여 줍니다. +는 추가된 줄, -는 지워진 줄, @@는 위치입니다. git commit -am은 추적 중인 파일을 스테이징하고 커밋까지 한 번에 합니다. git log --oneline은 커밋마다 한 줄씩, 최신 것부터 보여 줍니다. 함정: -a는 새 파일을 건너뜁니다. 새로 만든 storage.py는 여전히 git add가 필요합니다.

starter_repo의 마지막 단계는 report.py의 한 줄을 바꾸고 diff -u로 변경 전후를 비교합니다. 출력 형식(---, +++, @@, -/+ 줄)이 git diff와 같으므로 읽는 연습이 됩니다.

GitHub에 올리기

git remote add origin \
  https://github.com/jiwoo-park/study-logger.git
git push -u origin main
To https://github.com/jiwoo-park/study-logger.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

github.com에서 New repository로 저장소를 만들되, README나 .gitignore 없이 비워 둡니다. 공개든 비공개든 괜찮으며, 비공개라면 교수자를 collaborator로 추가합니다. 원격 저장소는 한 번만 연결하고, 처음에는 push -u, 그다음부터는 그냥 git push를 씁니다.

처음 만나는 두 가지 push 오류

! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com/...'

remote: Support for password authentication was removed on August 13, 2021.
fatal: Authentication failed

첫날에는 둘 다 흔하고, 고치는 방법도 짧습니다. Rejected: GitHub에서 "Add a README"를 체크해 GitHub에 내 노트북에 없는 커밋이 있는 경우입니다. git pull --rebase origin main을 실행한 뒤 다시 push합니다. Authentication failed: GitHub는 명령줄에서 계정 비밀번호를 받지 않습니다. VS Code로 로그인하거나(Source Control, Publish) gh auth login을 사용합니다.

2막 · 브랜치: 안전하게 시도하는 곳

main은 언제나 실행되고, 새 작업은 옆집에서 합니다. 기능마다 브랜치 하나를 만들어 동작하면 병합합니다. 그다음 충돌이 어떻게 보이고 어떻게 끝내는지 봅니다.

혼자인데 왜 브랜치인가?

브랜치는 병합하기 전까지 main이 보지 못하는 두 번째 커밋 줄기입니다. main은 어느 순간에나 시연할 수 있는 상태를 유지합니다. Must 기능마다 수명이 짧은 브랜치를 하나씩 만듭니다. 실패한 실험은 망가진 프로젝트가 아니라 지운 브랜치 하나일 뿐입니다. 그래프는 각 기능이 어떻게 만들어졌는지 평가자에게 정확히 보여 줍니다.

브랜치를 만들고 작업하기

git switch -c feature/save-records
git add storage.py
git commit -m "Add load_records stub"
ls
Switched to a new branch 'feature/save-records'
[feature/save-records d05376a] Add load_records stub
 1 file changed, 2 insertions(+)
 create mode 100644 storage.py
README.md  __pycache__  main.py  storage.py

switch -c는 브랜치를 만들고 그 브랜치로 옮겨 갑니다. 이제 커밋은 main이 아니라 feature/save-records에 쌓이고, 새 파일 storage.py는 이 브랜치에 있습니다.

storage.py는 어디로 갔나?

git switch main
ls
Switched to branch 'main'
README.md  __pycache__  main.py

git switch는 폴더의 파일을 그 브랜치에 맞게 바꿉니다. storage.py는 기능 브랜치의 커밋 안에 안전하게 있고, main은 아직 그것을 보지 못했습니다. 바로 그것이 핵심입니다. 예측 질문: git switch feature/save-records 후에 ls는 무엇을 보여 줄까요?

병합: 작업을 집으로 가져오기

git merge feature/save-records
git branch -d feature/save-records
git log --oneline --graph
Updating 71b8a6e..d05376a
Fast-forward
 storage.py | 2 ++
Deleted branch feature/save-records (was d05376a).
* d05376a Add load_records stub
* 71b8a6e Print the week in the banner
* c4f930b Add project skeleton

기능이 동작하면 main에서 병합합니다. main에 새 커밋이 없었다면 main이 그냥 앞으로 이동하는 fast-forward가 됩니다. 병합한 브랜치는 지웁니다. 그 커밋들은 main에 남습니다. log --graph는 이력을 그림으로 보여 줍니다.

브랜치 이름과 습관

git branch
  feature/report-title
* main

좋은 브랜치 이름은 할 일 항목입니다: feature/save-records, fix/negative-minutes. 브랜치 하나에 기능 하나, 며칠 안에 병합합니다. git branch는 브랜치 목록을 보여 주며 *가 현재 브랜치입니다. 브랜치를 바꾸기 전에 커밋합니다. 입력하기 전에 VS Code 왼쪽 아래에 표시된 브랜치 이름을 확인하는 습관을 들입니다.

두 편집이 부딪칠 때

git merge feature/report-title
git status --short
cat report.py
CONFLICT (content): Merge conflict in report.py
Automatic merge failed; fix conflicts and then commit the result.
UU report.py
<<<<<<< HEAD
TITLE = "Minutes per course"
=======
TITLE = "Study time this week"
>>>>>>> feature/report-title

같은 줄을 두 브랜치에서 서로 다르게 바꾸었습니다. main은 TITLE을 "Minutes per course"로, feature/report-title은 "Study time this week"로 바꿨습니다. Git은 추측하지 않고 멈춰서 파일에 표시를 남깁니다. UU는 병합되지 않음(unmerged)을 뜻합니다. <<<<<<< HEAD부터 =======까지가 현재 브랜치(main)의 내용, 그 아래 >>>>>>>까지가 병합해 들어오는 브랜치의 내용입니다.

세 단계로 해결하기

git add report.py
git commit -m "Merge report title: keep both ideas"
git log --oneline --graph
*   f84e248 Merge report title: keep both ideas
|\
| * dd6fc23 Rename report title
* | b7d071f Clarify report title
|/
* 7846ed1 Add report title

충돌은 질문이고, 파일을 고쳐서 답합니다. 첫째, 원하는 줄을 남기고 표시 줄 세 개를 모두 지웁니다. 둘째, git add로 "답했다"고 알립니다. 셋째, git commit으로 병합을 마칩니다. VS Code는 각 충돌 위에 Accept Current, Accept Incoming, Accept Both 버튼을 보여 줍니다.

연습: 일부러 충돌 만들기 (7분)

mkdir conflict-practice && cd conflict-practice
git init
echo "Hello" > title.txt
git add title.txt && git commit -m "Add title"
git switch -c feature/greeting
echo "Hello, class" > title.txt
git commit -am "Greet the class"

프로젝트가 아닌 연습용 폴더에서 합니다. title.txt가 있는 저장소를 만들어 커밋하고, 브랜치에서 그 줄을 바꿔 커밋한 뒤, main에서 같은 줄을 다르게 바꿔 커밋합니다. 그리고 병합하고, 해결하고, add, commit한 다음 git log --oneline --graph로 확인합니다. (이 연습도 git이 필요하므로 자신의 PC에서 합니다.)

휴식

10분 쉬고, 돌아오면 github.com을 열어 로그인합니다. 휴식 후에는 자신의 저장소에서 풀 리퀘스트를 다루고, 실습으로 저장소, 기능 브랜치, 병합된 풀 리퀘스트를 만듭니다.

3막 · 풀 리퀘스트: 내 작업을 스스로 검토하기

풀 리퀘스트(PR)는 대화가 붙은 병합입니다. GitHub에서 내 브랜치와 main 사이에 놓이며, 설명하고, 확인하고, 피드백을 받는 곳입니다.

개인 프로젝트에 왜 PR인가?

아무도 승인할 필요가 없어도 PR은 작업의 가장 좋은 기록입니다. 설명란에는 무엇이 왜 바뀌었는지 내 말로 적습니다. Files changed 탭은 내 diff를 직접 읽게 만듭니다. 교수자가 코드의 특정 줄에 댓글을 달 수 있습니다. 기능 하나가 브랜치, 커밋, 검토, 병합이 묶인 링크 하나가 됩니다.

브랜치를 push하고 PR 열기

git switch -c feature/append-record
git add storage.py
git commit -m "Add append_record with header"
git push -u origin feature/append-record
remote: Create a pull request for
remote: 'feature/append-record' on GitHub:
remote: https://github.com/jiwoo-park/
remote: study-logger/pull/new/feature/append-record
 * [new branch]      feature/append-record

이번에는 노트북에서 병합하지 않습니다. 브랜치를 push하고 GitHub가 병합하게 합니다. base는 main, compare는 내 기능 브랜치로 지정합니다. 제목은 커밋 메시지처럼 기능이 하는 일을 쓰고, 설명란은 다음 네 제목으로 채웁니다.

점수를 얻는 PR 설명

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: 변경 내용과 연결된 기능 ID.
  • Why: 설계 문서의 계약이나 수용 기준.
  • How I checked: 실행한 명령과 그 출력.
  • Not in this PR: 다음 브랜치로 남긴 것.

쓰는 데 2분이면 기능 하나가 완전히 설명됩니다. 예로 든 append_record의 계약("파일이 새로 만들어질 때만 헤더를 쓴다")은 1차시 study_logger의 storage.py에 구현되어 있습니다.

스스로 검토 체크리스트

Files changed 탭을 낯선 사람이 쓴 코드처럼 읽습니다.

  • 새 터미널에서 python3 main.py가 여전히 실행된다.
  • 새 함수마다 계약과 docstring에 맞다.
  • 디버그용 print()나 주석 처리한 실험이 남아 있지 않다.
  • 무시해야 할 파일(__pycache__, .venv, .env)이 섞여 들어가지 않았다.
  • 이 PR에는 기능 하나만 있다.

문제를 찾았다면 같은 브랜치에서 고치고 다시 push합니다. PR은 자동으로 갱신됩니다.

병합하고 노트북 동기화하기

git switch main
git pull
git branch -d feature/append-record
Updating d05376a..e2a91c4
Fast-forward
 storage.py | 9 +++++++++
Deleted branch feature/append-record (was 5a0c7e1).

GitHub에서 Merge pull request, 그다음 Delete branch를 누릅니다. 노트북은 pull하기 전까지 그 사실을 모릅니다. 노트북에서 main으로 돌아가 pull하고 로컬 브랜치를 지운 뒤, 갱신된 main에서 다음 기능 브랜치를 시작합니다. 함정: git pull을 건너뛰면 다음 브랜치가 예전 main에서 시작됩니다.

주간 반복

Must 기능 하나당 한 바퀴입니다: pull, branch, 몇 번의 commit, push, 풀 리퀘스트, merge, pull. 11–13주차는 서너 바퀴가 됩니다. 작은 바퀴는 끝나고, 거대한 브랜치는 썩습니다. 평가자는 이력에서 이 리듬을 봅니다.

실습: 나의 저장소, 나의 첫 PR (30분)

저장소 링크와 병합된 풀 리퀘스트 링크, 두 개를 가지고 나가는 것이 목표입니다. 스타터 저장소의 내용은 starter_repo에서 볼 수 있지만, 실습 자체는 git과 GitHub가 필요하므로 자신의 PC에서 합니다.

1단계: 저장소 (10분)

cd my-project
git init
git add .
git commit -m "Add project skeleton"
git remote add origin \
  https://github.com/<you>/my-project.git
git push -u origin main

스타터를 프로젝트 이름의 폴더로 복사하고, README.md 맨 위에 한 문장 목표를 씁니다. python3 main.py를 한 번 실행하면 Loaded 0 records가 나옵니다(starter_repo의 두 번째 단계에서 같은 출력을 확인할 수 있습니다). GitHub에 같은 이름의 빈 저장소를 만든 뒤 커밋하고, 연결하고, push합니다.

2단계: 기능 브랜치 (12분)

# A stub: final name, full contract, no body yet
def make_record(date, course, minutes_text):
    """Return one record dict.

    Raises ValueError if course is empty
    or minutes is not positive.
    """
    raise NotImplementedError("make_record")

설계 문서를 스텁으로 바꿉니다. git switch -c feature/skeleton으로 브랜치를 만들고, 스텁 함수 이름을 설계 문서의 이름으로 바꾸고, 각 계약을 docstring에 옮깁니다. 몸체는 TODO로 둡니다. 실제 메시지로 적어도 두 번 커밋하고, python3 main.py가 여전히 실행되는지 확인한 뒤 브랜치를 push합니다. starter-repo의 logic.parse_value가 바로 이런 스텁입니다. 계약은 있지만 몸체는 raise NotImplementedError이고, main.py가 아직 호출하지 않으므로 프로그램은 그대로 실행됩니다.

3단계: 풀 리퀘스트와 병합 (8분)

$ git log --oneline --graph
*   3b8e0f1 Merge pull request #1 from you/feature/skeleton
|\
| * 9c41d2a Copy contracts into docstrings
| * 52f7a90 Rename stubs to design names
|/
* 1a6c3e8 Add project skeleton

feature/skeleton에서 main으로 PR을 열고, What, Why, How I checked, Not in this PR을 채웁니다. Files changed 탭에서 스스로 검토 체크리스트를 확인한 뒤 병합하고 브랜치를 지웁니다. 그다음 git switch main, git pull을 합니다.

Git이 거절할 때

메시지의 마지막 줄을 읽으면 대개 해결책이 나와 있습니다.

메시지원인과 해결
not a git repository폴더를 잘못 찾았다. 프로젝트 폴더로 cd한다.
nothing to commit파일을 저장하지 않았거나 git add를 잊었다.
src refspec main does not match anypush하기 전에 첫 커밋을 만든다.
Authentication failedVS Code나 gh auth login으로 로그인한다.
Your branch is behindgit pull을 실행한 뒤 계속한다.

git status가 대부분의 질문에 답합니다. 모든 명령 전후에 실행합니다.

확인 질문과 11주차

  1. git add는 git commit이 하지 않는 무엇을 하나요?
  2. 이 수업에서 .gitignore에 들어가야 할 파일이나 폴더 네 가지는?
  3. 아무도 내 저장소를 쓰지 않는데 왜 main을 동작하는 상태로 유지하나요?
  4. 병합 충돌을 끝내는 세 단계는?
  5. GitHub에서 병합한 뒤 노트북에서 무엇을 실행해야 하나요?

LMS로 저장소 URL, 병합된 PR 링크, git log --oneline --graph 출력을 제출합니다. 비공개 저장소라면 먼저 교수자를 collaborator로 추가합니다. 이제 Must 범위는 동결되었으며 새 아이디어는 Should나 Could로 갑니다. 11주차에는 Must 기능마다 브랜치 하나와 풀 리퀘스트 하나로 구현합니다. 개인 작업이므로 저장소의 모든 커밋은 본인의 것이어야 합니다.
