"""Rules of the study logger. No input(), print() or open() in this file."""
 
 
def parse_minutes(text):
    """Return text as a positive whole number of minutes.
 
    Raises ValueError if text is not a whole number or is not above 0.
    """
    minutes = int(text)
    if minutes <= 0:
        raise ValueError(f"minutes must be positive, got {minutes}")
    return minutes
 
 
def make_record(date, course, minutes_text):
    """Return one record: {"date": str, "course": str, "minutes": int}.
 
    The course is stored in lower case. Raises ValueError for an empty
    course or invalid minutes.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    return {"date": date.strip(), "course": course,
            "minutes": parse_minutes(minutes_text)}
 
 
def weekly_totals(records):
    """Return {course: total minutes} for a list of records.
 
    An empty list returns {}. The input list is not changed.
    """
    totals = {}
    for record in records:
        course = record["course"]
        totals[course] = totals.get(course, 0) + record["minutes"]
    return totals

"""Reading and writing study.csv. The only file that touches the disk."""
import csv
from pathlib import Path
 
FIELDS = ["date", "course", "minutes"]
 
 
def load_records(path):
    """Return every row of the CSV file as a record dict.
 
    minutes is converted to int. A missing file returns [].
    """
    path = Path(path)
    if not path.exists():
        return []
    with open(path, newline="", encoding="utf-8") as f:
        return [{"date": row["date"], "course": row["course"],
                 "minutes": int(row["minutes"])}
                for row in csv.DictReader(f)]
 
 
def append_record(path, record):
    """Append one record to the CSV file, writing the header if the file is new."""
    path = Path(path)
    is_new = not path.exists()
    with open(path, "a", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=FIELDS)
        if is_new:
            writer.writeheader()
        writer.writerow(record)

def format_totals(totals):
    """Return one line per course, largest total first: "python   90 min"."""
    ordered = sorted(totals.items(), key=lambda item: item[1], reverse=True)

Act 1 · Decompose: from stories to functions

Big problems are small problems standing in a line. A story says why, a feature says what, and a function says how.

Story, feature, function

  • Story: As a student, I want to log study time by course, so that I can review my week.
  • Feature: F1 accepts date, course and positive minutes and saves valid entries.
  • Function: one verb, one job, testable alone.

Aim for 2–4 functions per Must feature.

The verb test

Read the feature sentence aloud and the verbs become functions. "F1: accept date, course and minutes; check the minutes; save valid entries."

F1 accept, check and save one entry
  -> read_entry()     asks the user       I/O
  -> make_record()    checks and builds   logic
  -> append_record()  writes the file     I/O

Verbs become functions, and nouns (date, course, minutes, record) become data. Name functions verb_noun, like make_record, not record_stuff. If a function name needs "and", it is two functions.

Input, processing, output

Every feature is a pipeline. Input is what arrives from the keyboard or a file, processing is the rules and calculations on that input, and output is what goes to the screen or a file. Processing is where the bugs live, and where the marks are. Draw the picture before you write code.

Act 2 · Contracts: promises between functions

"Give me this and I give you that, or I tell you why not." A contract is decided before the function body is written, and it is the part of your design that a grader can check line by line.

Anatomy of a contract

  • Name: a verb that says what you get back
  • Arguments: names and types
  • Return value: one type, always the same type
  • Failure: what happens with bad input

If you cannot fill in all four fields, the function is not designed yet.

Write the contract in the docstring

One file per responsibility, one shape per kind of data. A module is just a .py file you import, and your design decides which function goes in which file.

Two import traps

Both cause confusing errors far from the real cause.

  • Never name a file after a library, such as csv.py or random.py. Your csv.py hides the real module and you get AttributeError: module 'csv' has no attribute 'DictReader'.
  • Never let two of your modules import each other. One of them would see a half-built module.

If the error remains after renaming the file, delete __pycache__. The last step of study_logger creates a csv.py in a temporary folder to reproduce the first trap.

Three shapes of data

  • One record: a dict with fixed keys.
  • All records: a list of dicts, in file order, duplicates allowed.
  • A summary: a dict from key to result, one entry per key.

  • 스토리: 학생으로서, 나는 과목별 공부 시간을 기록하고 싶다. 그래야 한 주를 돌아볼 수 있다.
  • 기능: F1은 날짜, 과목, 양수인 분을 받아 올바른 항목을 저장한다.
  • 함수: 동사 하나, 일 하나, 혼자서 시험할 수 있음.

Must 기능 하나당 함수 2–4개를 목표로 합니다.

동사 테스트

기능 문장을 소리 내어 읽으면 동사가 함수가 됩니다. "F1: 날짜, 과목, 분을 받고, 분을 검사하고, 올바른 항목을 저장한다."

F1 accept, check and save one entry
  -> read_entry()     asks the user       I/O
  -> make_record()    checks and builds   logic
  -> append_record()  writes the file     I/O

동사는 함수가 되고, 명사(날짜, 과목, 분, 레코드)는 데이터가 됩니다. 함수 이름은 record_stuff가 아니라 make_record처럼 동사_명사로 짓습니다. 함수 이름에 "and"가 필요하다면 함수 두 개라는 뜻입니다.

2막 · 계약: 함수 사이의 약속

"이것을 주면 저것을 돌려주겠다, 그렇지 않으면 이유를 말하겠다." 계약은 함수 본문을 쓰기 전에 정하며, 평가자가 한 줄씩 확인할 수 있는 설계 부분입니다.

계약의 네 칸

  • 실패: 잘못된 입력에서 일어나는 일

네 칸을 모두 채울 수 없다면 그 함수는 아직 설계되지 않은 것입니다.

  • 함수 안에서 print: 피한다. 호출한 쪽이 대응할 수 없고 테스트도 볼 수 없다.

3막 · 모듈과 데이터: 어디에 둘 것인가

파일 하나에 책임 하나, 데이터 종류마다 모양 하나. 모듈은 import하는 .py 파일일 뿐이며, 어떤 함수가 어느 파일에 들어갈지는 설계가 정합니다.

파일 하나에 책임 하나

  • main.py는 프로그램을 실행한다: 묻고, 호출하고, 보여 준다.
  • logic.py는 규칙을 담는다. 입출력이 전혀 없다.
  • storage.py는 데이터 파일을 여는 유일한 파일이다.
  • report.py는 결과를 텍스트 줄로 바꾼다.

규칙: import는 한 방향으로만 향합니다. logic.py는 내가 만든 다른 파일을 하나도 import하지 않습니다.

내 파일 import하기

from logic import make_record, weekly_totals
from report import format_totals

rows = [make_record("2026-10-24", "python", "90"),
        make_record("2026-10-25", "Stats", "45")]
for line in format_totals(weekly_totals(rows)):
    print(line)
python    90 min
stats     45 min

같은 폴더의 파일은 모듈이고, 이름은 .py를 뗀 파일 이름입니다. from logic import weekly_totals는 logic.py를 한 번 불러옵니다. 필요한 이름만 import하고 import *는 피합니다. 파이썬이 파일을 찾을 수 있도록 python3는 프로젝트 폴더에서 실행합니다. study_logger의 여섯 번째 단계가 이 코드를 실행합니다. make_record가 "Stats"를 stats로 바꿔 저장하는 것도 볼 수 있습니다.

실행할 것인가, import할 것인가

def format_totals(totals):
    return [f"{c:<8}{m:>4} min"
            for c, m in totals.items()]

if __name__ == "__main__":
    print(format_totals({"python": 90}))

if __name__ == "__main__":은 "이 파일을 실행한다"와 "함수를 빌려 준다"를 구분합니다. python3 report.py로 실행하면 블록이 실행되어 ['python 90 min']이 나오고, 다른 파일에서 import report하면 블록은 건너뜁니다. 모듈 맨 아래에 간단한 자체 점검을 넣을 때 씁니다. (study_logger의 report.py에는 이 블록이 없으므로, 직접 추가해 실행해 볼 수 있습니다.)

import 함정 두 가지

둘 다 진짜 원인에서 멀리 떨어진 곳에서 이해하기 어려운 오류를 냅니다.

  • 라이브러리 이름으로 파일을 만들지 않는다: csv.py, random.py. 내 csv.py가 진짜 모듈을 가려 AttributeError: module 'csv' has no attribute 'DictReader'가 난다.
  • 내 모듈 두 개가 서로를 import하게 하지 않는다. 한쪽이 반쯤 만들어진 모듈을 보게 된다.

파일 이름을 바꿨는데도 오류가 남으면 __pycache__를 지웁니다. study_logger의 마지막 단계에서 임시 폴더에 csv.py를 만들어 첫 번째 함정을 재현합니다.

데이터의 세 가지 모양

  • 레코드 하나: 고정된 키를 가진 dict.
  • 모든 레코드: dict의 list. 파일 순서대로, 중복 허용.
  • 요약: 키에서 결과로 가는 dict. 키마다 항목 하나.

모양은 지금 정합니다. 모든 함수의 계약이 이 모양을 언급하기 때문입니다. 예측 질문: 레코드는 왜 list이고 합계는 왜 dict일까요? (레코드는 순서가 있고 같은 과목이 여러 번 나올 수 있지만, 합계는 과목마다 하나의 값만 있어야 하기 때문입니다.)

파일에서 레코드로

import csv

with open("data/study.csv", newline="") as f:
    rows = list(csv.DictReader(f))
print(rows[0]["course"], repr(rows[0]["minutes"]))

csv.DictReader는 헤더를 키로 삼아 각 행을 dict로 만들지만, 모든 값은 str로 들어옵니다. 숫자는 읽은 직후 storage.py에서 한 번만 변환하고, 그다음부터 다른 모든 함수는 자료형을 믿을 수 있게 합니다. 함정: "90" + "45"는 "9045"입니다. 더하기 전에 변환합니다. study_logger의 일곱 번째 단계에서 변환 없이 더하면 실제로 9045가 나옵니다.

Act 2 · Branch: a safe place to try

main always runs; new work happens next door. Make one branch per feature and merge it when it works. Then we look at what conflicts look like and how to end them.

Why branch when you are alone?

A branch is a second line of commits that main does not see until you merge. main stays demo-ready at every moment. Each Must feature gets its own short-lived branch. A failed experiment is just one deleted branch, not a broken project. The graph shows the grader exactly how each feature was built.

Branch names and habits

git branch
  feature/report-title
* main

A good branch name is a to-do item: feature/save-records, fix/negative-minutes. One feature per branch, merged within days. git branch lists the branches, and * marks the current one. Commit before you switch branches. Make a habit of checking the branch name shown in the bottom-left corner of VS Code before you type.

When two edits collide

git merge feature/report-title
git status --short
cat report.py
CONFLICT (content): Merge conflict in report.py
Automatic merge failed; fix conflicts and then commit the result.
UU report.py
<<<<<<< HEAD
TITLE = "Minutes per course"
=======
TITLE = "Study time this week"
>>>>>>> feature/report-title

The same line was changed differently on two branches: main changed TITLE to "Minutes per course" and feature/report-title changed it to "Study time this week". Git will not guess; it stops and marks the file. UU means unmerged. From <<<<<<< HEAD to ======= is the current branch's (main's) content, and below it, up to >>>>>>>, is the content of the branch being merged in.

Resolve in three moves

git add report.py
git commit -m "Merge report title: keep both ideas"
git log --oneline --graph
*   f84e248 Merge report title: keep both ideas
|\
| * dd6fc23 Rename report title
* | b7d071f Clarify report title
|/
* 7846ed1 Add report title

A conflict is a question, and you answer it by editing the file. First, keep the line you want and delete all three marker lines. Second, git add the file to say "answered". Third, git commit to finish the merge. VS Code shows Accept Current, Accept Incoming and Accept Both buttons above each conflict.

Act 3 · Pull request: review your own work

A pull request (PR) is a merge with a conversation attached. It lives on GitHub, between your branch and main, and it is where you explain, check and get feedback.

Why a pull request in a solo project?

Even if nobody needs to approve it, a PR is the best record of your work. The description says what changed and why, in your own words. The Files changed tab makes you read your own diff. The instructor can comment on a specific line of your code. Each feature becomes one link that ties together branch, commits, review and merge.

Push the branch, open the PR

git switch -c feature/append-record
git add storage.py
git commit -m "Add append_record with header"
git push -u origin feature/append-record

 * [new branch]      feature/append-record

This time we do not merge on the laptop. We push the branch and let GitHub merge. Set base to main and compare to your feature branch. Write the title like a commit message, saying what the feature does, and fill the description with the following four headings.

A PR description that earns points

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: the change, linked to a feature ID.
  • Why: the contract or acceptance criterion from your design document.
  • How I checked: the command you ran and what it printed.
  • Not in this PR: what is left for the next branch.

Two minutes to write, and a whole feature is explained. The contract of the example append_record ("write the header only when the file is newly created") is implemented in Session 1's study_logger storage.py.

The self-review checklist

Read the Files changed tab as if a stranger wrote the code.

  • python3 main.py still runs from a fresh terminal.
  • Every new function matches its contract and docstring.
  • No leftover debug print() or commented-out experiments.
  • No ignored files (__pycache__, .venv, .env) slipped in.
  • Only one feature in this PR.

If you find a problem, fix it on the same branch and push again. The PR updates automatically.

git pull
git branch -d feature/append-record
Updating d05376a..e2a91c4
Fast-forward

Deleted branch feature/append-record (was 5a0c7e1).

On GitHub, click Merge pull request, then Delete branch. Your laptop does not know until you pull. On the laptop, go back to main, pull and delete the local branch, then start the next feature branch from the updated main. Trap: skip git pull and your next branch starts from the old main.

The weekly loop

One loop per Must feature: pull, branch, commit a few times, push, pull request, merge, pull. Weeks 11–13 are three or four loops. Small loops finish; giant branches rot. The grader sees this rhythm in your history.

2막 · 브랜치: 안전하게 시도하는 곳

main은 언제나 실행되고, 새 작업은 옆집에서 합니다. 기능마다 브랜치 하나를 만들어 동작하면 병합합니다. 그다음 충돌이 어떻게 보이고 어떻게 끝내는지 봅니다.

혼자인데 왜 브랜치인가?

브랜치는 병합하기 전까지 main이 보지 못하는 두 번째 커밋 줄기입니다. main은 어느 순간에나 시연할 수 있는 상태를 유지합니다. Must 기능마다 수명이 짧은 브랜치를 하나씩 만듭니다. 실패한 실험은 망가진 프로젝트가 아니라 지운 브랜치 하나일 뿐입니다. 그래프는 각 기능이 어떻게 만들어졌는지 평가자에게 정확히 보여 줍니다.

브랜치를 만들고 작업하기

git switch -c feature/save-records
git add storage.py
git commit -m "Add load_records stub"
ls

 1 file changed, 2 insertions(+)
 create mode 100644 storage.py
README.md  __pycache__  main.py  storage.py

switch -c는 브랜치를 만들고 그 브랜치로 옮겨 갑니다. 이제 커밋은 main이 아니라 feature/save-records에 쌓이고, 새 파일 storage.py는 이 브랜치에 있습니다.

storage.py는 어디로 갔나?

Switched to branch 'main'
README.md  __pycache__  main.py

git switch는 폴더의 파일을 그 브랜치에 맞게 바꿉니다. storage.py는 기능 브랜치의 커밋 안에 안전하게 있고, main은 아직 그것을 보지 못했습니다. 바로 그것이 핵심입니다. 예측 질문: git switch feature/save-records 후에 ls는 무엇을 보여 줄까요?

기능이 동작하면 main에서 병합합니다. main에 새 커밋이 없었다면 main이 그냥 앞으로 이동하는 fast-forward가 됩니다. 병합한 브랜치는 지웁니다. 그 커밋들은 main에 남습니다. log --graph는 이력을 그림으로 보여 줍니다.

브랜치 이름과 습관

좋은 브랜치 이름은 할 일 항목입니다: feature/save-records, fix/negative-minutes. 브랜치 하나에 기능 하나, 며칠 안에 병합합니다. git branch는 브랜치 목록을 보여 주며 *가 현재 브랜치입니다. 브랜치를 바꾸기 전에 커밋합니다. 입력하기 전에 VS Code 왼쪽 아래에 표시된 브랜치 이름을 확인하는 습관을 들입니다.

3막 · 풀 리퀘스트: 내 작업을 스스로 검토하기

풀 리퀘스트(PR)는 대화가 붙은 병합입니다. GitHub에서 내 브랜치와 main 사이에 놓이며, 설명하고, 확인하고, 피드백을 받는 곳입니다.

개인 프로젝트에 왜 PR인가?

아무도 승인할 필요가 없어도 PR은 작업의 가장 좋은 기록입니다. 설명란에는 무엇이 왜 바뀌었는지 내 말로 적습니다. Files changed 탭은 내 diff를 직접 읽게 만듭니다. 교수자가 코드의 특정 줄에 댓글을 달 수 있습니다. 기능 하나가 브랜치, 커밋, 검토, 병합이 묶인 링크 하나가 됩니다.

브랜치를 push하고 PR 열기

git switch -c feature/append-record
git add storage.py
git commit -m "Add append_record with header"
git push -u origin feature/append-record
remote: Create a pull request for
remote: 'feature/append-record' on GitHub:
remote: https://github.com/jiwoo-park/
remote: study-logger/pull/new/feature/append-record
 * [new branch]      feature/append-record

이번에는 노트북에서 병합하지 않습니다. 브랜치를 push하고 GitHub가 병합하게 합니다. base는 main, compare는 내 기능 브랜치로 지정합니다. 제목은 커밋 메시지처럼 기능이 하는 일을 쓰고, 설명란은 다음 네 제목으로 채웁니다.

점수를 얻는 PR 설명

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: 변경 내용과 연결된 기능 ID.
  • Why: 설계 문서의 계약이나 수용 기준.
  • How I checked: 실행한 명령과 그 출력.
  • Not in this PR: 다음 브랜치로 남긴 것.

쓰는 데 2분이면 기능 하나가 완전히 설명됩니다. 예로 든 append_record의 계약("파일이 새로 만들어질 때만 헤더를 쓴다")은 1차시 study_logger의 storage.py에 구현되어 있습니다.

스스로 검토 체크리스트

Files changed 탭을 낯선 사람이 쓴 코드처럼 읽습니다.

  • 새 터미널에서 python3 main.py가 여전히 실행된다.
  • 새 함수마다 계약과 docstring에 맞다.
  • 디버그용 print()나 주석 처리한 실험이 남아 있지 않다.
  • 무시해야 할 파일(__pycache__, .venv, .env)이 섞여 들어가지 않았다.
  • 이 PR에는 기능 하나만 있다.

문제를 찾았다면 같은 브랜치에서 고치고 다시 push합니다. PR은 자동으로 갱신됩니다.

병합하고 노트북 동기화하기

git switch main
git pull
git branch -d feature/append-record
Updating d05376a..e2a91c4
Fast-forward
 storage.py | 9 +++++++++
Deleted branch feature/append-record (was 5a0c7e1).

GitHub에서 Merge pull request, 그다음 Delete branch를 누릅니다. 노트북은 pull하기 전까지 그 사실을 모릅니다. 노트북에서 main으로 돌아가 pull하고 로컬 브랜치를 지운 뒤, 갱신된 main에서 다음 기능 브랜치를 시작합니다. 함정: git pull을 건너뛰면 다음 브랜치가 예전 main에서 시작됩니다.

주간 반복

Must 기능 하나당 한 바퀴입니다: pull, branch, 몇 번의 commit, push, 풀 리퀘스트, merge, pull. 11–13주차는 서너 바퀴가 됩니다. 작은 바퀴는 끝나고, 거대한 브랜치는 썩습니다. 평가자는 이력에서 이 리듬을 봅니다.
