from datetime import date
 
FIELDS = ["date", "code", "name", "market", "previous_close", "close", "volume"]
MARKETS = ("ALL", "KOSPI", "KOSDAQ")
 
 
def parse_row(row):
    """Return a typed quote; raise ValueError for any invalid field. No I/O."""
    if set(row) != set(FIELDS) or any(not isinstance(v, str) for v in row.values()):
        raise ValueError("each row needs exactly seven fields")
    quote = {key: value.strip() for key, value in row.items()}
    day = quote["date"]
    if date.fromisoformat(day).isoformat() != day:
        raise ValueError("date must be YYYY-MM-DD")
    code = quote["code"]
    if len(code) != 6 or not code.isascii() or not code.isdigit():
        raise ValueError("code must be six ASCII digits")
    if not quote["name"] or quote["market"] not in MARKETS[1:]:
        raise ValueError("name and KOSPI/KOSDAQ market are required")
    for field in ("previous_close", "close", "volume"):
        text = quote[field]
        if not text.isascii() or not text.isdigit():
            raise ValueError(f"{field} must be a whole number")
        quote[field] = int(text)
        minimum = 0 if field == "volume" else 1
        if quote[field] < minimum:
            raise ValueError(f"{field} must be >= {minimum}")
    return quote
 
 
def change_pct(previous_close, close):
    """Return unrounded daily percent change; both prices must be positive."""
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    return (close - previous_close) / previous_close * 100
 
 
def analyze(quotes, market):
    """Validate snapshot identity; filter and sort by change desc, then code asc.
 
    Return fresh quote dicts with change_pct. Empty input/selection returns [].
    Mixed dates, duplicate codes or an unknown market raise ValueError.
    quotes must already contain typed, validated values from parse_row().
    """
    if market not in MARKETS:
        raise ValueError("market must be ALL, KOSPI or KOSDAQ")
    if len({q["date"] for q in quotes}) > 1:
        raise ValueError("snapshot must contain one date")
    codes = [q["code"] for q in quotes]
    if len(set(codes)) != len(codes):
        raise ValueError("duplicate code in snapshot")
    rows = [dict(q, change_pct=change_pct(q["previous_close"], q["close"]))
            for q in quotes if market == "ALL" or q["market"] == market]
    return sorted(rows, key=lambda q: (-q["change_pct"], q["code"]))
 
 
def summarize(rows):
    """Return sample count, up/down/flat counts and equal-weight mean (or None)."""
    count = len(rows)
    return {"count": count,
            "up": sum(q["change_pct"] > 0 for q in rows),
            "down": sum(q["change_pct"] < 0 for q in rows),
            "flat": sum(q["change_pct"] == 0 for q in rows),
            "mean": sum(q["change_pct"] for q in rows) / count if count else None}

import csv

from pathlib import Path
import tempfile
from logic import FIELDS, parse_row
 
 
def load_quotes(path):
    """Read UTF-8(-BOM) CSV; reject malformed header/rows with ValueError.
 
    Missing or unreadable files raise OSError. Header-only files return [].
    """
    with open(path, encoding="utf-8-sig", newline="") as stream:
        reader = csv.DictReader(stream)
        if reader.fieldnames != FIELDS:
            raise ValueError("CSV header must be " + ",".join(FIELDS))
        quotes = []
        for number, row in enumerate(reader, start=2):
            try:
                quotes.append(parse_row(row))
            except ValueError as error:
                raise ValueError(f"CSV row {number}: {error}") from error
    return quotes
 
 
def write_html(path, html):
    """Replace output only after a complete UTF-8 write; raise OSError on failure."""
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    temporary = None
    try:
        with tempfile.NamedTemporaryFile(mode="w", encoding="utf-8",
                                         dir=path.parent, delete=False) as stream:
            temporary = Path(stream.name)
            stream.write(html)
        os.replace(temporary, path)
    finally:
        if temporary is not None and temporary.exists():
            temporary.unlink()

## 3. Feature 명세
 
### FEAT-01: 검증된 스냅샷 불러오기 (REQ-01/02/06)
 
- 사용자: CSV를 준비한 학생. 명령: `python3 main.py --input data/prices.csv`.
- 정상: 파일 열기 → 헤더 검증 → 각 행 검증/타입 변환 → 한 날짜·중복코드 확인.
- 결과: 코드가 문자열인 종목 목록. 이 결과는 FEAT-02로 전달된다.
- 오류: 파일 없음/권한/인코딩/행 형식 오류는 `Report not generated: <reason>`. 기존 보고서 유지. 행 오류에는 CSV 행 번호 포함.
 
### FEAT-02: 시장별 분석 (REQ-02/03/04)
 
- 명령: `python3 main.py --market KOSPI`. 허용: ALL(기본), KOSPI, KOSDAQ.
- 계산: `(close - previous_close) / previous_close * 100`. 계산·정렬 중에는 반올림하지 않는다.
- 정상: 입력 전체의 날짜·중복을 검증 → 시장 필터 → 등락률 내림차순/코드 오름차순 → 표본 요약.
- 결과: KOSPI 표본 3개, 순서 005930→035420→000660, 평균 +0.33% 표시.
- 예외: 알 수 없는 시장은 argparse 사용 오류(종료 2). 선택 결과가 비면 0개·N/A.
 
### FEAT-03: 웹 보고서 생성·열람 (REQ-05/06)
 
- 명령: `python3 main.py --output docs/index.html`; 브라우저로 생성 파일을 연다.
- 정상: HTML 문자열 생성 → 임시 파일 쓰기 → 최종 파일 교체 → Generated 메시지.
- 결과: 표와 요약, 기준일·출처·가상 데이터 표시. 상승/하락 색상과 함께 +/− 부호를 사용한다.
- 오류: 출력 실패 시 `Report not generated: ...`, 종료 1. 기존 출력 보존.

FEAT-01 PR → FEAT-02 PR → FEAT-03 PR 순서로 구현한다. 각 PR은 간단한 화면 출력 또는 임시 HTML까지 이어지는 실행 가능한 슬라이스로 제출한다. FEAT-01 단계의 분석/HTML fake는 명확히 표시하고 마지막 PR 전에 모두 교체한다.

## 4. System Architecture
 
### 4.1 Processes and Threads
 
```text
[학생 CLI] -> [Python main: 단일 프로세스·메인 스레드]
                |-> storage.load_quotes -> logic.parse_row
                |-> logic.analyze -> logic.summarize
                |-> report.render_html
                `-> storage.write_html -> docs/index.html
 
[브라우저] -> 생성된 HTML 파일 열기
선택: [python -m http.server] -> 정적 HTML 제공 (분석을 실행하지 않음)
```
 
| Process / Thread | Role | Creation / Termination |
|---|---|---|
| Python CLI / 메인 스레드 | CSV 검증·분석·HTML 생성 | `python3 main.py`; 성공 0, 데이터/I/O 실패 1, CLI 인자 오류 2로 종료 |
| 브라우저 | 생성된 파일 표시 | 사용자가 파일을 연다. CLI와 별도 프로그램이며 자식 프로세스로 만들지 않음 |
| 로컬 HTTP 서버 (선택) | docs 폴더의 정적 파일 제공 | 별도 터미널에서 실행, Ctrl+C 종료. Python 분석 백엔드가 아님 |
 
fork·자식 프로세스·작업 스레드·서버 프레임워크는 사용하지 않는다.
 
### 4.2 IPC and Synchronization
 
| Where Used | Method | Reason |
|---|---|---|
| 모듈 간 | 일반 함수 인자와 반환값 | 단일 Python 프로세스이므로 IPC 없음 |
| HTML 출력 | 같은 디렉터리의 임시 파일 작성 후 `os.replace` | 작성 실패가 기존 보고서를 훼손하지 않도록 함 |
| 동시 생성 | 지원 범위 밖, 같은 경로에 한 번에 한 프로세스만 실행 | 파일 잠금·다중 작성자 동기화는 구현하지 않음 |
 
### 4.3 Data Storage Format
 
| File / Data | Format (Text / Binary) | Structure |
|---|---|---|
| `data/prices.csv` | UTF-8 text (BOM 허용) | `date,code,name,market,previous_close,close,volume`; 단일 날짜·중복 없는 코드 |
| `data/invalid-zero.csv` | UTF-8 text | 같은 구조, 첫 종목 전일종가 0인 오류 실습 파일 |
| `data/empty.csv` | UTF-8 text | 정상 헤더만 존재 |
| `docs/index.html` | UTF-8 HTML | 한글 제목·기준일·시장·출처·표본 요약·종목 표; 외부 텍스트 escape |
| 메모리 Quote | Python dict | 날짜/코드/이름/시장 str, 가격·거래량 int; 분석 후 change_pct float 추가 |
| 메모리 Summary | Python dict | count/up/down/flat int, mean float 또는 None |

The four documents do not describe different programs; they look at the same program from four directions. The requirement answers what must hold, the feature what the user sees, the function what the code promises, and UML how they connect. Today's shared example is the study logger from Weeks 9 and 10. On the lab pages you run study_logger_skeleton, a skeleton with only contracts, and study_logger_f1, which implements F1, and carry out the documents' checks yourself.

Project guidance and document scope

The project uses only Python 3 and the standard library. Data is kept in a file and results are reported on the screen. Every project is checked on the same three points:

  • Does it refuse bad input?
  • Does it survive a missing file?
  • Is the file left unchanged after a failure?

The design covers the problem, the feature scope, the module structure and the data format. The four documents introduced today are a guide; the actual submission items and weights follow the syllabus.

Linking requirements to implementation

A requirement is a condition to satisfy, and a feature is what the user does to satisfy it. A function is the code's promise, and a check decides whether that promise holds. UML sits under feature and function and shows the structure and flow that connect them.

Rule: use the same ID in every document. Then you can follow one requirement all the way to its code and its check.

Shared example: the study logger

There are three basic features: log one entry, reload the file, and show weekly totals per course. DOC 1 · Requirement: the specification

The requirement document states what must hold, for whom, and how far. Each line must be something you can judge pass or fail.

  • Purpose and scope: who has what problem, what the program solves, and where it stops.
  • Requirement items: an ID, the statement, a priority (Must, Should, Could) and a check.
  • Functional requirements: log an entry, apply the input rules, report totals, keep the data.
  • Constraints: standard library only, input checked, file unchanged on failure.

Write only one condition per line. A check must be something a classmate can do at the keyboard.

Requirement example

Every requirement carries an observable check. No check, no requirement. The statement says what, not how: no function names and no file formats. These checks become next session's test_logic.py, and the Week 12 test list.

Matching requirements to checks

Give each requirement sentence an input condition and an observable result.

  • Input condition: exactly what is typed, or what the file holds before the run.
  • Observed result: what is printed, and what the file contains after the run.

A check that only works if its author stands beside you and explains it is not a check yet.

DOC 2 · Feature: the user-facing specification

The feature document describes the program as the user meets it: the command, the questions (prompts), and the results that come back.

FEAT-xx  <name>              basic | extension

usage    command, prompts, allowed values
flow     step 1 ... step n, the normal path
result   what the user sees on success

serves   REQ-xx, REQ-yy
  • Identification: feature ID, name, purpose, and whether it is a basic feature or an extension.
  • How to use: the command, the prompts, the allowed values, the preconditions.
  • Behavior and result: the normal flow and the output the user checks.
  • Exceptions and links: bad input, failures, and the requirement IDs this feature serves.

Feature example: logging one entry

FEAT-01  Log one entry                     basic

The usage line is what you will actually type in the demo. Write it so that a stranger could follow it. List errors one by one, each with its message; a single line saying "handles errors" is not an error entry. The serves line is the traceability link back to the requirements.

A feature's normal path and error path

Define what the user sees on both the good day and the bad day. Both belong in the feature sheet.

  • Normal path: four steps, each with something the user can observe.
  • Input error: a sentence with the reason is printed, and nothing is written to the file.
  • File error: the cause is reported, nothing is left half-written, and the program ends cleanly.

One function, one contract. Your Week 10 design document already has the fields.

  • Inputs and results: allowed values and units, what success returns, and how failure shows.
  • Where it runs: which module it is in and who calls it, and whether it uses the keyboard, a file, or neither.
  • Failure and resources: whether it raises an exception or returns None, and who opens and closes the file.

Function example: make_record()

Write the contract in the docstring and the body under it, then add one call that shows the promise is kept.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))

The input is three strings from input(). Trimming and lower-casing the course happens here and only here. main() calls this function before anything is written. It returns one dict, with minutes as an int. On failure it raises ValueError with a reason, and main prints Not saved and writes nothing. The real implementation is in logic.py of study_logger_f1 (with the minutes check split out into parse_minutes()), and you can run the same call on the lab page.

Once main() has asked the user, each module answers only one kind of question. None of them asks the user anything.

Traceability across documents

Write the requirement ID in the feature, the function, the diagram and the test, and nothing gets lost. For example, REQ-02 says what must hold (minutes that are not positive are rejected). Document review and demo preparation

  1. Scope: are basic features and extensions separated, and is the MVP boundary visible?

  5. Reproduction: are the setup, the run command, one normal scenario and one error scenario written down?

DOC 2 · 기능: 사용자 관점의 명세

기능 문서는 사용자가 만나는 프로그램을 적습니다. 명령, 질문(프롬프트), 그리고 돌아오는 결과입니다.

FEAT-xx  <name>              basic | extension
purpose  one sentence
usage    command, prompts, allowed values
flow     step 1 ... step n, the normal path
result   what the user sees on success
errors   each failure and its message
serves   REQ-xx, REQ-yy
  • 식별: 기능 ID, 이름, 목적, 기본 기능인지 확장 기능인지.
  • 사용 방법: 명령, 프롬프트, 허용되는 값, 사전 조건.
  • 동작과 결과: 정상 흐름과 사용자가 확인하는 출력.
  • 예외와 연결: 잘못된 입력, 실패, 그리고 이 기능이 충족하는 요구사항 ID.

기능 예: 한 건 기록하기

FEAT-01  Log one entry                     basic
purpose  record one study session
usage    python3 main.py, then three prompts:
         date YYYY-MM-DD, course, minutes > 0
flow     check input -> build record
         -> append one row to data/study.csv
result   "Saved."
errors   bad minutes or empty course:
         "Not saved: <reason>", file unchanged
         data/ missing: report it, write nothing
serves   REQ-01, REQ-02, REQ-04

usage 줄은 시연에서 실제로 입력할 내용입니다. 처음 보는 사람도 따라 할 수 있게 씁니다. 오류는 하나씩, 각각의 메시지와 함께 나열합니다. "오류를 처리한다"는 한 줄은 오류 항목이 아닙니다. serves 줄은 요구사항으로 돌아가는 추적 연결입니다.

정상 경로와 오류 경로

좋은 날과 나쁜 날에 사용자가 무엇을 보는지 모두 정의합니다. 둘 다 기능 명세에 들어갑니다.

  • 정상 경로: 네 단계, 각 단계마다 사용자가 관찰할 수 있는 것이 있습니다.
  • 입력 오류: 이유를 담은 문장이 나오고 파일에는 아무것도 쓰지 않습니다.
  • 파일 오류: 원인을 알리고, 반쯤 쓴 파일을 남기지 않으며, 프로그램은 깔끔하게 끝납니다.

DOC 3 · 함수: 파이썬 함수 설계

함수 하나에 계약 하나입니다. 10주차 설계 문서에 이미 항목이 있습니다.

make_record(date: str, course: str,
            minutes_text: str) -> dict
module   logic.py       called by main()
I/O      none           pure   yes
returns  {"date", "course", "minutes": int}
fails    ValueError: empty course, or
         minutes not a whole number above 0
  • 시그니처: 이름, 자료형이 붙은 매개변수, 반환 자료형.
  • 입력과 결과: 허용되는 값과 단위, 성공하면 무엇을 반환하는지, 실패는 어떻게 드러나는지.
  • 실행 위치: 어느 모듈에 있고 누가 호출하는지, 키보드나 파일에 접근하는지 아니면 둘 다 하지 않는지.
  • 실패와 자원: 예외를 던지는지 None을 반환하는지, 파일은 누가 열고 닫는지.

함수 예: make_record()

계약은 docstring에, 본문은 그 아래에 씁니다. 그리고 약속이 지켜지는 것을 보여 주는 호출 하나를 붙입니다.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))
python 90

입력은 input()에서 온 문자열 세 개입니다. 과목의 공백 제거와 소문자 변환은 여기에서만 합니다. 이 함수는 무엇이든 쓰기 전에 main()이 호출합니다. 반환값은 dict 하나이고 minutes는 int입니다. 실패하면 이유를 담은 ValueError를 던지고, main은 Not saved를 출력하고 아무것도 쓰지 않습니다. study_logger_f1의 logic.py에 실제 구현이 있으며(분 검사는 parse_minutes()로 분리), 실습 페이지에서 같은 호출을 실행할 수 있습니다.

함수로 나누기

여섯 함수, 여섯 개의 단일 책임입니다. 10주차의 동사 테스트로 이름을 붙입니다.

함수계약
parse_minutes()분 문자열 → 양의 int, 아니면 ValueError
make_record()날짜, 과목, 분 → 기록 dict 하나
append_record()기록 하나 → data/study.csv에 한 행

규칙 함수 둘, 파일 함수 둘, 보고 함수 하나, 그리고 이들을 호출하는 main()입니다. 이름은 모두 동사+명사이고, 위 표의 한 줄이 계약 표의 한 행입니다. 함수를 설명하는 데 "그리고"가 필요하다면, 계약을 쓰기 전에 나눕니다.

이 표가 코드가 된 모습이 study_logger_skeleton입니다. 모든 함수가 이름과 docstring을 갖추었지만 본문은 raise NotImplementedError나 TODO입니다. 실행하면 동작은 하지만(Loaded 0 records) 요구사항은 아직 만족하지 못합니다.

함수와 모듈: 누가 무엇을 하는가

main()이 사용자에게 묻고 나면, 각 모듈은 한 종류의 질문에만 답합니다. 그중 어느 모듈도 사용자에게 무언가를 묻지 않습니다.

  • main.py는 묻고, 호출하고, 출력합니다. 규칙은 갖지 않습니다.
  • logic.py는 규칙을 갖고, 키보드나 디스크를 절대 건드리지 않습니다.
  • storage.py는 data/study.csv를 여는 유일한 모듈입니다.
  • report.py는 결과를 줄로 바꿉니다.

DOC 4 · UML: 목적에 따라 다이어그램 고르기

모든 다이어그램이 필요하지는 않습니다. 읽는 사람의 질문에 답하는 다이어그램 하나를 고릅니다.

읽는 사람의 질문다이어그램
누가 무엇을 위해 쓰는가?유스케이스
어느 파일이 어느 파일을 import하는가?모듈(컴포넌트) 다이어그램
호출은 어떤 순서로 일어나는가?시퀀스 다이어그램
기록 하나에 무슨 일이 일어나는가?상태(또는 활동) 다이어그램

모듈 다이어그램의 화살표는 한 방향만 가리킵니다. 활동 다이어그램은 오류 분기를 포함한 단계를 보여 줍니다.

유스케이스 예

사용자와, 시스템이 제공하는 목표를 그립니다. 함수가 아니라 목표입니다. 행위자(actor)는 학생 한 명이고, 시스템 경계는 공부 기록기입니다. 목표는 세 가지입니다. 한 건 기록하기, 주간 합계 보기, 예전 기록 다시 찾기. 함수 이름은 여기에 나오지 않습니다. 호출 순서는 시퀀스 다이어그램의 몫입니다.

시퀀스 예: 한 번의 실행

정상 경로의 한 번 실행을, 시간이 위에서 아래로 흐르게 그립니다. 모든 화살표는 계약 표에 있는 호출입니다. main()은 logic을 먼저 호출하므로, 기록이 유효해지기 전에는 아무것도 쓰이지 않습니다. 돌아오는 화살표마다 데이터 모양 하나를 나릅니다. 기록, 기록 목록, 합계 dict, 줄 목록입니다. 실패 경로(ValueError)는 별도의 분기로 그리거나, 더 짧은 두 번째 다이어그램으로 그립니다.

상태 예: 기록 하나

상태 넷과 막다른 길 하나입니다. 각 전이는 표에 있는 함수입니다. 입력됨(typed) → make_record()가 검사함(checked) → append_record()가 저장함(saved) → weekly_totals()가 셈(counted). 빈 과목이나 잘못된 분이면 거절됨(rejected)으로 끝나고 "Not saved"가 나오며 아무것도 쓰이지 않습니다. 검사를 통과한 뒤에 파일 오류가 나도 보고하고, 반쯤 쓴 파일은 남기지 않습니다.

문서 간 추적성

요구사항 ID를 기능, 함수, 다이어그램, 테스트에 모두 적으면 아무것도 잃어버리지 않습니다. 예를 들어 REQ-02는 무엇이 성립해야 하는지(양수가 아닌 분은 거절)를 말합니다. FEAT-01은 그것을 사용자에게 보여 주고, parse_minutes()가 강제하고, 상태 다이어그램이 그리고, TEST-02가 증명합니다. 채점자나 14주차의 내가 이 사슬을 어느 방향으로든 따라갈 수 있습니다.

ACT 1 · Requirements and features

Requirement: observable conditions

Each REQ in the Requirement sheet links to SC IDs and has a check.

  • REQ-01: read a valid CSV and preserve stock codes.
  • REQ-02: reject invalid values, duplicate codes and mixed dates.
  • REQ-03: calculate, filter and sort daily percentage changes. For example, previous_close=70000 and close=71400 gives +2%. Choosing KOSPI yields only KOSPI rows. The order is by change, descending; ties are broken by code, ascending.

The output and the failure policy are part of the product too. A header-only CSV produces a valid empty report (count 0, mean N/A). A missing CSV file is an error, not a successful empty report.

ACT 2 · Functions and tests

Contracts before bodies

Keep the values and failure rules that cross module boundaries consistent.

Quote = {date, code, name, market,
         previous_close: int, close: int,
         volume: int}
Analyzed row = Quote + {change_pct: float}
Summary = {count, up, down, flat, mean}
  • FUNC-01 parse_row(row): strings → a typed quote. ValueError on invalid fields.
  • FUNC-02 load_quotes(path): CSV → list. A missing file raises OSError.
  • FUNC-04 analyze(quotes, market): validated list → freshly made, sorted rows.
  • FUNC-05 summarize(rows): counts and mean. If empty, the mean is None.

Implement the smallest rule

Compute with full precision and round only in the report. The formula is (close − previous_close) / previous_close × 100. Reject a zero or negative price before dividing. A rise, a fall and a flat price are separate checks.

def change_pct(previous_close, close):
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    difference = close - previous_close
    return difference / previous_close * 100

assert change_pct(70000, 71400) == 2.0
assert change_pct(200000, 198000) == -1.0
assert change_pct(100, 100) == 0.0
print("Daily change checks passed.")

가장 작은 규칙 구현하기

계산은 전체 정밀도로 하고, 반올림은 보고서에서만 합니다. 공식은 (close − previous_close) / previous_close × 100입니다. 나누기 전에 0이나 음수 가격을 거절합니다. 상승, 하락, 보합은 각각 별도의 검사입니다.

def change_pct(previous_close, close):
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    difference = close - previous_close
    return difference / previous_close * 100

assert change_pct(70000, 71400) == 2.0
assert change_pct(200000, 198000) == -1.0
assert change_pct(100, 100) == 0.0
print("Daily change checks passed.")

HTML은 결과를 보여 주는 뷰다

서식은 보여 주는 방식을 바꿀 뿐 계산을 바꾸면 안 됩니다. render_html은 문자열을 반환하고, 쓰기는 storage가 합니다. 종목 이름처럼 외부에서 온 텍스트에는 html.escape를 씁니다. 색깔뿐 아니라 부호와 숫자도 보여 줍니다. 날짜, 출처, 가상 데이터 표시, 단위를 넣습니다.

from html import escape
name = "<b>Example</b>"
change = 2.0
print(escape(name))
print(f"{change:+.2f}%")
