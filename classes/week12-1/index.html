This session is about where to find the evidence when you fix a working MVP. There are four goals: reproduce a failure with a small fixed input, read a traceback and inspect variable state, write a regression test and fix the cause, and explain why the fix satisfies the requirements. The lab code is market_rules.py, which contains three deliberate defects. You reproduce and diagnose the defects in debug_lab, and fix them one at a time while watching the test results change in debug_fix.

Week 11 MVP review

The market report reads a CSV, analyses the stocks and saves an HTML file. Stock codes stay strings, and prices are validated before any calculation. A missing file is an error; a valid file with only a header is empty data. Even if a run fails, the existing report must be preserved. A feature is only done when both its success and its failure behaviour meet the criteria.

The debugging loop

  1. Reproduce: confirm the same failure with the same command and the same input.
  2. Diagnose: compare the function contract, the traceback and the variable state.
  3. Record: write a failing test that catches the observed defect.
  4. Fix: change only the smallest part that explains the failure.
  5. Re-verify: run the relevant test first, then the full test suite.

For example, for BUG-01 we fix the inputs at 100 and 110 and check that both the corrected formula and the test satisfy the +10% contract.

Three kinds of errors

  • Syntax error: Python cannot parse the code.
  • Runtime exception: some operation fails while the program is running.
  • Logic bug: the program runs but returns a wrong result.

From 100 to 110 should be +10%. A result near +9.09% is a logic bug. When a test fails, the cause can be in the code, the data or the test itself.

Bug report

Record the command you ran, the environment and the exact input, and keep the expected behaviour separate from the actual behaviour. Take the expected value from the requirements, not from what the implementation produces. The lab uses made-up data for the class.

BUG-01 / daily percentage change
Input:    previous_close=100, close=110
Expected: 10.0
Observed: 9.090909...

The worksheet debugging-report.md (in the file list of the lab pages) has a form to fill in for each bug: the related requirement, the command and minimal input, the expected and actual results, the last line of the traceback or the failed assertion, your hypothesis and the variable values you checked, the function you fixed and why, and the test results before and after the fix.

Reading a traceback

  • Start with the last line: the exception type and message.
  • Find the last operation that failed in your own code.
  • Go back up through the callers to see how the value got there.
  • Where the failure happens and its root cause can be different.

A traceback across two calls

Traceback (most recent call last):
  File "debug_empty.py", line 2, in <module>
    summarize([])
  File "market_rules.py", line 18, in summarize
    return {"count": len(changes),
            "mean": sum(changes) / len(changes)}
ZeroDivisionError: division by zero

The last line tells you the failed operation is a division by zero. The function frame shows that changes is empty, so len(changes) is 0. The caller frame shows that the reproduction script passed an empty list. But according to the contract, an empty list is a valid input. So we fix the summary function, not the caller, and keep this case as a test.

Hypothesis and confirmation

Observation: the computed increase is smaller than expected. Hypothesis: it divides by the current price instead of the previous price. Check the numerator and the denominator separately, and compare with the hand calculation (110 − 100) / 100 × 100 = 10. The principle: confirm the cause with evidence, then fix one thing at a time.

Checking state with print

previous_close, close = 100, 110
print("difference:", close - previous_close)
print("previous:", previous_close, "current:", close)

Check the types as well as the values. Remove the temporary debugging output after the fix.

Verifying with unittest

import unittest
from market_rules import change_pct

class ChangeTests(unittest.TestCase):
    def test_increase(self):
        self.assertAlmostEqual(change_pct(100, 110), 10.0)

Write it in the order: prepare the input, call the function, assert the result. Use approximate comparison for floating-point results. Default test discovery looks for files named test*.py.

Arrange, act, assert

def test_increase(self):
    # Arrange: known input and expected answer.
    previous, close = 100, 110
    expected = 10.0
    # Act: call the function once.
    actual = change_pct(previous, close)
    # Assert: check the contract.
    self.assertAlmostEqual(actual, expected)

Decide the expected value 10 first, by hand. If you copy the implementation's formula into the expected value, you may copy its defect along with it.

Choosing the assertion that fits the contract

assertionExampleContract checked
assertEqualcount, 3exact count or order
assertAlmostEqualchange, 10.0a computed float
assertIsNonemeanno mean
assertRaisesValueErrorrejecting invalid input
 
with self.assertRaises(ValueError):
    change_pct(0, 100)

Put the call inside the with block. If no ValueError is raised, or a different exception is raised, the test fails.

Failure, error, regression

  • Failure: an assertion found a difference between the expected and actual values.
  • Error: the test stopped because of an unexpected exception.
  • Regression: after a change, behaviour that used to work is broken.

Before the fix, check that the new test catches the defect; after the fix, run the full test suite to make sure no other behaviour was damaged.

Running one test and reading the result

python3 -m unittest -v test_market_rules.MarketRuleTests.test_empty_summary
python3 -m unittest -v
Ran 5 tests ...
FAILED (failures=3, errors=1)

This is the result for the starter code. Three defects are reported as four problems because the two subTests inside the price test method (100→110 and 100→90) each fail. The empty summary raises an exception before it reaches an assertion, so it counts as an error, not a failure. Focus on fixing one problem, then run everything. The number of tests alone does not tell you whether the verification is sufficient. You can check this output in the first step of debug_lab.

Contracts of the lab functions

  • change_pct: accepts only positive integer prices, excluding bool. Returns the unrounded percentage change.
  • summarize: computes the count and mean of a list of validated numbers. The mean of an empty list is None.
  • rank_changes: sorts validated rows by percentage change descending, then code ascending. Returns a new list and does not change the input.

In this lab the calculation rules are kept separate from file input and output.

Lab A: percentage change

Before fixing, reproduce the wrong result for 100 → 110, check the denominator and record the cause. After correcting the formula, run the rise, fall and unchanged tests. Rounding is done at the output stage, not in the calculation function. Ask yourself: does this test catch the wrong formula, or does it just repeat it?

# Before: wrong reference price.
return (close - previous_close) / close * 100
# After: change relative to the previous price.
return (close - previous_close) / previous_close * 100

Before the fix, the result for 100 to 110 is about 9.09, so the test fails; after the fix, the same test gets 10 and passes. Also check that a fall from 100 to 90 gives -10%. Keep the existing input validation and the parameters of the public function. A fake fix that returns the constant 10 may pass one example but fails the fall and unchanged cases.

Lab B: empty summary

Call summarize([]) and read the traceback. With no observations there is no arithmetic mean. Return a count of 0 and a mean of None. After the fix, also check one element and several elements. An actual mean of 0 must be distinguishable from no data.

summary = {"count": 3, "mean": 0.0}
mean = summary["mean"]
label = "N/A" if mean is None else f"{mean:.2f}%"
print(label)  # 0.00%

[] has count 0 and mean None; [10, -10, 0] has count 3 and an actual mean of 0. if not mean treats both None and 0.0 as false, so check for None explicitly when displaying the no-value state.

Lab C: sorting ties

Sort by percentage change descending; when percentage changes are equal, sort by stock code ascending. Prepare the input in an order different from the expected one, and check that the original list and the row values have not changed.

Input codes:  000003(-1), 000002(+2), 000001(+2)
Output codes: 000001, 000002, 000003

A sort key with two parts

key = lambda row: (-row["change_pct"], row["code"])
Code and changeSort keyFinal position
000003, -1(1, "000003")3
000002, +2(-2, "000002")2
000001, +2(-2, "000001")1

Python compares tuples in ascending order, starting from the first item. Negating the percentage change puts the originally larger values first. When the first items are equal, the second item, the code, decides the order.

A new list with shared row objects

before = [dict(row) for row in rows]
ranked = rank_changes(rows)
self.assertEqual(rows, before)
self.assertIsNot(ranked, rows)

rows.sort() changes the input list; sorted() builds a new list. But the dictionaries in the new list still refer to the original row objects. The lab's contract is not to change the original while sorting; it does not promise a deep copy. Copy each flat row to build a state to compare against. before = rows points to the same object, so it misses any change.

Two extra tests

Pick cases that are not in the provided tests, for example the smallest positive price, a summary of one element, or ranking an empty list. Write down the expected value before running the function, and record the requirement each case checks. Rerun the full test suite after your last fix.

Weak checks and checks that catch defects

# Weak: an empty dictionary would also pass.
self.assertIsNotNone(summarize([]))
# Stronger: verify the agreed empty-state values.
self.assertEqual(summarize([]), {"count": 0, "mean": None})

If you change the implementation to a plausible wrong answer, the test should fail. Ask whether it would catch ascending sorting or missing tie handling. Prepare inputs in the reverse of the expected order so that such mistakes show up. Do not build expected values by calling the function under test.

Reviewing the fix

  • Show the failing input and the relevant code diff.
  • Explain the cause based on values or control flow.
  • Check that you did not delete tests or weaken any check.
  • Consider whether the contract might break for other valid inputs.
  • Record the review in debugging-report.md in the lab folder.

시장 보고서는 CSV를 읽고 종목을 분석한 뒤 HTML을 저장합니다. 종목 코드는 문자열로 유지하고, 계산 전에 가격을 검증합니다. 파일 누락은 오류이고, 헤더만 있는 정상 파일은 빈 데이터입니다. 실행이 실패해도 기존 보고서는 보존해야 합니다. 기능이 완료되었다고 하려면 성공했을 때와 실패했을 때의 동작이 모두 기준을 만족해야 합니다.

디버깅의 반복 과정

  1. 재현: 같은 명령, 같은 입력으로 같은 실패를 확인한다.
  2. 진단: 함수 계약, traceback, 변수 상태를 비교한다.
  3. 기록: 관찰한 결함을 잡아내는 실패 테스트를 만든다.
  4. 수정: 실패 원인을 설명하는 최소한의 부분만 고친다.
  5. 재검증: 해당 테스트를 먼저, 전체 테스트를 나중에 실행한다.

예를 들어 BUG-01은 입력 100과 110을 고정해 두고, 고친 식과 테스트가 모두 +10%라는 계약을 만족하는지 확인합니다.

오류의 세 가지 유형

  • 문법 오류: 파이썬이 코드를 해석할 수 없다.
  • 실행 중 예외: 실행 도중 어떤 연산이 실패한다.
  • 논리 버그: 실행은 되지만 잘못된 결과를 반환한다.

100에서 110이면 +10%여야 합니다. +9.09% 근처의 결과가 나온다면 논리 버그입니다. 테스트가 실패했을 때 원인은 코드, 데이터, 테스트 중 어디에나 있을 수 있습니다.

Traceback 읽기

  • 마지막 줄에서 예외 유형과 메시지를 먼저 확인한다.
  • 자신의 코드에서 실패한 마지막 연산을 찾는다.
  • 호출자를 거슬러 올라가 값이 전달된 경로를 확인한다.
  • 실패한 위치와 근본 원인은 다를 수 있다.

두 호출에 걸친 traceback

Traceback (most recent call last):
  File "debug_empty.py", line 2, in <module>
    summarize([])
  File "market_rules.py", line 18, in summarize
    return {"count": len(changes),
            "mean": sum(changes) / len(changes)}
ZeroDivisionError: division by zero

마지막 줄은 실패한 연산이 0으로 나누기라는 것을 알려 줍니다. 함수 프레임을 보면 changes가 비어 있어 len(changes)가 0입니다. 호출자 프레임을 보면 재현 스크립트가 빈 목록을 넘겼습니다. 그런데 계약에 따르면 빈 목록은 유효한 입력입니다. 따라서 호출자가 아니라 요약 함수를 고치고, 이 상태를 테스트로 남깁니다.

가설과 확인

관찰: 계산된 상승률이 기대값보다 작다. 가설: 이전 가격 대신 현재 가격으로 나누고 있다. 분자와 분모를 각각 확인하고, 손으로 계산한 (110 − 100) / 100 × 100 = 10과 비교합니다. 원칙은 증거로 원인을 확인한 뒤 한 가지씩 고치는 것입니다.

가격 0과 1처럼 허용 여부가 바뀌는 지점을 고릅니다. bool은 int의 하위 클래스이므로 True도 별도 사례로 확인합니다.

unittest로 검증하기

import unittest
from market_rules import change_pct

class ChangeTests(unittest.TestCase):
    def test_increase(self):
        self.assertAlmostEqual(change_pct(100, 110), 10.0)

입력 준비, 함수 호출, 결과 단언 순서로 씁니다. 부동소수점 결과에는 근사 비교를 씁니다. 기본 자동 탐색은 test*.py 이름의 파일을 찾습니다.

입력 준비·실행·결과 단언

def test_increase(self):
    # Arrange: known input and expected answer.
    previous, close = 100, 110
    expected = 10.0
    # Act: call the function once.
    actual = change_pct(previous, close)
    # Assert: check the contract.
    self.assertAlmostEqual(actual, expected)

기대값 10은 손으로 계산해 먼저 정합니다. 구현의 계산식을 기대값에 복사하면 같은 결함을 함께 복사할 수 있습니다.

계약에 맞는 assertion 고르기

assertion예시확인할 계약
assertEqualcount, 3정확한 개수·순서
assertAlmostEqualchange, 10.0계산한 실수
assertIsNonemean평균 없음
assertRaisesValueError잘못된 입력 거절
 
with self.assertRaises(ValueError):
    change_pct(0, 100)

호출은 with 블록 안에 넣습니다. ValueError가 나지 않거나 다른 예외가 나면 테스트가 실패합니다.

실패·오류·회귀

  • 실패(Failure): assertion이 기대값과 실제값의 차이를 발견했다.
  • 오류(Error): 예상하지 않은 예외로 테스트가 중단됐다.
  • 회귀(Regression): 변경 뒤에 기존에 되던 동작이 깨졌다.

고치기 전에 새 테스트가 해당 결함을 발견하는지 확인하고, 고친 뒤에는 전체 테스트로 다른 동작이 손상되지 않았는지 확인합니다.

테스트 하나 실행하고 결과 읽기

python3 -m unittest -v

시작 코드의 결과입니다. 결함 세 개가 문제 네 건으로 보고되는 이유는, 가격 테스트 메서드 안의 subTest 두 개(100→110, 100→90)가 각각 실패하기 때문입니다. 빈 요약은 assertion에 닿기 전에 예외가 나므로 실패가 아니라 오류로 셉니다. 한 문제를 집중해서 고친 뒤 전체를 실행합니다. 테스트 개수만으로 검증이 충분한지 판단할 수는 없습니다. debug_lab의 첫 단계에서 이 출력을 확인합니다.

실습 함수의 계약

  • change_pct: 양의 정수 가격만 허용하며 bool은 제외한다. 반올림하지 않은 등락률을 반환한다.
  • summarize: 검증된 숫자 목록에서 개수와 평균을 구한다. 빈 목록의 평균은 None이다.
  • rank_changes: 검증된 행을 등락률 내림차순, 코드 오름차순으로 정렬한다. 새 목록을 반환하고 입력을 바꾸지 않는다.

이 실습에서는 계산 규칙을 파일 입출력과 분리합니다.

실습 A: 등락률 계산

고치기 전에 100 → 110의 잘못된 결과를 재현하고, 분모를 확인해 원인을 기록합니다. 식을 고친 뒤 상승·하락·보합 테스트를 실행합니다. 반올림은 계산 함수가 아니라 출력 단계에서 합니다. 이 테스트가 잘못된 식을 잡아내는지, 아니면 그대로 반복하는지 물어봅니다.

# Before: wrong reference price.
return (close - previous_close) / close * 100
# After: change relative to the previous price.
return (close - previous_close) / previous_close * 100

고치기 전에는 100에서 110의 결과가 약 9.09라 테스트가 실패하고, 고친 뒤에는 같은 테스트에서 10을 반환해 통과합니다. 100에서 90으로 떨어지면 -10%인지도 확인합니다. 기존 입력 검증과 공개 함수의 인자 형식은 유지합니다. 상수 10을 반환하는 가짜 수정은 한 예제를 통과해도 하락·보합 사례에서 실패합니다.

실습 B: 빈 요약

summarize([])를 호출하고 traceback을 읽습니다. 관측값이 없으면 산술평균도 없습니다. 개수는 0, 평균은 None으로 반환합니다. 고친 뒤 원소가 한 개일 때와 여러 개일 때도 확인합니다. 실제 평균 0과 데이터 없음은 구별할 수 있어야 합니다.

summary = {"count": 3, "mean": 0.0}
mean = summary["mean"]
label = "N/A" if mean is None else f"{mean:.2f}%"
print(label)  # 0.00%

[]는 개수 0, 평균 None이고, [10, -10, 0]은 개수 3, 실제 평균 0입니다. if not mean은 None과 0.0을 모두 거짓으로 판단하므로, 값이 없는 상태를 표시할 때는 None을 명시적으로 확인합니다.

실습 C: 동률 정렬

등락률은 내림차순, 등락률이 같으면 종목 코드 오름차순입니다. 기대 순서와 다른 순서로 입력을 준비하고, 원래 목록과 행의 값이 바뀌지 않았는지 확인합니다.

Input codes:  000003(-1), 000002(+2), 000001(+2)
Output codes: 000001, 000002, 000003

두 항목으로 된 정렬 키

key = lambda row: (-row["change_pct"], row["code"])
코드와 등락률정렬 키최종 위치
000003, -1(1, "000003")3
000002, +2(-2, "000002")2
000001, +2(-2, "000001")1

파이썬은 튜플을 앞 항목부터 오름차순으로 비교합니다. 등락률에 음수를 붙이면 원래 큰 값이 먼저 옵니다. 첫 항목이 같을 때는 두 번째 항목인 코드가 순서를 정합니다.

새 목록과 공유되는 행 객체

before = [dict(row) for row in rows]
ranked = rank_changes(rows)
self.assertEqual(rows, before)
self.assertIsNot(ranked, rows)

rows.sort()는 입력 목록을 바꾸고, sorted()는 새 목록을 만듭니다. 하지만 새 목록 안의 딕셔너리는 여전히 원래 행 객체를 가리킵니다. 실습의 계약은 정렬하는 동안 원본을 바꾸지 않는 것이지 깊은 복사를 보장하는 것이 아닙니다. 평평한 행을 하나씩 복사해 비교용 상태를 만듭니다. before = rows는 같은 객체를 가리키므로 변경을 놓칩니다.

세 결함을 sed로 하나씩 고치며 실패 수가 3+1 → 1+1 → 1 → 0으로 줄어드는 과정과 최종 diff는 debug_fix에 있습니다. 실습에서는 nano market_rules.py로 직접 고칩니다.

추가 테스트 두 개

제공된 테스트에 없는 사례를 고릅니다. 예를 들어 최소 양의 가격, 원소 한 개의 요약, 빈 순위입니다. 함수를 실행하기 전에 기대값을 먼저 적고, 각 사례가 확인하는 요구사항을 기록합니다. 마지막 수정 뒤에 전체 테스트를 다시 실행합니다.

약한 검사와 결함을 잡는 검사

# Weak: an empty dictionary would also pass.
self.assertIsNotNone(summarize([]))
# Stronger: verify the agreed empty-state values.
self.assertEqual(summarize([]), {"count": 0, "mean": None})

구현을 그럴듯한 오답으로 바꾸면 테스트가 실패해야 합니다. 오름차순으로 정렬하거나 동률 처리를 빼면 잡아낼 수 있는지 물어봅니다. 이런 실수가 드러나도록 기대 순서와 반대인 입력도 준비합니다. 기대값을 검사 대상 함수를 호출해서 만들지 않습니다.
