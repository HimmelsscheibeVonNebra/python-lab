ACT 1 · Change rows: UPDATE and DELETE

Two statements that can ruin a table in one line. UPDATE changes values in rows that already exist, and DELETE removes rows. Both act on every row that WHERE selects; with no WHERE, every row is affected.

UPDATE with WHERE

UPDATE = """
    UPDATE quotes SET close = ?
    WHERE code = ?
"""
cur = con.execute(UPDATE, (72000, "005930"))
print(cur.rowcount)
cur = con.execute(UPDATE, (72000, "999999"))
print(cur.rowcount)
1
0

SET names the column and its new value, and WHERE chooses the rows, as in SELECT. rowcount is the number of rows changed. Trap: a wrong code is not an error. It changes 0 rows, silently.

The WHERE you forgot

cur = con.execute("DELETE FROM quotes")
print(cur.rowcount)
print(con.execute(count).fetchone())
con.rollback()
print(con.execute(count).fetchone())
5
(0,)
(5,)

One short line, and five rows are gone. Nothing was committed yet, so rollback() undoes it. It also undoes the earlier 72000 update. Before deleting, first run a SELECT with the same WHERE. The second step of sql_changes shows everything from the UPDATE to the rollback in one go.

ACT 2 · Summarize: count and group

Ask for the answer, not for the rows. Aggregate functions turn many rows into one value, and GROUP BY gives one answer per group. The loop you wrote in Week 4 becomes one line of SQL.

COUNT, SUM, MAX, AVG

query = """
    SELECT COUNT(*), SUM(volume),
           MAX(close), AVG(close)
    FROM quotes
"""
print(con.execute(query).fetchone())
(5, 2100000, 200000, 124280.0)

Four questions, one row back. COUNT(*) counts rows; SUM and AVG need a numeric column. AVG returns a REAL even for INTEGER columns.

GROUP BY: one row per market

query = """
    SELECT market, COUNT(*), SUM(volume)
    FROM quotes
    GROUP BY market
    ORDER BY market
"""
('KOSDAQ', 2, 300000)
('KOSPI', 3, 1800000)

Split the rows by market, then aggregate each group. Rows with the same market fall into one group. Every selected column must be the group column or an aggregate. ORDER BY still applies to the result. Trap: if you SELECT name with GROUP BY market, which name comes out? Do not ask for it.

Where should the rule live?

query = """
    SELECT SUM(close > previous_close),
           SUM(close < previous_close),
           SUM(close = previous_close)
    FROM quotes
"""
(2, 2, 1)

SQL can count up, down and flat, and so can summarize(). A comparison is 1 when true and 0 when false, so the SUM of a comparison counts the rows where it holds. The answer matches summarize(). But each rule should have one home, and ours is logic.py, with its tests. SQL fetches rows.

ACT 3 · Transactions: all or nothing

A transaction is a group of changes that succeed together or are cancelled together. It starts with the first change; commit() keeps all of it, and rollback() discards all of it. There is no state in between.

Half a snapshot is worse than none

Suppose tomorrow's file has a bad row in the middle. Committing row by row leaves a table nobody asked for, and the report would mix two days yet look correct. Grouping everything in one transaction keeps yesterday's rows instead. This is the Week 12 rule again: on failure, keep the old result.

Two new rows, one of them bad

INSERT = """
    INSERT INTO quotes
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""
new_rows = [
    ("2026-11-06", "005930", "삼성전자",
     "KOSPI", 71400, 72100, 900000),
    ("2026-11-06", "000660", "SK하이닉스",
     "KOSPI", 198000, 0, 450000),
]

The first row is valid; the second has close 0, so the CHECK must refuse it. After the failure, how many rows does the table hold: 5, 6 or 7?

with con: commit or roll back

try:
    with con:
        con.executemany(INSERT, new_rows)
except sqlite3.IntegrityError as error:
    print(error)
print(con.execute(count).fetchone())
CHECK constraint failed: close > 0
(5,)

The with block is the transaction. If the block ends normally, it commits; if it raises, it rolls back and the exception continues. Row 1 was inserted, then taken back together with row 2. Trap: with con does not close the connection; it only ends the transaction. sql_changes runs this code side by side with, for comparison, committing row by row, which ends at (6,).

ACT 4 · Swap the storage layer

You now have every piece the swap needs. SELECT with dict(row) reads quotes, and with con with executemany replaces a snapshot safely. Keep the same promises to the callers and replace only the machinery inside.

  • connect() and init_db() open and prepare the file.
  • replace_quotes() stores a validated snapshot.
  • load_quotes() returns the same dicts as before.
  • read_csv() is the old reader, kept for importing.

Open storage.py in the example folder and find these four names (it is in the file list on the lab page).

load_quotes(): before and after

# BEFORE
def load_quotes(path):
    with open(path, encoding="utf-8-sig",
              newline="") as stream:
        reader = csv.DictReader(stream)
        return [parse_row(r) for r in reader]

# AFTER
def load_quotes(con):
    query = "SELECT * FROM quotes ORDER BY code"
    return [dict(r) for r in con.execute(query)]

The caller still receives a list of quote dicts. Before, it opened a file and parsed every row; after, it asks the table and converts each row. Validation already happened when the rows were stored. The old function is not deleted; it becomes read_csv().

Rows become the dicts logic.py expects

con.row_factory = sqlite3.Row
query = "SELECT * FROM quotes ORDER BY code"

for key, value in quotes[0].items():
    print(f"{key:<15}{value!r}")

code           '000660'

The keys are the column names, in table order. code is still text, with its leading zeros. Prices and volume are int, so no int() calls are needed. analyze() and summarize() accept these rows unchanged.

replace_quotes(): one transaction

def replace_quotes(con, quotes):
    rows = [tuple(q[f] for f in FIELDS)
            for q in quotes]
    with con:
        con.execute("DELETE FROM quotes")
        con.executemany(INSERT, rows)

Deleting the old snapshot and inserting the new one happen together. FIELDS fixes the column order, the same as the CSV header. A failure inside with con restores the old rows, and the IntegrityError still reaches the caller. main.py catches sqlite3.Error next to ValueError and prints one message.

Testing with an in-memory database

class StorageTests(unittest.TestCase):
    def setUp(self):
        self.con = connect(":memory:")
        init_db(self.con)

    def test_failed_replace_keeps_rows(self):
        replace_quotes(self.con, QUOTES)
        bad = [dict(QUOTES[0], close=0)]
        with self.assertRaises(
                sqlite3.IntegrityError):
            replace_quotes(self.con, bad)
        self.assertEqual(
            len(load_quotes(self.con)), 5)

":memory:" is a database with no file, created fresh for every test. setUp builds an empty table in an instant, and tests cannot damage your real market.db. One round-trip test checks storing and loading at once. This is why connect() takes the path as a parameter.

완료 기준: 같은 테스트, 새 저장소

SQLite를 아는 모듈은 하나뿐이어야 합니다. logic.py와 report.py는 한 줄도 바뀌지 않습니다. storage.py는 연결(connection)을 중심으로 다시 씁니다. main.py는 연결을 열고 넘기는 몇 줄만 바뀝니다. 12주차의 계약은 교체 뒤에도 유지됩니다.

ACT 1 · 행 바꾸기: UPDATE와 DELETE

한 줄로 테이블을 망칠 수 있는 두 문장입니다. UPDATE는 이미 있는 행의 값을 바꾸고, DELETE는 행을 지웁니다. 둘 다 WHERE가 고른 모든 행에 적용되며, WHERE가 없으면 모든 행이 대상입니다.

WHERE가 있는 UPDATE

UPDATE = """
    UPDATE quotes SET close = ?
    WHERE code = ?
"""
cur = con.execute(UPDATE, (72000, "005930"))
print(cur.rowcount)
cur = con.execute(UPDATE, (72000, "999999"))
print(cur.rowcount)
1
0

SET에 열 이름과 새 값을 쓰고, WHERE는 SELECT에서처럼 행을 고릅니다. rowcount는 바뀐 행의 수입니다. 함정: 틀린 코드는 오류가 아닙니다. 조용히 0행을 바꿉니다.

잊어버린 WHERE

cur = con.execute("DELETE FROM quotes")
print(cur.rowcount)
print(con.execute(count).fetchone())
con.rollback()
print(con.execute(count).fetchone())
5
(0,)
(5,)

짧은 한 줄에 다섯 행이 사라집니다. 아직 커밋하지 않았으므로 rollback()으로 되돌립니다. 앞의 72000 수정도 함께 되돌아갑니다. 지우기 전에 같은 WHERE로 SELECT를 먼저 실행해 봅니다. sql_changes의 둘째 단계가 UPDATE부터 rollback까지를 한 번에 보여 줍니다.

ACT 2 · 요약하기: 세고 묶기

행이 아니라 답을 요청합니다. 집계 함수는 여러 행을 값 하나로 만들고, GROUP BY는 그룹마다 답 하나를 줍니다. 4주차에 쓰던 반복문이 SQL 한 줄이 됩니다.

COUNT, SUM, MAX, AVG

query = """
    SELECT COUNT(*), SUM(volume),
           MAX(close), AVG(close)
    FROM quotes
"""
print(con.execute(query).fetchone())
(5, 2100000, 200000, 124280.0)

질문 네 개에 행 하나가 돌아옵니다. COUNT(*)는 행을 세고, SUM과 AVG에는 숫자 열이 필요합니다. AVG는 INTEGER 열에서도 REAL을 돌려줍니다.

GROUP BY: 시장마다 한 행

query = """
    SELECT market, COUNT(*), SUM(volume)
    FROM quotes
    GROUP BY market
    ORDER BY market
"""
('KOSDAQ', 2, 300000)
('KOSPI', 3, 1800000)

행을 시장별로 나눈 뒤 묶음마다 집계합니다. market이 같은 행들이 한 그룹이 됩니다. SELECT의 열은 그룹 열이거나 집계 함수여야 합니다. 결과에도 ORDER BY를 쓸 수 있습니다. 함정: GROUP BY market에 SELECT name을 쓰면 어느 name이 나올까요? 그런 것은 요청하지 않습니다.

규칙은 어디에 둘까?

query = """
    SELECT SUM(close > previous_close),
           SUM(close < previous_close),
           SUM(close = previous_close)
    FROM quotes
"""
(2, 2, 1)

SQL도 상승·하락·보합을 셀 수 있고, summarize()도 셉니다. 비교식은 참이면 1, 거짓이면 0이므로 비교식의 SUM은 조건이 참인 행의 수입니다. 답은 summarize()와 같습니다. 하지만 규칙의 집은 한 곳이어야 하고, 우리는 테스트가 있는 logic.py로 정했습니다. SQL은 행을 가져옵니다.

ACT 3 · 트랜잭션: 전부 아니면 전무

트랜잭션은 함께 성공하거나 함께 취소되는 변경의 묶음입니다. 첫 변경과 함께 시작되고, commit()은 전부를 확정하고, rollback()은 전부를 버립니다. 그 중간 상태는 없습니다.

반쪽짜리 스냅숏은 없는 것보다 나쁘다

내일 받은 파일의 한가운데에 잘못된 행이 있다고 해 봅시다. 행마다 커밋하면 아무도 원하지 않은 테이블이 남고, 보고서에 이틀 치가 섞이는데도 정상처럼 보입니다. 트랜잭션 하나로 묶으면 어제의 행이 그대로 남습니다. 실패하면 기존 결과를 보존한다는 12주차의 규칙과 같습니다.

새 행 둘, 그중 하나는 불량

INSERT = """
    INSERT INTO quotes
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""
new_rows = [
    ("2026-11-06", "005930", "삼성전자",
     "KOSPI", 71400, 72100, 900000),
    ("2026-11-06", "000660", "SK하이닉스",

첫째 행은 정상이고 둘째 행은 close가 0이라 CHECK가 거절해야 합니다. 실패한 뒤 테이블의 행은 5, 6, 7개 중 몇 개일까요?

with con: 커밋 또는 롤백

try:

with 블록이 곧 트랜잭션입니다. 블록이 정상적으로 끝나면 커밋하고, 예외가 나면 롤백한 뒤 예외를 다시 전달합니다. 1행은 들어갔다가 2행과 함께 취소됐습니다. 함정: with con은 연결을 닫지 않고 트랜잭션만 끝냅니다. sql_changes에서는 이 코드와, 비교를 위해 행마다 커밋해서 (6,)이 되는 경우를 나란히 실행합니다.

ACT 4 · 저장 계층 교체하기

교체에 필요한 조각은 이제 모두 있습니다. SELECT와 dict(row)로 quotes를 읽고, with con과 executemany로 스냅숏을 안전하게 교체합니다. 호출하는 쪽과의 약속은 그대로 두고 안쪽 장치만 새로 바꿉니다.

  • connect()와 init_db()가 파일을 열고 준비한다.
  • replace_quotes()가 검증된 스냅숏을 저장한다.
  • load_quotes()는 전과 같은 dict를 돌려준다.
  • read_csv()는 예전 읽기 함수다. 가져오기용으로 남긴다.

예제 폴더의 storage.py를 열어 이 네 이름을 찾아봅니다(실습 페이지의 파일 목록에 있습니다).

키는 열 이름이고 순서는 테이블의 열 순서입니다. code는 여전히 글자이고 앞자리 0이 남아 있습니다. 가격과 거래량은 int이므로 int()를 부를 필요가 없습니다. analyze()와 summarize()가 이 행을 그대로 받습니다.

replace_quotes(): 트랜잭션 하나

def replace_quotes(con, quotes):
    rows = [tuple(q[f] for f in FIELDS)
            for q in quotes]
    with con:
        con.execute("DELETE FROM quotes")
        con.executemany(INSERT, rows)

기존 스냅숏 삭제와 새 스냅숏 삽입을 함께 처리합니다. FIELDS가 CSV 헤더와 같은 열 순서를 정합니다. with con 안에서 실패하면 기존 행이 복구되고, IntegrityError는 호출한 쪽으로 그대로 전달됩니다. main.py는 ValueError 옆에서 sqlite3.Error도 잡아 메시지 하나를 출력합니다.

메모리 데이터베이스로 테스트하기

class StorageTests(unittest.TestCase):
    def setUp(self):
        self.con = connect(":memory:")
        init_db(self.con)

    def test_failed_replace_keeps_rows(self):
        replace_quotes(self.con, QUOTES)
        bad = [dict(QUOTES[0], close=0)]
        with self.assertRaises(
                sqlite3.IntegrityError):
            replace_quotes(self.con, bad)
        self.assertEqual(
            len(load_quotes(self.con)), 5)

":memory:"는 파일이 없는 데이터베이스이며 테스트마다 새로 만듭니다. setUp이 빈 테이블을 순식간에 만들고, 테스트가 실제 market.db를 망가뜨릴 수 없습니다. 왕복 테스트 하나로 저장과 조회를 함께 확인합니다. connect()가 경로를 매개변수로 받는 이유가 이것입니다.

실습: 내 저장소 교체하기

34분 동안 진행하며, 테스트가 안전망입니다. 고치기 전에 테스트 18개를 실행해 통과에서 시작하고, 같은 테스트에 내 테스트를 더해 통과로 끝냅니다.

  • A: 테스트를 실행한다. OK가 나와야 한다.
  • B: load_quotes()에 선택 매개변수 market을 추가한다. "ALL"이면 모든 행, 아니면 WHERE와 ?로 고른 행. market 없이 부르는 load_quotes(con)도 계속 동작해야 한다.
  • C: ":memory:"로 테스트한다. KOSPI는 3행, ALL은 5행, 인자 없이 5행.
  • D: 내 프로젝트. schema.sql에 테이블 하나, 저장·조회 함수 하나씩. 값은 ?로 넘긴다.

이 가상 머신에서는 nano storage.py, nano test_market.py로 고치고 python3 -m unittest로 확인합니다.

내 프로젝트: 테이블 하나

CREATE TABLE을 쓰기 전에 네 가지에 답합니다. 내 프로젝트에서 한 행은 무엇인가? 어떤 열이 있고 각각 TEXT, INTEGER, REAL 중 무엇인가? 어떤 열이 기본 키가 되는가? 테이블이 거절해야 하는 값은 무엇인가? 모든 프로젝트에 데이터베이스가 필요하지는 않습니다. CSV로 충분하면 그 이유를 적습니다.
