create_db ~/week13/examples/sqlite_lab

Create the table with CREATE TABLE IF NOT EXISTS from schema.sql, insert the five rows of prices.csv in one go with a seven-? INSERT and executemany, then commit. It is safe to run again (it deletes and reloads). Then observe, in turn, the limits of file storage, what happens when you forget commit, and constraint violations.schema.sql의 CREATE TABLE IF NOT EXISTS로 테이블을 만들고, prices.csv 다섯 행을 ? 일곱 개짜리 INSERT와 executemany로 한 번에 넣은 뒤 commit한다. 다시 실행해도 안전하다(DELETE 후 다시 적재). 이어서 파일 저장의 한계, commit을 잊었을 때, 제약 조건 위반을 차례로 관찰한다.

Steps실행 순서

  1. python3 -c 'import sqlite3; print("sqlite", sqlite3.sqlite_version)'

    sqlite3 is part of the standard library, so there is nothing to install. No server, no login: one file is the whole database. This virtual machine has no sqlite3 command-line shell, so all SQL is run from Python.sqlite3는 표준 라이브러리에 들어 있어 설치할 것이 없다. 서버도 로그인도 없이 파일 하나가 데이터베이스 전체다. 이 가상 머신에는 sqlite3 명령줄 셸이 없으므로 모든 SQL을 파이썬에서 실행한다.

  2. python3 - <<'EOF' import csv rows = list(csv.DictReader(open("prices.csv", encoding="utf-8"))) kospi = [r for r in rows if r["market"] == "KOSPI"] print(len(rows), len(kospi)) print(type(rows[0]["close"])) EOF

    What a CSV cannot do: every question means reading all the rows and looping (5 3). Even prices arrive as <class 'str'>. Nothing stops a duplicate row or a missing price.CSV가 못 하는 일: 질문할 때마다 모든 행을 읽고 반복문을 돈다(5 3). 가격도 <class 'str'>로 들어온다. 중복 행이나 빠진 가격도 막아 주지 않는다.

  3. python3 - <<'EOF' from pathlib import Path f = Path("/tmp/balance.txt") f.write_text("100") a = int(f.read_text()) b = int(f.read_text()) f.write_text(str(a - 50)) f.write_text(str(b - 50)) print("saved:", f.read_text(), "expected: 0") EOF

    Two users, one file: both read 100 before the other saves, and each saves 50. saved: 50 expected: 0. One withdrawal disappears without any error (a lost update). A file cannot make writers take turns.두 사람, 파일 하나: 둘 다 상대가 저장하기 전에 100을 읽고 각자 50을 저장한다. saved: 50 expected: 0. 오류 없이 인출 한 건이 사라진다(갱신 손실). 파일은 쓰는 순서를 세워 주지 못한다.

  4. cat schema.sql

    Seven columns and their types: date, code, name and market are TEXT; prices in KRW and volume are INTEGER. code must be TEXT so that 005930 does not become 5930. NOT NULL, CHECK (prices > 0, volume >= 0) and PRIMARY KEY (date, code) are the rules the table enforces. code alone cannot be the key, because tomorrow's price for the same stock will arrive too.열 일곱 개와 자료형: 날짜·코드·이름·시장은 TEXT, 원 단위 가격과 거래량은 INTEGER다. code가 TEXT여야 005930이 5930이 되지 않는다. NOT NULL, CHECK(가격 > 0, 거래량 >= 0), PRIMARY KEY (date, code)가 테이블이 지키는 규칙이다. code만으로는 키가 될 수 없다. 내일 같은 종목의 가격이 또 들어오기 때문이다.

  5. rm -f market.db; python3 create_db.py; ls -l market.db

    market.db ready: 5 rows. connect("market.db") created a file that did not exist. A database, too, is in the end an ordinary file on disk.market.db ready: 5 rows. connect("market.db")가 없던 파일을 새로 만들었다. 데이터베이스도 결국 디스크의 평범한 파일이다.

  6. python3 create_db.py

    The second run does not fail either, and it is still 5 rows. IF NOT EXISTS leaves the existing table alone, and DELETE FROM quotes empties it before inserting again.두 번째 실행도 실패하지 않고 여전히 5 rows다. IF NOT EXISTS가 이미 있는 테이블을 그대로 두고, DELETE FROM quotes로 비운 뒤 다시 넣기 때문이다.

  7. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") print(con.execute("SELECT typeof(code), code, typeof(close), close FROM quotes").fetchone()) EOF

    Every value read from the CSV was a string, but the INTEGER column stored "71400" as the number 71400 (integer), and the TEXT column stored '005930' exactly as written.CSV에서 읽은 값은 모두 문자열이었지만 INTEGER 열은 "71400"을 숫자 71400(integer)으로, TEXT 열은 '005930'을 글자 그대로 저장했다.

  8. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") con.execute("INSERT INTO quotes VALUES (?, ?, ?, ?, ?, ?, ?)", ("2026-11-05", "999999", "Test", "KOSPI", 100, 110, 1)) print("before close:", con.execute("SELECT COUNT(*) FROM quotes").fetchone()) con.close() con = sqlite3.connect("market.db") print("after reopen:", con.execute("SELECT COUNT(*) FROM quotes").fetchone()) EOF

    Forget commit() and the row is lost. Within the same connection it shows (6,), but after closing without commit and reopening it is (5,). No error, no warning. "It worked on my screen" is not "it was saved".commit()을 잊으면 행이 사라진다. 같은 연결 안에서는 (6,)으로 보이지만, commit 없이 close하고 다시 열면 (5,)다. 오류도 경고도 없다. "화면에서는 됐다"와 "저장됐다"는 다른 말이다.

  9. cat > try_insert.py <<'EOF' import sqlite3 con = sqlite3.connect("market.db") INSERT = "INSERT INTO quotes VALUES (?, ?, ?, ?, ?, ?, ?)" row = ("2026-11-05", "000660", "SK하이닉스", "KOSPI", 200000, 198000, 500000) for values in (row, row[:5] + (0, 500000)): try: con.execute(INSERT, values) except sqlite3.IntegrityError as error: print(type(error).__name__, error) print(con.execute("SELECT COUNT(*) FROM quotes").fetchone()) EOF cat try_insert.py python3 try_insert.py

    A script that previews Lab C. Inserting the existing (2026-11-05, 000660) again gives IntegrityError UNIQUE constraint failed: quotes.date, quotes.code; changing close to 0 gives IntegrityError CHECK constraint failed: close > 0. Only the failed statement is cancelled, and the row count stays (5,).실습 C를 미리 보는 스크립트다. 이미 있는 (2026-11-05, 000660)을 한 번 더 넣으면 IntegrityError UNIQUE constraint failed: quotes.date, quotes.code, close를 0으로 바꾸면 IntegrityError CHECK constraint failed: close > 0이다. 실패한 문장만 취소되고 행 수는 (5,) 그대로다.

Run the SELECT examples from the slides to gather what you need for Q2 to Q5. Every value from outside goes in through a ? placeholder.질문 다섯 개 실습의 시작 파일이다. Q1(KOSPI 종목의 이름과 종가, 코드순)만 작성되어 있고 Q2~Q5는 주석으로 질문만 있다. 슬라이드의 SELECT 예제를 실행해 보며 Q2~Q5를 쓸 재료를 모은다. 바깥에서 온 값은 모두 ? 자리표시자로 넘긴다.

Steps실행 순서

  1. [ -f market.db ] || python3 create_db.py; python3 queries.py

    Under Q1 KOSPI stocks you get ('SK하이닉스', 198000), ('삼성전자', 71400), ('NAVER', 200000). The order is not by name but ORDER BY code (000660, 005930, 035420). "KOSPI" is passed not inside the SQL string but as the tuple ("KOSPI",).Q1 KOSPI stocks 아래에 ('SK하이닉스', 198000), ('삼성전자', 71400), ('NAVER', 200000)이 나온다. 이름순이 아니라 ORDER BY code(000660, 005930, 035420) 순서다. "KOSPI"는 SQL 문자열 안이 아니라 ("KOSPI",) 튜플로 전달된다.

  2. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") print(*con.execute("SELECT code, name, close FROM quotes"), sep="\n") EOF

    SELECT picks the columns. Each row comes back as one tuple in the order of the columns you asked for. Without ORDER BY, no order is promised (right now it just happens to look like insertion order).SELECT는 열을 고른다. 행마다 요청한 열 순서의 튜플 하나가 돌아온다. ORDER BY가 없으면 순서는 보장되지 않는다(지금은 넣은 순서로 보일 뿐이다).

  3. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") print(con.execute("SELECT name, close FROM quotes WHERE market = ? AND close >= ?", ("KOSDAQ", 50000)).fetchall()) EOF

    WHERE picks the rows. = compares, and AND combines conditions. The only result is [('에코프로비엠', 103000)]. JYP Ent. is also on KOSDAQ, but its close of 49000 is less than 50000. close is INTEGER, so the comparison is numeric.WHERE는 행을 고른다. 비교는 =이고 AND로 조건을 묶는다. 결과는 [('에코프로비엠', 103000)]뿐이다. JYP Ent.도 KOSDAQ이지만 종가 49000이 50000보다 작다. close가 INTEGER라서 숫자로 비교된다.

  4. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") print(*con.execute("SELECT name, volume FROM quotes ORDER BY volume DESC LIMIT 3"), sep="\n") EOF

    ORDER BY volume DESC sorts largest first and LIMIT 3 keeps only the first three rows: 삼성전자 1000000, SK하이닉스 500000, NAVER 300000. If there are ties, give a second sort column, as in ORDER BY volume DESC, code.ORDER BY volume DESC로 큰 값부터 정렬하고 LIMIT 3으로 앞의 세 행만 남긴다: 삼성전자 1000000, SK하이닉스 500000, NAVER 300000. 동점이 있으면 ORDER BY volume DESC, code처럼 둘째 기준을 준다.

  5. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") q = "SELECT name, (close - previous_close) * 100.0 / previous_close AS change_pct FROM quotes ORDER BY change_pct DESC, code" print(*[f"{pct:+5.1f}% {name}" for name, pct in con.execute(q)], sep="\n") EOF

    Inside SELECT, compute the same formula as change_pct() in logic.py, name it with AS and use it in ORDER BY. The output runs from +3.0% 에코프로비엠 to -2.0% JYP Ent. Each row is unpacked into two variables, name and pct.SELECT 안에서 logic.py의 change_pct()와 같은 식을 계산하고 AS로 이름을 붙여 ORDER BY에 쓴다. +3.0% 에코프로비엠부터 -2.0% JYP Ent.까지 나온다. 각 행을 name, pct 두 변수로 풀어 받았다.

  6. python3 - <<'EOF' import sqlite3 con = sqlite3.connect(":memory:") print(con.execute("SELECT 7 / 2, 7 * 1.0 / 2, (71400 - 70000) / 70000").fetchone()) EOF

    Trap: in SQL, integer / integer drops the decimals. 7 / 2 is 3, 7 * 1.0 / 2 is 3.5, and (71400 - 70000) / 70000, without multiplying by 100.0 first, becomes 0. ":memory:" is a temporary database with no file.함정: SQL에서 정수 / 정수는 소수점을 버린다. 7 / 2는 3, 7 * 1.0 / 2는 3.5이고, 100.0을 먼저 곱하지 않은 (71400 - 70000) / 70000은 0이 된다. ":memory:"는 파일이 없는 임시 데이터베이스다.

  7. python3 - <<'EOF' import sqlite3 con = sqlite3.connect('market.db') market = "KOSPI' OR '1'='1" bad = f"SELECT COUNT(*) FROM quotes WHERE market = '{market}'" print(bad) print(con.execute(bad).fetchone()) print(con.execute('SELECT COUNT(*) FROM quotes WHERE market = ?', (market,)).fetchone()) EOF

    SQL injection: an f-string pastes the input into the SQL text, so the quote inside the input rewrites the condition into OR '1'='1'. Reading the printed SQL shows why you get (5,), that is, every row. With ?, the input is only ever a value, and there is no market with that name, so the result is (0,).SQL 인젝션: f-string은 입력을 SQL 문장 안에 붙여 넣으므로 입력 속 따옴표가 조건을 OR '1'='1'로 바꿔 쓴다. 출력된 SQL을 읽어 보면 (5,), 즉 모든 행이 나온 이유가 보인다. ? 를 쓰면 입력은 언제나 값일 뿐이어서 그런 시장 이름은 없으므로 (0,)이다.

  8. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") con.row_factory = sqlite3.Row row = con.execute("SELECT * FROM quotes WHERE code = ?", ("005930",)).fetchone() print(row["name"], row["close"]) quote = dict(row) print(type(quote["close"]), quote["code"]) EOF

    With sqlite3.Row you get values by column name, as in row["close"] instead of row[2]. You get 삼성전자 71400, and in dict(row) the price is already <class 'int'> while the code stays 005930. This dict is exactly the shape logic.py expects (Session 2).sqlite3.Row를 쓰면 row[2] 대신 row["close"]처럼 열 이름으로 꺼낸다. 삼성전자 71400, 그리고 dict(row)의 가격은 이미 <class 'int'>, 코드는 005930 그대로다. 이 dict가 logic.py가 받는 바로 그 모양이다(2차시).

sql_changes ~/week13/examples/sqlite_lab

Change rows, summarize them and group changes into transactions in Session 1's market.db (five rows in quotes). Each step starts from five clean rows rebuilt by create_db.py.1차시의 market.db(quotes 다섯 행)에서 행을 바꾸고, 요약하고, 트랜잭션으로 묶는다. 각 단계는 create_db.py로 다시 만든 깨끗한 다섯 행에서 출발한다.

Steps실행 순서

  1. python3 create_db.py python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") print(con.execute("SELECT COUNT(*) FROM quotes").fetchone()) print(*con.execute("SELECT code, close FROM quotes"), sep="\n") EOF

    Recap: (5,) and the codes and closing prices of the five stocks. SELECT only asks; it never changes the table.복습: (5,)와 다섯 종목의 코드·종가. SELECT는 묻기만 하고 테이블을 바꾸지 않는다.

  2. python3 - <<'EOF' import sqlite3 con = sqlite3.connect("market.db") U = "UPDATE quotes SET close = ? WHERE code = ?" print(con.execute(U, (72000, "005930")).rowcount) print(con.execute(U, (72000, "999999")).rowcount) print(con.execute("DELETE FROM quotes").rowcount) print(con.execute("SELECT COUNT(*) FROM quotes").fetchone()) con.rollback() print(con.execute("SELECT COUNT(*) FROM quotes").fetchone(), con.execute("SELECT close FROM quotes WHERE code = ?", ("005930",)).fetchone()) EOF

    An UPDATE with WHERE changes one row (1). The wrong code 999999 is not an error; it silently changes 0 rows. A DELETE with a forgotten WHERE deletes all 5 rows, leaving (0,). Nothing has been committed yet, so rollback() brings it back to (5,), and the earlier 72000 update is undone too, so the close is (71400,).WHERE가 있는 UPDATE는 1행을 바꾼다(1). 틀린 코드 999999는 오류가 아니라 조용히 0행이다. import sqlite3

BASE = Path(__file__).resolve().parent

import csv
import os
from pathlib import Path
import sqlite3
import tempfile
from logic import FIELDS, parse_row
 
SCHEMA = Path(__file__).resolve().parent / "schema.sql"
INSERT = """
    INSERT INTO quotes
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""
 
 
def connect(path):
    """Open the database (":memory:" in tests) with rows readable by name."""
    if str(path) != ":memory:":
        Path(path).parent.mkdir(parents=True, exist_ok=True)
    con = sqlite3.connect(path)
    con.row_factory = sqlite3.Row
    return con
 
 
def init_db(con):
    """Create the quotes table if it is missing. Safe to call every run."""
    con.executescript(SCHEMA.read_text(encoding="utf-8"))
 
 
def replace_quotes(con, quotes):
    """Replace the whole snapshot in one transaction: all rows or none.
 
    quotes are typed dicts from parse_row(). A constraint failure raises
    sqlite3.IntegrityError and leaves the previous rows in place.
    """
    rows = [tuple(q[f] for f in FIELDS) for q in quotes]
    with con:
        con.execute("DELETE FROM quotes")
        con.executemany(INSERT, rows)
 
 
def load_quotes(con):
    """Return every stored quote as a dict, in code order. Empty table -> []."""
    query = "SELECT * FROM quotes ORDER BY code"
    return [dict(row) for row in con.execute(query)]
 
 
def read_csv(path):
    """Read UTF-8(-BOM) CSV; reject malformed header/rows with ValueError.
 
    Missing or unreadable files raise OSError. Header-only files return [].
    (This was load_quotes() in the week 11 MVP.)
    """
    with open(path, encoding="utf-8-sig", newline="") as stream:
        reader = csv.DictReader(stream)
        if reader.fieldnames != FIELDS:
            raise ValueError("CSV header must be " + ",".join(FIELDS))
        quotes = []
        for number, row in enumerate(reader, start=2):
            try:
                quotes.append(parse_row(row))
            except ValueError as error:
                raise ValueError(f"CSV row {number}: {error}") from error
    return quotes
 
 
def write_html(path, html):
    """Replace output only after a complete UTF-8 write; raise OSError on failure."""
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    temporary = None
    try:
        with tempfile.NamedTemporaryFile(mode="w", encoding="utf-8",
                                         dir=path.parent, delete=False) as stream:
            temporary = Path(stream.name)
            stream.write(html)
        os.replace(temporary, path)
    finally:
        if temporary is not None and temporary.exists():
            temporary.unlink()

"""Pure rules for a single-date classroom snapshot; prices are integer KRW."""
from datetime import date
 
FIELDS = ["date", "code", "name", "market", "previous_close", "close", "volume"]
MARKETS = ("ALL", "KOSPI", "KOSDAQ")
 
 
def parse_row(row):
    """Return a typed quote; raise ValueError for any invalid field. No I/O."""
    if set(row) != set(FIELDS) or any(not isinstance(v, str) for v in row.values()):
        raise ValueError("each row needs exactly seven fields")
    quote = {key: value.strip() for key, value in row.items()}
    day = quote["date"]
    if date.fromisoformat(day).isoformat() != day:
        raise ValueError("date must be YYYY-MM-DD")
    code = quote["code"]
    if len(code) != 6 or not code.isascii() or not code.isdigit():
        raise ValueError("code must be six ASCII digits")
    if not quote["name"] or quote["market"] not in MARKETS[1:]:
        raise ValueError("name and KOSPI/KOSDAQ market are required")
    for field in ("previous_close", "close", "volume"):
        text = quote[field]
        if not text.isascii() or not text.isdigit():
            raise ValueError(f"{field} must be a whole number")
        quote[field] = int(text)
        minimum = 0 if field == "volume" else 1
        if quote[field] < minimum:
            raise ValueError(f"{field} must be >= {minimum}")
    return quote
 
 
def change_pct(previous_close, close):
    """Return unrounded daily percent change; both prices must be positive."""
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    return (close - previous_close) / previous_close * 100
 
 
def analyze(quotes, market):
    """Validate snapshot identity; filter and sort by change desc, then code asc.
 
    Return fresh quote dicts with change_pct. Empty input/selection returns [].
    Mixed dates, duplicate codes or an unknown market raise ValueError.
    quotes must already contain typed, validated values from parse_row().
    """
    if market not in MARKETS:
        raise ValueError("market must be ALL, KOSPI or KOSDAQ")
    if len({q["date"] for q in quotes}) > 1:
        raise ValueError("snapshot must contain one date")
    codes = [q["code"] for q in quotes]
    if len(set(codes)) != len(codes):
        raise ValueError("duplicate code in snapshot")
    rows = [dict(q, change_pct=change_pct(q["previous_close"], q["close"]))
            for q in quotes if market == "ALL" or q["market"] == market]
    return sorted(rows, key=lambda q: (-q["change_pct"], q["code"]))
 
 
def summarize(rows):
    """Return sample count, up/down/flat counts and equal-weight mean (or None)."""
    count = len(rows)
    return {"count": count,
            "up": sum(q["change_pct"] > 0 for q in rows),
            "down": sum(q["change_pct"] < 0 for q in rows),
            "flat": sum(q["change_pct"] == 0 for q in rows),
            "mean": sum(q["change_pct"] for q in rows) / count if count else None}

ACT 0 · Why a database?

Programs forget, but data has to outlive the program. Your phone still shows messages from last year. Where are they kept?

Three places to keep data

  • Variable: fast, but gone when the program ends.
  • File: it survives, but it is only text, so your code has to do all the rest of the work.
  • Database: it survives, and it checks, searches and protects the data.

A database is still files on disk. The difference is the engine that guards them.

The MVP so far

Every run of the MVP starts by reading a text file from the top. storage.py is the only module that touches files; logic.py and report.py never open anything. That separation is why we can change the storage and keep the tests.

You cannot safely edit just one line in the middle of a text file. So you read every row, change one, and write every row back. A crash during the write leaves half a file. In SQL this is one UPDATE statement that changes one row (Session 2).

Real data is shared

A database is the shared memory of an organization. Course sign-up, bank accounts, orders, reservations: many people read and change the same data at the same moment. Everyone must see one correct state, even after a crash. A file helps with none of this: no turns, no undo, no permissions. In Week 14, when Flask turns the MVP into a web app, that web app serves many users at once.

What a database adds

Four jobs you would otherwise have to code yourself if you only used files:

  • Rules: types and constraints refuse bad rows.
  • Questions: SELECT finds the rows. You write no loop.
  • Safe changes: a change is saved completely or not at all.
  • Sharing: several programs can use one database safely.

Today covers rules and questions, Session 2 covers safe changes, and Week 14 covers sharing, with Flask.

CSV or database?

A database is a tool, not an upgrade of CSV. Pick by the job. CSV suits data that is small, read once, opened in Excel or sent to others. A database suits data that changes, gets many questions and has strict rules. Many projects use both: CSV to exchange, a database to keep. Does your project's data change while the program runs?

ACT 1 · Design the table first

A database is a file that knows the rules of its data. When designing, ask four questions. What is one row (one stock on one day)? Which columns are needed, and what type is each one? Which columns identify a row? Which values must never be stored? Ten minutes of design here saves an hour of cleaning data later.

SQLite in one picture

The whole database is one ordinary file. There is no server to install, start or log in to. sqlite3 is part of Python's standard library. The same engine runs inside phones and browsers. You talk to it in SQL, a language for tables. You can check it right now with python3 -c "import sqlite3". The virtual machine in this lab has no sqlite3 command-line shell, so all SQL is run from Python.

Table, row, column, key

  • Table: one kind of thing. Here, quotes.
  • Column: one named value with one type.
  • Row: one record. Here, one stock on one day.
  • Key: the columns that find exactly one row.

Is code alone enough as the key? Think about tomorrow's prices: the same stock gets a new row every day, so code alone is not enough.

Choosing column types

CREATE TABLE quotes (
    date   TEXT,
    code   TEXT,
    name   TEXT,
    market TEXT,
    previous_close INTEGER,
    close  INTEGER,
    volume INTEGER
);

The seven CSV fields become seven typed columns. TEXT is for words, dates and codes, INTEGER for whole numbers (prices in KRW and volume), and REAL for decimals (we store none here). SQL keywords are not case-sensitive; writing them in capitals is a habit. Trap: code is TEXT. Stored as a number, 005930 becomes 5930.

Rules the table enforces

In Week 12, Python did the validation. The table can refuse too.

CREATE TABLE IF NOT EXISTS quotes (
    date   TEXT NOT NULL,
    code   TEXT NOT NULL,
    name   TEXT NOT NULL,
    market TEXT NOT NULL,
    previous_close INTEGER NOT NULL
        CHECK (previous_close > 0),
    close  INTEGER NOT NULL
        CHECK (close > 0),
    volume INTEGER NOT NULL
        CHECK (volume >= 0),
    PRIMARY KEY (date, code)
);
  • NOT NULL: this column may not be empty.
  • CHECK: this condition must hold for every row.
  • PRIMARY KEY (date, code): no two rows share both values.
  • IF NOT EXISTS: running the file twice is safe.

오늘은 테이블 하나, 파일 하나, 질문 다섯 개입니다. 파일만으로는 왜 부족해졌는지 묻고(ACT 0), 파이썬을 쓰기 전에 quotes 테이블을 설계하고(ACT 1), 내장 모듈 sqlite3로 market.db를 열고(ACT 2), CSV 다섯 행을 ? 자리표시자로 안전하게 넣고(ACT 3), SELECT·WHERE·ORDER BY로 질문합니다(ACT 4). 앞의 세 막은 create_db, 질문하기는 queries에서 실행합니다. 다음 차시에는 이 테이블이 MVP의 CSV 읽기를 대신합니다.

ACT 0 · 왜 데이터베이스인가?

프로그램은 잊지만, 데이터는 프로그램보다 오래 남아야 합니다. 휴대폰에는 작년에 주고받은 메시지가 아직 남아 있습니다. 그것은 어디에 저장되어 있을까요?

데이터를 두는 세 곳

  • 변수: 빠르지만 프로그램이 끝나면 사라진다.
  • 파일: 남는다. 하지만 글자일 뿐이라 나머지 일은 모두 내 코드가 해야 한다.
  • 데이터베이스: 남는다. 그리고 데이터를 검사하고, 찾아 주고, 지켜 준다.

데이터베이스도 결국 디스크의 파일입니다. 차이는 그 파일을 지키는 엔진에 있습니다.

지금까지의 MVP

MVP는 실행할 때마다 텍스트 파일을 처음부터 읽습니다. 파일을 만지는 모듈은 storage.py 하나뿐이고, logic.py와 report.py는 아무것도 열지 않습니다. 이렇게 나눠 두었기 때문에 저장 방식을 바꿔도 테스트는 그대로입니다.

CSV가 못 하는 일

import csv
with open("prices.csv", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))
kospi = [r for r in rows
         if r["market"] == "KOSPI"]
print(len(rows), len(kospi))
print(type(rows[0]["close"]))

<class 'str'>

CSV는 글자를 저장할 뿐 스스로 답하지 않습니다. 질문할 때마다 모든 행을 읽고 반복문을 돕니다. 가격을 포함해 모든 값이 str로 들어옵니다. 중복 행이나 빠진 가격도 막아 주지 않습니다.

한 값을 고치려면 파일 전체를

changed = 0
for r in rows:
    if r["code"] == "005930":
        r["close"] = "72000"
        changed += 1
print(changed, "row changed")
print(len(rows), "rows to write back")
1 row changed
5 rows to write back

텍스트 파일은 가운데 한 줄만 안전하게 고칠 수 없습니다. 그래서 전부 읽고, 하나를 고치고, 전부 다시 씁니다. 쓰는 도중에 멈추면 반쪽짜리 파일이 남습니다. SQL에서는 UPDATE 한 문장이 한 행만 바꿉니다(2차시).

진짜 데이터는 여럿이 함께 쓴다

데이터베이스는 조직이 함께 쓰는 기억입니다. 수강 신청, 은행 계좌, 주문, 예약처럼 많은 사람이 같은 데이터를 같은 순간에 읽고 고칩니다. 모두가 장애가 난 뒤에도 하나의 정확한 상태를 봐야 합니다. 파일은 여기서 아무것도 돕지 않습니다. 순서도, 되돌리기도, 권한도 없습니다. 14주차에 Flask가 MVP를 웹 앱으로 만들면, 그 웹 앱은 여러 사용자를 동시에 상대합니다.

두 사람, 파일 하나

from pathlib import Path
f = Path("balance.txt")
f.write_text("100")
a = int(f.read_text())       # user A reads
b = int(f.read_text())       # user B reads
f.write_text(str(a - 50))    # A saves 50
f.write_text(str(b - 50))    # B saves 50
print("saved:", f.read_text(), "expected: 0")

잔액 100에서 두 사람이 같은 순간에 50씩 인출합니다. 둘 다 상대가 저장하기 전에 100을 읽고, 각자 50을 빼서 50을 저장합니다. 오류는 없지만 인출 한 건이 사라집니다. 이것이 갱신 손실입니다. 파일은 쓰는 순서를 세워 주지 못하고, 데이터베이스는 세워 줍니다. create_db에서 이 코드를 실행해 볼 수 있습니다.

데이터베이스가 더해 주는 것

파일만 쓴다면 내가 직접 짜야 하는 네 가지 일입니다.

  • 규칙: 자료형과 제약 조건이 잘못된 행을 거절한다.
  • 질문: SELECT가 행을 찾아 준다. 반복문을 쓰지 않는다.
  • 안전한 변경: 변경은 전부 저장되거나 하나도 저장되지 않는다.
  • 공유: 여러 프로그램이 데이터베이스 하나를 안전하게 함께 쓴다.

오늘은 규칙과 질문, 2차시는 안전한 변경, 14주차는 Flask와 함께 공유를 다룹니다.

CSV인가, 데이터베이스인가?

데이터베이스는 CSV의 상위 버전이 아니라 도구입니다. 일에 맞춰 고릅니다. CSV는 작고, 한 번 읽고, 엑셀로 열어 보고, 남에게 보내는 데이터에 맞습니다. 데이터베이스는 계속 바뀌고, 질문이 많고, 규칙이 엄격한 데이터에 맞습니다. 주고받을 때는 CSV, 보관은 데이터베이스로 둘을 함께 쓰는 프로젝트도 많습니다. 내 프로젝트의 데이터는 프로그램이 실행되는 동안 바뀌나요?

ACT 1 · 테이블부터 설계한다

데이터베이스는 데이터의 규칙을 아는 파일입니다. 설계할 때 네 가지를 묻습니다. 한 행은 무엇인가(어느 날의 한 종목)? 어떤 열이 필요하고 각 열의 자료형은 무엇인가? 어떤 열이 한 행을 구별하는가? 어떤 값은 절대 저장되면 안 되는가? 여기서 설계에 쓴 10분이 나중의 데이터 정리 1시간을 줄입니다.

그림 한 장으로 보는 SQLite

데이터베이스 전체가 평범한 파일 하나입니다. 설치하거나 켜거나 로그인할 서버가 없습니다. sqlite3는 파이썬 표준 라이브러리에 들어 있습니다. 휴대폰과 브라우저 안에서도 같은 엔진이 돕니다. 테이블을 다루는 언어인 SQL로 대화합니다. python3 -c "import sqlite3"로 바로 확인해 볼 수 있습니다. 이 실습의 가상 머신에는 sqlite3 명령줄 셸이 없으므로 모든 SQL은 파이썬에서 실행합니다.

테이블, 행, 열, 키

  • 테이블: 한 종류의 대상. 여기서는 quotes.
  • 열: 이름과 자료형이 정해진 값 하나.
  • 행: 기록 하나. 여기서는 어느 날의 한 종목.
  • 키: 정확히 한 행을 찾아내는 열.

code만으로 키가 될까요? 내일의 가격을 생각해 보면 같은 종목이 날마다 한 행씩 생기므로 code만으로는 부족합니다.

열의 자료형 정하기

CREATE TABLE quotes (
    date   TEXT,
    code   TEXT,
    name   TEXT,
    market TEXT,
    previous_close INTEGER,
    close  INTEGER,
    volume INTEGER
);

CSV의 일곱 필드가 자료형이 있는 일곱 열이 됩니다. TEXT는 글자·날짜·코드, INTEGER는 정수(원 단위 가격과 거래량), REAL은 소수입니다(여기서는 저장하지 않습니다). SQL 키워드는 대소문자를 가리지 않으며 대문자로 쓰는 것이 관례입니다. 함정: code는 TEXT입니다. 숫자로 저장하면 005930이 5930이 됩니다.

테이블이 지키는 규칙

12주차에는 파이썬이 검증했습니다. 테이블도 거절할 수 있습니다.

CREATE TABLE IF NOT EXISTS quotes (
    date   TEXT NOT NULL,
    code   TEXT NOT NULL,
    name   TEXT NOT NULL,
    market TEXT NOT NULL,
    previous_close INTEGER NOT NULL
        CHECK (previous_close > 0),
    close  INTEGER NOT NULL
        CHECK (close > 0),
    volume INTEGER NOT NULL
        CHECK (volume >= 0),
    PRIMARY KEY (date, code)
);
  • NOT NULL: 이 열은 비워 둘 수 없다.
  • CHECK: 모든 행이 이 조건을 만족해야 한다.
  • PRIMARY KEY (date, code): 두 값이 모두 같은 행은 없다.
  • IF NOT EXISTS: 파일을 두 번 실행해도 안전하다.

실습 폴더의 schema.sql이 바로 이 내용입니다.

ACT 2 · 파이썬에서 연결하기

호출 네 개를 학기 내내 이 순서로 씁니다. connect는 파일을 열거나 새로 만들고, execute는 SQL 문장 하나를 보내고, commit은 변경을 확정하고, close는 파일을 놓아줍니다.

데이터베이스 파일 만들기

import sqlite3
from pathlib import Path

schema = Path("schema.sql").read_text()
con = sqlite3.connect("market.db")
con.executescript(schema)
con.commit()
con.close()
print(Path("market.db").exists())
True

실행하면 스크립트 옆에 새 파일이 생깁니다. connect("market.db")는 파일이 없으면 만듭니다. executescript는 schema.sql의 모든 문장을 실행합니다. commit() 전에는 아무것도 확정되지 않습니다. 두 번 실행하면 실패할까요? IF NOT EXISTS 덕분에 실패하지 않습니다.

한 행 INSERT

con = sqlite3.connect("market.db")
con.execute("""
    INSERT INTO quotes VALUES
    ('2026-11-05', '005930', '삼성전자',
     'KOSPI', 70000, 71400, 1000000)
""")
con.commit()
count = "SELECT COUNT(*) FROM quotes"
print(con.execute(count).fetchone())
(1,)

문장 하나에 행 하나, 값은 열 순서대로 씁니다. SQL에서 글자 값은 작은따옴표로 감쌉니다. 삼중 따옴표 문자열을 쓰면 SQL이 읽기 쉽습니다. COUNT(*)는 행 수를 묻고, fetchone()은 한 행을 튜플로 돌려줍니다.

commit()을 잊으면 행이 사라진다

con.execute("""
    INSERT INTO quotes VALUES
    ('2026-11-05', '000660', 'SK하이닉스',
     'KOSPI', 200000, 198000, 500000)
""")
con.close()  # no commit!
con = sqlite3.connect("market.db")
print(con.execute(count).fetchone())
(1,)

두 번째 INSERT는 오류 없이 실행됐지만 그 행은 없습니다. INSERT는 commit() 전까지 대기 상태이고, commit 없이 close하면 대기 중인 변경을 버립니다. 오류도 경고도 없습니다. "화면에서는 됐다"와 "저장됐다"는 다른 말입니다. create_db에서 같은 연결 안에서는 (6,)으로 보이던 행이 다시 열면 (5,)로 돌아가는 것을 확인합니다.

ACT 3 · 데이터를 안전하게 넣기

값은 SQL 문자열 안에 들어가지 않습니다. ?는 값이 들어갈 자리를 표시하고, 값은 파이썬이 튜플로 따로 전달합니다. executemany는 한 문장을 여러 행에 반복합니다. 규칙을 어긴 행은 테이블이 거절합니다.

자리표시자: 값 하나에 ? 하나

INSERT = """
    INSERT INTO quotes
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""
row = ("2026-11-05", "000660", "SK하이닉스",
       "KOSPI", 200000, 198000, 500000)
con.execute(INSERT, row)
con.commit()
print(con.execute(count).fetchone())
(2,)

SQL 문장은 그대로 두고 값만 바꿉니다. 열이 일곱 개이므로 물음표도 일곱 개이고, 두 번째 인자는 값을 담은 튜플입니다. ?에는 따옴표를 붙이지 않습니다. 글자와 숫자는 sqlite3가 처리합니다. 문장은 상수에 담아 두고 다시 씁니다.

executemany: CSV 적재

import csv
with open("prices.csv", encoding="utf-8") as f:
    rows = [tuple(r.values())
            for r in csv.DictReader(f)]

con.execute("DELETE FROM quotes")
con.executemany(INSERT, rows)
con.commit()
print(con.execute(count).fetchone())
(5,)

다섯 행을 호출 한 번, 커밋 한 번으로 넣습니다. DELETE FROM quotes로 연습용 두 행을 지우고, CSV의 각 행을 열 순서의 튜플로 만듭니다. INTEGER 열은 "71400"을 숫자 71400으로 저장합니다. 프로젝트에서는 parse_row()로 검증한 뒤에 넣습니다. 실습 폴더의 create_db.py가 이 과정 전체이며, 실행하면 market.db ready: 5 rows가 나옵니다(create_db).

데이터베이스가 거절한다

try:
    con.execute(INSERT, row)
except sqlite3.IntegrityError as error:
    print(type(error).__name__)
    print(error)
print(con.execute(count).fetchone())
IntegrityError
UNIQUE constraint failed: quotes.date, quotes.code
(5,)

같은 날짜의 같은 종목을 한 번 더 넣으면 PRIMARY KEY (date, code) 때문에 sqlite3.IntegrityError가 납니다. 그 문장만 실패하고 저장된 행은 바뀌지 않습니다. 가격 0도 CHECK 때문에 같은 방식으로 실패합니다. create_db의 마지막 단계에서 두 오류를 모두 봅니다.

ACT 4 · SELECT로 질문하기

원하는 것을 말하면, 찾는 방법은 데이터베이스가 정합니다. SELECT는 열을, WHERE는 행을 고르고, ORDER BY는 정렬하고 LIMIT은 개수를 자릅니다. 조회는 테이블을 바꾸지 않습니다. 쉬기 전에 내 폴더에 market.db가 있는지 확인하고, 테이블이 비어 있으면 create_db.py를 실행합니다.

SELECT: 열 고르기

query = "SELECT code, name, close FROM quotes"
for row in con.execute(query):
    print(row)
('005930', '삼성전자', 71400)
('000660', 'SK하이닉스', 198000)
('035420', 'NAVER', 200000)
('247540', '에코프로비엠', 103000)
('035900', 'JYP Ent.', 49000)

execute()의 결과는 for문으로 바로 돌 수 있습니다. 각 행은 요청한 열 순서의 튜플입니다. SELECT *는 모든 열인데, 가능하면 열 이름을 씁니다. 함정: ORDER BY가 없으면 행의 순서는 보장되지 않습니다.

WHERE: 행 고르기

query = """
    SELECT name, close FROM quotes
    WHERE market = 'KOSDAQ'
      AND close >= 50000
"""
for row in con.execute(query):
    print(row)
('에코프로비엠', 103000)

조건을 통과한 행만 돌아옵니다. 비교는 =이고 SQL에는 == 연산자가 없습니다. AND, OR, NOT으로 조건을 묶습니다. close는 INTEGER이므로 >=는 숫자를 비교합니다. JYP Ent.도 KOSDAQ인데 결과에 없는 이유는 종가 49000이 50000보다 작기 때문입니다. queries에서는 같은 질문을 ? 두 개로 실행합니다.

ORDER BY와 LIMIT

query = """
    SELECT name, volume FROM quotes
    ORDER BY volume DESC
    LIMIT 3
"""
('삼성전자', 1000000)
('SK하이닉스', 500000)
('NAVER', 300000)

순위는 정렬하고 자른 것입니다. DESC는 큰 값부터, ASC(작은 값부터)가 기본입니다. LIMIT 3은 정렬한 뒤 앞의 세 행만 남깁니다. 동점은 둘째 정렬 기준으로 가릅니다: ORDER BY volume DESC, code.

쿼리 안에서 계산하기

query = """
    SELECT name,
           (close - previous_close) * 100.0
           / previous_close AS change_pct
    FROM quotes
    ORDER BY change_pct DESC, code
"""
for name, pct in con.execute(query):
    print(f"{pct:+5.1f}% {name}")
 +3.0% 에코프로비엠
 +2.0% 삼성전자
 +0.0% NAVER
 -1.0% SK하이닉스
 -2.0% JYP Ent.

SELECT는 새 열을 계산하고 AS로 이름을 붙일 수 있습니다. 식은 logic.py의 change_pct()와 같습니다. AS change_pct로 이름을 붙여야 ORDER BY에서 쓸 수 있습니다. 각 행은 변수 두 개로 풀어 받습니다. 함정: SQL에서 정수 / 정수는 소수점을 버리므로 먼저 100.0을 곱합니다.

사용자 입력은 SQL이 아니다

bad = f"""SELECT COUNT(*) FROM quotes
          WHERE market = '{market}'"""
print(con.execute(bad).fetchone())

good = """SELECT COUNT(*) FROM quotes
          WHERE market = ?"""

ACT 1 · Change rows: UPDATE and DELETE

Two statements that can ruin a table in one line. UPDATE changes values in rows that already exist, and DELETE removes rows. Both act on every row that WHERE selects; with no WHERE, every row is affected.

UPDATE with WHERE

UPDATE = """
    UPDATE quotes SET close = ?
    WHERE code = ?
"""
cur = con.execute(UPDATE, (72000, "005930"))
print(cur.rowcount)
cur = con.execute(UPDATE, (72000, "999999"))
print(cur.rowcount)
1
0

SET names the column and its new value, and WHERE chooses the rows, as in SELECT. rowcount is the number of rows changed. Trap: a wrong code is not an error. It changes 0 rows, silently.

The WHERE you forgot

cur = con.execute("DELETE FROM quotes")
print(cur.rowcount)
print(con.execute(count).fetchone())
con.rollback()
print(con.execute(count).fetchone())
5
(0,)
(5,)

One short line, and five rows are gone. Nothing was committed yet, so rollback() undoes it. It also undoes the earlier 72000 update. Before deleting, first run a SELECT with the same WHERE. The second step of sql_changes shows everything from the UPDATE to the rollback in one go.

ACT 3 · Transactions: all or nothing

A transaction is a group of changes that succeed together or are cancelled together. It starts with the first change; commit() keeps all of it, and rollback() discards all of it. There is no state in between.

Half a snapshot is worse than none

Suppose tomorrow's file has a bad row in the middle. Committing row by row leaves a table nobody asked for, and the report would mix two days yet look correct. Grouping everything in one transaction keeps yesterday's rows instead. This is the Week 12 rule again: on failure, keep the old result.

Two new rows, one of them bad

    INSERT INTO quotes
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""

    ("2026-11-06", "005930", "삼성전자",
     "KOSPI", 71400, 72100, 900000),
    ("2026-11-06", "000660", "SK하이닉스",
     "KOSPI", 198000, 0, 450000),
]

The first row is valid; the second has close 0, so the CHECK must refuse it. After the failure, how many rows does the table hold: 5, 6 or 7?

with con: commit or roll back

try:

        con.executemany(INSERT, new_rows)

    print(error)

CHECK constraint failed: close > 0
(5,)

The with block is the transaction. If the block ends normally, it commits; if it raises, it rolls back and the exception continues. Row 1 was inserted, then taken back together with row 2. Trap: with con does not close the connection; it only ends the transaction. sql_changes runs this code side by side with, for comparison, committing row by row, which ends at (6,).

  • load_quotes()는 전과 같은 dict를 돌려준다.
  • read_csv()는 예전 읽기 함수다. 가져오기용으로 남긴다.

def replace_quotes(con, quotes):
    rows = [tuple(q[f] for f in FIELDS)
            for q in quotes]

        con.execute("DELETE FROM quotes")
        con.executemany(INSERT, rows)

Session 3 — Introduction to Database Systems3차시 — 데이터베이스 시스템 개론

This session is an introduction adapted from Week 1 of a Database Systems course. Starting from storing data, we draw the whole map, up to systems that handle sharing, change and failure. We answer three questions. Why is it needed (what goes wrong when files are all you have)? What does it look like (models, schemas and query languages hide the details)? What happens inside (storage, query and transaction modules handle each request)? Session 1 gave the short answer to the first question; this session is the whole map. Some of the concepts are collected in db_internals so you can look at them directly with Session 1's market.db.

ACT 1 · Why it is needed

A database is shared memory

When repeated work is shared among many people, you need a database. Customers, products, payments, payroll, stock. Accounts, courses, bookings, call records, routes. The work differs, but the core need is the same: an accurate state has to be shared for a long time.

Files fail at sharing and failure

A file stores data, but it cannot manage business rules or concurrency.

  • Every new need takes a new program.
  • Data sits isolated in many files and formats.
  • Rules hide all over the code, so change is hard.

A DBMS keeps shared state safe

Shared data + explicit rules + consistent execution.

  • Structure: declare schemas and relationships.
  • Access: find the data you need with queries.
  • Protection: apply permissions and integrity rules.
  • Recovery: keep the state through concurrent runs and failures.

A DBMS is not a pile of files. It is a system that guards shared state.

ACT 2 · Model: what it looks like

A data model translates reality

A data model says four things: data, relationships, meaning and constraints. It says more than what is stored: it says how things connect and which rules they keep. Older models include the network and hierarchical models.

The relational model uses tables

A relation is a table. A column is an attribute, with its kind and its meaning; a row is one record, also called a tuple. The tables and their relationships carry the meaning of the data. Ted Codd proposed this model, and he received the Turing Award in 1981.

Linked tables make one world

The instructor table and the department table hold different facts. A department's building and budget are not repeated for every instructor. To combine the two tables, follow dept_name. Store separately; combine by following relationships. In db_internals you can build small instructor and department tables and combine them (JOIN) on dept_name.

Three levels hide complexity

  • View level: the part each user needs.
  • Logical level: the logical structure of all the data.
  • Physical level: how files, pages and indexes actually store it.

Each level hides the complexity of the one below.

Schema is design, instance is now

The schema is the structure; the instance is the content at one moment. The schema is which tables and attributes exist and how they relate, like a type in a program. The instance changes as rows are added, changed and deleted, like a variable's current value. Physical data independence means the storage can change while the logical schema stays the same. In db_internals you can see that deleting rows changes the instance (the row count) but not the schema (the column list), and that after adding an index to change how the data is stored, the same SQL gives the same result.

DDL declares structure and rules

CREATE TABLE instructor (
    ID        CHAR(5),
    name      VARCHAR(20),
    dept_name VARCHAR(20),
    salary    NUMERIC(8,2)
);

DDL (Data Definition Language) defines table structure and data types, keys and integrity constraints, and access permissions. These definitions are stored as metadata in the data dictionary. In SQLite, sqlite_master plays that role, and it holds the quotes definition created from Session 1's schema.sql (db_internals).

SQL asks for the result you want

SELECT name
FROM instructor
WHERE dept_name = 'Comp. Sci.';

SQL is declarative: say what you need, and the DBMS finds the way. Tables go in and a table comes out. The result in this example is the names of the instructors in the Comp. Sci. department. SQL is the most widely used commercial query language.

SQL is one part of an application

The host language (Java, Python, C/C++) handles input, screens and networks, and SQL handles data. The interfaces between them include embedded SQL, ODBC and JDBC; for us, it is the sqlite3 module. The database runs the SQL. Nobody builds a whole application in SQL; it is the language for the data layer.

ACT 3 · Engine: what happens inside

Three jobs inside the engine

Where to store it, how to compute it, how to trust it.

  • Storage manager: sits between the operating system's files and the data.
  • Query processor: picks a low-cost plan and runs it.
  • Transaction manager: keeps consistency through failures and concurrent runs.

From query to result

The execution plan decides the performance. First, parsing and translation turn SQL into an internal form; in optimization, the lowest-cost plan is chosen; in evaluation, the execution engine produces the result. In SQLite you can see the chosen plan with EXPLAIN QUERY PLAN. Searching by the primary key gives a SEARCH that uses an index; searching by a column without an index gives a SCAN that reads the whole table (db_internals).

A transaction is all or nothing

A transaction is a group of operations that performs one logical function. In a bank transfer, the withdrawal and the deposit both finish, or both are cancelled. If two users read a balance of 100 and each withdraw 50, the orders can collide; the concurrency controller arranges the order. Failure recovery and concurrency control together give shared state you can trust. Unlike the lost update reproduced with a file in Session 1, in the last step of db_internals you see that when two connections try to change the same row at the same time, SQLite blocks the second write with database is locked and accepts it only after the first has committed, so both changes are applied. Session 2's with con showed the all-or-nothing nature of transactions.

Architecture follows scale

The architecture depends on where the work runs and how much work there is.

  • Centralized: one system does the work.
  • Client-server: one server, many clients.
  • Parallel: many cores or nodes work together.
  • Distributed: data is spread over several locations.

Choose by throughput, latency, scalability, failure scope and data location. The SQLite we use is an embedded engine that runs inside the application and writes a single file.

Two tiers or three

The difference is where the responsibilities sit. In a two-tier architecture, the client calls the database server directly. In a three-tier architecture, an application server in between holds the business rules and the data access. In Week 14, Flask becomes our application server.

ACT 4 · People and history

Different users, different access

  • Naive users: use ready-made applications.
  • Application developers: write database applications.
  • Sophisticated users: use query languages and analysis tools.
  • Specialized users: CAD, graphics, audio, video.

The DBA (database administrator) has central control of the whole system and is responsible for running it.

Databases grew with workloads

Each decade brought new hardware and new workloads, and storage and scale changed. Even so, the relational core of relations and queries survived all of these changes.

Today's core: a DBMS manages boundaries

Five boundaries, one system.

  1. File and shared state: it controls redundancy, concurrency and failure.
  2. Reality and data model: it expresses relationships and constraints as structure.
  3. Logical and physical: data independence limits the effect of change.
  4. Request and execution: it turns SQL into a plan and optimizes it.
  5. User and system: it separates application layers, permissions and operations.

Next, we work with the relational model and SQL in practice, using SQLite.

ACT 1 · 왜 필요한가

데이터베이스는 공유하는 기억이다

반복되는 일을 여럿이 나눠 하면 데이터베이스가 필요해집니다. 고객, 상품, 결제, 급여, 재고. 계좌, 수강, 예약, 통화 기록, 노선. 하는 일은 달라도 핵심 필요는 같습니다. 정확한 상태를 오랫동안 공유해야 한다는 것입니다.

파일은 공유와 장애에서 실패한다

파일은 데이터를 저장하지만 업무 규칙이나 동시 실행을 관리하지 못합니다.

  • 새로운 필요가 생길 때마다 새 프로그램이 필요하다.
  • 데이터가 여러 파일과 형식으로 흩어져 고립된다.
  • 규칙이 코드 곳곳에 숨어 있어 바꾸기 어렵다.

DBMS는 공유 상태를 안전하게 지킨다

공유 데이터 + 명시적인 규칙 + 일관된 실행입니다.

  • 구조: 스키마와 관계를 선언한다.
  • 접근: 질의로 필요한 데이터를 찾는다.
  • 보호: 권한과 무결성 규칙을 적용한다.
  • 복구: 동시 실행과 장애를 거쳐도 상태를 유지한다.

DBMS는 파일 더미가 아니라 공유 상태를 지키는 시스템입니다.

ACT 2 · 모델: 어떻게 생겼는가

데이터 모델은 현실을 번역한다

데이터 모델은 네 가지를 말합니다. 데이터, 관계, 의미, 제약입니다. 무엇이 저장되는지보다 더 많은 것, 즉 것들이 어떻게 연결되고 어떤 규칙을 지키는지를 말합니다. 오래된 모델로는 네트워크 모델과 계층 모델이 있습니다.

관계형 모델은 테이블을 쓴다

관계(relation)가 곧 테이블입니다. 열은 속성(attribute)으로 그 종류와 의미를 가지고, 행은 기록 하나로 튜플(tuple)이라고도 부릅니다. 테이블과 그 관계가 데이터의 의미를 담습니다. 이 모델은 Ted Codd가 제안했고, 그는 1981년 튜링상을 받았습니다.

연결된 테이블이 하나의 세계를 만든다

instructor 테이블과 department 테이블은 서로 다른 사실을 담습니다. 학과의 건물과 예산은 교수마다 반복해서 저장하지 않습니다. 두 테이블을 합치려면 dept_name을 따라갑니다. 따로 저장하고, 관계를 따라 결합합니다. db_internals에서 작은 instructor·department 테이블을 만들어 dept_name으로 결합(JOIN)해 볼 수 있습니다.

세 단계가 복잡함을 숨긴다

  • 뷰 단계: 각 사용자에게 필요한 부분.
  • 논리 단계: 전체 데이터의 논리 구조.
  • 물리 단계: 파일, 페이지, 인덱스가 실제로 저장하는 방식.

각 단계는 그 아래 단계의 복잡함을 숨깁니다.

스키마는 설계, 인스턴스는 지금

스키마는 구조이고, 인스턴스는 한 순간의 내용입니다. 스키마는 어떤 테이블과 속성이 있고 어떻게 관계를 맺는지로, 프로그램의 자료형과 같습니다. 인스턴스는 행이 추가·변경·삭제되며 바뀌는 것으로, 변수의 현재 값과 같습니다. 물리적 데이터 독립성이란 논리 스키마는 그대로 둔 채 저장 방식을 바꿀 수 있다는 뜻입니다. db_internals에서 행을 지우면 인스턴스(행 수)는 바뀌지만 스키마(열 목록)는 그대로인 것, 인덱스를 추가해 저장 방식을 바꿔도 같은 SQL이 같은 결과를 내는 것을 확인합니다.

DDL은 구조와 규칙을 선언한다

CREATE TABLE instructor (
    ID        CHAR(5),
    name      VARCHAR(20),
    dept_name VARCHAR(20),
    salary    NUMERIC(8,2)
);

DDL(Data Definition Language)은 테이블 구조와 자료형, 키와 무결성 제약, 접근 권한을 정의합니다. 이 정의들은 데이터 사전(data dictionary)에 메타데이터로 저장됩니다. SQLite에서는 sqlite_master가 그 역할을 하며, 1차시의 schema.sql로 만든 quotes 정의가 거기에 들어 있습니다(db_internals).

SQL은 원하는 결과를 요청한다

SELECT name
FROM instructor
WHERE dept_name = 'Comp. Sci.';

SQL은 선언적입니다. 필요한 것을 말하면 DBMS가 방법을 찾습니다. 입력도 테이블이고 출력도 테이블입니다. 이 예의 결과는 Comp. Sci. 학과 교수들의 이름입니다. SQL은 가장 널리 쓰이는 상용 질의 언어입니다.

SQL은 응용의 한 부분이다

호스트 언어(Java, Python, C/C++)가 입력, 화면, 네트워크를 맡고 SQL은 데이터를 맡습니다. 둘 사이의 인터페이스로 임베디드 SQL, ODBC, JDBC가 있고, 우리에게는 sqlite3 모듈이 그것입니다. 데이터베이스가 SQL을 실행합니다. 응용 전체를 SQL로 만드는 사람은 없습니다. SQL은 데이터 계층의 언어입니다.

ACT 3 · 엔진: 안에서 무슨 일이 일어나는가

엔진 안의 세 가지 일

어디에 저장할지, 어떻게 계산할지, 어떻게 믿을 수 있게 할지입니다.

  • 저장 관리자: 운영체제의 파일과 데이터 사이에 있다.
  • 질의 처리기: 비용이 낮은 계획을 골라 실행한다.
  • 트랜잭션 관리자: 장애와 동시 실행을 거쳐도 일관성을 지킨다.

질의에서 결과까지

실행 계획이 성능을 결정합니다. 먼저 파싱과 변환으로 SQL이 내부 형태가 되고, 최적화 단계에서 가장 비용이 낮은 계획이 선택되며, 평가 단계에서 실행 엔진이 결과를 만듭니다. SQLite에서는 EXPLAIN QUERY PLAN으로 고른 계획을 볼 수 있습니다. 기본 키로 찾으면 인덱스를 쓰는 SEARCH, 인덱스가 없는 열로 찾으면 표 전체를 훑는 SCAN이 나옵니다(db_internals).

트랜잭션은 전부 아니면 전무

트랜잭션은 하나의 논리적 기능을 수행하는 연산의 묶음입니다. 계좌 이체라면 출금과 입금이 모두 끝나거나 모두 취소됩니다. 두 사용자가 잔액 100을 읽고 각자 50씩 인출하면 순서가 충돌할 수 있는데, 동시성 제어기가 그 순서를 정리합니다. 장애 복구와 동시성 제어가 합쳐져 믿을 수 있는 공유 상태가 됩니다. 1차시에 파일로 재현한 갱신 손실과 달리, db_internals의 마지막 단계에서는 두 연결이 같은 행을 동시에 고치려 할 때 SQLite가 두 번째 쓰기를 database is locked로 막고, 첫 번째가 커밋한 뒤에야 받아들여 두 변경이 모두 반영되는 것을 봅니다. 2차시의 with con이 트랜잭션의 전부 아니면 전무를 보여 주었습니다.

구조는 규모를 따른다

일이 어디에서 돌아가는지, 얼마나 많은지에 따라 구조가 달라집니다.

  • 중앙집중형: 시스템 하나가 일을 한다.
  • 클라이언트-서버: 서버 하나, 클라이언트 여럿.
  • 병렬: 여러 코어나 노드가 함께 일한다.
  • 분산: 데이터가 여러 장소에 흩어져 있다.

처리량, 지연 시간, 확장성, 장애 범위, 데이터 위치를 보고 고릅니다. 우리가 쓰는 SQLite는 응용 안에 들어가 파일 하나를 쓰는 내장형 엔진입니다.

2계층과 3계층

차이는 책임이 어디에 있는가입니다. 2계층에서는 클라이언트가 데이터베이스 서버를 직접 호출합니다. 3계층에서는 그 사이의 응용 서버가 업무 규칙과 데이터 접근을 맡습니다. 14주차에는 Flask가 우리의 응용 서버가 됩니다.

ACT 4 · 사람과 역사

사용자마다 접근 방식이 다르다

  • 일반 사용자: 만들어진 응용 프로그램을 쓴다.
  • 응용 개발자: 데이터베이스 응용을 작성한다.
  • 숙련 사용자: 질의 언어와 분석 도구를 쓴다.
  • 특수 사용자: CAD, 그래픽, 오디오, 비디오.

DBA(데이터베이스 관리자)는 전체 시스템을 중앙에서 통제하고 운영을 책임집니다.

데이터베이스는 작업량과 함께 자랐다

10년마다 새로운 하드웨어와 새로운 작업량이 등장했고, 저장 방식과 규모가 바뀌었습니다. 그래도 관계와 질의라는 관계형 핵심은 그 모든 변화를 견뎌 냈습니다.

오늘의 핵심: DBMS는 경계를 관리한다

다섯 경계, 하나의 시스템입니다.

  1. 파일과 공유 상태: 중복, 동시성, 장애를 통제한다.
  2. 현실과 데이터 모델: 관계와 제약을 구조로 표현한다.
  3. 논리와 물리: 데이터 독립성이 변경의 영향을 제한한다.
  4. 요청과 실행: SQL을 계획으로 바꾸고 최적화한다.
  5. 사용자와 시스템: 응용 계층, 권한, 운영을 분리한다.
