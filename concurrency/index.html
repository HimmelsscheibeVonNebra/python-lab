Concurrency: Threads and asyncio동시성: 스레드와 asyncio

Make programs faster by overlapping the time they spend waiting (I/O). Practice threading.Thread with start and join, race conditions on shared values and Lock, producer/consumer with queue.Queue, ThreadPoolExecutor's map, submit and as_completed, asyncio's async/await and gather, and an asyncio echo server on 127.0.0.1. Also see why pure computation does not get faster on this one-core virtual machine.기다리는 일(I/O)을 겹쳐서 프로그램을 빠르게 만든다. threading.Thread의 start와 join, 공유 값의 경쟁 조건과 Lock, queue.Queue로 만드는 생산자-소비자, ThreadPoolExecutor의 map·submit·as_completed, asyncio의 async/await와 gather, 그리고 127.0.0.1의 asyncio 에코 서버를 실습한다. 코어가 하나인 가상 머신에서 계산만 하는 일은 왜 빨라지지 않는지도 확인한다. Examples예제

threads ~/concurrency/threads

Run three pretend downloads (each waits 1 second) one at a time, then in three threads, and compare the time taken. threading.Thread(target=..., args=...) creates a thread, start() sets it going and join() waits for it to finish. Time is measured with time.perf_counter().가짜 다운로드 세 개(각 1초 대기)를 한 번에 하나씩, 그리고 스레드 세 개로 실행해 걸린 시간을 비교한다. threading.Thread(target=..., args=...)로 스레드를 만들고 start()로 출발시키며 join()으로 끝나기를 기다린다. 시간은 time.perf_counter()로 잰다.

Steps실행 순서

  1. python3 download_sim.py

    sequential alternates start and done and takes about 3 s; threaded prints the three start lines first, then the three done lines, and takes about 1 s. While waiting, the CPU is idle, so the three waits overlap. The order of the lines in the threaded run can change from run to run.sequential은 start와 done이 번갈아 나오고 about 3 s, threaded는 start 세 줄이 먼저 나온 뒤 done 세 줄이 나오고 about 1 s다. 기다리는 동안 CPU는 놀고 있으므로 세 번의 기다림이 겹친다. 스레드 쪽의 줄 순서는 실행마다 달라질 수 있다.

  2. python3 - <<'EOF' import threading import time results = {} def work(name, seconds): time.sleep(seconds) results[name] = seconds jobs = [("x", 0.6), ("y", 0.2), ("z", 0.4)] threads = [threading.Thread(target=work, args=job) for job in jobs] for t in threads: t.start() print("right after start:", results) for t in threads: t.join() print("after join:", dict(sorted(results.items()))) print("finish order:", list(results)) EOF

    A thread function's return value is thrown away, so the results go into a shared dictionary. Right after start() nobody has finished yet, so it is {}; only after every join() are all three results there. They finished in order of the shortest wait: y, z, x.스레드 함수의 return 값은 버려지므로 결과는 공유 딕셔너리에 담는다. start() 직후에는 아직 아무도 끝나지 않아 {}이고, join()을 모두 마친 뒤에야 세 결과가 다 있다. 끝난 순서는 짧게 기다린 순서 y, z, x다.

  3. python3 - <<'EOF' import threading import time def work(): time.sleep(1) print("worker: done") t = threading.Thread(target=work) t.start() print("main: worker alive?", t.is_alive()) print("main: last line of the program") EOF

    Without join(), the main thread does not wait and goes straight on. The two main lines come first and worker: done appears a second later. Python does not end the process until every non-daemon thread has finished, but wherever you need the results, wait with join() first.join()이 없으면 메인 스레드는 기다리지 않고 바로 다음 줄로 간다. main 두 줄이 먼저 나오고 1초 뒤에 worker: done이 나온다. 파이썬은 데몬이 아닌 스레드가 모두 끝날 때까지 프로세스를 끝내지 않는다. 결과를 써야 하는 지점 앞에서는 join()으로 기다려야 한다.

  4. python3 - <<'EOF' import threading import time from download_sim import download, FILES start = time.perf_counter() threads = [threading.Thread(target=download(name)) for name in FILES] for t in threads: t.start() for t in threads: t.join() print(f"about {round(time.perf_counter() - start)} s") EOF

    A common mistake: target=download(name) calls the function right there and passes its return value, None, as the target. The downloads run one by one before any thread is created, so it takes about 3 s. Pass the function as target=download and its arguments separately as args=(name,).흔한 실수: target=download(name)은 함수를 지금 이 자리에서 호출하고 그 반환값 None을 target으로 넘긴다. 다운로드가 스레드를 만들기 전에 하나씩 실행되어 about 3 s가 걸린다. 함수는 target=download, 인자는 args=(name,)으로 따로 넘긴다.

race_lock ~/concurrency/race

Four threads each deposit 1 into a single balance 1000 times. When another thread slips in between a read and a write, deposits disappear (a race condition). Holding a threading.Lock with a with statement lets only one thread read and write at a time, so the result is always right.스레드 네 개가 하나의 잔액(balance)에 1000번씩 입금한다. 읽기와 쓰기 사이에 다른 스레드가 끼어들면 입금이 사라진다(경쟁 조건). threading.Lock을 with 문으로 잡으면 한 번에 한 스레드만 읽고 쓰므로 결과가 항상 맞다.

Steps실행 순서

  1. python3 counter_race.py

    expected 4000, but got is far smaller (around 1000 on this virtual machine, and it can vary a little between runs). time.sleep(0) hands the turn to another thread between the read and the write, so all four threads read the same value and all write that value + 1: three deposits out of four vanish. There is no error message, which is exactly what makes race conditions dangerous.expected 4000인데 got은 훨씬 작다(이 가상 머신에서는 1000 근처이고 실행마다 조금 다를 수 있다). time.sleep(0)이 읽기와 쓰기 사이에서 다른 스레드에 차례를 넘기므로, 네 스레드가 같은 값을 읽고 똑같이 그 값+1을 써서 네 번의 입금 중 세 번이 사라진다. 오류 메시지는 없다. 이것이 경쟁 조건이 위험한 이유다.

  2. python3 counter_race.py lock

    Inside with lock:, other threads wait until one thread has finished its read and write. expected 4000, got 4000, correct, however many times you run it.with lock: 안에서는 한 스레드가 읽기-쓰기를 끝낼 때까지 다른 스레드가 기다린다. expected 4000, got 4000, correct. 몇 번을 실행해도 같다.

  3. python3 - <<'EOF' import dis counter = 0 def add(): global counter counter += 1 dis.dis(add) EOF

    counter += 1 is one line but not one action. In bytecode it splits into LOAD_GLOBAL (read), BINARY_OP += (add) and STORE_GLOBAL (write). A thread switch can happen anywhere in between.counter += 1은 한 줄이지만 한 동작이 아니다. 바이트코드로 보면 LOAD_GLOBAL(읽기), BINARY_OP +=(더하기), STORE_GLOBAL(쓰기)로 나뉜다. 스레드 전환은 이 사이 어디에서나 일어날 수 있다.

  4. python3 - <<'EOF' import threading counter = 0 def work(): global counter for _ in range(100_000): counter += 1 threads = [threading.Thread(target=work) for _ in range(4)] for t in threads: t.start() for t in threads: t.join() print("expected 400000, got", counter) EOF

    With plain counter += 1 and no sleep, you will usually get the right 400000 here, because Python with a GIL rarely switches threads at that point. But the language does not promise it: another version, a free-threaded build or several cores can get it wrong. A correct result does not make the code safe. Wrap code that changes a shared value in a Lock.sleep 없이 counter += 1만 하면 여기서는 대개 400000이 맞게 나온다. GIL이 있는 파이썬이 스레드를 바꾸는 시점이 드물기 때문이다. 하지만 언어가 보장하는 것이 아니다. 다른 버전, GIL이 없는 빌드, 여러 코어에서는 틀릴 수 있다. 결과가 맞게 나왔다고 안전한 코드가 아니다. 공유 값을 바꾸는 코드는 Lock으로 감싼다.

  5. python3 - <<'EOF' import threading lock = threading.Lock() with lock: print("got the lock once") print("again?", lock.acquire(timeout=1)) EOF

    A Lock cannot be taken again even by the thread that already holds it. With timeout=1 you get again? False after one second; without a timeout it would wait forever (a deadlock). If the same thread needs to take it several times, use threading.RLock.Lock은 이미 잡은 스레드도 다시 잡을 수 없다. timeout=1을 주었으므로 1초 뒤 again? False가 나온다. timeout이 없으면 영원히 기다린다(교착 상태, deadlock). 같은 스레드가 여러 번 잡아야 한다면 threading.RLock을 쓴다.

producer_consumer ~/concurrency/queue

The producer/consumer pattern. A waiter thread (the producer) puts six orders into a queue.Queue and two cook threads (the consumers) take them out one at a time and cook each for 0.5 s. The queue handles the locking, so the threads never share a list directly. None is the "no more orders" signal.생산자-소비자 패턴. 웨이터 스레드(생산자)가 주문 여섯 개를 queue.Queue에 넣고, 요리사 스레드 두 개(소비자)가 하나씩 꺼내 0.5초씩 요리한다. 큐가 잠금을 대신 처리하므로 스레드끼리 리스트를 직접 나눠 쓰지 않는다. None은 "주문 끝" 신호다.

Steps실행 순서

  1. python3 kitchen.py

    The waiter pauses after placing five orders: once the two cooks have taken one each, the counter (a queue with maxsize=3) holds three, and put() waits until there is room. The cooks finish dishes in turn, and at the end you get the sorted list of dishes and 2 cooks: about 1.5 s (one cook would need 3.0 s). Which cook gets which dish can change from run to run.웨이터가 주문 다섯 개를 넣은 뒤 잠시 멈춘다. 요리사 둘이 하나씩 가져가고 나면 카운터(maxsize=3인 큐)에 셋이 차서 put()이 자리가 날 때까지 기다리기 때문이다. 요리사 둘이 번갈아 요리를 끝내고, 마지막에 정렬한 요리 목록과 2 cooks: about 1.5 s (one cook would need 3.0 s)가 나온다. 어느 요리사가 어느 요리를 맡는지는 실행마다 달라질 수 있다.

  2. python3 - <<'EOF' import kitchen kitchen.COOKS = 3 kitchen.main() EOF

    With three cooks it takes about 1.0 s. Only the side that takes the work grew; the waiter's code is unchanged. It also puts COOKS stop signals (None), so all three cooks finish.요리사를 셋으로 늘리면 about 1.0 s다. 일을 나눠 받는 쪽만 늘렸고 웨이터 코드는 그대로다. 정지 신호 None도 COOKS개만큼 넣으므로 세 요리사가 모두 끝난다.

  3. python3 - <<'EOF' import queue q = queue.Queue(maxsize=2) q.put("first") q.put("second") try: q.put_nowait("third") except queue.Full: print("full:", q.qsize(), "items") print(q.get(), q.get()) try: q.get(timeout=1) except queue.Empty: print("empty: nothing came within 1 s") EOF

    A queue hands items out in the order they went in (FIFO): first second. put_nowait() on a full queue raises queue.Full, and get() on an empty queue raises queue.Empty once the timeout passes. A get() without a timeout waits forever for something to arrive, which is why a program never ends if you forget to send the consumers a stop signal.큐는 넣은 순서대로 꺼낸다(FIFO): first second. 가득 찬 큐에 put_nowait()하면 queue.Full, 빈 큐에서 timeout이 지나면 queue.Empty가 난다. timeout 없는 get()은 무엇이 들어올 때까지 영원히 기다린다. 소비자에게 정지 신호를 보내지 않으면 프로그램이 끝나지 않는 이유다.

thread_pool ~/concurrency/pool

concurrent.futures.ThreadPoolExecutor creates and joins the threads for you. map gives results in input order; submit with as_completed gives them in the order they finish. cpu_pool.py splits pure computation across a thread pool and a process pool (ProcessPoolExecutor) and shows that on this one-core virtual machine it does not get faster.concurrent.futures.ThreadPoolExecutor는 스레드를 직접 만들고 join하는 일을 대신해 준다. map은 입력 순서대로, submit과 as_completed는 끝난 순서대로 결과를 준다. cpu_pool.py는 계산만 하는 일을 스레드 풀과 프로세스 풀(ProcessPoolExecutor)로 나눠 보고, 코어가 하나인 이 가상 머신에서는 빨라지지 않는다는 것을 확인한다.

Steps실행 순서

  1. python3 pool_demo.py

    The three pages wait 1.5, 0.5 and 1.0 s. map returns them in input order (home, news, about); as_completed returns them in the order they finished (news, about, home). Both together take about 3 s; one by one it would be 6 s.페이지 세 개는 각각 1.5, 0.5, 1.0초를 기다린다. map은 입력 순서(home, news, about)대로 돌려주고, as_completed는 먼저 끝난 순서(news, about, home)대로 돌려준다. 두 번 합쳐 about 3 s다. 하나씩 했다면 6초다.

  2. python3 - <<'EOF' import time from concurrent.futures import ThreadPoolExecutor from pool_demo import fetch, PAGES for workers in (1, 2, 3): start = time.perf_counter() with ThreadPoolExecutor(max_workers=workers) as pool: list(pool.map(fetch, PAGES)) print(f"{workers} workers: about {round((time.perf_counter() - start) * 2) / 2} s") EOF

    max_workers is how many threads work at once. With 1 it takes 3.0 s, the same as one by one; with 2 or 3 it takes 1.5 s. Even with two workers, the one that finishes the short news page picks up about, so everything is done within the longest wait, home's 1.5 s. Leaving the with block waits for all the work and cleans up the threads.max_workers는 동시에 일하는 스레드 수다. 1이면 하나씩과 같은 3.0 s, 2와 3이면 1.5 s다. 일꾼이 둘일 때도 짧은 news가 끝난 자리에서 about을 이어 받으므로 가장 긴 home 1.5초 안에 다 끝난다. with 블록을 나갈 때 풀이 모든 일을 기다리고 스레드를 정리한다.

  3. python3 - <<'EOF' from concurrent.futures import ThreadPoolExecutor def check(n): if n == 3: raise ValueError(f"bad input {n}") return n * n with ThreadPoolExecutor(max_workers=2) as pool: futures = [pool.submit(check, n) for n in range(1, 5)] for n, future in zip(range(1, 5), futures): try: print(n, "->", future.result()) except ValueError as error: print(n, "-> error:", error) EOF

    submit() immediately returns a Future (a receipt for a result that comes later). An exception raised inside a job is not shown where it happens; it is raised again when you call future.result(). That is why the result() call is wrapped in try: 1 -> 1, 2 -> 4, 3 -> error: bad input 3, 4 -> 16.submit()은 바로 Future(나중에 나올 결과의 영수증)를 돌려준다. 작업 안에서 난 예외는 그 자리에서 보이지 않고 future.result()를 부를 때 다시 발생한다. 그래서 result() 호출을 try로 감싼다: 1 -> 1, 2 -> 4, 3 -> error: bad input 3, 4 -> 16.

  4. python3 cpu_pool.py

    CPU cores: 1. Counting primes is pure computation with no waiting, so splitting it across threads takes about the same time (about the same as). The process pool is even slower (slower than) because starting processes and passing data between them costs time. The seconds vary a little between runs. On a PC with several cores and a big enough job, the processes would come out ahead.CPU cores: 1이다. 소수 세기는 기다림 없이 계산만 하므로 스레드로 나눠도 걸리는 시간이 비슷하다(about the same as). 프로세스 풀은 프로세스를 띄우고 데이터를 주고받는 비용 때문에 오히려 느리다(slower than). 초 단위 숫자는 실행마다 조금씩 다르다. 코어가 여러 개인 PC에서 일이 충분히 크면 프로세스 쪽이 빨라진다.

cpu_pool.py takes about 10 seconds. A file that uses ProcessPoolExecutor must have the if __name__ == "__main__": guard, because the worker processes import the file to find count_primes. For the same reason a process pool does not work in code fed through standard input with python3 -.cpu_pool.py는 약 10초 걸린다. ProcessPoolExecutor를 쓰는 파일에는 if __name__ == "__main__": 가드가 꼭 있어야 한다. 일꾼 프로세스가 이 파일을 import해서 count_primes를 찾기 때문이다. 같은 이유로 python3 - 로 표준 입력에 넣은 코드에서는 프로세스 풀이 동작하지 않는다.

asyncio_basics ~/concurrency/asyncio

asyncio overlaps many waits on a single thread. A coroutine defined with async def pauses at each await while the event loop runs other coroutines. Awaiting one at a time takes 3 seconds; waiting for all of them together with asyncio.gather takes 1. Also see what happens when you forget await and when time.sleep blocks the loop.asyncio는 스레드 하나에서 여러 기다림을 겹친다. async def로 만든 코루틴은 await에서 멈추고, 그동안 이벤트 루프가 다른 코루틴을 돌린다. await를 하나씩 하면 3초, asyncio.gather로 한꺼번에 기다리면 1초다. await를 잊었을 때와 time.sleep으로 루프를 막았을 때도 본다.

Steps실행 순서

"""Four threads add to one shared balance.  Run: python3 counter_race.py [lock]
 
Without the lock, a thread can read the balance, get paused, and write back
an old value: other threads' deposits are lost.  With the lock, only one
thread at a time runs the read-and-write part.
"""
import sys
import threading
import time
 
THREADS = 4
DEPOSITS = 1000              # per thread
 
balance = 0
lock = threading.Lock()
 
 
def deposit(times, use_lock):
    global balance
    for _ in range(times):
        if use_lock:
            with lock:                   # acquire ... release, even on errors
                current = balance
                time.sleep(0)
                balance = current + 1
        else:
            current = balance            # 1. read
            time.sleep(0)                # 2. pause: another thread may run now
            balance = current + 1        # 3. write back (maybe a stale value)
 
 
def main():
    use_lock = sys.argv[1:] == ["lock"]
    threads = [threading.Thread(target=deposit, args=(DEPOSITS, use_lock))
               for _ in range(THREADS)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
 
    expected = THREADS * DEPOSITS
    print("with lock:" if use_lock else "without lock:", f"expected {expected}, got {balance}")
    if balance == expected:
        print("correct")
    else:
        print(f"lost updates: {expected - balance}")
 
 
if __name__ == "__main__":

The waiter (producer) puts orders into a queue.Queue; each cook (consumer)
takes the next order out.  queue.Queue does its own locking, so the threads
never touch a shared list directly.  None is the "no more orders" signal.

import threading
import time

COOKS = 2
COOK_TIME = 0.5              # seconds per dish
 
orders = queue.Queue(maxsize=3)   # the counter holds at most 3 tickets
served = queue.Queue()
 
 
def waiter():
    for dish in ORDERS:
        orders.put(dish)              # blocks while the counter is full
        print(f"waiter: order {dish}")
    for _ in range(COOKS):
        orders.put(None)              # one stop signal per cook
 
 
def cook(name):
    while True:
        dish = orders.get()           # blocks until there is an order
        if dish is None:
            break
        time.sleep(COOK_TIME)
        print(f"{name}: {dish} ready")
        served.put((dish, name))
 
 
def main():
    start = time.perf_counter()
    threads = [threading.Thread(target=waiter)]
    threads += [threading.Thread(target=cook, args=(f"cook{i}",)) for i in range(1, COOKS + 1)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    elapsed = time.perf_counter() - start
 
    dishes = sorted(served.get()[0] for _ in range(served.qsize()))
    print(f"served {len(dishes)} dishes:", ", ".join(dishes))
    alone = len(ORDERS) * COOK_TIME
    print(f"{COOKS} cooks: about {round(elapsed * 2) / 2} s (one cook would need {alone} s)")

Concurrency: Threads and asyncio동시성: 스레드와 asyncio

This topic is concurrency. Much of what programs do is not computing but waiting: for a web page to arrive, for a file to be read, for the user to type. If a program does something else while it waits, the same work can finish in far less time. First we use threading to create threads and overlap waits, and look at the race conditions that appear when several threads change the same value, and at Lock. Then we cover the producer/consumer pattern with queue.Queue, concurrent.futures, which manages threads for you, and asyncio, which handles many waits on a single thread. Finally we build an asyncio TCP echo server. The practice pages are threads, race_lock, producer_consumer, thread_pool, asyncio_basics and echo_server.

What concurrency is: overlapping waits

The barista

Say a barista takes an order for three coffees. If they stand by the machine for the minute it takes to brew one cup and only then start the next, it takes three minutes. If they put the first cup on, then the second and third right away, it takes about one minute. There is still one barista with two hands. The only change is that the waiting times overlap. That is concurrency.

With three baristas, three people really move their hands at the same time. That is parallelism. Concurrency means dealing with several tasks at once by taking turns; parallelism means actually running several tasks at the same instant. Running in parallel needs several CPU cores.

I/O-bound and CPU-bound work

Whether a task can get faster depends on what it spends its time on.

KindTime goes intoExamplesWith threads or asyncio
I/O-boundwaiting for the outside world: network, disk, the userdownloads, database queries, a server answering clientsthe waits overlap, so it gets faster
CPU-boundcomputingcounting primes, image processing, big matrix productsno faster on one core

In this lab, time.sleep stands in for a real network wait. A sleeping thread does not use the CPU, so it behaves just like a real I/O wait.

About this virtual machine

The virtual machine in your browser has one CPU core, and because it is emulated it is much slower than a real PC. os.cpu_count() returns 1. Examples that overlap waits therefore speed up exactly as they would on a PC, but pure computation does not get faster whether you split it into threads or processes. The section on CPU-bound work below explains what changes on a PC with several cores.

threading: creating threads

What a thread is

A thread is a separate flow of execution inside one program (process). A program starts with a single main thread. New threads see the same memory (the same variables, the same objects) while each runs its own function. While one thread waits in time.sleep or a network read, other threads run.

Thread, start, join

threading.Thread(target=function, args=(argument,)) creates a thread object, start() sets it going and join() waits for it to finish. Here is the heart of the threads example.

import threading
import time

def download(name):
    print(f"  start {name}")
    time.sleep(1.0)             # waiting: this thread sleeps, the CPU is free
    print(f"  done  {name}")

threads = [threading.Thread(target=download, args=(name,)) for name in FILES]
for t in threads:
    t.start()                   # starts running download(name) in the background
for t in threads:
    t.join()                    # waits until that thread has finished

Splitting the starting and the waiting into two loops matters. If you call join() right after start() in the same loop, the second thread does not start until the first has finished, which is the same as running them one by one. Start them all, then wait for them all.

Measuring time: time.perf_counter

Measure elapsed time with time.perf_counter(). Its value by itself means nothing; the difference between two calls is the number of seconds in between. It is not affected by changes to the clock, which makes it right for measurements. Measurements vary a little from run to run, so the examples round them with round() and print things like "about 1 s".

start = time.perf_counter()
func()
elapsed = time.perf_counter() - start
print(f"about {round(elapsed)} s")
sequential: about 3 s
threaded: about 1 s

In the threaded run the three start lines come first, followed by the three done lines. Which thread prints first is up to the operating system, so the order can change between runs. Never write code that depends on the order in which threads print.

Getting results out of a thread

The return value of a thread's function is thrown away. If you need results, put them in a dictionary or list that all threads can see, and read it after join() has confirmed they are all done. Right after start() it is still empty. concurrent.futures, below, is the more convenient way to get results back.

results = {}

def work(name, seconds):
    time.sleep(seconds)
    results[name] = seconds      # each thread writes its own key

# ... start all, then join all ...
print(results)

Without join

Without join(), the main thread does not wait for the threads and moves straight on. The program still does not vanish before the work is done, because Python ends the process only when every non-daemon thread has finished. A daemon thread, created with Thread(..., daemon=True), is stopped when the main thread ends. Wherever you need the results, always join() first.

Two deposits were made but the value went up by only 1, because B read the old value before A wrote. When the result depends on the order in which threads happen to run, that is a race condition. There is no error message, and some runs happen to come out right, which makes these bugs hard to find. The time.sleep(0) in the example deliberately hands over the turn between the read and the write so that the problem shows up every time.

One line is not safe either

counter += 1 is one line but not one action. Looking at the bytecode with dis.dis shows it split into a read, an add and a write.

LOAD_GLOBAL              0 (counter)
LOAD_SMALL_INT           1
BINARY_OP               13 (+=)
STORE_GLOBAL             0 (counter)

On the lab machine, doing plain counter += 1 400,000 times with no sleep usually gives exactly 400000, because today's CPython rarely switches threads in the middle of such short code. But that is an accident of the implementation, not a promise of the language. A different version, slightly longer code, or a build without the GIL running on several cores can give a wrong value. A correct result is not proof that the code is safe.

threading.Lock

A Lock is a key that only one thread can hold at a time. Entering a with lock: block takes the key (acquire) and leaving it gives the key back (release). If another thread holds the key, you wait until it is returned. Even if an exception happens inside the block, with gives the key back, so it is safer than calling acquire() and release() yourself.

lock = threading.Lock()

def deposit(times):
    global balance
    for _ in range(times):
        with lock:                 # only one thread at a time in here
            current = balance
            time.sleep(0)
            balance = current + 1
with lock: expected 4000, got 4000
correct

Keep the part inside the lock (the critical section) down to the minimum that reads and changes the shared value. If you wait for a long time inside the lock, every other thread stops too and the threads gain you nothing.

Deadlock

A Lock cannot be taken again even by the thread that already holds it. If a thread inside with lock: tries to take lock again, it waits for itself forever. The same happens when two threads each wait for the other's lock. This is called a deadlock. The example uses lock.acquire(timeout=1) to wait for just one second and see False. When the same thread needs to take a lock several times, use threading.RLock. If you use several locks, make every thread take them in the same order.

queue.Queue: producers and consumers

The safest way to share work

Instead of guarding shared variables with locks, have threads pass messages to each other; there is less room for mistakes. A queue.Queue is a first-in, first-out line that many threads can use at the same time safely. The side that creates work (the producer) puts items in with put(), and the side that handles it (the consumer) takes them out with get(). The queue does the locking itself.

The waiter and the cooks

In kitchen.py from producer_consumer, a waiter thread puts orders into a queue, and two cook threads take them out one at a time and cook each for 0.5 seconds.

orders = queue.Queue(maxsize=3)   # the counter holds at most 3 tickets

def waiter():
    for dish in ORDERS:
        orders.put(dish)              # blocks while the counter is full
    for _ in range(COOKS):
        orders.put(None)              # one stop signal per cook

def cook(name):
    while True:
        dish = orders.get()           # blocks until there is an order
        if dish is None:
            break
        time.sleep(COOK_TIME)
        served.put((dish, name))

The cooks keep taking orders in a while True loop, so they need some way to learn that the work is over. Here the waiter puts one None per cook, and a cook who takes out None leaves the loop. A special value like this is called a sentinel. With only one sentinel, only one cook would stop; the other would wait in get() forever and the program would never end.

maxsize=3 limits the size of the queue. When the producer is faster than the consumers, it pauses the producer so that work does not pile up in memory without end (backpressure). When you run it, you can see the waiter stop after five orders until a dish is finished.

With three cooks it takes about 1.0 s. Only the number of consumers changes; the producer code stays the same. The list of results is printed with sorted() because which dish finishes first can change from run to run. Queues also offer task_done() and join() for "wait until everything that was put in has been handled".

concurrent.futures: thread pools

ThreadPoolExecutor and map

Creating threads, starting them, waiting for them and collecting results looks much the same every time. concurrent.futures.ThreadPoolExecutor keeps a few worker threads ready (a pool), shares out the jobs you give it and hands back the results. Leaving the with block waits for all jobs to finish and cleans up the threads.

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=3) as pool:
    for result in pool.map(fetch, PAGES):
        print("  got", result)

pool.map(function, inputs) is used like the built-in map but runs in several threads. Results come out in the order of the inputs. If home, which takes 1.5 seconds, is the first input, then news, done after 0.5 seconds, still waits for home and comes out second. You get the function's return value directly, so no shared dictionary is needed.

submit, Future, as_completed

pool.submit(function, argument) hands over one job and immediately returns a Future, a receipt for a result that will come later. future.result() waits for the result and returns it. as_completed(futures) yields the futures one by one in the order they finish. Use it when you want to handle whichever result is ready first.

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(fetch, page) for page in PAGES]
    for future in as_completed(futures):
        print("  got", future.result())

Exceptions inside jobs

When a worker thread raises an exception, nothing shows at that moment. The exception is stored in the Future and raised again when you call future.result(), which is why that call is wrapped in try. If you never call result(), the exception disappears silently, so watch out.

for n, future in zip(range(1, 5), futures):
    try:
        print(n, "->", future.result())
    except ValueError as error:
        print(n, "-> error:", error)

max_workers

max_workers is the number of threads working at once. With 1 it is the same as one by one, and more workers than jobs does not help. For work that is mostly waiting, even dozens of workers are fine, but it is polite to keep the number reasonable so you do not hit someone else's server with too many requests at once.

CPU-bound work, the GIL and processes

Why computation does not get faster

cpu_pool.py splits a pure computation, counting primes, into four chunks and runs them one by one, in a thread pool and in a process pool. Here is the result on this virtual machine (the seconds change from run to run).

CPU cores: 1
one by one 1862 primes  0.7 s

processes  1862 primes  3.3 s
threads: about the same as one by one
processes: slower than one by one

With one core, only one computation can run at a time. Threads and processes just take turns, and the total amount of computing stays the same. The processes are even slower, because starting new Python processes and passing data to and from them adds its own cost.

The GIL

Even on a PC with several cores, splitting computation across threads does not speed it up in standard CPython. A lock called the GIL (Global Interpreter Lock) means that only one thread in a process runs Python code at any moment. Threads do release the GIL while they wait, in time.sleep, file reads or socket reads, which is why I/O-bound work overlaps well in threads. Since Python 3.13 there is also a separate free-threaded build without the GIL, in which threads can compute together on several cores, but the default install is still the build with the GIL. The Python in this virtual machine has the GIL enabled too.

ProcessPoolExecutor

The standard way to spread computation over several cores is processes. Each process has its own interpreter and its own GIL, so as many can compute at once as there are cores. ProcessPoolExecutor is used just like ThreadPoolExecutor.

from concurrent.futures import ProcessPoolExecutor

def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        total = sum(pool.map(count_primes, CHUNKS))

if __name__ == "__main__":   # required: worker processes import this file
    main()

There are some differences. The worker processes import this file to find count_primes, so the if __name__ == "__main__": guard is required and the code has to live in a file (code fed through standard input with python3 - cannot be imported, so it fails). Arguments and results are copied between processes, so they must be values that pickle can convert, and big ones are slow to send. Processes do not share memory, so changing a global variable in one is invisible to the others. On a PC with several cores and a big enough job (at least tens of milliseconds per chunk), a process pool runs faster than one by one by a factor close to the number of cores. If the job is too small, starting the processes costs more than it saves, even on a PC.

asyncio: overlapping waits on one thread

Coroutines and the event loop

The operating system can switch threads at any moment, so with threads you always have to watch for race conditions. asyncio works differently. There is one thread, and it moves on to other work only at the points where a function itself says "I am waiting here" (await). A function defined with async def is a coroutine function, and the manager that runs coroutines in turn is the event loop. asyncio.run(main()) starts the event loop and runs it until main() finishes.

import asyncio

async def brew(drink, seconds):
    print(f"  start {drink}")
    await asyncio.sleep(seconds)     # pause here; other coroutines run meanwhile
    print(f"  done  {drink}")
    return f"{drink} ({seconds} s)"

async def together():
    return await asyncio.gather(brew("coffee", 1), brew("tea", 1), brew("cocoa", 1))

asyncio.run(together())

Awaiting one at a time vs gather

Writing await brew(...) three times in a row starts each one only after the previous one has finished, so it takes 3 seconds. Passing several coroutines to asyncio.gather(...) runs them all together, and when they are all done it returns their results as a list in the order you passed them. Here is the output of asyncio_basics.

one after another: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 3 s
gather: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 1 s

create_task and time limits

asyncio.create_task(coroutine) puts the coroutine on the event loop right away and returns a Task. The caller carries on without waiting and later gets the result with await task when it needs it. Give waits that might never get an answer a time limit with async with asyncio.timeout(seconds):. When the time is up, the awaited work is cancelled and TimeoutError is raised.

task = asyncio.create_task(slow())
try:
    async with asyncio.timeout(0.5):
        await task
except TimeoutError:
    print("gave up after 0.5 s, task cancelled:", task.cancelled())

Two asyncio traps

First, if you forget await, nothing happens. Just calling a coroutine function does not run its body; it only creates a coroutine object. Such a coroutine shows up later as the warning RuntimeWarning: coroutine 'hello' was never awaited.

Second, calling an ordinary function that waits, such as time.sleep(), inside a coroutine stops the whole event loop. There is no await point, so there is no chance to switch to another coroutine. In the example, even under gather, bad takes about 3 s while good, which uses asyncio.sleep, takes about 1 s. Inside coroutines, use awaitable functions such as asyncio.sleep and asyncio.open_connection. If you really must call an ordinary function that waits, run it in a separate thread with await asyncio.to_thread(function, argument).

An asyncio TCP echo server

The server: start_server

asyncio shines brightest in network servers that handle many connections at once. Most clients are quiet most of the time, so one thread can move from connection to connection, handling only the data that has arrived. echo_server.py in echo_server is a server that sends each line it receives back in capitals.

async def handle(reader, writer):
    """Called once per connection; echoes each line back in capitals."""
    while True:
        line = await reader.readline()        # b"" when the client hangs up
        if not line:
            break
        writer.write(line.upper())
        await writer.drain()
    writer.close()
    await writer.wait_closed()

server = await asyncio.start_server(handle, "127.0.0.1", 8765)

asyncio.start_server starts a new handle coroutine for every connection that comes in and passes it a reader for reading and a writer for writing. reader.readline() waits until a line arrives, and returns the empty bytes b"" when the other side hangs up. writer.write() only puts the data in a buffer; await writer.drain() waits until it can actually be sent. What travels over a socket is bytes, not strings, so convert with encode() and decode().

The client: open_connection

reader, writer = await asyncio.open_connection("127.0.0.1", port)
writer.write(b"hi\n")
await writer.drain()
reply = await reader.readline()

Run without arguments, the example opens the server and runs three clients together with gather, all in one script. Port 0 lets the operating system pick a free port, so it cannot clash with other programs. Each client rests half a second between messages, and meanwhile the server answers the other clients: one thread handling three connections together.

A server in its own process

python3 echo_server.py serve & runs only the server, in the background on port 8765, and echo_client.py, a separate process, connects to it. 127.0.0.1 is the address that means "this machine" (loopback), so only programs on the same computer can connect. This server stops by itself after two clients or 30 seconds. Giving a practice server a way to end means a forgotten process never sits on the port. Connecting after the server has ended raises ConnectionRefusedError; the client catches it and prints client: no server on 127.0.0.1:8765.

Most of the time a ThreadPoolExecutor is simpler and safer than handling Thread yourself. If you already use libraries built on asyncio (web frameworks, network clients), go with asyncio. If a computation is slow, first improve the algorithm and data structures, and only then think about processes.

Common mistakes

  • target=f(x): calls the function right there. Write target=f, args=(x,). With a single argument, args=(x) is not a tuple; add the comma: (x,).
  • join() right after start() in the loop: the same as running one by one. Start them all, then wait for them all.
  • Reading results before join(): they are still empty or incomplete.
  • "It was right when I tested it": race conditions show up only sometimes. Guard values that several threads change with a Lock, or pass them through a Queue.
  • Waiting a long time inside a lock, taking the same Lock twice: things slow down or deadlock.
  • Not sending the consumers a stop signal: get() waits forever and the program never ends.
  • Never calling future.result(): exceptions inside jobs vanish silently.
  • Forgetting await, time.sleep inside a coroutine: the code does not run, or the whole event loop stops.
  • Trying to speed up computation with threads: the GIL prevents it. With several cores, use processes.
  • Relying on output order or exact timings: they change from run to run. Sort results or collect them in the order you submitted them, and treat times as approximate.

Summary

  • Concurrency is overlapping waits; parallelism is actually running at the same time on several cores.
  • Overlapping I/O waits with Thread(target=..., args=...), start() and join() turns a 3-second job into a 1-second one.
  • Code that reads, changes and writes a shared value creates race conditions. with lock: lets only one thread run it at a time.
  • queue.Queue is a safe channel for passing work between threads; a sentinel signals the end.
  • ThreadPoolExecutor's map gives results in input order, as_completed in the order they finish.
  • asyncio overlaps waits on one thread by switching coroutines at every await; gather waits for them together.
  • Pure computation does not get faster on this one-core virtual machine. On a multi-core PC, split it across processes.

동시성이란: 기다림을 겹치기

카페의 바리스타

바리스타 한 명이 커피 세 잔을 주문받았다고 해 봅시다. 커피 머신이 한 잔을 내리는 1분 동안 옆에 서서 기다렸다가 다음 잔을 시작하면 3분이 걸립니다. 첫 잔을 머신에 올려 두고 두 번째, 세 번째 잔도 바로 올려 두면 약 1분이면 됩니다. 바리스타는 여전히 한 명이고 손도 두 개뿐입니다. 달라진 것은 기다리는 시간을 겹쳤다는 것뿐입니다. 이것이 동시성입니다.

바리스타가 세 명이면 세 사람이 정말로 동시에 손을 움직입니다. 이것은 병렬성(parallelism)입니다. 동시성은 여러 일을 번갈아 진행하며 함께 다루는 것이고, 병렬성은 여러 일을 같은 순간에 실제로 실행하는 것입니다. 병렬로 실행하려면 CPU 코어가 여러 개 있어야 합니다.

threading: 스레드 만들기

스레드란

스레드는 한 프로그램(프로세스) 안에서 따로 진행되는 실행 흐름입니다. 프로그램은 메인 스레드 하나로 시작합니다. 새 스레드를 만들면 같은 메모리(같은 변수, 같은 객체)를 함께 보면서 각자 자기 함수를 실행합니다. 한 스레드가 time.sleep이나 네트워크 읽기로 기다리는 동안 다른 스레드가 실행됩니다.

Thread, start, join

threading.Thread(target=함수, args=(인자,))로 스레드 객체를 만들고, start()로 출발시키며, join()으로 끝나기를 기다립니다. threads 예제의 핵심 부분입니다.

import threading
import time

def download(name):
    print(f"  start {name}")
    time.sleep(1.0)             # waiting: this thread sleeps, the CPU is free
    print(f"  done  {name}")

threads = [threading.Thread(target=download, args=(name,)) for name in FILES]
for t in threads:
    t.start()                   # starts running download(name) in the background
for t in threads:
    t.join()                    # waits until that thread has finished

시작과 기다림을 두 개의 반복문으로 나눈 것이 중요합니다. 한 반복문 안에서 start() 바로 뒤에 join()을 하면 첫 스레드가 끝날 때까지 두 번째 스레드를 시작하지 않으므로 결국 하나씩 실행하는 것과 같아집니다. 모두 출발시킨 다음에 모두 기다립니다.

시간 재기: time.perf_counter

경과 시간은 time.perf_counter()로 잽니다. 이 함수의 값 자체에는 의미가 없고, 두 번 부른 값의 차가 그 사이에 흐른 초입니다. 시계를 바꿔도 영향을 받지 않아 측정용으로 알맞습니다. 측정값은 실행마다 조금씩 다르므로 예제에서는 round()로 반올림해 "about 1 s"처럼 출력합니다.

func()

스레드에서 결과 받기

스레드가 실행한 함수의 return 값은 버려집니다. 결과가 필요하면 모든 스레드가 볼 수 있는 딕셔너리나 리스트에 넣고, join()으로 모두 끝난 뒤에 읽습니다. start() 직후에 읽으면 아직 비어 있습니다. 결과를 돌려받는 더 편한 방법은 아래 concurrent.futures입니다.

results = {}

def work(name, seconds):
    time.sleep(seconds)
    results[name] = seconds      # each thread writes its own key

# ... start all, then join all ...
print(results)

join을 하지 않으면

join()이 없으면 메인 스레드는 스레드가 끝나기를 기다리지 않고 바로 다음 줄로 갑니다. 그래도 프로그램이 일을 끝내기 전에 사라지지는 않습니다. 파이썬은 데몬이 아닌 스레드가 모두 끝나야 프로세스를 끝내기 때문입니다. Thread(..., daemon=True)로 만든 데몬 스레드는 메인 스레드가 끝나면 함께 중단됩니다. 결과를 써야 하는 지점에서는 반드시 join()합니다.

공유 상태와 경쟁 조건

사라지는 입금

스레드는 메모리를 함께 쓰기 때문에 편리하지만, 바로 그 점이 위험합니다. race_lock 예제에서 스레드 네 개가 하나의 balance에 1000번씩 1을 더합니다. 결과는 4000이어야 합니다.

def deposit(times):
    global balance
    for _ in range(times):
        current = balance          # 1. read
        time.sleep(0)              # 2. pause: another thread may run now
        balance = current + 1      # 3. write back (maybe a stale value)
without lock: expected 4000, got 1001
lost updates: 2999

두 스레드 A와 B가 번갈아 실행되면 이런 일이 생깁니다.

순서스레드 A스레드 Bbalance
1current = balance (10)10
2current = balance (10)10
3balance = 1111
4balance = 1111

입금은 두 번 했는데 값은 1만 늘었습니다. B는 A가 쓰기 전의 낡은 값을 읽었기 때문입니다. 결과가 스레드의 실행 순서에 따라 달라지는 상황을 경쟁 조건(race condition)이라고 합니다. 오류 메시지가 없고, 어떤 실행에서는 우연히 맞기도 해서 찾기 어려운 버그입니다. 예제의 time.sleep(0)은 읽기와 쓰기 사이에서 일부러 차례를 넘겨 이 문제를 매번 드러나게 합니다.

한 줄이어도 안전하지 않다

counter += 1은 한 줄이지만 한 동작이 아닙니다. dis.dis로 바이트코드를 보면 읽기, 더하기, 쓰기로 나뉘어 있습니다.

LOAD_GLOBAL              0 (counter)
LOAD_SMALL_INT           1
BINARY_OP               13 (+=)
STORE_GLOBAL             0 (counter)

실습 가상 머신에서 sleep 없이 counter += 1만 40만 번 하면 대개 400000이 정확히 나옵니다. 지금의 CPython이 이런 짧은 코드 중간에서 스레드를 바꾸는 일이 드물기 때문입니다. 하지만 이것은 구현의 우연이지 언어의 약속이 아닙니다. 버전이 바뀌거나, 코드가 조금 길어지거나, GIL이 없는 빌드에서 여러 코어로 실행하면 틀린 값이 나올 수 있습니다. 결과가 맞게 나왔다는 것은 안전하다는 증거가 아닙니다.

threading.Lock

Lock(잠금)은 한 번에 한 스레드만 가질 수 있는 열쇠입니다. with lock: 블록에 들어갈 때 열쇠를 얻고(acquire) 나올 때 돌려줍니다(release). 다른 스레드가 열쇠를 갖고 있으면 돌려받을 때까지 기다립니다. 블록 안에서 예외가 나도 with가 열쇠를 돌려주므로 acquire()와 release()를 직접 부르는 것보다 안전합니다.

lock = threading.Lock()

def deposit(times):
    global balance
    for _ in range(times):
        with lock:                 # only one thread at a time in here
            current = balance
            time.sleep(0)
            balance = current + 1
with lock: expected 4000, got 4000
correct

잠금으로 감싸는 부분(임계 구역)은 공유 값을 읽고 바꾸는 최소한으로 합니다. 잠금 안에서 오래 기다리면 다른 스레드가 모두 멈춰 스레드를 쓴 의미가 없어집니다.

교착 상태

Lock은 이미 열쇠를 가진 스레드도 다시 얻을 수 없습니다. 같은 스레드가 with lock: 안에서 다시 lock을 얻으려 하면 자기 자신을 영원히 기다립니다. 두 스레드가 서로 상대의 잠금을 기다리는 경우도 마찬가지입니다. 이를 교착 상태(deadlock)라고 합니다. 예제에서는 lock.acquire(timeout=1)로 1초만 기다려 False를 확인합니다. 같은 스레드가 여러 번 얻어야 하는 경우에는 threading.RLock을 씁니다. 잠금을 여러 개 쓴다면 모든 스레드가 같은 순서로 얻도록 합니다.

queue.Queue: 생산자와 소비자

일을 나누는 가장 안전한 방법

공유 변수를 잠금으로 지키는 대신, 스레드끼리 메시지를 주고받게 하면 실수할 여지가 줄어듭니다. queue.Queue는 여러 스레드가 동시에 써도 안전한 줄(FIFO)입니다. 일을 만드는 쪽(생산자)은 put()으로 넣고, 일을 처리하는 쪽(소비자)은 get()으로 꺼냅니다. 큐 안에서 잠금을 알아서 처리합니다.

메서드하는 일
q.put(item)넣는다. maxsize가 차 있으면 자리가 날 때까지 기다린다
q.get()가장 먼저 넣은 것을 꺼낸다. 비어 있으면 들어올 때까지 기다린다
q.get(timeout=1)1초까지만 기다리고, 그래도 없으면 queue.Empty
q.put_nowait(item)기다리지 않는다. 가득 차 있으면 queue.Full
q.qsize()지금 들어 있는 개수(다른 스레드 때문에 곧 바뀔 수 있다)

웨이터와 요리사

producer_consumer의 kitchen.py에서는 웨이터 스레드가 주문을 큐에 넣고, 요리사 스레드 두 개가 하나씩 꺼내 0.5초씩 요리합니다.

orders = queue.Queue(maxsize=3)   # the counter holds at most 3 tickets

def waiter():
    for dish in ORDERS:
        orders.put(dish)              # blocks while the counter is full
    for _ in range(COOKS):
        orders.put(None)              # one stop signal per cook

def cook(name):
    while True:
        dish = orders.get()           # blocks until there is an order
        if dish is None:
            break
        time.sleep(COOK_TIME)
        served.put((dish, name))

요리사는 while True로 계속 주문을 꺼내므로, 일이 끝났다는 것을 알려 줄 방법이 필요합니다. 여기서는 요리사 수만큼 None을 넣고, None을 꺼낸 요리사는 반복을 끝냅니다. 이런 특별한 값을 센티널(sentinel)이라고 합니다. 센티널을 하나만 넣으면 요리사 하나만 끝나고 나머지는 get()에서 영원히 기다려 프로그램이 끝나지 않습니다.

maxsize=3은 큐의 크기를 제한합니다. 생산자가 소비자보다 빠를 때 메모리에 일이 끝없이 쌓이지 않도록 생산자를 잠시 세우는 역할(배압, backpressure)을 합니다. 실행해 보면 웨이터가 주문 다섯 개를 넣은 뒤 요리가 하나 끝날 때까지 멈추는 것을 볼 수 있습니다.

served 6 dishes: bibimbap, japchae, kimbap, mandu, ramen, tteokbokki
2 cooks: about 1.5 s (one cook would need 3.0 s)

요리사를 셋으로 늘리면 about 1.0 s입니다. 소비자 수만 바꾸면 되고 생산자 코드는 그대로입니다. 결과 목록을 sorted()로 정렬해 출력하는 이유는 어느 요리가 먼저 끝나는지가 실행마다 다를 수 있기 때문입니다. 큐에는 task_done()과 join()으로 "넣은 일이 모두 처리될 때까지 기다리기"를 하는 방법도 있습니다.

concurrent.futures: 스레드 풀

ThreadPoolExecutor와 map

스레드를 만들고, 출발시키고, 기다리고, 결과를 모으는 일은 매번 비슷합니다. concurrent.futures.ThreadPoolExecutor는 일꾼 스레드 몇 개를 미리 만들어 두고(풀), 맡긴 일을 나눠 처리한 뒤 결과를 돌려줍니다. with 블록을 나갈 때 모든 일이 끝나기를 기다리고 스레드를 정리합니다.

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=3) as pool:
    for result in pool.map(fetch, PAGES):
        print("  got", result)

pool.map(함수, 입력들)은 내장 map처럼 쓰지만 여러 스레드에서 실행합니다. 결과는 입력 순서대로 나옵니다. 1.5초 걸리는 home이 첫 입력이면, 0.5초 만에 끝난 news도 home이 끝날 때까지 기다렸다가 두 번째로 나옵니다. 함수의 return 값을 그대로 받을 수 있으니 공유 딕셔너리가 필요 없습니다.

submit, Future, as_completed

pool.submit(함수, 인자)는 일 하나를 맡기고 곧바로 Future를 돌려줍니다. Future는 나중에 나올 결과의 영수증입니다. future.result()는 결과가 나올 때까지 기다렸다가 돌려줍니다. as_completed(futures)는 Future들을 끝난 순서대로 하나씩 내줍니다. 먼저 끝난 결과부터 처리하고 싶을 때 씁니다.

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(fetch, page) for page in PAGES]
    for future in as_completed(futures):
        print("  got", future.result())
map: results in the order of the inputs
  got home.html
  got news.html
  got about.html
submit + as_completed: results in the order they finish
  got news.html
  got about.html
  got home.html
total: about 3 s (one by one: 6 s)

작업 안의 예외

일꾼 스레드에서 예외가 나도 그 자리에서는 아무것도 보이지 않습니다. 예외는 Future 안에 보관되었다가 future.result()를 부를 때 다시 발생합니다. 그래서 result() 호출을 try로 감쌉니다. result()를 한 번도 부르지 않으면 예외가 조용히 사라지므로 주의합니다.

for n, future in zip(range(1, 5), futures):
    try:
        print(n, "->", future.result())
    except ValueError as error:
        print(n, "-> error:", error)

max_workers

max_workers는 동시에 일하는 스레드 수입니다. 1이면 하나씩 하는 것과 같고, 일의 개수보다 많아도 더 빨라지지 않습니다. 기다림이 대부분인 일이라면 수십 개까지 늘려도 괜찮지만, 상대 서버에 너무 많은 요청을 한꺼번에 보내지 않도록 적당히 제한하는 것이 예의입니다.

cpu_pool.py는 소수를 세는 계산만 하는 일을 네 조각으로 나눠 하나씩, 스레드 풀로, 프로세스 풀로 각각 실행합니다. 이 가상 머신에서의 결과입니다(초 단위 숫자는 실행마다 다릅니다).

코어가 하나이면 계산은 한 번에 하나만 할 수 있습니다. 스레드든 프로세스든 번갈아 실행할 뿐 전체 계산량은 그대로입니다. 프로세스 쪽은 새 파이썬 프로세스를 띄우고 데이터를 주고받는 비용까지 더해져 오히려 느립니다.

GIL

코어가 여러 개인 PC에서도 보통의 CPython에서는 스레드로 계산을 나눠도 빨라지지 않습니다. GIL(Global Interpreter Lock)이라는 잠금 때문에 한 프로세스 안에서 파이썬 코드를 실행하는 스레드는 한순간에 하나뿐이기 때문입니다. 대신 스레드가 time.sleep, 파일 읽기, 소켓 읽기처럼 기다리는 동안에는 GIL을 내려놓으므로 I/O 작업은 스레드로 잘 겹쳐집니다. 파이썬 3.13부터는 GIL이 없는 별도 빌드(free-threaded build)도 있어 스레드가 여러 코어에서 함께 계산할 수 있지만, 아직 기본 설치는 GIL이 있는 빌드입니다. 이 가상 머신의 파이썬도 GIL이 켜져 있습니다.

ProcessPoolExecutor

여러 코어로 계산을 나누는 표준적인 방법은 프로세스입니다. 프로세스마다 자기 인터프리터와 자기 GIL을 가지므로 코어 수만큼 동시에 계산할 수 있습니다. ProcessPoolExecutor는 ThreadPoolExecutor와 사용법이 같습니다.

from concurrent.futures import ProcessPoolExecutor

def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        total = sum(pool.map(count_primes, CHUNKS))

if __name__ == "__main__":   # required: worker processes import this file
    main()

몇 가지 차이가 있습니다. 일꾼 프로세스는 이 파일을 import해서 count_primes를 찾으므로 if __name__ == "__main__": 가드가 반드시 필요하고, 코드가 파일에 있어야 합니다(python3 -로 표준 입력에 넣은 코드는 import할 수 없어 오류가 납니다). 인자와 결과는 프로세스 사이를 복사되어 오가므로 pickle로 바꿀 수 있는 값이어야 하고, 크면 그만큼 느립니다. 프로세스끼리는 메모리를 공유하지 않으므로 전역 변수를 바꿔도 다른 프로세스에는 보이지 않습니다. 코어가 여러 개인 PC에서 일이 충분히 크면(조각마다 적어도 수십 밀리초 이상) 프로세스 풀이 하나씩보다 코어 수에 가까운 배수만큼 빨라집니다. 일이 너무 작으면 PC에서도 프로세스를 띄우는 비용이 더 큽니다.

I/O 작업 + 스레드/asyncio빨라진다빨라진다
CPU 작업 + 스레드그대로그대로(GIL). free-threaded 빌드에서는 빨라질 수 있다
CPU 작업 + 프로세스오히려 느려진다일이 크면 빨라진다

asyncio: 스레드 하나로 기다림 겹치기

코루틴과 이벤트 루프

스레드는 운영체제가 언제든 바꿔 실행하므로 경쟁 조건을 늘 조심해야 합니다. asyncio는 다른 방식을 씁니다. 스레드는 하나이고, 함수가 스스로 "여기서 기다린다"고 밝힌 지점(await)에서만 다른 일로 넘어갑니다. async def로 정의한 함수를 코루틴 함수라고 하고, 코루틴들을 번갈아 실행하는 관리자를 이벤트 루프라고 합니다. asyncio.run(main())이 이벤트 루프를 시작하고 main()이 끝날 때까지 돌립니다.

import asyncio

async def brew(drink, seconds):
    print(f"  start {drink}")
    await asyncio.sleep(seconds)     # pause here; other coroutines run meanwhile
    print(f"  done  {drink}")
    return f"{drink} ({seconds} s)"

async def together():
    return await asyncio.gather(brew("coffee", 1), brew("tea", 1), brew("cocoa", 1))

asyncio.run(together())

await를 하나씩 vs gather

await brew(...)를 세 번 차례로 쓰면 하나가 끝나야 다음을 시작하므로 3초가 걸립니다. asyncio.gather(...)에 코루틴 여러 개를 넘기면 모두 함께 진행하고, 모두 끝나면 결과를 넘긴 순서대로 리스트로 돌려줍니다. asyncio_basics의 출력입니다.

one after another: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 3 s
gather: ['coffee (1 s)', 'tea (1 s)', 'cocoa (1 s)'] in about 1 s

create_task와 시간 제한

asyncio.create_task(코루틴)은 코루틴을 이벤트 루프에 바로 올리고 Task를 돌려줍니다. 만든 쪽은 기다리지 않고 계속 진행하다가, 필요할 때 await task로 결과를 받습니다. 응답이 오지 않을 수 있는 기다림에는 async with asyncio.timeout(초):로 시간 제한을 둡니다. 제한 시간이 지나면 기다리던 작업이 취소되고 TimeoutError가 납니다.

task = asyncio.create_task(slow())
try:
    async with asyncio.timeout(0.5):
        await task
except TimeoutError:
    print("gave up after 0.5 s, task cancelled:", task.cancelled())

asyncio의 두 가지 함정

첫째, await를 잊으면 아무 일도 일어나지 않습니다. 코루틴 함수를 부르기만 하면 몸체는 실행되지 않고 coroutine 객체만 생깁니다. 이런 코루틴은 나중에 RuntimeWarning: coroutine 'hello' was never awaited 경고로 드러납니다.

둘째, 코루틴 안에서 time.sleep()처럼 기다리는 일반 함수를 부르면 이벤트 루프 전체가 멈춥니다. await 지점이 없으니 다른 코루틴으로 넘어갈 기회가 없습니다. 예제에서 gather로 묶어도 bad는 about 3 s, asyncio.sleep을 쓴 good은 about 1 s입니다. 코루틴 안에서는 asyncio.sleep, asyncio.open_connection처럼 await할 수 있는 함수를 씁니다. 어쩔 수 없이 기다리는 일반 함수를 불러야 한다면 await asyncio.to_thread(함수, 인자)로 별도 스레드에서 실행합니다.

asyncio TCP 에코 서버

서버: start_server

asyncio가 가장 빛나는 곳은 많은 연결을 동시에 다루는 네트워크 서버입니다. 클라이언트 대부분은 대부분의 시간 동안 조용하므로, 스레드 하나가 이 연결 저 연결을 오가며 도착한 데이터만 처리하면 됩니다. echo_server의 echo_server.py는 받은 줄을 대문자로 돌려주는 서버입니다.

async def handle(reader, writer):
    """Called once per connection; echoes each line back in capitals."""
    while True:
        line = await reader.readline()        # b"" when the client hangs up
        if not line:
            break
        writer.write(line.upper())
        await writer.drain()
    writer.close()
    await writer.wait_closed()

server = await asyncio.start_server(handle, "127.0.0.1", 8765)

asyncio.start_server는 연결이 하나 들어올 때마다 handle 코루틴을 새로 시작하고, 읽기용 reader와 쓰기용 writer를 넘깁니다. reader.readline()은 줄 하나가 올 때까지 기다리며, 상대가 연결을 끊으면 빈 바이트열 b""을 돌려줍니다. writer.write()는 보낼 데이터를 버퍼에 넣기만 하고, await writer.drain()이 실제로 보낼 수 있을 때까지 기다립니다. 소켓으로 오가는 것은 문자열이 아니라 바이트이므로 encode()와 decode()로 바꿉니다.

클라이언트: open_connection

reader, writer = await asyncio.open_connection("127.0.0.1", port)
writer.write(b"hi\n")
await writer.drain()
reply = await reader.readline()

예제를 인자 없이 실행하면 한 스크립트 안에서 서버를 열고 클라이언트 세 개를 gather로 함께 돌립니다. 포트로 0을 주면 운영체제가 빈 포트를 골라 주므로 다른 프로그램과 부딪히지 않습니다. 각 클라이언트는 메시지 사이에 0.5초씩 쉬지만, 그동안 서버는 다른 클라이언트에 답합니다. 스레드 하나로 세 연결을 함께 처리하는 것입니다.

client got: ['MINA: HI', 'MINA: BYE']
client got: ['JUN: HELLO', 'JUN: SEE YOU']
client got: ['SORA: HEY', 'SORA: LATER']

따로 띄운 서버

python3 echo_server.py serve &는 서버만 8765번 포트에서 백그라운드로 실행하고, 다른 프로세스인 echo_client.py가 접속합니다. 127.0.0.1은 자기 자신을 가리키는 주소(루프백)라 같은 컴퓨터 안에서만 연결됩니다. 이 서버는 클라이언트 두 명을 받거나 30초가 지나면 스스로 끝납니다. 연습용 서버에 종료 조건을 넣어 두면 잊고 켜 둔 프로세스가 포트를 차지하는 일이 없습니다. 서버가 끝난 뒤 접속하면 ConnectionRefusedError가 나는데, 클라이언트는 이를 잡아 client: no server on 127.0.0.1:8765를 출력합니다.

무엇을 고를까

도구알맞은 일주의할 점
threading.Thread기다림이 있는 일 몇 개를 겹치기공유 값은 Lock으로. 결과 받기가 번거롭다
queue.Queue만드는 쪽과 처리하는 쪽이 나뉜 흐름소비자에게 정지 신호를 보낸다
ThreadPoolExecutor같은 함수를 여러 입력에 실행하는 I/O 작업예외는 result()에서 나온다
asyncio연결이 아주 많은 네트워크 프로그램모든 기다림이 await여야 한다
ProcessPoolExecutor여러 코어에서 큰 계산__main__ 가드, 복사 비용, 코어가 하나면 이득 없음

대부분의 경우 직접 Thread를 다루기보다 ThreadPoolExecutor가 간단하고 안전합니다. 이미 asyncio로 된 라이브러리(웹 프레임워크, 네트워크 클라이언트)를 쓴다면 asyncio를 따릅니다. 계산이 느리다면 먼저 알고리즘과 자료 구조를 개선하고, 그다음에 프로세스를 생각합니다.

흔한 실수

  • target=f(x): 함수를 그 자리에서 호출해 버립니다. target=f, args=(x,)로 씁니다. 인자가 하나일 때 args=(x)는 튜플이 아니므로 쉼표를 붙여 (x,)로 씁니다.
  • 반복문 안에서 start() 직후 join(): 하나씩 실행하는 것과 같아집니다. 모두 시작한 뒤 모두 기다립니다.
  • join() 전에 결과 읽기: 아직 비어 있거나 일부만 있습니다.
  • "테스트할 때는 맞았다": 경쟁 조건은 가끔만 나타납니다. 여러 스레드가 바꾸는 값은 Lock으로 지키거나 Queue로 주고받습니다.
  • 잠금 안에서 오래 기다리기, 같은 Lock을 두 번 얻기: 느려지거나 교착 상태가 됩니다.
  • 소비자에게 정지 신호를 보내지 않기: get()이 영원히 기다려 프로그램이 끝나지 않습니다.
  • future.result()를 부르지 않기: 작업 안의 예외가 조용히 사라집니다.
  • await 잊기, 코루틴 안의 time.sleep: 실행되지 않거나 이벤트 루프 전체가 멈춥니다.
  • 계산을 스레드로 빠르게 하려 하기: GIL 때문에 빨라지지 않습니다. 코어가 여러 개라면 프로세스를 씁니다.
  • 출력 순서나 정확한 시간에 기대기: 실행마다 달라집니다. 결과는 정렬하거나 넘긴 순서로 모으고, 시간은 대략으로 봅니다.

정리

  • 동시성은 기다림을 겹치는 것이고, 병렬성은 여러 코어에서 실제로 동시에 실행하는 것입니다.
  • Thread(target=..., args=...), start(), join()으로 I/O 대기를 겹치면 3초 걸리던 일이 1초가 됩니다.
  • 공유 값을 읽고-바꾸고-쓰는 코드는 경쟁 조건을 만듭니다. with lock:으로 한 번에 한 스레드만 실행하게 합니다.
  • queue.Queue는 스레드끼리 일을 안전하게 주고받는 통로입니다. 센티널로 끝을 알립니다.
  • ThreadPoolExecutor의 map은 입력 순서, as_completed는 끝난 순서로 결과를 줍니다.
  • asyncio는 스레드 하나에서 await 지점마다 코루틴을 바꿔 가며 기다림을 겹칩니다. gather로 함께 기다립니다.
  • 계산만 하는 일은 코어가 하나인 이 가상 머신에서 빨라지지 않습니다. 여러 코어 PC에서는 프로세스로 나눕니다.
