Examples예제

paths ~/files/paths

Look around the notes folder with pathlib's Path: check it with exists() and is_dir(), list what is inside with iterdir(), pick only matching files with glob() and rglob() and read them with read_text(encoding="utf-8"). Join paths with the / operator, take them apart with name, stem, suffix and parent, and write a Korean text file with write_text.pathlib의 Path로 notes 폴더를 둘러본다. exists()·is_dir()로 확인하고, iterdir()로 안의 항목을, glob()·rglob()으로 패턴에 맞는 파일만 골라 read_text(encoding="utf-8")로 읽는다. / 연산자로 경로를 잇고 name·stem·suffix·parent로 쪼개 보며, write_text로 한글 파일을 써 본다.

Steps실행 순서

  1. ls -R notes

    The practice folder: notes holds three files (memo.txt, scores.csv, todo.txt) and a subfolder archive, which holds old.txt.실습용 폴더 구조다. notes 안에 파일 세 개(memo.txt, scores.csv, todo.txt)와 하위 폴더 archive가 있고, archive 안에 old.txt가 있다.

  2. python3 explore.py

    iterdir() returns only what is directly inside the folder, in no fixed order, so the program sorts it. glob("*.txt") finds the two .txt files directly in notes; rglob("*.txt") also finds archive/old.txt. The Korean file reads fine with encoding="utf-8": '오늘 할 일' comes out as written.iterdir()는 폴더 바로 안의 항목만 돌려주고 순서가 정해져 있지 않아서 sorted()로 정렬했다. glob("*.txt")는 notes 바로 안의 .txt 두 개만, rglob("*.txt")는 archive/old.txt까지 세 개를 찾는다. 한글 파일도 encoding="utf-8"로 읽으니 '오늘 할 일'이 그대로 나온다.

  3. python3 - <<'EOF' from pathlib import Path p = Path("notes") / "archive" / "old.txt" print(p) print(p.name, p.stem, p.suffix) print(p.parent, p.parent.parent) print(p.with_suffix(".bak")) print(p.exists(), Path("notes/nope.txt").exists()) print(Path.cwd()) print(p.resolve()) print(Path.home()) EOF

    The / operator joins path pieces into notes/archive/old.txt (no need to glue "/" onto strings yourself). name is old.txt, stem is old, suffix is .txt and parent is notes/archive. with_suffix only builds a new path with another extension; it does not touch the file. A relative path is relative to the current folder (Path.cwd()), and resolve() turns it into an absolute path such as /home/student/files/paths/notes/archive/old.txt./ 연산자가 경로 조각을 이어 notes/archive/old.txt를 만든다(문자열 더하기로 "/"를 직접 붙일 필요가 없다). name은 old.txt, stem은 old, suffix는 .txt, parent는 notes/archive다. with_suffix는 확장자만 바꾼 새 경로를 만들 뿐 파일은 건드리지 않는다. 상대 경로는 현재 폴더(Path.cwd())를 기준으로 하고, resolve()는 그것을 /home/student/files/paths/notes/archive/old.txt 같은 절대 경로로 바꾼다.

  4. python3 - <<'EOF' from pathlib import Path out = Path("notes/hello.txt") n = out.write_text("안녕하세요\nHello\n", encoding="utf-8") print(n, "characters written") print(out.read_text(encoding="utf-8"), end="") print(len(out.read_bytes()), "bytes on disk") EOF

    write_text creates the file or overwrites it completely, and returns the number of characters written: 12. On disk it takes 22 bytes, because in UTF-8 each Korean character is 3 bytes (5×3 + 1 + 5 + 1). Running it again overwrites the file, so the result is the same.write_text는 파일을 새로 만들거나 통째로 덮어쓰고, 쓴 글자 수 12를 돌려준다. 디스크에는 22바이트가 저장된다. UTF-8에서 한글 한 글자는 3바이트이기 때문이다(5×3 + 1 + 5 + 1). 다시 실행해도 덮어쓰므로 결과가 같다.

  5. python3 - <<'EOF' from pathlib import Path p = Path("notes/nope.txt") if p.exists(): print(p.read_text(encoding="utf-8")) else: print(p, "does not exist, skipping") Path("notes/out/2026").mkdir(parents=True, exist_ok=True) print(sorted(x.name for x in Path("notes").iterdir())) EOF

    Checking with exists() before reading keeps a missing file from stopping the program (a later example does the same with try/except). mkdir(parents=True, exist_ok=True) creates the in-between folder out as well, and raises no error if the folder already exists. hello.txt and out now appear in the listing.읽기 전에 exists()로 확인하면 없는 파일 때문에 멈추지 않는다(다음 예제에서는 try/except로 같은 일을 한다). mkdir(parents=True, exist_ok=True)는 중간 폴더 out까지 한 번에 만들고, 이미 있어도 오류를 내지 않는다. 목록에 hello.txt와 out이 새로 보인다.

  6. rm -r notes/out notes/hello.txt; ls notes

    Remove the practice file and folders to get back to the starting state.연습으로 만든 파일과 폴더를 지워 처음 상태로 돌린다.

file_modes ~/files/file_modes

Compare open()'s modes r, w, a and x. diary.py appends one line from the command line to the end of diary.txt in "a" mode, then loops over the file object with for and prints the whole diary with line numbers. Then see that w empties a file, x refuses to overwrite one, and a file is closed when its with block ends.open()의 모드 r·w·a·x를 비교한다. diary.py는 명령줄로 받은 한 줄을 "a" 모드로 diary.txt 끝에 붙이고, 파일 객체를 for로 돌며 줄 번호를 붙여 전체를 출력한다. 이어서 w가 파일을 비우는 것, x가 덮어쓰기를 거부하는 것, with 블록이 끝나면 파일이 닫히는 것을 확인한다.

Steps실행 순서

  1. rm -f diary.txt python3 diary.py 오늘 파이썬으로 파일을 썼다

    First delete diary.txt to start clean. "a" mode creates the file if it does not exist: 1: 오늘 파이썬으로 파일을 썼다.먼저 diary.txt를 지워 깨끗하게 시작한다. "a" 모드는 파일이 없으면 새로 만든다. 1: 오늘 파이썬으로 파일을 썼다.

  2. python3 diary.py 두 번째 줄 cat diary.txt

    "a" adds after the existing content, so there are now two lines. write() does not add a newline, so the program writes entry + "\n". When printing, rstrip() removes the \n at the end of each line so no blank lines sneak in."a"는 기존 내용 뒤에 덧붙인다. 이제 두 줄이다. write()는 줄바꿈을 붙여 주지 않으므로 프로그램이 entry + "\n"을 썼다. 출력할 때는 rstrip()으로 줄 끝의 \n을 떼어 빈 줄이 끼지 않게 했다.

  3. python3 - <<'EOF' with open("diary.txt", "w", encoding="utf-8") as f: f.write("새 일기장\n") with open("diary.txt", encoding="utf-8") as f: print(repr(f.read())) EOF

    "w" erases the whole file the moment it is opened. The two earlier lines are gone and only '새 일기장\n' remains. Losing data by opening an existing file with "w" is a common mistake."w"는 파일을 여는 순간 내용을 모두 지운다. 앞의 두 줄은 사라지고 '새 일기장\n'만 남는다. 기존 파일에 "w"를 쓰는 실수로 데이터를 잃는 일이 흔하다.

  4. python3 - <<'EOF' try: with open("diary.txt", "x", encoding="utf-8") as f: f.write("never written\n") except FileExistsError as e: print("x refused:", e) with open("fresh.txt", "x", encoding="utf-8") as f: f.write("created\n") print("fresh.txt created") EOF rm fresh.txt

    "x" only creates new files; if the file exists it raises FileExistsError: [Errno 17] File exists: 'diary.txt'. That makes it safe for files that must not be overwritten. The rm at the end deletes fresh.txt so pressing the button again gives the same result."x"는 새 파일만 만든다. 이미 있으면 FileExistsError: [Errno 17] File exists: 'diary.txt'를 낸다. 덮어쓰면 안 되는 파일에 안전하다. 마지막의 rm은 다시 눌러도 같은 결과가 나오게 fresh.txt를 지운다.

  5. python3 - <<'EOF' f = open("diary.txt", encoding="utf-8") print("after open:", f.closed) f.close() print("after close():", f.closed) with open("diary.txt", encoding="utf-8") as f: print("inside with:", f.closed) print("after with:", f.closed) try: f.read() except ValueError as e: print("ValueError:", e) EOF

    A file from a bare open() stays open until you call close(). A with block closes it the moment the block ends, even if an error happens inside: inside with: False, after with: True. Reading a closed file gives ValueError: I/O operation on closed file.open()만 하면 close()를 부를 때까지 열려 있다. with 블록은 끝나는 순간(중간에 오류가 나도) 파일을 닫아 준다: inside with: False, after with: True. 닫힌 파일을 읽으면 ValueError: I/O operation on closed file.이다.

  6. python3 - <<'EOF' with open("log.txt", "w", encoding="utf-8") as f: f.write("a") f.write("b\n") print("c", "d", sep=",", file=f) f.writelines(["e\n", "f\n"]) with open("log.txt", encoding="utf-8") as f: print(repr(f.read())) with open("log.txt", encoding="utf-8") as f: print(f.readline(), end="") print(f.readlines()) EOF rm log.txt

    Three ways to write: write() writes exactly the string you give it (a and b end up on one line), print(..., file=f) follows the same rules as on screen, newline included, and writelines() writes a list one after another (newlines are up to you). Reading: read() gives the whole text, readline() one line, readlines() a list of the remaining lines. A file object remembers where it stopped, so readlines() after readline() no longer has the first line.쓰는 방법 세 가지: write()는 준 문자열 그대로(a와 b가 한 줄에 붙는다), print(..., file=f)는 화면과 같은 규칙으로 줄바꿈까지, writelines()는 리스트를 이어 쓴다(줄바꿈은 직접). 읽기: read()는 전체 문자열, readline()은 한 줄, readlines()는 남은 줄의 리스트다. 파일 객체는 읽은 위치를 기억해서 readline() 뒤의 readlines()에는 첫 줄이 없다.

exceptions ~/files/exceptions

Learn how try/except/else/finally flows. calc.py splits each input line "a b" and computes a / b; a bad line has its ValueError or ZeroDivisionError caught separately, the reason is printed, and the program goes on with the next line. Also catch KeyError and FileNotFoundError, and finally read the traceback of an uncaught error from the bottom up.try/except/else/finally의 흐름을 익힌다. calc.py는 입력 한 줄마다 "a b"를 나눠 a / b를 계산하고, 잘못된 줄은 ValueError·ZeroDivisionError를 따로 잡아 이유를 알린 뒤 다음 줄로 넘어간다. KeyError·FileNotFoundError도 잡아 보고, 마지막에는 잡지 않은 오류의 Traceback을 아래에서 위로 읽는다.

Steps실행 순서

  1. printf '10 4\n7 0\nten 2\n9\n8 2\n' | python3 calc.py

    Feed in five lines. Line 2 raises ZeroDivisionError, line 3 the ValueError from int('ten'), and line 4 has only one number, so unpacking into a_text, b_text raises ValueError (not enough values to unpack). Each line has its own try, so the bad lines do not stop the rest: 2 done, 3 skipped. Only the lines that succeeded are printed, from else.다섯 줄을 넣는다. 둘째 줄은 ZeroDivisionError, 셋째 줄은 int('ten')의 ValueError, 넷째 줄은 숫자가 하나뿐이라 a_text, b_text = ... 풀기에서 ValueError(not enough values to unpack)가 난다. 각 줄의 try가 따로 있어서 나쁜 줄이 있어도 끝까지 처리한다: 2 done, 3 skipped. 성공한 줄만 else에서 출력한다.

  2. python3 - <<'EOF' def to_int(text): try: n = int(text) except ValueError: print(f" except: {text!r} is not a number") return None else: print(f" else: got {n}") return n finally: print(" finally: always runs") print(to_int("42")) print(to_int("abc")) EOF

    Watch the order. On success it is try → else → finally; on failure try → except → finally. finally always runs just before the function ends, even when there is a return, which is why clean-up code such as closing a file goes there.실행 순서를 본다. 성공하면 try → else → finally, 실패하면 try → except → finally다. finally는 return이 있어도 함수가 끝나기 직전에 반드시 실행된다. 그래서 파일 닫기 같은 정리 코드를 둔다.

  3. python3 - <<'EOF' prices = {"apple": 1200, "pear": 2500} for item in ["apple", "mango"]: try: print(item, prices[item]) except KeyError as e: print("no price for", e) print(prices.get("mango", 0)) EOF

    Looking up a missing key with [] raises KeyError; printing the exception caught with as e shows the missing key 'mango'. If the key may simply be absent, get(key, default) is simpler: 0.딕셔너리에 없는 키를 []로 꺼내면 KeyError다. as e로 받은 예외를 출력하면 빠진 키 'mango'가 보인다. 없을 수도 있는 키라면 get(키, 기본값)이 더 간단하다: 0.

  4. python3 - <<'EOF' for name in ["calc.py", "nope.txt"]: try: with open(name, encoding="utf-8") as f: print(name, "has", len(f.readlines()), "lines") except FileNotFoundError as e: print("missing:", e.filename, "|", e) EOF

    Opening a missing file raises FileNotFoundError. The exception object carries information: e.filename is nope.txt and the message is [Errno 2] No such file or directory: 'nope.txt'. Instead of checking with exists() first, you just open the file and handle the failure.없는 파일을 열면 FileNotFoundError다. 예외 객체에는 정보가 들어 있다: e.filename은 nope.txt, 메시지는 [Errno 2] No such file or directory: 'nope.txt'. exists()로 미리 확인하는 대신 일단 열어 보고 실패를 처리하는 방식이다.

  5. python3 report.py

    An uncaught error stops the program and leaves a traceback. Mina: 84.0 was printed, but the program stopped at Joon, so Sora never appears. The bottom line, ZeroDivisionError: division by zero, says what went wrong; the line just above (line 5, in average) says where; the lines above that say who called it (line 9 in report, and at the top line 13, report("Joon", [])). The ~~~^^^ marks point at the part of the line that failed.잡지 않은 오류는 프로그램을 멈추고 Traceback을 남긴다. Mina: 84.0은 출력됐지만 Joon에서 멈춰 Sora는 출력되지 않는다. 맨 아래 줄 ZeroDivisionError: division by zero가 무엇이 잘못됐는지, 바로 위 줄(average의 line 5)이 어디서 났는지, 그 위가 누가 불렀는지(report의 line 9, 그리고 맨 위 line 13의 report("Joon", []))를 알려 준다. ~~~^^^ 표시는 줄 안에서 문제가 된 부분이다.

custom_errors ~/files/custom_errors

Raise exceptions yourself with raise. bank.py defines BankError, a subclass of Exception, and its subclass InsufficientFunds; it raises ValueError for an invalid amount and InsufficientFunds when the balance is too low. config.py turns low-level errors such as a missing file or a non-number into raise ConfigError(...) from e, so the caller only has one exception to catch (exception chaining).raise로 직접 예외를 일으킨다. bank.py는 Exception을 상속한 BankError와 그 하위 InsufficientFunds를 만들고, 잘못된 금액에는 ValueError를, 잔액 부족에는 InsufficientFunds를 raise한다. config.py는 파일 없음·숫자 아님 같은 낮은 수준의 오류를 raise ConfigError(...) from e로 바꿔 호출하는 쪽이 한 가지만 잡으면 되게 한다(예외 연결).

Steps실행 순서

  1. python3 bank.py

    Four withdrawals from a balance of 10000. -500 hits the ValueError raised by withdraw; 20000 hits InsufficientFunds. The shortfall of 13000 is computed from e.amount and e.balance, stored in the exception object. A failed withdrawal leaves the balance alone, so the last one (7000) succeeds and the balance becomes 0.잔액 10000에서 네 번 출금한다. -500은 withdraw가 raise한 ValueError, 20000은 InsufficientFunds다. 예외 객체에 담아 둔 e.amount와 e.balance로 부족한 금액 13000을 계산했다. 실패한 출금은 잔액을 바꾸지 않으므로 마지막 7000은 성공하고 잔액이 0이 된다.

  2. python3 - <<'EOF' from bank import Account, BankError, InsufficientFunds account = Account("Joon", 500) try: account.withdraw(1000) except BankError as e: print(type(e).__name__, "|", e) print(issubclass(InsufficientFunds, BankError), issubclass(BankError, Exception)) EOF

    except BankError also catches its subclass InsufficientFunds. Putting all of a module's errors under one parent class lets the caller catch them as broadly or as narrowly as it needs. The chain is InsufficientFunds → BankError → Exception: True True.except BankError는 그 하위 클래스인 InsufficientFunds도 잡는다. 모듈의 오류를 모두 한 부모 클래스 아래 두면, 쓰는 쪽은 필요한 만큼만 자세히 잡을 수 있다. 상속 관계는 InsufficientFunds → BankError → Exception이다: True True.

  3. cat port.txt bad_port.txt big_port.txt python3 config.py port.txt bad_port.txt big_port.txt nope.txt

def parse(row):
    """Check one DictReader row and return a clean dict, or raise BadRow."""
    if None in row:                       # more fields than the header

Paths and pathlib

Path Objects

A file's location is written as a path such as notes/todo.txt. You can handle paths as plain strings, but with the standard library's pathlib.Path, joining, splitting and checking a path each take a single method. Paths are joined with the division sign /. Gluing "/" onto strings by hand easily drops a slash or doubles one; the / operator rules that out.

from pathlib import Path

p = Path("notes") / "archive" / "old.txt"
print(p)              # notes/archive/old.txt
print(p.name)         # old.txt
print(p.stem)         # old
print(p.suffix)       # .txt
print(p.parent)       # notes/archive
print(p.with_suffix(".bak"))   # notes/archive/old.bak

Methods that change a name, such as with_suffix, only build a new Path; they do not touch the file on disk. A Path is a value that says "where". What actually creates or deletes files are methods such as write_text, mkdir and unlink.

Relative Paths and the Current Folder

A path that does not start with / is relative: it is interpreted from the folder the program was started in (Path.cwd()). If you cd to another folder in the shell and run the same program, Path("notes") points somewhere else. The example pages here cd into each example's folder before running commands, so relative paths work as intended. The home folder is Path.home() (/home/student in this virtual machine).

Read a short text file all at once with read_text() and write one all at once with write_text(). write_text creates the file if it does not exist and otherwise erases it and writes it anew. To split the text into lines, use splitlines(): you get a list without the \n at the end of each line.

Why Always encoding="utf-8"

A disk stores bytes, not characters. The rule that turns characters into bytes is an encoding, and today's standard is UTF-8. In UTF-8 an English letter takes 1 byte and a Korean character 3 bytes, so the 12 characters above become 22 bytes. If you leave out encoding, Python uses the operating system's default, which differs from computer to computer (older Korean Windows uses cp949). That is why a Korean file that reads fine on your computer can raise UnicodeDecodeError or show garbled characters on another. Make a habit of writing encoding="utf-8" every time you open a text file.

Adding b to the mode ("rb", "wb") gives binary mode, which reads and writes bytes instead of characters; no encoding is used then. It is for files that are not text, such as images or archives.

with Closes the File

A file you opened must be closed when you are done. Until it is closed, what you wrote may not be fully on disk yet, and there is a limit on how many files one program can have open. You can call f.close() yourself, but if an error happens in between, the program never reaches the close() line. The with statement closes the file the moment the block ends, whether it ends normally or because of an error.

# closing by hand: an error in the middle skips close()
f = open("diary.txt", encoding="utf-8")
text = f.read()
f.close()

# with: always closed when the block ends
with open("diary.txt", encoding="utf-8") as f:
    text = f.read()
print(f.closed)     # True

Trying to read a closed file gives ValueError: I/O operation on closed file. Finish the file work inside the with block, and outside it use the value you read (text).

Exceptions: Dealing with Errors

Exceptions and Tracebacks

When a program hits a situation in which it cannot go on, Python raises an exception. int("ten") raises ValueError, opening a missing file raises FileNotFoundError, and dividing by zero raises ZeroDivisionError. If nobody handles the exception, the program stops right there and prints a traceback.

    report("Joon", [])

Read a traceback from the bottom up.

  1. The last line: the kind of exception and its message. It tells you what went wrong (ZeroDivisionError: division by zero).
  2. The File line just above: where the exception actually happened (line 5 of average, where len(scores) is 0).
  3. The lines above that: the chain of calls that led there. report("Joon", []) on line 13 called average by way of line 9. Line 13, which passes an empty list, may well be the place to fix.

Recent versions of Python point at the failing part of each line with ~~~^^^ marks (since 3.11) and use colours in the terminal (since 3.13). Anything printed before the traceback (here Mina: 84.0) stays on screen, and code after the exception (Sora's report) never runs.

try and except

Put the code that may raise an exception in a try block, and what to do when that exception happens in an except block. If an exception is raised inside try, the rest of the block is skipped and control jumps to the matching except; after that, execution continues after the whole try statement.

text = "ten"
try:
    n = int(text)
    print("got", n)          # skipped when an exception is raised
except ValueError as e:
    print("not a number:", e)
print("program goes on")

as e puts the exception object in a variable. Printing it shows the message, and depending on the kind it carries more information, such as e.filename on a FileNotFoundError or the missing key on a KeyError.

Catch Only What You Expect

One try can have several except blocks; only the first one that matches, from the top, runs. Exceptions that get the same treatment can be grouped in a tuple: except (ValueError, ZeroDivisionError):. A bare except: or except Exception: swallows every error, quietly hiding even a NameError from a typo. The rule is: catch the exceptions you expect by name, and let unexpected errors show up as tracebacks.

else and finally

The else block runs only when the try raised no exception. Moving the success code out of try into else leaves only the lines that can really fail in try, which makes it clear which line's error you mean to catch. The finally block always runs last, on success or failure, even while a return is leaving the function. It is the place for clean-up work.

def to_int(text):
    try:
        n = int(text)
    except ValueError:
        print("except")
        return None
    else:
        print("else")
        return n
    finally:
        print("finally")

to_int("42")    # else, finally
to_int("abc")   # except, finally

caught exceptiontry (up to the error) → matching except → finally

calc.py in the exceptions example divides two numbers for each input line. Input is read line by line with for line in sys.stdin, just like a file. Check First, or Try First

There are two ways to prepare for a missing file: check first with if p.exists(): (Look Before You Leap), or just call open() and catch FileNotFoundError (Easier to Ask Forgiveness than Permission). Python code usually takes the second route: another program could delete the file between the check and the use, and failures that are hard to check in advance, such as a missing permission or broken contents, are handled the same way. For dicts, a method with a default such as prices.get("mango", 0) is often simpler still.

Raising Exceptions: raise and Your Own Exceptions

raise

When a function you wrote receives a value it cannot handle, do not return some odd value; raise an exception with raise. Then the caller cannot carry on as if nothing happened, and it is the caller who decides whether to handle it. For a bad value, ValueError is the usual choice.

def withdraw(self, amount):
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    ...

A bare raise inside an except block re-raises the exception you just caught, unchanged. Use it when you only want to log something and leave the handling to the code further up.

Exception Classes of Your Own

Exceptions are classes too; inherit from Exception to make a new one. Give each module one parent exception (BankError) and put the specific ones under it: the caller can then catch narrowly with except InsufficientFunds, or catch all of the module's errors at once with except BankError. Storing values as attributes in __init__ lets the code that catches the exception use the information without picking apart the message string.

class BankError(Exception):
    """Base class for every error this module raises."""

class InsufficientFunds(BankError):
    def __init__(self, balance, amount):
        super().__init__(f"balance {balance}, tried to withdraw {amount}")
        self.balance = balance
        self.amount = amount
try:
    left = account.withdraw(20000)
except InsufficientFunds as e:
    print("short by", e.amount - e.balance)    # 13000

Exceptions form a hierarchy, and except catches the class it names plus all of its subclasses. FileNotFoundError and FileExistsError are subclasses of OSError, and json.JSONDecodeError is a subclass of ValueError. So with several except blocks, put the specific ones on top and the broad ones below: a broad one on top would catch everything before the lines below get a chance.

Exception Chaining: raise ... from

config.py in the custom_errors example reads a port number from a settings file. It can fail for several reasons (no file: FileNotFoundError; not a number: ValueError; out of range), but the caller does not need to know all of them. So the low-level exceptions are caught and re-raised as a single ConfigError. Adding from e links the original exception to the new one's __cause__.

def read_port(path):
    try:
        with open(path, encoding="utf-8") as f:
            text = f.read().strip()
        port = int(text)
    except FileNotFoundError as e:
        raise ConfigError(f"{path}: file not found") from e
    except ValueError as e:
        raise ConfigError(f"{path}: port must be a number, got {text!r}") from e
    if not 1 <= port <= 65535:
        raise ConfigError(f"{path}: port {port} is outside 1-65535")
    return port

If nobody catches this ConfigError, you get two tracebacks: the cause (ValueError) on top, then The above exception was the direct cause of the following exception:, and the final error (ConfigError) at the bottom. The cause is not hidden, so while debugging you can see what went wrong in the first place. When there is no need to show the cause, cut the link with raise ... from None (BadRow in csv_import does this).

CSV: A Robust Importer

The csv Module Instead of split(",")

You can split a CSV line yourself with strip().split(","), but it breaks as soon as a value contains a comma. CSV wraps such values in double quotes, as in "Kim, Jiwoo", and split knows nothing about quotes. The standard library's csv module knows the quoting and line-break rules.

'"Kim, Jiwoo",math,88'.split(",")
# ['"Kim', ' Jiwoo"', 'math', '88']     broken into four pieces

DictReader and DictWriter

csv.DictReader uses the first line (the header) as keys and gives one dict for each of the other lines. You read row["score"] instead of row[2], so the code still works if the columns are reordered. All values are strings, so numbers need int(). When a line's field count differs from the header, this is what you get:

  • Too few fields: the missing key's value is None ({'name': '지우', 'subject': 'math', 'score': None}).
  • Too many fields: the extra values go into a list under the key None ({..., None: ['extra']}).
  • A field that is present but empty: the empty string ''.

csv.DictWriter goes the other way and writes dicts as lines. Set the column order with fieldnames, then write the header with writeheader() and the rows with writerows(). Values containing commas are quoted automatically. Open CSV files with newline="", both for reading and writing: it leaves line-break handling to the csv module. Without it, depending on the operating system, blank lines can appear between rows or line breaks inside quotes can break.

Code Walk-through: importer.py

Real data nearly always has bad lines mixed in. One bad line should not make you give up the whole import, and it should not be dropped silently either. importer.py in the csv_import example collects the good lines and reports the bad ones with their line numbers and reasons. The work is split in two: parse(row) checks one line and either returns a clean dict or raises BadRow, and main calls parse for every line and catches BadRow.

class BadRow(Exception):
    """A row we cannot use; the message says why."""

def parse(row):
    if None in row:
        raise BadRow(f"extra fields {row[None]}")
    if row["score"] is None:
        raise BadRow("missing score column")
    name = row["name"].strip()
    if not name:
        raise BadRow("empty name")
    try:
        score = int(row["score"])
    except ValueError:
        raise BadRow(f"score is not a whole number: {row['score']!r}") from None
    if not 0 <= score <= 100:
        raise BadRow(f"score {score} is outside 0-100")
    return {"name": name, "subject": row["subject"], "score": score}

Whatever the reason, parse reports it as one kind of exception, BadRow, so main needs only one except. The ValueError from int() is also re-raised as BadRow; since the message already says everything about the cause, from None cuts the link.

try:

The inner one sits inside the loop and handles one line's failure; the outer one handles the file itself being missing. reader.line_num is the file's line number read so far (the header is 1), so it matches the numbers from cat -n scores.csv. Common Mistakes

  • Opening an existing file with "w". Its contents vanish the moment it opens. To add, use "a"; if it must not be overwritten, use "x".
  • Leaving out encoding. A Korean file that works on your computer turns into garbage on another. Always write encoding="utf-8" for text files.
  • Forgetting the \n at the end of a line. In for line in f, line ends in \n, so line == "5000" is false; strip() before comparing. In the other direction, write() adds no \n.
  • Reading a file outside its with block. It is already closed: ValueError: I/O operation on closed file.
  • Catching everything with except:. It swallows typos (NameError) and even Ctrl+C, so bugs hide. Catch the exceptions you expect, by name.
  • Putting too much code in try. It blurs which line's error you mean to catch, and it also catches the same kind of error from lines you did not expect. Move the success code into else.
  • Catching an exception and doing nothing (except ValueError: pass). Data disappears silently. If you skip something, say what and why.
  • Single quotes or a trailing comma in JSON. {'a': 1} and [1, 2,] are not JSON. Do not write it by hand; produce it with json.dump.
  • Forgetting that CSV values are strings. row["score"] > 90 is a TypeError. Convert with int(), and handle the case where the conversion fails.

/로 시작하지 않는 경로는 상대 경로이고, 프로그램을 실행한 현재 폴더(Path.cwd())를 기준으로 해석됩니다. 셸에서 cd로 다른 폴더에 가서 같은 프로그램을 실행하면 Path("notes")는 다른 곳을 가리킵니다. 이 실습의 예제 페이지는 각 예제의 폴더로 cd한 뒤 명령을 실행하므로 상대 경로가 맞게 동작합니다. 홈 폴더는 Path.home()(이 가상 머신에서는 /home/student)입니다.

폴더 둘러보기: iterdir, glob, rglob

iterdir()는 폴더 바로 안의 항목을 모두 돌려주고, glob(패턴)은 이름이 패턴에 맞는 것만 돌려줍니다. *는 "아무 글자나 몇 개든"이라는 뜻이라 "*.txt"는 .txt로 끝나는 이름입니다. rglob은 하위 폴더까지 모두 뒤집니다. 돌려주는 순서는 정해져 있지 않으므로 화면에 보여 줄 때는 sorted()로 정렬합니다.

folder = Path("notes")
for p in sorted(folder.iterdir()):
    kind = "dir " if p.is_dir() else "file"
    print(kind, p.name)

for p in sorted(folder.glob("*.txt")):     # notes 바로 안의 .txt
    print(p.name)

for p in sorted(folder.rglob("*.txt")):    # 하위 폴더까지
    print(p)                               # notes/archive/old.txt ...

read_text와 write_text

짧은 텍스트 파일은 read_text()로 통째로 읽고 write_text()로 통째로 씁니다. write_text는 파일이 없으면 만들고, 있으면 내용을 모두 지우고 새로 씁니다. 줄 단위로 나누려면 splitlines()를 씁니다. 줄 끝의 \n이 없는 리스트가 나옵니다.

out = Path("notes/hello.txt")
out.write_text("안녕하세요\nHello\n", encoding="utf-8")   # 12 (글자 수)
text = out.read_text(encoding="utf-8")
print(text.splitlines())                  # ['안녕하세요', 'Hello']
print(len(out.read_bytes()))              # 22 (바이트 수)

encoding="utf-8"을 항상 쓰는 이유

디스크에는 글자가 아니라 바이트가 저장됩니다. 글자를 바이트로 바꾸는 규칙이 인코딩이고, 오늘날의 표준은 UTF-8입니다. UTF-8에서 영문자는 1바이트, 한글은 한 글자에 3바이트라서 위의 12글자는 22바이트가 됩니다. encoding을 생략하면 Python은 운영체제의 기본값을 쓰는데, 이 값이 컴퓨터마다 다릅니다(예전 한국어 Windows는 cp949). 내 컴퓨터에서 잘 읽히던 한글 파일이 다른 컴퓨터에서 UnicodeDecodeError를 내거나 깨진 글자로 보이는 이유입니다. 텍스트 파일을 열 때는 언제나 encoding="utf-8"을 적는 습관을 들입니다.

확인하고 만들기: exists와 mkdir

파일이 있는지 exists()로 먼저 확인하면 없는 파일을 읽다가 멈추는 일을 피할 수 있습니다. 폴더는 mkdir()로 만드는데, parents=True는 중간 폴더까지 한꺼번에 만들고 exist_ok=True는 이미 있어도 오류를 내지 않게 합니다. 두 옵션을 함께 쓰면 몇 번을 실행해도 안전합니다.

p = Path("notes/nope.txt")

else:

open()과 with

파일 객체와 모드

read_text/write_text는 파일 전체를 한 번에 다룹니다. 조금씩 읽거나, 기존 파일 끝에 덧붙이거나, 큰 파일을 한 줄씩 처리하려면 open()으로 파일 객체를 얻습니다. 두 번째 인자인 모드가 파일을 어떻게 열지 정합니다.

모드뜻파일이 없으면파일이 있으면
"r" (기본값)읽기FileNotFoundError처음부터 읽는다
"w"쓰기새로 만든다내용을 모두 지우고 쓴다
"a"덧붙이기(append)새로 만든다끝에 이어 쓴다
"x"새 파일 만들기(exclusive)새로 만든다FileExistsError

모드 뒤에 b를 붙이면("rb", "wb") 글자 대신 바이트를 주고받는 바이너리 모드가 되며, 이때는 encoding을 쓰지 않습니다. 이미지나 압축 파일처럼 텍스트가 아닌 파일에 씁니다.

가장 조심할 모드는 "w"입니다. 파일을 여는 순간, 아직 아무것도 쓰지 않았어도 기존 내용이 사라집니다. 기록을 쌓아 가는 파일이라면 "a"를, 절대 덮어쓰면 안 되는 파일이라면 "x"를 씁니다.

with가 파일을 닫는다

연 파일은 다 쓰고 나면 닫아야 합니다. 닫기 전에는 쓴 내용이 아직 디스크에 다 저장되지 않았을 수 있고, 한 프로그램이 동시에 열 수 있는 파일 수에도 한계가 있습니다. f.close()를 직접 부를 수도 있지만, 그 사이에서 오류가 나면 close() 줄까지 가지 못합니다. with 문은 블록이 끝나는 순간 — 정상적으로 끝나든 오류로 빠져나가든 — 파일을 닫아 줍니다.

# 직접 닫기: 중간에 오류가 나면 close()가 실행되지 않는다
f = open("diary.txt", encoding="utf-8")
text = f.read()
f.close()

# with: 블록이 끝나면 항상 닫힌다
with open("diary.txt", encoding="utf-8") as f:
    text = f.read()
print(f.closed)     # True

닫힌 파일을 읽으려 하면 ValueError: I/O operation on closed file.이 납니다. 파일 작업은 with 블록 안에서 끝내고, 블록 밖에서는 읽어 둔 값(text)을 씁니다.

읽는 방법

코드결과언제
f.read()남은 내용 전체(문자열 하나)작은 파일
f.readline()한 줄(끝의 \n 포함), 끝이면 ""헤더 한 줄만 먼저 읽을 때
f.readlines()남은 줄들의 리스트줄을 여러 번 다시 볼 때
for line in f:한 번에 한 줄씩큰 파일, 대부분의 경우

파일 객체는 어디까지 읽었는지 기억합니다. readline()으로 첫 줄을 읽은 뒤의 readlines()에는 첫 줄이 없습니다. for line in f는 파일 전체를 메모리에 올리지 않고 한 줄씩 읽으므로 아주 큰 파일에도 쓸 수 있습니다. 각 줄 끝에는 \n이 붙어 있으니 비교하거나 출력하기 전에 strip()이나 rstrip()으로 떼어 냅니다.

쓰는 방법

f.write(s)는 준 문자열을 그대로 쓰고 줄바꿈을 붙여 주지 않습니다. print(..., file=f)는 화면에 출력할 때와 같은 규칙(공백으로 구분, 끝에 줄바꿈)으로 파일에 씁니다. f.writelines(리스트)는 리스트의 문자열을 이어 쓰며, 이것도 줄바꿈은 직접 넣어야 합니다.

with open("log.txt", "w", encoding="utf-8") as f:
    f.write("a")
    f.write("b\n")                      # 'ab\n'  (a와 b가 한 줄)
    print("c", "d", sep=",", file=f)    # 'c,d\n'
    f.writelines(["e\n", "f\n"])

예외와 Traceback

프로그램이 실행 중에 더 진행할 수 없는 상황을 만나면 Python은 예외(exception)를 일으킵니다. int("ten")은 ValueError, 없는 파일을 여는 것은 FileNotFoundError, 0으로 나누는 것은 ZeroDivisionError입니다. 아무도 예외를 처리하지 않으면 프로그램은 그 자리에서 멈추고 Traceback을 출력합니다.

try와 except

예외가 날 수 있는 코드를 try 블록에 넣고, 그 예외를 만났을 때 할 일을 except 블록에 씁니다. try 안에서 예외가 나면 나머지 줄은 건너뛰고 맞는 except로 이동하며, 처리가 끝나면 try 문 다음부터 계속 실행됩니다.

text = "ten"
try:
    n = int(text)
    print("got", n)          # 예외가 나면 실행되지 않는다
except ValueError as e:
    print("not a number:", e)
print("program goes on")

as e는 예외 객체를 변수에 받습니다. 출력하면 메시지가 나오고, 종류에 따라 추가 정보도 들어 있습니다. FileNotFoundError의 e.filename, KeyError의 빠진 키 같은 것입니다.

자주 만나는 예외

예외언제 나는가예

필요한 예외만 잡는다

한 try에 except를 여러 개 둘 수 있고, 위에서부터 처음 맞는 하나만 실행됩니다. 같은 처리를 할 예외는 튜플로 묶습니다: except (ValueError, ZeroDivisionError):. 종류를 적지 않은 except:나 except Exception:은 모든 오류를 삼켜 버려서, 오타로 생긴 NameError까지 조용히 숨깁니다. 예상한 예외만 이름으로 잡고, 예상하지 못한 오류는 Traceback으로 드러나게 두는 것이 원칙입니다.

else와 finally

else 블록은 try에서 예외가 나지 않았을 때만 실행됩니다. 성공했을 때의 코드를 try 밖의 else에 두면, try에는 정말 실패할 수 있는 줄만 남아 어떤 줄의 오류를 잡으려는 것인지 분명해집니다. finally 블록은 성공하든 실패하든, 심지어 return으로 함수를 빠져나가는 중에도 마지막에 반드시 실행됩니다. 정리 작업을 둡니다.

def to_int(text):
    try:
        n = int(text)
    except ValueError:
        print("except")
        return None
    else:
        print("else")
        return n
    finally:
        print("finally")

to_int("42")    # else, finally
to_int("abc")   # except, finally
상황실행 순서
예외 없음try 전체 → else → finally
잡은 예외try(예외 난 곳까지) → 맞는 except → finally
잡지 않은 예외try(예외 난 곳까지) → finally → 바깥으로 전달(Traceback)

with open(...)이 파일을 닫는 것도 사실 이 finally와 같은 원리입니다.

코드 살펴보기: calc.py

exceptions 예제의 calc.py는 입력 한 줄마다 두 수를 나눕니다. 입력도 파일처럼 for line in sys.stdin으로 한 줄씩 읽습니다. 핵심은 try가 반복문 안에 있다는 점입니다. 그래서 한 줄이 실패해도 그 줄만 건너뛰고 다음 줄로 갑니다. try를 반복문 바깥에 두면 첫 실패에서 반복 전체가 끝납니다.

for number, line in enumerate(sys.stdin, start=1):
    try:
        a_text, b_text = line.split()   # ValueError: 두 조각이 아님
        a = int(a_text)                 # ValueError: 정수가 아님
        b = int(b_text)
        result = a / b                  # ZeroDivisionError
    except ValueError as e:
        print(f"line {number}: skipped, {e}")
    except ZeroDivisionError:
        print(f"line {number}: skipped, cannot divide by zero")

        print(f"line {number}: {a} / {b} = {result:g}")

확인 먼저, 아니면 시도 먼저

없는 파일에 대비하는 방법은 두 가지입니다. if p.exists():로 먼저 확인하거나(Look Before You Leap), 일단 open()하고 FileNotFoundError를 잡습니다(Easier to Ask Forgiveness than Permission). Python에서는 뒤의 방식을 흔히 씁니다. 확인과 사용 사이에 다른 프로그램이 파일을 지울 수도 있고, 권한 없음이나 깨진 내용처럼 미리 확인하기 어려운 실패도 같은 모양으로 처리할 수 있기 때문입니다. 딕셔너리에서는 prices.get("mango", 0)처럼 기본값을 주는 메서드가 더 간단할 때도 많습니다.

예외를 일으키기: raise와 사용자 정의 예외

raise

내가 만든 함수가 받은 값을 처리할 수 없을 때는 이상한 값을 돌려주지 말고 raise로 예외를 일으킵니다. 그러면 호출한 쪽이 오류를 무시하고 넘어갈 수 없고, 처리할지 말지를 그쪽에서 결정합니다. 잘못된 값에는 보통 ValueError를 씁니다.

def withdraw(self, amount):
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    ...

except 블록 안에서 이름 없이 raise만 쓰면 방금 잡은 예외를 그대로 다시 던집니다. 로그만 남기고 처리는 위쪽에 맡길 때 씁니다.

나만의 예외 클래스

예외도 클래스입니다. Exception을 상속하면 새 예외를 만들 수 있습니다. 모듈마다 부모 예외 하나(BankError)를 두고 구체적인 예외를 그 아래 두면, 쓰는 쪽은 except InsufficientFunds로 자세히 잡을 수도, except BankError로 모듈의 오류를 한꺼번에 잡을 수도 있습니다. __init__에서 값을 속성으로 저장해 두면 잡은 쪽이 메시지 문자열을 해석하지 않고도 정보를 꺼내 쓸 수 있습니다.

class BankError(Exception):
    """Base class for every error this module raises."""

class InsufficientFunds(BankError):
    def __init__(self, balance, amount):
        super().__init__(f"balance {balance}, tried to withdraw {amount}")
        self.balance = balance
        self.amount = amount
try:
    left = account.withdraw(20000)
except InsufficientFunds as e:
    print("short by", e.amount - e.balance)    # 13000

예외는 계층을 이룹니다. except는 적힌 클래스와 그 모든 하위 클래스를 잡습니다. FileNotFoundError와 FileExistsError는 OSError의 하위 클래스이고, json.JSONDecodeError는 ValueError의 하위 클래스입니다. 그래서 여러 except를 쓸 때는 구체적인 것을 위에, 넓은 것을 아래에 둡니다. 넓은 것이 위에 있으면 아래 줄까지 내려가지 못합니다.

예외 연결: raise ... from

custom_errors 예제의 config.py는 설정 파일에서 포트 번호를 읽습니다. 실패하는 이유는 파일 없음(FileNotFoundError), 숫자 아님(ValueError), 범위 밖 등 여러 가지인데, 부르는 쪽에서 그 모두를 알 필요는 없습니다. 그래서 낮은 수준의 예외를 잡아 ConfigError 하나로 바꿔 던집니다. 이때 from e를 붙이면 원래 예외가 새 예외의 __cause__에 연결됩니다.

def read_port(path):
    try:
        with open(path, encoding="utf-8") as f:
            text = f.read().strip()
        port = int(text)
    except FileNotFoundError as e:
        raise ConfigError(f"{path}: file not found") from e
    except ValueError as e:
        raise ConfigError(f"{path}: port must be a number, got {text!r}") from e
    if not 1 <= port <= 65535:
        raise ConfigError(f"{path}: port {port} is outside 1-65535")
    return port

이 ConfigError를 아무도 잡지 않으면 Traceback이 두 개 나옵니다. 위쪽이 원인(ValueError), 그 아래에 The above exception was the direct cause of the following exception:, 맨 아래가 최종 오류(ConfigError)입니다. 원인을 감추지 않으므로 디버깅할 때 처음 무엇이 잘못됐는지 알 수 있습니다. 원인을 보여 줄 필요가 없을 때는 raise ... from None으로 연결을 끊습니다(csv_import의 BadRow가 그렇게 합니다).

JSON이란

JSON(JavaScript Object Notation)은 딕셔너리와 리스트 같은 구조를 텍스트로 적는 형식입니다. 사람이 읽을 수 있고, 거의 모든 언어와 웹 서비스가 주고받을 수 있어서 설정 파일, 저장 파일, 웹 API의 응답에 널리 쓰입니다. 겉모습은 Python의 딕셔너리와 비슷하지만 규칙이 더 엄격합니다. 문자열은 반드시 큰따옴표로 쓰고, 객체의 키는 문자열이어야 하며, 마지막 항목 뒤에 쉼표를 둘 수 없습니다.

import json

# {"name": "민지", "tags": ["a", "b"], "pet": null, "ok": true}

json_save 예제의 save.py는 게임 기록을 save.json에 저장합니다. 실행할 때마다 읽고, 고치고, 다시 씁니다. 읽기 함수가 두 가지 실패를 모두 처리하는 것이 핵심입니다. 처음 실행하면 파일이 없고(FileNotFoundError), 저장 도중 전원이 꺼지면 파일이 반쯤만 쓰여 있을 수 있습니다(JSONDecodeError). 어느 경우든 새 게임으로 시작합니다.

def load():
    try:
        with open(SAVE, encoding="utf-8") as f:
            return json.load(f)

    return new_game()

def save(data):
    with open(SAVE, "w", encoding="utf-8") as f:

CSV: 견고한 가져오기 프로그램

split(",") 대신 csv 모듈

CSV 한 줄을 strip().split(",")으로 직접 나눌 수도 있지만, 값 안에 쉼표가 들어 있으면 깨집니다. CSV는 그런 값을 "Kim, Jiwoo"처럼 큰따옴표로 감싸는데, split은 따옴표를 모르기 때문입니다. 표준 라이브러리의 csv 모듈은 따옴표와 줄바꿈 규칙을 알고 있습니다.

'"Kim, Jiwoo",math,88'.split(",")
# ['"Kim', ' Jiwoo"', 'math', '88']     네 조각으로 깨진다

DictReader와 DictWriter

csv.DictReader는 첫 줄(헤더)을 키로 써서 나머지 줄마다 딕셔너리 하나를 줍니다. row[2] 대신 row["score"]로 읽으니 열 순서가 바뀌어도 코드가 그대로 동작합니다. 값은 모두 문자열이므로 숫자는 int()로 바꿔야 합니다. 줄의 칸 수가 헤더와 다르면 이렇게 들어옵니다.

  • 칸이 모자라면: 빠진 키의 값이 None입니다({'name': '지우', 'subject': 'math', 'score': None}).
  • 칸이 남으면: 남은 값들이 None 키 아래 리스트로 들어갑니다({..., None: ['extra']}).
  • 칸은 있지만 비어 있으면: 빈 문자열 ''입니다.

csv.DictWriter는 반대로 딕셔너리를 줄로 씁니다. 열 순서를 fieldnames로 정하고, writeheader()로 헤더를, writerows()로 행들을 씁니다. 쉼표가 들어 있는 값은 자동으로 따옴표로 감쌉니다. CSV 파일은 읽을 때도 쓸 때도 newline=""으로 엽니다. 줄바꿈 처리를 csv 모듈에 맡기라는 뜻으로, 생략하면 운영체제에 따라 빈 줄이 끼거나 따옴표 안의 줄바꿈이 깨질 수 있습니다.

코드 살펴보기: importer.py

실제 데이터에는 거의 항상 잘못된 줄이 섞여 있습니다. 한 줄이 잘못됐다고 전체 가져오기를 포기하면 안 되고, 조용히 버려서도 안 됩니다. csv_import 예제의 importer.py는 좋은 줄은 모으고 나쁜 줄은 줄 번호와 이유를 보고합니다. 일을 둘로 나눴습니다. parse(row)는 한 줄을 검사해 깨끗한 딕셔너리를 돌려주거나 BadRow를 raise하고, main은 줄마다 parse를 부르며 BadRow를 잡습니다.

class BadRow(Exception):
    """A row we cannot use; the message says why."""

def parse(row):
    if None in row:
        raise BadRow(f"extra fields {row[None]}")
    if row["score"] is None:
        raise BadRow("missing score column")
    name = row["name"].strip()
    if not name:
        raise BadRow("empty name")
    try:
        score = int(row["score"])
    except ValueError:
        raise BadRow(f"score is not a whole number: {row['score']!r}") from None
    if not 0 <= score <= 100:
        raise BadRow(f"score {score} is outside 0-100")
    return {"name": name, "subject": row["subject"], "score": score}

검사하는 이유가 모두 달라도 parse는 BadRow 한 가지로 알리므로 main의 except는 하나면 됩니다. int()의 ValueError도 BadRow로 바꿔 던지는데, 원인이 메시지에 이미 다 들어 있으므로 from None으로 연결을 끊었습니다.

try:
    with open(path, encoding="utf-8", newline="") as f:
        reader = csv.DictReader(f)
        for row in reader:
            try:
                good.append(parse(row))
            except BadRow as e:
                bad += 1
                print(f"line {reader.line_num}: skipped, {e}")
except FileNotFoundError:
    print(f"error: {path} not found")
    return 1

try가 두 겹입니다. 안쪽 try는 반복문 안에 있어 한 줄의 실패를 처리하고, 바깥 try는 파일 자체가 없는 경우를 처리합니다. reader.line_num은 지금까지 읽은 파일의 줄 번호(헤더가 1)라서 cat -n scores.csv의 번호와 같습니다. 파일이 없으면 main이 1을 돌려주고 sys.exit(main(...))가 그것을 종료 코드로 씁니다. 0은 성공, 0이 아니면 실패라는 셸의 약속을 지키는 것입니다.

line 5: skipped, score is not a whole number: ''
line 6: skipped, score is not a whole number: 'eighty'
line 7: skipped, score 105 is outside 0-100
line 8: skipped, missing score column
line 9: skipped, empty name
line 10: skipped, extra fields ['extra']
4 rows saved to clean.csv, 6 skipped
average of the good rows: 82.2

흔한 실수

  • 있는 파일을 "w"로 연다. 여는 순간 내용이 사라집니다. 덧붙이려면 "a", 덮어쓰면 안 되면 "x"입니다.
  • encoding을 생략한다. 내 컴퓨터에서는 되던 한글 파일이 다른 컴퓨터에서 깨집니다. 텍스트 파일에는 항상 encoding="utf-8"을 씁니다.
  • 줄 끝의 \n을 잊는다. for line in f의 line은 \n으로 끝납니다. line == "5000"은 거짓이므로 strip()한 뒤 비교합니다. 반대로 write()는 \n을 붙여 주지 않습니다.
  • with 블록 밖에서 파일을 읽는다. 이미 닫혀 있어 ValueError: I/O operation on closed file.이 납니다.
  • except:로 모든 예외를 잡는다. 오타(NameError)나 Ctrl+C까지 삼켜 버그가 숨습니다. 예상한 예외만 이름으로 잡습니다.
  • try에 너무 많은 코드를 넣는다. 어느 줄의 오류를 잡으려는 것인지 흐려지고, 예상하지 못한 줄의 같은 종류 오류까지 잡힙니다. 성공했을 때의 코드는 else로 옮깁니다.
  • 예외를 잡고 아무것도 하지 않는다(except ValueError: pass). 데이터가 조용히 사라집니다. 건너뛰더라도 무엇을 왜 건너뛰었는지 알립니다.
  • JSON에 작은따옴표나 끝 쉼표를 쓴다. {'a': 1}과 [1, 2,]는 JSON이 아닙니다. 손으로 쓰지 말고 json.dump로 만듭니다.
  • CSV 값이 문자열이라는 것을 잊는다. row["score"] > 90은 TypeError입니다. int()로 바꾸고, 바꾸다 실패하는 경우를 처리합니다.

확인 퀴즈

  1. Path("data") / "2026" / "a.csv"의 suffix와 parent는? .csv와 data/2026입니다.
  2. 기존 로그 파일 끝에 한 줄을 더하려면 어떤 모드로 여는가? "a"입니다.
  3. with 블록 안에서 예외가 나면 파일은? 블록을 빠져나가면서 닫힙니다.
  4. else 블록은 언제 실행되는가? try에서 예외가 나지 않았을 때만 실행됩니다.
  5. finally는 return이 있어도 실행되는가? 네, 함수가 끝나기 직전에 실행됩니다.
  6. except BankError는 InsufficientFunds를 잡는가? 네, 하위 클래스이기 때문입니다.
  7. raise ConfigError(...) from e에서 e는 어디에 남는가? 새 예외의 __cause__에 남고, Traceback에도 함께 나옵니다.
  8. json.dumps((1, 2))를 loads로 되돌리면? 튜플이 아니라 리스트 [1, 2]입니다.
  9. DictReader에서 칸이 모자란 줄의 빠진 값은? None입니다.

정리

경로는 Path로 만들고 /로 잇습니다. 파일은 with open(..., encoding="utf-8")으로 열어 블록 안에서 끝내고, 모드(r, w, a, x)를 목적에 맞게 고릅니다. 실패할 수 있는 일은 try에 넣고 예상한 예외만 이름으로 잡으며, 내 함수가 처리할 수 없는 값은 raise로 알립니다. 구조가 있는 데이터는 json으로, 표 형태의 데이터는 csv로 저장하되, 읽을 때는 파일이 없거나 깨졌을 가능성을 항상 생각합니다. 각 예제 페이지에서 단계를 실행해 보고, 일부러 입력을 망가뜨려 프로그램이 어떻게 반응하는지 확인해 봅니다.
