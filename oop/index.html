05_encapsulation ~/oop/classes/examples

The balance is kept in the internal _balance and read with get_balance(). deposit rejects amounts of 0 or less, and withdraw rejects amounts of 0 or less or above the balance, returning False; when rejecting, they return before changing the state.잔액을 내부용 _balance에 두고 get_balance()로 읽게 한다. deposit은 0 이하 금액을, withdraw는 0 이하이거나 잔액을 넘는 금액을 False로 거부하며, 거부할 때는 상태를 바꾸기 전에 return한다.

Steps실행 순서

  1. python3 05_encapsulation.py

    The result matches the lab's table of expected results. Withdraw 10000, Deposit -1000 and Withdraw 0 are all False, and the balance stays at 9000. Jisu withdraw 5000, which withdraws the whole balance, is allowed and leaves 0.실습 기대표와 같은 결과다. 03 · Encapsulation: State and the Rules for Changing It

Direct changes can break a rule

An account's balance must not become negative. But a direct assignment can skip the withdrawal rule. We need a clear way to read and change the balance. In the second step of the 04_methods page you can see both a withdraw without checks accepting a withdrawal larger than the balance and the direct assignment below.

account = BankAccount("Minsu", 10000)
account.balance = -9999
print(account.balance)   # -9999

Encapsulation: state and rules together

Keep related data and methods in one class, and check changes through public methods. A rejected request does not change the state.

Encapsulation and the account interface

The underscore in _balance marks it as an internal attribute. get_balance() reads the current value, and deposit() and withdraw() control the valid changes.

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self._balance = balance

    def get_balance(self):
        return self._balance

A deposit can be rejected

Zero and negative numbers are invalid amounts. A rejected call returns before changing the state, and a valid call changes the balance and then returns True.

def deposit(self, amount):
    if amount <= 0:
        return False
    self._balance = self._balance + amount
    return True

A withdrawal checks two conditions

The amount must be positive and must not exceed the balance. Withdrawing the whole balance is allowed.

def withdraw(self, amount):
    if amount <= 0 or amount > self._balance:
        return False
    self._balance = self._balance - amount
    return True

Rejected operations preserve the balance

A failed call returns False and the balance stays the same. After a successful withdrawal of the full amount, 0 is left. 05_encapsulation runs the operations in the same order as the lab's table of expected results.

account = BankAccount("Jisu", 5000)
print(account.deposit(-1000))    # False
print(account.withdraw(6000))    # False
print(account.get_balance())     # 5000
print(account.withdraw(5000))    # True
print(account.get_balance())     # 0

An underscore is a convention

Python still allows access to _balance. The underscore only signals that it is internal, and people using the class should follow the public methods. Encapsulation depends on a clear interface and rules. In the second step of the 05_encapsulation page you can see account._balance = -1 actually go through.

함수는 잔액을 명시적으로 받고, 호출하는 쪽이 돌려받은 값을 다시 저장합니다. 다른 계좌의 잔액을 실수로 넘겨도 함수는 알 수 없습니다. 객체는 자기 데이터와 관련 동작을 함께 지니게 됩니다.

def deposit(balance, amount):
    return balance + amount

minsu_balance = 10000
minsu_balance = deposit(minsu_balance, 3000)
print(minsu_balance)   # 13000

객체는 데이터와 동작을 가진다

객체 하나가 계좌 하나를 나타냅니다. 클래스는 객체의 종류를 정의하고, 인스턴스는 그 클래스로 만든 객체 하나입니다. 계좌 객체의 데이터 속성은 owner와 balance, 메서드는 deposit(amount)와 withdraw(amount)입니다.

첫 클래스

class는 클래스 정의를 시작하고, 들여쓴 몸체가 클래스에 속합니다. pass는 아무 일도 하지 않는 빈 문장으로, 지금은 자리만 채웁니다. BankAccount()를 호출하면 인스턴스가 만들어집니다.

class BankAccount:
    pass

account = BankAccount()
print(type(account).__name__)   # BankAccount

속성은 객체에 속한다

점은 속성을 선택합니다. account.owner = ...처럼 대입하면 이 객체에 데이터가 저장되고, account.balance를 읽으면 현재 값을 꺼냅니다.

account = BankAccount()
account.owner = "Minsu"
account.balance = 10000
print(account.owner, account.balance)   # Minsu 10000

두 객체, 따로따로인 잔액

BankAccount()를 부를 때마다 새 객체가 만들어집니다. 같은 속성 이름이 객체마다 다른 값을 가질 수 있고, 민수의 잔액을 바꿔도 지수의 잔액은 그대로입니다. 02_classes_and_objects는 마지막에 minsu is jisu가 False임도 보여 줍니다.

minsu = BankAccount()
minsu.balance = 10000
jisu = BankAccount()
jisu.balance = 5000
minsu.balance = minsu.balance + 3000
print(minsu.balance, jisu.balance)   # 13000 5000

클래스, 객체, 인스턴스

클래스는 객체의 한 종류를 정의합니다. 각 계좌는 별개의 객체입니다. "인스턴스"는 객체와 그 클래스의 관계를 나타내는 말로, 각 계좌는 BankAccount의 인스턴스입니다.

02 · 초기화와 메서드

__init__으로 초기화

Python은 새 인스턴스를 만들 때 __init__을 호출합니다. 인자가 초기값을 제공하고, self에 대입한 속성은 그 인스턴스에 남습니다.

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

초기화된 계좌 만들기

인자는 owner와 balance에 차례로 대응합니다. 새 객체는 Python이 self로 넘겨 주므로 호출할 때 쓰지 않습니다. 호출할 때마다 자기 인스턴스가 초기화됩니다.

minsu = BankAccount("Minsu", 10000)
jisu = BankAccount("Jisu", 5000)
print(minsu.owner, minsu.balance)   # Minsu 10000
print(jisu.owner, jisu.balance)     # Jisu 5000

self는 현재 인스턴스를 가리킨다

self는 관례적인 매개변수 이름입니다. self.owner는 현재 객체의 속성이고, owner는 이번 호출에 넘어온 값입니다. self.owner = owner는 그 값을 객체에 저장합니다. 03_init_and_self에서 확인합니다.

account = BankAccount("Minsu", 10000)
print(account.owner)   # Minsu

클래스 변수와 인스턴스 변수

클래스 변수는 클래스 몸체에서 메서드 밖에 정의하며, 모든 인스턴스가 공유된 값을 읽을 수 있습니다. 인스턴스 변수는 보통 __init__에서 self에 정의하며, 각 계좌가 자기 owner와 balance를 따로 가집니다. 03b_class_and_instance_variables는 클래스 변수를 바꾸면 모든 계좌가 바뀐 값을 읽고, 한 인스턴스에 같은 이름을 대입하면 그 인스턴스에만 새 속성이 생긴다는 것까지 보여 줍니다.

class BankAccount:
    bank_name = "Python Bank"        # class variable

    def __init__(self, owner, balance):
        self.owner = owner           # instance variable
        self.balance = balance

minsu = BankAccount("Minsu", 10000)
jisu = BankAccount("Jisu", 5000)
print(minsu.bank_name, jisu.bank_name)   # Python Bank Python Bank
print(minsu.balance, jisu.balance)       # 10000 5000

예측: 어느 잔액이 바뀔까

실행하기 전에 두 줄의 출력을 예측하고, 각 점이 어느 객체를 가리키는지 설명해 봅니다. 그다음 나만의 세 번째 계좌를 만들어 봅니다. 03_init_and_self 페이지의 두 번째 단계가 이 코드를 실행합니다(답: 3000과 7000).

a = BankAccount("A", 2000)
b = BankAccount("B", 7000)
a.balance = a.balance + 1000
print(a.balance)
print(b.balance)

메서드는 자기 객체의 상태를 바꾼다

메서드는 클래스 안에 정의한 함수입니다. self가 잔액이 바뀔 계좌를 고릅니다. 이 첫 버전은 금액이 양수라고 가정합니다.

def deposit(self, amount):
    self.balance = self.balance + amount
    return True

인스턴스 메서드 호출

minsu.deposit(3000)은 minsu에 대해 메서드를 부르고, Python이 minsu를 self로 넘깁니다. 호출은 minsu.balance를 바꿉니다. 점 앞의 객체가 self가 되므로 그 계좌의 잔액만 바뀌고, 다른 인스턴스는 자기 상태를 유지합니다.

minsu = BankAccount("Minsu", 10000)
jisu = BankAccount("Jisu", 5000)
accepted = minsu.deposit(3000)
print(accepted, minsu.balance)   # True 13000
print(jisu.balance)              # 5000

출금도 메서드다

출금 메서드도 같은 계좌 상태를 씁니다. 지금은 금액이 양수이고 잔액이 충분하다고 가정하며, 잘못된 요청에 대한 검사는 다음 절에서 추가합니다.

def withdraw(self, amount):
    self.balance = self.balance - amount
    return True

return과 print는 하는 일이 다르다

return은 호출한 쪽에 값을 돌려주고, print는 값을 화면에 보여 줍니다. 메서드는 돌려주기 전에 잔액을 바꿉니다. 04_methods에서 확인합니다.

account = BankAccount("Minsu", 10000)
accepted = account.withdraw(4000)
print(accepted)          # True
print(account.balance)   # 6000

03 · 캡슐화: 상태와 그 변경 규칙

직접 변경은 규칙을 깰 수 있다

계좌는 잔액이 음수가 되면 안 됩니다. 그런데 직접 대입하면 출금 규칙을 건너뛸 수 있습니다. 잔액을 읽고 바꾸는 분명한 방법이 필요합니다. 04_methods 페이지의 두 번째 단계에서 검사 없는 withdraw가 잔액보다 큰 출금도 받아들이는 것과 아래 직접 대입을 함께 볼 수 있습니다.

account = BankAccount("Minsu", 10000)
account.balance = -9999
print(account.balance)   # -9999

캡슐화: 상태와 규칙을 함께

관련된 데이터와 메서드를 한 클래스에 두고, 변경은 공개 메서드를 통해 검사합니다. 거부된 요청은 상태를 바꾸지 않습니다.

캡슐화와 계좌 인터페이스

_balance의 밑줄은 내부용 속성이라는 표시입니다. get_balance()는 현재 값을 읽고, deposit()과 withdraw()가 정상적인 변경을 통제합니다.

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self._balance = balance

    def get_balance(self):
        return self._balance

입금은 거부될 수 있다

0과 음수는 잘못된 금액입니다. 거부된 호출은 상태를 바꾸기 전에 반환하고, 올바른 호출은 잔액을 바꾼 뒤 True를 돌려줍니다.

def deposit(self, amount):
    if amount <= 0:
        return False
    self._balance = self._balance + amount
    return True

출금은 두 조건을 검사한다

금액은 양수여야 하고 잔액을 넘으면 안 됩니다. 잔액 전부를 출금하는 것은 허용됩니다.

def withdraw(self, amount):
    if amount <= 0 or amount > self._balance:
        return False
    self._balance = self._balance - amount
    return True

거부된 연산은 잔액을 보존한다

실패한 호출은 False를 돌려주고 잔액은 그대로입니다. 성공한 전액 출금 뒤에는 0이 남습니다. 05_encapsulation은 실습의 기대 결과표와 같은 순서의 연산을 실행합니다.

account = BankAccount("Jisu", 5000)
print(account.deposit(-1000))    # False
print(account.withdraw(6000))    # False
print(account.get_balance())     # 5000
print(account.withdraw(5000))    # True
print(account.get_balance())     # 0

밑줄은 관례다

Python은 여전히 _balance에 접근하는 것을 허용합니다. 밑줄은 내부용이라는 뜻을 전할 뿐이고, 클래스를 쓰는 사람은 공개 메서드를 따라야 합니다. 캡슐화는 분명한 인터페이스와 규칙에 달려 있습니다. 05_encapsulation 페이지의 두 번째 단계에서 account._balance = -1이 실제로 통과하는 것을 볼 수 있습니다.

식목적
account.get_balance()상태 읽기
account.deposit(1000)올바른 변경 요청
account._balance = -1약속된 인터페이스를 우회

호출하는 쪽은 출금을 요청하고, 결과를 확인하고, 잔액을 읽습니다. _balance를 직접 고치는 일은 결코 없습니다. 07_abstraction에서 실행해 봅니다.

account = BankAccount("Minsu", 10000)

05 · 상속: 관련된 계좌 종류의 공통 동작

저축 계좌(SavingsAccount)는 일종의 은행 계좌(BankAccount)입니다. 공통 계좌 연산을 물려받고, 보너스 데이터와 보너스 연산을 추가합니다.

상속은 기존 클래스를 확장한다

괄호 안에 부모 클래스를 쓰면 deposit, withdraw, get_balance를 물려받습니다. 몸체가 pass뿐이어도 부모의 메서드가 그대로 동작합니다. 여기에 고정 보너스 금액을 추가할 것입니다.

class SavingsAccount(BankAccount):
    pass

savings = SavingsAccount("Minsu", 10000)
print(savings.deposit(1000))    # True
print(savings.get_balance())    # 11000

super로 부모의 초기화를 재사용

하위 클래스는 인자 하나(bonus)를 더 받습니다. super().__init__(owner, balance)가 owner와 _balance를 초기화하고, self.bonus가 새 속성을 저장합니다.

class SavingsAccount(BankAccount):
    def __init__(self, owner, balance, bonus):
        super().__init__(owner, balance)
        self.bonus = bonus

새 메서드가 물려받은 동작을 재사용

add_bonus는 물려받은 deposit을 호출하므로 기존 검사가 그대로 적용됩니다. 부를 때마다 고정 보너스가 한 번 더해집니다. 06_inheritance에서 보너스, 입금, 출금, 거부된 출금을 차례로 확인합니다.

def add_bonus(self):
    return self.deposit(self.bonus)

06 · 다형성: 같은 호출, 다른 구현

두 객체 모두 account_type()을 지원하지만 각 클래스가 자기 구현을 제공합니다. 호출하는 쪽은 같은 메서드 이름을 씁니다.

물려받은 메서드 재정의(override)

부모는 기본 라벨을 제공하고, 자식은 같은 이름의 메서드를 정의합니다. Python은 실제 객체의 클래스에 맞는 메서드를 고릅니다. 아래는 메서드만 보인 것이며 전체 클래스는 08_polymorphism에 있습니다.

class BankAccount:
    def account_type(self):
        return "Standard"

class SavingsAccount(BankAccount):
    def account_type(self):
        return "Savings"

반복문 하나가 두 계좌 종류를 다룬다

리스트에 서로 다른 계좌 종류가 들어 있어도 각 호출은 그 객체의 구현을 씁니다. 클래스 이름으로 분기할 필요가 없습니다.

accounts = [BankAccount("Minsu", 10000),
            SavingsAccount("Jisu", 5000, 500)]
for account in accounts:
    print(account.owner, account.account_type(),
          account.get_balance())
# Minsu Standard 10000
# Jisu Savings 5000

1. State and object identity

Recap: class, object and instance

In a = BankAccount("Minsu", 1000) and b = BankAccount("Jisu", 500), BankAccount is the class that defines how an account behaves, and a and b refer to two separate account objects. Both objects are instances of BankAccount. An object is already an instance the moment it is created, so there is no extra step that turns an object into an instance.

class SimpleAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

account = SimpleAccount("Minsu", 1000)

__init__ initializes the newly created instance. self receives that instance, and owner and balance receive the other arguments. This minimal example has no validation; the main model we look at later adds it.

Attributes store state, and methods describe operations on the object. After account.deposit(200), account.balance becomes 1200.

Class variables and instance variables

class LabelledAccount:
    bank_name = "Python Bank"
    def __init__(self, owner):
        self.owner = owner

a = LabelledAccount("Minsu")
b = LabelledAccount("Jisu")
LabelledAccount.bank_name = "Campus Bank"
print(a.bank_name, b.bank_name)   # Campus Bank Campus Bank

bank_name belongs to the class, while each instance has its own owner. If you change the class's value, every instance sees the new value. But if you assign through an instance, as in a.bank_name = ..., the class variable does not change; instead a new instance attribute with the same name is created on a only. You can check both cases in turn in week7_review.

Calling a method and self

Both forms pass a as self. To deposit only once, run only one of them. self is a conventional parameter name, not a Python keyword, and the method reads and changes the instance through self. Assignment creates another reference

Assignment only binds another name to the existing object; it does not construct a second BankAccount. Conversely, calling the class twice with the same values creates two separate objects. 2. Valid state and method contracts

The balance invariant

An invariant is a rule that must hold right after construction and after every public operation. The account rules in this lesson are:

  • The balance is a nonnegative integer in the smallest currency unit.
  • Deposits and withdrawals accept positive integers only.
  • A rejected operation changes nothing.
  • The internal _balance changes only through the account's methods.

Question to think about: if amount is negative and balance -= amount runs as is, which rule is broken?

Validate during initialization

class BankAccount:
    def __init__(self, owner, balance=0):
        if not isinstance(owner, str) or not owner.strip():
            raise ValueError("owner must be nonblank text")
        if type(balance) is not int or balance < 0:
            raise ValueError("balance must be a nonnegative integer")
        self.owner = owner.strip()
        self._balance = balance

If invalid starting data comes in, an exception is raised before construction finishes, so an account with an invalid balance is never created at all. The caller can catch the exception, as below, and explain the error or ask for another value. If construction ends with an exception, the assignment account = ... does not happen either.

try:
    account = BankAccount("Minsu", -100)
except ValueError as error:
    print(error)

There is a reason the code uses type(balance) is not int rather than isinstance(balance, int). In Python, bool is a subclass of int, so isinstance(True, int) is True. This lesson's integer policy does not accept True as an amount, so the check requires exactly int. In validation you can see that a blank name, a negative balance and a True balance are all rejected, and that deposits of 0, -10, 1.5, "10" and True all return False.

Deposits and withdrawals that preserve the rules

def deposit(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    self._balance += amount
    return True

def withdraw(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    if amount > self._balance:
        return False
    self._balance -= amount
    return True

False means "rejected and nothing changed"; True means "the balance changed by amount". The key is to validate before mutating state. A withdrawal has two kinds of failure, an invalid amount and insufficient funds, and both leave the balance unchanged. Withdrawing exactly the balance is allowed.

3. Objects that collaborate

The key sentence of this section is "AccountBook has accounts; SavingsAccount is an account."

Composition: an AccountBook holds accounts

class AccountBook:
    def __init__(self):
        self._accounts = []

    def add_account(self, account):
        if account in self._accounts:
            return False
        self._accounts.append(account)
        return True

Each AccountBook instance gets its own list, and that list stores references to account objects. Adding the same account again returns False.

The shared mutable class-attribute trap

class BadBook:
    accounts = []

first = BadBook()
second = BadBook()
first.accounts.append("Minsu")
print(second.accounts)   # ["Minsu"]

If a list is a class attribute, every instance shares that one list. Mutable state that each book should have for itself must be created inside __init__ as self._accounts. shared_state compares the two approaches.

Delegate to each account

def total_balance(self):
    total = 0
    for account in self._accounts:
        total += account.get_balance()
    return total

def report(self):
    rows = []
    for account in self._accounts:
        rows.append((account.owner, account.account_type(),
                     account.get_balance()))
    return rows

AccountBook coordinates accounts through their public methods. It does not need to read account._balance directly. The total of an empty book is 0. report returns result data instead of printing, so the caller can decide whether to print it or save it. It must not return the mutable internal account list itself.

Changes remain visible through references

a = BankAccount("Minsu", 1000)
book = AccountBook()
book.add_account(a)
a.withdraw(300)
print(book.total_balance())   # 700

book and a refer to the same account object, and the book recalculates the total from the current account state every time. A separately created empty AccountBook still has total 0. In composition you can also see that the report() result (a list of tuples) taken before the withdrawal still says 1000, and only a fresh call shows 700.

Inheritance: a specialized account

class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, bonus=100):
        super().__init__(owner, balance)
        if type(bonus) is not int or bonus <= 0:
            raise ValueError("bonus must be a positive integer")
        self.bonus = bonus

    def add_bonus(self):
        return self.deposit(self.bonus)

The subclass reuses the base account's validation rules through super().__init__ and adds one operation (add_bonus). add_bonus also calls the inherited deposit, so it keeps the same rules.

Overriding one public operation

class BankAccount:
    def account_type(self):
        return "Standard"

class SavingsAccount(BankAccount):
    def account_type(self):
        return "Savings"

A shared method name provides behavior that fits each type. SavingsAccount still supports all of get_balance, deposit and withdraw, so one piece of calling code can use the same operations on different accounts.

accounts = [BankAccount("Minsu", 700),
            SavingsAccount("Jisu", 600, 100)]
for account in accounts:
    print(account.owner, account.account_type(), account.get_balance())
# Minsu Standard 700
# Jisu Savings 600

잔액 불변식

불변식(invariant)은 생성 직후와 모든 공개 동작 뒤에 항상 성립해야 하는 규칙입니다. 이 수업의 계좌 규칙은 다음과 같습니다.

  • 잔액은 가장 작은 화폐 단위의 0 이상 정수다.
  • 입금과 출금은 양의 정수만 받는다.
  • 거부된 동작은 아무것도 바꾸지 않는다.
  • 내부의 _balance는 계좌의 메서드를 통해서만 바뀐다.

생각해 볼 질문: amount가 음수일 때 balance -= amount를 그대로 실행하면 어떤 규칙이 깨질까요?

        self.owner = owner.strip()
        self._balance = balance

잘못된 초기값이 들어오면 생성이 끝나기 전에 예외가 발생합니다. 그래서 잘못된 잔액을 가진 계좌는 아예 만들어지지 않습니다. 호출하는 쪽에서는 다음처럼 예외를 잡아 설명하거나 다른 값을 다시 요청할 수 있습니다. 생성이 예외로 끝나면 account = ... 대입도 일어나지 않습니다.

try:
    account = BankAccount("Minsu", -100)
except ValueError as error:
    print(error)

여기서 isinstance(balance, int)가 아니라 type(balance) is not int를 쓴 이유가 있습니다. 파이썬의 bool은 int의 하위 클래스라서 isinstance(True, int)가 True입니다. 이 수업의 정수 정책에서는 True를 금액으로 받지 않으므로 정확히 int인지 검사합니다. validation에서 공백 이름, 음수 잔액, True 잔액이 모두 거부되고, 0, -10, 1.5, "10", True 입금이 모두 False인 것을 확인합니다.

규칙을 지키는 입금과 출금

def deposit(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    self._balance += amount
    return True

def withdraw(self, amount):
    if type(amount) is not int or amount <= 0:
        return False
    if amount > self._balance:
        return False
    self._balance -= amount
    return True

False는 "거부되었고 아무것도 바뀌지 않았다", True는 "잔액이 amount만큼 바뀌었다"는 뜻입니다. 핵심은 상태를 바꾸기 전에 먼저 검증하는 것입니다. 출금에는 잘못된 금액과 잔액 부족이라는 두 종류의 실패가 있으며, 둘 다 잔액을 그대로 둡니다. 잔액과 정확히 같은 금액을 출금하는 것은 허용됩니다.

캡슐화와 공개 접근

def get_balance(self):
    return self._balance

get_balance는 잔액을 바꾸지 않고 결과만 보여 줍니다. 앞의 밑줄은 내부용이라는 관례이므로, 파이썬은 account._balance = -100을 막지 않습니다. 팀 코드에서는 문서로 정한 공개 인터페이스를 존중해야 합니다. state_checks의 두 번째 단계에서 실제로 -100이 들어가는 것을 볼 수 있습니다.

3. 함께 일하는 객체

이 절의 핵심 문장은 "AccountBook은 계좌들을 가지고 있다(has), SavingsAccount는 계좌이다(is)"입니다.

합성: AccountBook이 계좌를 담는다

class AccountBook:
    def __init__(self):
        self._accounts = []

    def add_account(self, account):
        if account in self._accounts:
            return False
        self._accounts.append(account)
        return True

AccountBook 인스턴스마다 자기 리스트가 따로 생기고, 그 리스트에는 계좌 객체에 대한 참조가 저장됩니다. 같은 계좌를 다시 추가하면 False를 돌려줍니다.

변경 가능한 클래스 속성의 함정

class BadBook:
    accounts = []

first = BadBook()
second = BadBook()
first.accounts.append("Minsu")
print(second.accounts)   # ["Minsu"]

리스트를 클래스 속성으로 두면 모든 인스턴스가 리스트 하나를 함께 씁니다. 장부마다 따로 가져야 하는 변경 가능한 상태는 __init__ 안에서 self._accounts로 만들어야 합니다. shared_state에서 두 방식을 비교합니다.

각 계좌에 일을 맡기기

def total_balance(self):
    total = 0
    for account in self._accounts:
        total += account.get_balance()
    return total

def report(self):
    rows = []
    for account in self._accounts:
        rows.append((account.owner, account.account_type(),
                     account.get_balance()))
    return rows

AccountBook은 계좌의 공개 메서드를 통해 계좌들을 조정합니다. account._balance를 직접 읽을 필요가 없습니다. 빈 장부의 합계는 0입니다. report는 출력하지 않고 결과 데이터를 돌려주므로, 호출한 쪽이 출력할지 저장할지 정할 수 있습니다. 이때 내부의 변경 가능한 계좌 리스트를 그대로 돌려주면 안 됩니다.

참조를 통해 변화가 보인다

a = BankAccount("Minsu", 1000)
book = AccountBook()
book.add_account(a)
a.withdraw(300)
print(book.total_balance())   # 700

book과 a는 같은 계좌 객체를 가리키고, 장부는 합계를 현재 계좌 상태로부터 매번 다시 계산합니다. 따로 만든 빈 AccountBook의 합계는 여전히 0입니다. composition에서는 출금 전에 받아 둔 report() 결과(튜플 목록)는 1000 그대로이고, 다시 호출한 결과만 700으로 바뀌는 것도 확인할 수 있습니다.

상속: 특화된 계좌

class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, bonus=100):
        super().__init__(owner, balance)
        if type(bonus) is not int or bonus <= 0:
            raise ValueError("bonus must be a positive integer")
        self.bonus = bonus

    def add_bonus(self):
        return self.deposit(self.bonus)

하위 클래스는 super().__init__으로 기반 계좌의 검증 규칙을 재사용하고, 동작 하나(add_bonus)를 추가합니다. add_bonus도 물려받은 deposit을 호출하므로 같은 규칙을 지킵니다.

공개 동작 하나를 재정의하기

class BankAccount:
    def account_type(self):
        return "Standard"

class SavingsAccount(BankAccount):
    def account_type(self):
        return "Savings"

같은 메서드 이름이 종류에 맞는 동작을 제공합니다. SavingsAccount는 여전히 get_balance, deposit, withdraw를 모두 지원합니다. 그래서 하나의 호출 코드가 서로 다른 계좌에 같은 동작을 쓸 수 있습니다.

accounts = [BankAccount("Minsu", 700),
            SavingsAccount("Jisu", 600, 100)]
for account in accounts:
    print(account.owner, account.account_type(), account.get_balance())
# Minsu Standard 700
# Jisu Savings 600

inheritance에서 보너스를 두 번 받아 700이 되는 것과 이 반복문의 출력을 확인합니다.

상속과 합성 비교

관계예책임
계좌이다 (is-a)SavingsAccount가 BankAccount를 상속계좌의 계약을 지키며 동작을 확장
계좌를 가진다 (has-a)AccountBook이 계좌 참조를 저장계좌 모음을 조정

get_balance를 재사용하겠다고 AccountBook이 BankAccount를 상속해서는 안 됩니다. 장부는 계좌가 아니기 때문입니다. 또한 객체 상태가 필요 없다면 딕셔너리와 함수만으로도 충분할 수 있습니다.

체크포인트
