In the planning stage, rather than the code structure, observe how the data format written in the proposal (study.csv: date,course,minutes) and the acceptance criteria (F1 log entry, F1 bad input, F3 totals) are checked as pass/fail.슬라이드의 예시 주제 '공부 시간 기록기'를 설계 단계에서 실제로 구현한 프로그램이다. 기획 단계에서는 코드 구조보다, 제안서에 쓴 데이터 형식(study.csv: date,course,minutes)과 수용 기준(F1 기록, F1 잘못된 입력, F3 합계)이 통과/실패로 확인되는 모습을 관찰한다.

Steps실행 순서

  1. cat data/study.csv

    The answers to the four data-design questions are right there: the file name study.csv, the columns date,course,minutes, the value rules (dates as YYYY-MM-DD, course names in lowercase, minutes as positive integers), and a small hand-checked sample of 2 rows.데이터 설계 네 가지 질문의 답이 그대로 보인다: 파일 이름 study.csv, 열 date,course,minutes, 값의 규칙(날짜 YYYY-MM-DD, 과목 소문자, 분은 양의 정수), 손으로 확인한 작은 표본 2행.

  2. wc -l data/study.csv

    Baseline: 3 lines including the header. Compare the line count before and after the bad input in the next step.기준선: 헤더 포함 3줄이다. 다음 단계의 잘못된 입력 전후로 줄 수를 비교한다.

  3. printf '2026-10-26\npython\n-30\n' | python3 main.py wc -l data/study.csv

    Acceptance criterion 'F1 bad input: entering -30 minutes prints a warning; file unchanged'. The warning Not saved: minutes must be positive appears and the line count is still 3. The F3 totals also stay python 90, stats 45. The input was fed in with printf, but you can also run python3 main.py and type it yourself.수용 기준 'F1 bad input: -30분을 입력하면 경고가 나오고 파일은 그대로'. Not saved: minutes must be positive 경고가 나오고 줄 수는 여전히 3이다. F3 합계도 python 90, stats 45 그대로다. 입력은 printf로 넣었지만 python3 main.py를 실행해 직접 입력해도 된다.

  4. printf '2026-10-26\npython\n60\n' | python3 main.py tail -n 1 data/study.csv

    Acceptance criterion 'F1 log entry: valid input appends one row to study.csv'. Saved. appears and one row, 2026-10-26,python,60, is added at the end of the file. The python total becomes 90 + 60 = 150.수용 기준 'F1 log entry: 올바른 입력은 study.csv에 한 행을 추가'. Saved.가 나오고 파일 끝에 2026-10-26,python,60 한 행이 붙었다. 합계의 python은 90 + 60 = 150이 된다.

  5. python3 test_logic.py

    This file writes the same acceptance criteria as asserts, with no keyboard input. It checks that the sample week's totals are python 90 and stats 45 and that -30, 0 and abc are rejected, then prints All checks passed. This is what the slide means when it says the acceptance-criterion lines written in the planning stage become tests in the testing stage almost word for word.같은 수용 기준을 키보드 입력 없이 assert로 적은 파일이다. 표본 주의 합계가 python 90, stats 45인지, -30·0·abc가 거부되는지 검사하고 All checks passed.를 출력한다. 기획 단계에서 쓴 수용 기준 문장이 테스트 단계에서 거의 그대로 테스트가 된다는 슬라이드의 말이 이런 뜻이다.

The structure of this program (splitting into logic, storage and report; function contracts) is covered in detail in "From Proposal to Design: Decomposition, Contracts, Modules" in the same chapter. Here you only need to see that the requirements and acceptance criteria in a proposal must be 'statements you can judge pass/fail by running the program'. Step 4 adds a row to data/study.csv, so reload the page if you want to return to the original state.이 프로그램의 구조(logic·storage·report로 나누기, 함수 계약)는 같은 장의 '제안서에서 설계로: 분해, 계약, 모듈'에서 자세히 다룬다. 여기서는 제안서의 요구사항과 수용 기준이 '실행해서 통과/실패를 판정할 수 있는 문장'이어야 한다는 점만 확인하면 된다. 단계 4는 data/study.csv에 행을 추가하므로, 처음 상태로 돌리고 싶으면 페이지를 새로 고친다.

Steps실행 순서

  1. ls; cat data/study.csv

    The same as the project-folder layout on the slide: code files at the top level, data in data/. The CSV has the header date,course,minutes and 2 sample rows.슬라이드의 프로젝트 폴더 구조와 같다: 코드 파일은 맨 위에, 데이터는 data/에 있다. CSV는 date,course,minutes 헤더와 표본 2행이다.

  2. printf '2026-10-26\nPython \n60\n' | python3 main.py

    The three input lines (date, course, minutes) were fed in with printf. You can also run python3 main.py yourself and type them. Even with mixed case and a space as in 'Python ', make_record's strip().lower() turns it into python, so it is added to the same course: python 150 min, stats 45 min. report.py sorts the output from the largest total down.입력 세 줄(날짜, 과목, 분)을 printf로 넣었다. 직접 python3 main.py를 실행해 입력해도 된다. 'Python '처럼 대문자와 공백이 섞여도 make_record가 strip().lower()로 python이 되어 같은 과목으로 합산된다: python 150 min, stats 45 min. report.py가 큰 합계부터 정렬해 출력한다.

  3. printf '2026-10-26\nart\n-30\n' | python3 main.py printf '2026-10-26\nart\nabc\n' | python3 main.py wc -l data/study.csv

    logic only raises ValueError; main decides the sentence the user sees (Not saved: ...). For -30 it is our own message; for abc it is the invalid literal message from int(). Neither is saved, so the file stays at the header plus 3 rows, 4 lines.logic은 ValueError를 일으키기만 하고, 사용자에게 보여 줄 문장(Not saved: ...)은 main이 정한다. -30은 우리가 쓴 메시지, abc는 int()가 낸 invalid literal 메시지다. 두 번 모두 저장되지 않아 파일은 헤더+3행, 4줄 그대로다.

  4. python3 test_logic.py

    This checks only the logic functions, with no keyboard and no files. It takes less than a second and you can rerun it after every change. All checks passed. means the acceptance criteria pass.키보드도 파일도 없이 logic 함수만 검사한다. 1초도 걸리지 않으며 변경할 때마다 다시 돌릴 수 있다. All checks passed.가 나오면 수용 기준이 통과한 것이다.

  5. python3 - <<'EOF' from logic import parse_minutes print(parse_minutes("45")) print(parse_minutes.__doc__.splitlines()[0]) EOF

    The docstring is the contract. Its first line says what is returned: Return text as a positive whole number of minutes.docstring이 곧 계약이다. 첫 줄은 무엇을 돌려주는지를 말한다: Return text as a positive whole number of minutes.

  6. python3 - <<'EOF' from logic import make_record, weekly_totals from report import format_totals rows = [make_record("2026-10-24", "python", "90"), make_record("2026-10-25", "Stats", "45")] print(rows[1]) print("\n".join(format_totals(weekly_totals(rows)))) EOF

    The example from the slide 'Importing your own files'. logic.py and report.py in the same folder are imported by module name. One record is a dict with fixed keys ({'date': ..., 'course': 'stats', 'minutes': 45}, minutes is an int), all records are a list of dicts, and the totals are a dict from course to minutes.슬라이드 '내 파일 import하기'의 예다. 같은 폴더의 logic.py, report.py를 모듈 이름으로 불러온다. 한 레코드는 고정된 키를 가진 dict({'date': ..., 'course': 'stats', 'minutes': 45}, minutes는 int), 전체 레코드는 dict의 list, 합계는 과목→분 dict다.

  7. python3 - <<'EOF' import csv rows = list(csv.DictReader(open("data/study.csv", newline=""))) print(rows[0]["course"], repr(rows[0]["minutes"])) print(rows[0]["minutes"] + rows[1]["minutes"]) EOF

    csv.DictReader uses the header as keys, but every value is a str. '90' + '45' becomes 9045, not 135. That is why storage.load_records converts with int() once, right after reading.csv.DictReader는 헤더를 키로 쓰지만 값은 모두 str이다. '90' + '45'는 135가 아니라 9045가 된다. 그래서 storage.load_records가 읽자마자 int()로 한 번 변환해 둔다.

  8. mkdir -p /tmp/trap echo 'x = 1' > /tmp/trap/csv.py cd /tmp/trap python3 - <<'EOF' import csv print(csv.__file__, hasattr(csv, "DictReader")) EOF cd -

    Import trap 1: if you name a file after a standard-library module, your own file hides the real module. /tmp/trap/csv.py is loaded and has no DictReader (False). If this happens in a project, you get AttributeError: module 'csv' has no attribute 'DictReader'. Rename the file and delete __pycache__ to fix it.import 함정 1: 표준 라이브러리 이름으로 파일을 만들면 자기 파일이 진짜 모듈을 가린다. /tmp/trap/csv.py가 불려 와 DictReader가 없다(False). 프로젝트에서 이런 일이 생기면 AttributeError: module 'csv' has no attribute 'DictReader'가 난다. 파일 이름을 바꾸고 __pycache__를 지우면 해결된다.

Step 2 adds one row (2026-10-26,python,60) to data/study.csv. To return to the original state, reload the page. The test_logic.py in this folder is not unittest but a script listing asserts, so run it with python3 test_logic.py.단계 2는 data/study.csv에 한 행(2026-10-26,python,60)을 추가한다. 처음 상태로 돌리려면 페이지를 새로 고친다. 이 폴더의 test_logic.py는 unittest가 아니라 assert를 나열한 스크립트이므로 python3 test_logic.py로 실행한다.

Steps실행 순서

  1. python3 refactor_lab.py

    In the starting state the TODO functions return only placeholder values (0, {}, []), so most checks FAIL. import csv
from pathlib import Path
 
FIELDS = ["date", "course", "minutes"]
 
 
def load_records(path):
    """Return every row of the CSV file as a record dict.
 
    minutes is converted to int. A missing file returns [].
    """
    path = Path(path)
    if not path.exists():
        return []
    with open(path, newline="", encoding="utf-8") as f:
        return [{"date": row["date"], "course": row["course"],
                 "minutes": int(row["minutes"])}
                for row in csv.DictReader(f)]
 
 
def append_record(path, record):
    """Append one record to the CSV file, writing the header if the file is new."""
    path = Path(path)
    is_new = not path.exists()
    with open(path, "a", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=FIELDS)
        if is_new:
            writer.writeheader()
        writer.writerow(record)

"""Pure rules for a single-date classroom snapshot; prices are integer KRW."""
from datetime import date
 
FIELDS = ["date", "code", "name", "market", "previous_close", "close", "volume"]
MARKETS = ("ALL", "KOSPI", "KOSDAQ")
 
 
def parse_row(row):
    """Return a typed quote; raise ValueError for any invalid field. No I/O."""
    if set(row) != set(FIELDS) or any(not isinstance(v, str) for v in row.values()):
        raise ValueError("each row needs exactly seven fields")
    quote = {key: value.strip() for key, value in row.items()}
    day = quote["date"]
    if date.fromisoformat(day).isoformat() != day:
        raise ValueError("date must be YYYY-MM-DD")
    code = quote["code"]
    if len(code) != 6 or not code.isascii() or not code.isdigit():
        raise ValueError("code must be six ASCII digits")
    if not quote["name"] or quote["market"] not in MARKETS[1:]:
        raise ValueError("name and KOSPI/KOSDAQ market are required")
    for field in ("previous_close", "close", "volume"):
        text = quote[field]
        if not text.isascii() or not text.isdigit():
            raise ValueError(f"{field} must be a whole number")
        quote[field] = int(text)
        minimum = 0 if field == "volume" else 1
        if quote[field] < minimum:
            raise ValueError(f"{field} must be >= {minimum}")
    return quote
 
 
def change_pct(previous_close, close):
    """Return unrounded daily percent change; both prices must be positive."""
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    return (close - previous_close) / previous_close * 100
 
 
def analyze(quotes, market):
    """Validate snapshot identity; filter and sort by change desc, then code asc.
 
    Return fresh quote dicts with change_pct. Empty input/selection returns [].
    Mixed dates, duplicate codes or an unknown market raise ValueError.
    quotes must already contain typed, validated values from parse_row().
    """
    if market not in MARKETS:
        raise ValueError("market must be ALL, KOSPI or KOSDAQ")
    if len({q["date"] for q in quotes}) > 1:
        raise ValueError("snapshot must contain one date")
    codes = [q["code"] for q in quotes]
    if len(set(codes)) != len(codes):
        raise ValueError("duplicate code in snapshot")
    rows = [dict(q, change_pct=change_pct(q["previous_close"], q["close"]))
            for q in quotes if market == "ALL" or q["market"] == market]
    return sorted(rows, key=lambda q: (-q["change_pct"], q["code"]))
 
 
def summarize(rows):
    """Return sample count, up/down/flat counts and equal-weight mean (or None)."""
    count = len(rows)
    return {"count": count,
            "up": sum(q["change_pct"] > 0 for q in rows),
            "down": sum(q["change_pct"] < 0 for q in rows),
            "flat": sum(q["change_pct"] == 0 for q in rows),
            "mean": sum(q["change_pct"] for q in rows) / count if count else None}

"""CSV input and atomic HTML output; all file I/O lives here."""
import csv
import os
from pathlib import Path
import tempfile
from logic import FIELDS, parse_row
 
 
def load_quotes(path):
    """Read UTF-8(-BOM) CSV; reject malformed header/rows with ValueError.
 
    Missing or unreadable files raise OSError. Header-only files return [].
    """
    with open(path, encoding="utf-8-sig", newline="") as stream:
        reader = csv.DictReader(stream)
        if reader.fieldnames != FIELDS:
            raise ValueError("CSV header must be " + ",".join(FIELDS))
        quotes = []
        for number, row in enumerate(reader, start=2):
            try:
                quotes.append(parse_row(row))
            except ValueError as error:
                raise ValueError(f"CSV row {number}: {error}") from error
    return quotes
 
 
def write_html(path, html):
    """Replace output only after a complete UTF-8 write; raise OSError on failure."""
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    temporary = None
    try:
        with tempfile.NamedTemporaryFile(mode="w", encoding="utf-8",
                                         dir=path.parent, delete=False) as stream:
            temporary = Path(stream.name)
            stream.write(html)
        os.replace(temporary, path)
    finally:
        if temporary is not None and temporary.exists():
            temporary.unlink()

## 1. 시나리오와 범위
 
학생 민지는 장 마감 후 KOSPI·KOSDAQ 종목 일부의 변화를 비교하고 싶다. CSV 파일을 준비하고 `python3 main.py --market ALL`을 실행한다. 프로그램은 전일종가 대비 등락률을 계산하고 등락률 내림차순 표와 표본 요약을 `docs/index.html`에 만든다. 민지는 브라우저에서 기준일·시장·종목별 종가·등락률·거래량을 확인한다. KOSDAQ만 보고 싶으면 `--market KOSDAQ`으로 다시 생성한다.
 
오류 시나리오: 전일종가가 0인 행을 전달하면 행 번호가 포함된 오류를 출력한다. 종료 코드 1이며 기존 HTML은 바뀌지 않는다. 빈 CSV(정상 헤더만 있음)는 종목 0개, 평균 N/A, 빈 상태 안내를 표시한다. 입력 파일을 찾지 못하면 빈 데이터로 가장하지 않고 오류로 종료한다.
 
이 프로젝트는 단일 날짜의 **수업용 가상 표본**을 분석한다. 전 종목 시장 분석, 실시간 데이터 수집, 지수 계산, 투자 추천은 범위에 포함하지 않는다. 화면과 CSV 기준일을 연결하고 출처·가상 데이터 표시를 유지한다. 기간 수익률, 이동평균, 로그인, 차트, 클릭 필터, API 연동은 Should/Could로 남긴다.

## 3. Feature 명세
 
### FEAT-01: 검증된 스냅샷 불러오기 (REQ-01/02/06)
 
- 사용자: CSV를 준비한 학생. 명령: `python3 main.py --input data/prices.csv`.
- 정상: 파일 열기 → 헤더 검증 → 각 행 검증/타입 변환 → 한 날짜·중복코드 확인.
- 결과: 코드가 문자열인 종목 목록. 이 결과는 FEAT-02로 전달된다.
- 오류: 파일 없음/권한/인코딩/행 형식 오류는 `Report not generated: <reason>`. 기존 보고서 유지. 행 오류에는 CSV 행 번호 포함.
 
### FEAT-02: 시장별 분석 (REQ-02/03/04)
 
- 명령: `python3 main.py --market KOSPI`. 허용: ALL(기본), KOSPI, KOSDAQ.
- 계산: `(close - previous_close) / previous_close * 100`. 계산·정렬 중에는 반올림하지 않는다.
- 정상: 입력 전체의 날짜·중복을 검증 → 시장 필터 → 등락률 내림차순/코드 오름차순 → 표본 요약.
- 결과: KOSPI 표본 3개, 순서 005930→035420→000660, 평균 +0.33% 표시.
- 예외: 알 수 없는 시장은 argparse 사용 오류(종료 2). 선택 결과가 비면 0개·N/A.
 
### FEAT-03: 웹 보고서 생성·열람 (REQ-05/06)
 
- 명령: `python3 main.py --output docs/index.html`; 브라우저로 생성 파일을 연다.
- 정상: HTML 문자열 생성 → 임시 파일 쓰기 → 최종 파일 교체 → Generated 메시지.
- 결과: 표와 요약, 기준일·출처·가상 데이터 표시. 상승/하락 색상과 함께 +/− 부호를 사용한다.
- 오류: 출력 실패 시 `Report not generated: ...`, 종료 1. 기존 출력 보존.
- 외부 텍스트는 HTML escape한다. 네트워크 접속 없이 동작한다.
 
FEAT-01 PR → FEAT-02 PR → FEAT-03 PR 순서로 구현한다. 각 PR은 간단한 화면 출력 또는 임시 HTML까지 이어지는 실행 가능한 슬라이스로 제출한다. FEAT-01 단계의 분석/HTML fake는 명확히 표시하고 마지막 PR 전에 모두 교체한다.
 
## 4. Function 계약
 
| 함수 / 모듈 | 입력 → 결과 | 실패·부작용 / 호출자 |
|---|---|---|
| FUNC-01 `parse_row(row)` / logic | 7개 문자열 필드 dict → 정수 가격·거래량을 가진 새 dict | ValueError; 순수 / load_quotes |
| FUNC-02 `load_quotes(path)` / storage | CSV 경로 → 검증한 quote 목록; 헤더만 있으면 [] | OSError, ValueError, UnicodeError; 읽기 / main |

| FUNC-04 `analyze(quotes, market)` / logic | parse_row를 통과한 목록, 시장 → change_pct를 더한 새 정렬 목록 | 시장/중복/날짜 혼합 ValueError; 순수 / main |

| FUNC-06 `render_html(rows, summary, market, snapshot_date)` / report | 검증된 분석 결과 → 완전한 HTML str | 텍스트 escape, 화면에서만 반올림; 순수 / main |

| FUNC-08 `main(argv=None)` / main | CLI 인자 → 종료 코드 0 또는 1 | argparse는 사용 오류 2; 출력·조립 |
 
Quote: `{date: str, code: str, name: str, market: str, previous_close: int, close: int, volume: int}`. 분석 행은 `change_pct: float` 추가. Summary는 정수 count/up/down/flat와 float 또는 None인 mean. 가격 단위는 원, 거래량은 주다. parse_row만 문자열을 숫자로 바꾼다. main과 storage가 I/O를 맡고 logic/report는 문자열·자료구조만 다룬다.

### 4.1 Processes and Threads
 
```text
[학생 CLI] -> [Python main: 단일 프로세스·메인 스레드]

                |-> logic.analyze -> logic.summarize
                |-> report.render_html
                `-> storage.write_html -> docs/index.html
 
[브라우저] -> 생성된 HTML 파일 열기
선택: [python -m http.server] -> 정적 HTML 제공 (분석을 실행하지 않음)
```
 
| Process / Thread | Role | Creation / Termination |
|---|---|---|
| Python CLI / 메인 스레드 | CSV 검증·분석·HTML 생성 | `python3 main.py`; 성공 0, 데이터/I/O 실패 1, CLI 인자 오류 2로 종료 |

fork·자식 프로세스·작업 스레드·서버 프레임워크는 사용하지 않는다.
 
### 4.2 IPC and Synchronization
 
| Where Used | Method | Reason |
|---|---|---|
| 모듈 간 | 일반 함수 인자와 반환값 | 단일 Python 프로세스이므로 IPC 없음 |

A requirement is testable

Not a requirementRequirement

"Easy to use""A new user can log an entry with one command and no manual"

Functional requirements say what the program does; non-functional requirements say how well it does it (speed, safety, readability). If you cannot imagine a test for it, it is not a requirement yet.

Each Must feature needs at least one statement that decides pass or fail.

From Proposal to Design: Decomposition, Contracts, Modules제안서에서 설계로: 분해, 계약, 모듈

The proposal you wrote earlier decided what the program will do. This lesson decides how. It is the time to draw the program on paper before you type it. The lesson has three acts and a lab. In Act 1 (decompose), stories become features and features become functions. In Act 2 (contracts), every function promises its inputs, output and failures. In Act 3 (modules and data), you settle on one file per job and one shape per kind of data. In the final lab, each of you writes a design document and reviews it with a classmate.

The examples are study_logger, the finished study-time logger, and refactor_lab, a practice in splitting an expense tracker that crams everything into one function. The slide paths examples/study_logger/ and labs/session1/refactor_lab.py are ~/project/design/examples/study_logger/ and ~/project/design/starter/refactor_lab.py in this web lab.

Where we are in the project

In the planning stage you made a proposal with a problem, user stories, Must features and acceptance criteria. The MVP stage needs an MVP in which the Must features run end to end. The design stage is the bridge between them: a design document today, a Git repository in the following lesson, "Your Project Has a History". Rule: the Must scope freezes at the end of the design stage, and new ideas go to Should or Could.

Check your proposal first

Design is built on the proposal, so cracks in the proposal spread. Spend five minutes checking:

  • At most 3 Must features, each one sentence.
  • Each Must feature has a pass/fail acceptance criterion.
  • Your data file has a name, columns and types.
  • Your Won't list has at least two items.

A criterion like "entering -30 minutes prints a warning and the file is unchanged" is excellent. It becomes a test in the testing stage as it is.

The 200-line main.py

Every project starts as one file, and the problem is that most stay that way. To test the totals you must type at the keyboard every time, a change to the printing breaks the arithmetic, and by the end of the project neither you nor the grader can find anything. The cure is not more code but a plan for where code lives.

Design means making decisions on paper. A box on paper takes a minute to move; the same change in code costs an evening. There are four things to decide. Which functions exist, and what is each one's single job? What does each function take and return, and what does it do with bad input? Which file holds each function? What does one record of data look like, in memory and on disk? Your design document becomes the MVP-stage checklist: each time you implement one contract, you tick one box.

Act 1 · Decompose: from stories to functions

Big problems are small problems standing in a line. A story says why, a feature says what, and a function says how.

Story, feature, function

  • Story: As a student, I want to log study time by course, so that I can review my week.
  • Feature: F1 accepts date, course and positive minutes and saves valid entries.
  • Function: one verb, one job, testable alone.

Aim for 2–4 functions per Must feature.

The verb test

Read the feature sentence aloud and the verbs become functions. "F1: accept date, course and minutes; check the minutes; save valid entries."

F1 accept, check and save one entry
  -> read_entry()     asks the user       I/O
  -> make_record()    checks and builds   logic
  -> append_record()  writes the file     I/O

Verbs become functions, and nouns (date, course, minutes, record) become data. Name functions verb_noun, like make_record, not record_stuff. If a function name needs "and", it is two functions.

Input, processing, output

Every feature is a pipeline. Input is what arrives from the keyboard or a file, processing is the rules and calculations on that input, and output is what goes to the screen or a file. Processing is where the bugs live, and where the marks are. Draw the picture before you write code.

Act 2 · Contracts: promises between functions

"Give me this and I give you that, or I tell you why not." A contract is decided before the function body is written, and it is the part of your design that a grader can check line by line.

Anatomy of a contract

  • Name: a verb that says what you get back
  • Arguments: names and types
  • Return value: one type, always the same type
  • Failure: what happens with bad input

If you cannot fill in all four fields, the function is not designed yet.

Write the contract in the docstring

def parse_minutes(text):

    Raises ValueError if text is not a whole

    return minutes

Bad input will arrive. Decide on paper how each function deals with it.

  • return None: "nothing found" is a normal answer.
  • print inside the function: avoid. The caller cannot react and tests cannot see it.

Act 3 · Modules and data: where things live

One file per responsibility, one shape per kind of data. A module is just a .py file you import, and your design decides which function goes in which file.

One responsibility per file

  • main.py runs the program: ask, call, show.
  • logic.py holds the rules. No I/O at all.
  • storage.py is the only file that opens data files.
  • report.py turns results into lines of text.

Rule: imports point one way only. logic.py imports none of your other files.

Two import traps

Both cause confusing errors far from the real cause.

  • Never name a file after a library, such as csv.py or random.py. Your csv.py hides the real module and you get AttributeError: module 'csv' has no attribute 'DictReader'.
  • Never let two of your modules import each other. One of them would see a half-built module.

If the error remains after renaming the file, delete __pycache__. The last step of study_logger creates a csv.py in a temporary folder to reproduce the first trap.

Three shapes of data

  • One record: a dict with fixed keys.
  • All records: a list of dicts, in file order, duplicates allowed.
  • A summary: a dict from key to result, one entry per key.

1막 · 분해: 스토리에서 함수로

큰 문제는 작은 문제들이 줄지어 선 것입니다. 스토리는 왜, 기능은 무엇, 함수는 어떻게를 말합니다.

스토리, 기능, 함수

  • 스토리: 학생으로서, 나는 과목별 공부 시간을 기록하고 싶다. 그래야 한 주를 돌아볼 수 있다.
  • 기능: F1은 날짜, 과목, 양수인 분을 받아 올바른 항목을 저장한다.
  • 함수: 동사 하나, 일 하나, 혼자서 시험할 수 있음.

Must 기능 하나당 함수 2–4개를 목표로 합니다.

동사 테스트

기능 문장을 소리 내어 읽으면 동사가 함수가 됩니다. "F1: 날짜, 과목, 분을 받고, 분을 검사하고, 올바른 항목을 저장한다."

F1 accept, check and save one entry
  -> read_entry()     asks the user       I/O
  -> make_record()    checks and builds   logic
  -> append_record()  writes the file     I/O

동사는 함수가 되고, 명사(날짜, 과목, 분, 레코드)는 데이터가 됩니다. 함수 이름은 record_stuff가 아니라 make_record처럼 동사_명사로 짓습니다. 함수 이름에 "and"가 필요하다면 함수 두 개라는 뜻입니다.

입력, 처리, 출력

모든 기능은 파이프라인입니다. 입력은 키보드나 파일에서 들어오는 것, 처리는 그 입력에 대한 규칙과 계산, 출력은 화면이나 파일로 나가는 것입니다. 버그가 사는 곳도, 점수가 있는 곳도 처리 부분입니다. 코드를 쓰기 전에 그림부터 그립니다.

def parse_minutes(text):

    Raises ValueError if text is not a whole

잘못된 입력은 반드시 들어옵니다. 각 함수가 그것을 어떻게 다룰지 종이 위에서 정합니다.

  • raise ValueError: 입력이 규칙을 어겼다. 호출한 쪽이 대응해야 한다.
  • return None: "찾지 못함"이 정상적인 답이다.
  • 함수 안에서 print: 피한다. 호출한 쪽이 대응할 수 없고 테스트도 볼 수 없다.

3막 · 모듈과 데이터: 어디에 둘 것인가

파일 하나에 책임 하나, 데이터 종류마다 모양 하나. 모듈은 import하는 .py 파일일 뿐이며, 어떤 함수가 어느 파일에 들어갈지는 설계가 정합니다.

파일 하나에 책임 하나

  • main.py는 프로그램을 실행한다: 묻고, 호출하고, 보여 준다.
  • logic.py는 규칙을 담는다. 입출력이 전혀 없다.
  • storage.py는 데이터 파일을 여는 유일한 파일이다.
  • report.py는 결과를 텍스트 줄로 바꾼다.

규칙: import는 한 방향으로만 향합니다. logic.py는 내가 만든 다른 파일을 하나도 import하지 않습니다.

내 파일 import하기

from logic import make_record, weekly_totals
from report import format_totals

rows = [make_record("2026-10-24", "python", "90"),
        make_record("2026-10-25", "Stats", "45")]
for line in format_totals(weekly_totals(rows)):
    print(line)
python    90 min
stats     45 min

같은 폴더의 파일은 모듈이고, 이름은 .py를 뗀 파일 이름입니다. from logic import weekly_totals는 logic.py를 한 번 불러옵니다. 필요한 이름만 import하고 import *는 피합니다. 파이썬이 파일을 찾을 수 있도록 python3는 프로젝트 폴더에서 실행합니다. study_logger의 여섯 번째 단계가 이 코드를 실행합니다. make_record가 "Stats"를 stats로 바꿔 저장하는 것도 볼 수 있습니다.

실행할 것인가, import할 것인가

def format_totals(totals):
    return [f"{c:<8}{m:>4} min"
            for c, m in totals.items()]

if __name__ == "__main__":
    print(format_totals({"python": 90}))

if __name__ == "__main__":은 "이 파일을 실행한다"와 "함수를 빌려 준다"를 구분합니다. python3 report.py로 실행하면 블록이 실행되어 ['python 90 min']이 나오고, 다른 파일에서 import report하면 블록은 건너뜁니다. 모듈 맨 아래에 간단한 자체 점검을 넣을 때 씁니다. (study_logger의 report.py에는 이 블록이 없으므로, 직접 추가해 실행해 볼 수 있습니다.)

import 함정 두 가지

둘 다 진짜 원인에서 멀리 떨어진 곳에서 이해하기 어려운 오류를 냅니다.

  • 라이브러리 이름으로 파일을 만들지 않는다: csv.py, random.py. 내 csv.py가 진짜 모듈을 가려 AttributeError: module 'csv' has no attribute 'DictReader'가 난다.
  • 내 모듈 두 개가 서로를 import하게 하지 않는다. 한쪽이 반쯤 만들어진 모듈을 보게 된다.

파일 이름을 바꿨는데도 오류가 남으면 __pycache__를 지웁니다. study_logger의 마지막 단계에서 임시 폴더에 csv.py를 만들어 첫 번째 함정을 재현합니다.

데이터의 세 가지 모양

  • 레코드 하나: 고정된 키를 가진 dict.
  • 모든 레코드: dict의 list. 파일 순서대로, 중복 허용.
  • 요약: 키에서 결과로 가는 dict. 키마다 항목 하나.

모양은 지금 정합니다. 모든 함수의 계약이 이 모양을 언급하기 때문입니다. 예측 질문: 레코드는 왜 list이고 합계는 왜 dict일까요? (레코드는 순서가 있고 같은 과목이 여러 번 나올 수 있지만, 합계는 과목마다 하나의 값만 있어야 하기 때문입니다.)

파일에서 레코드로

import csv

with open("data/study.csv", newline="") as f:
    rows = list(csv.DictReader(f))
print(rows[0]["course"], repr(rows[0]["minutes"]))

csv.DictReader는 헤더를 키로 삼아 각 행을 dict로 만들지만, 모든 값은 str로 들어옵니다. 숫자는 읽은 직후 storage.py에서 한 번만 변환하고, 그다음부터 다른 모든 함수는 자료형을 믿을 수 있게 합니다. 함정: "90" + "45"는 "9045"입니다. 더하기 전에 변환합니다. study_logger의 일곱 번째 단계에서 변환 없이 더하면 실제로 9045가 나옵니다.

The last step of starter_repo changes one line of report.py and compares before and after with diff -u. Its output format (---, +++, @@, and -/+ lines) is the same as git diff, so it is good reading practice.

Act 2 · Branch: a safe place to try

main always runs; new work happens next door. Make one branch per feature and merge it when it works. Then we look at what conflicts look like and how to end them.

Why branch when you are alone?

A branch is a second line of commits that main does not see until you merge. main stays demo-ready at every moment. Each Must feature gets its own short-lived branch. A failed experiment is just one deleted branch, not a broken project. The graph shows the grader exactly how each feature was built.

Branch names and habits

  feature/report-title
* main

A good branch name is a to-do item: feature/save-records, fix/negative-minutes. One feature per branch, merged within days. git branch lists the branches, and * marks the current one. Commit before you switch branches. Make a habit of checking the branch name shown in the bottom-left corner of VS Code before you type.

When two edits collide

git merge feature/report-title
git status --short
cat report.py
CONFLICT (content): Merge conflict in report.py
Automatic merge failed; fix conflicts and then commit the result.
UU report.py
<<<<<<< HEAD
TITLE = "Minutes per course"
=======
TITLE = "Study time this week"
>>>>>>> feature/report-title

The same line was changed differently on two branches: main changed TITLE to "Minutes per course" and feature/report-title changed it to "Study time this week". Git will not guess; it stops and marks the file. UU means unmerged. From <<<<<<< HEAD to ======= is the current branch's (main's) content, and below it, up to >>>>>>>, is the content of the branch being merged in.

Resolve in three moves

git add report.py
git commit -m "Merge report title: keep both ideas"
git log --oneline --graph
*   f84e248 Merge report title: keep both ideas
|\
| * dd6fc23 Rename report title
* | b7d071f Clarify report title
|/
* 7846ed1 Add report title

A conflict is a question, and you answer it by editing the file. First, keep the line you want and delete all three marker lines. Second, git add the file to say "answered". Third, git commit to finish the merge. VS Code shows Accept Current, Accept Incoming and Accept Both buttons above each conflict.

Act 3 · Pull request: review your own work

A pull request (PR) is a merge with a conversation attached. It lives on GitHub, between your branch and main, and it is where you explain, check and get feedback.

Why a pull request in a solo project?

Even if nobody needs to approve it, a PR is the best record of your work. The description says what changed and why, in your own words. The Files changed tab makes you read your own diff. The instructor can comment on a specific line of your code. Each feature becomes one link that ties together branch, commits, review and merge.

Push the branch, open the PR

git switch -c feature/append-record
git add storage.py

This time we do not merge on the laptop. We push the branch and let GitHub merge. Set base to main and compare to your feature branch. Write the title like a commit message, saying what the feature does, and fill the description with the following four headings.

A PR description that earns points

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: the change, linked to a feature ID.
  • Why: the contract or acceptance criterion from your design document.
  • How I checked: the command you ran and what it printed.
  • Not in this PR: what is left for the next branch.

Two minutes to write, and a whole feature is explained. The contract of the example append_record ("write the header only when the file is newly created") is implemented in the study_logger storage.py from "From Proposal to Design".

The self-review checklist

Read the Files changed tab as if a stranger wrote the code.

  • python3 main.py still runs from a fresh terminal.
  • Every new function matches its contract and docstring.
  • No leftover debug print() or commented-out experiments.
  • No ignored files (__pycache__, .venv, .env) slipped in.
  • Only one feature in this PR.

If you find a problem, fix it on the same branch and push again. The PR updates automatically.

The feature loop

One loop per Must feature: pull, branch, commit a few times, push, pull request, merge, pull. In the implementation stage you go around this small loop three or four times. Small loops finish; giant branches rot. The grader sees this rhythm in your history.

혼자 작업하는데 왜 Git인가?

아무도 내 코드를 고치지 않아도 Git은 제 몫을 합니다.

  • 프로젝트 전체에 대한 되돌리기 버튼.
  • 과정의 증거: Git 작업 흐름은 20% 항목의 일부다.
  • 언제나 실행되어 시연에 바로 쓸 수 있는 main 브랜치.
  • 어느 컴퓨터에서든 이어서 작업할 수 있다.

함정: 마감 직전에 "final"이라는 커밋 하나만 있으면 아무것도 증명하지 못합니다.

코드가 사는 네 장소

모든 Git 명령은 변경을 다음 네 장소 사이에서 옮깁니다.

  1. 작업 폴더: VS Code에서 편집하는 파일들.
  2. 스테이징 영역: 다음 커밋에 넣으려고 골라 둔 변경.
  3. 로컬 저장소: 숨김 폴더 .git 안에 있는 모든 커밋.
  4. GitHub: 온라인에 있는 저장소의 사본.

1막 · 커밋: 메시지가 달린 저장 지점

Git 기초를 10분 만에 복습하고(init, status, add, commit, log, diff, push), 쓸모없는 파일을 막는 .gitignore와 점수를 얻는 습관을 다룹니다.

컴퓨터마다 한 번: 나는 누구인가?

git config --global init.defaultBranch main
git config user.name

Git은 모든 커밋에 이름과 이메일을 서명합니다. 노트북마다 한 번 설정하고, 이메일은 GitHub 계정의 것을 씁니다. 새 프로젝트의 첫 브랜치 이름은 항상 main으로 합니다. 마지막 명령은 설정한 이름(Jiwoo Park)을 출력해 결과를 확인합니다.

프로젝트 폴더 안에서 프로젝트당 한 번 git init을 실행합니다. 숨김 폴더 .git이 만들어지지만 아직 아무것도 저장되지 않았습니다. git status는 Git이 무엇을 보고 있는지 알려 주므로 수시로 실행합니다. 예측 질문: 폴더에는 __pycache__도 있는데 왜 목록에 없을까요? 답은 다음 절의 .gitignore입니다.

.gitignore: 절대 넣지 않는 것

# Python
__pycache__/
*.pyc
.venv/

# Editors and operating systems
.vscode/
.DS_Store

# Secrets: never commit these
.env
*.key

패턴을 적은 텍스트 파일이며, 패턴에 맞는 파일은 Git에게 보이지 않습니다. 생성 파일(__pycache__, .pyc)은 파이썬이 다시 만들고, 가상 환경(.venv)은 컴퓨터마다 따로 만들며, 시스템 찌꺼기(.DS_Store, Thumbs.db)는 필요 없습니다. 비밀 정보(.env, 키, 비밀번호)는 절대로 넣지 않습니다. 함정: 한 번 push한 비밀번호는 나중에 지워도 공개된 것입니다. 비밀번호를 바꿔야 합니다.

2막 · 브랜치: 안전하게 시도하는 곳

main은 언제나 실행되고, 새 작업은 옆집에서 합니다. 기능마다 브랜치 하나를 만들어 동작하면 병합합니다. 그다음 충돌이 어떻게 보이고 어떻게 끝내는지 봅니다.

혼자인데 왜 브랜치인가?

브랜치는 병합하기 전까지 main이 보지 못하는 두 번째 커밋 줄기입니다. main은 어느 순간에나 시연할 수 있는 상태를 유지합니다. Must 기능마다 수명이 짧은 브랜치를 하나씩 만듭니다. 실패한 실험은 망가진 프로젝트가 아니라 지운 브랜치 하나일 뿐입니다. 그래프는 각 기능이 어떻게 만들어졌는지 평가자에게 정확히 보여 줍니다.

3막 · 풀 리퀘스트: 내 작업을 스스로 검토하기

풀 리퀘스트(PR)는 대화가 붙은 병합입니다. GitHub에서 내 브랜치와 main 사이에 놓이며, 설명하고, 확인하고, 피드백을 받는 곳입니다.

개인 프로젝트에 왜 PR인가?

아무도 승인할 필요가 없어도 PR은 작업의 가장 좋은 기록입니다. 설명란에는 무엇이 왜 바뀌었는지 내 말로 적습니다. Files changed 탭은 내 diff를 직접 읽게 만듭니다. 교수자가 코드의 특정 줄에 댓글을 달 수 있습니다. 기능 하나가 브랜치, 커밋, 검토, 병합이 묶인 링크 하나가 됩니다.

점수를 얻는 PR 설명

## What
Add append_record() in storage.py (F1).
## Why
Contract: write the header only if the file is new.
## How I checked
Ran main.py twice -> one header, two rows.
## Not in this PR
Sorted totals come in feature/sort-totals.
  • What: 변경 내용과 연결된 기능 ID.
  • Why: 설계 문서의 계약이나 수용 기준.
  • How I checked: 실행한 명령과 그 출력.
  • Not in this PR: 다음 브랜치로 남긴 것.

쓰는 데 2분이면 기능 하나가 완전히 설명됩니다. 예로 든 append_record의 계약("파일이 새로 만들어질 때만 헤더를 쓴다")은 '제안서에서 설계로' 수업의 study_logger storage.py에 구현되어 있습니다.

스스로 검토 체크리스트

Files changed 탭을 낯선 사람이 쓴 코드처럼 읽습니다.

  • 새 터미널에서 python3 main.py가 여전히 실행된다.
  • 새 함수마다 계약과 docstring에 맞다.
  • 디버그용 print()나 주석 처리한 실험이 남아 있지 않다.
  • 무시해야 할 파일(__pycache__, .venv, .env)이 섞여 들어가지 않았다.
  • 이 PR에는 기능 하나만 있다.

문제를 찾았다면 같은 브랜치에서 고치고 다시 push합니다. PR은 자동으로 갱신됩니다.

Writing the Project Documents: Requirement, Feature, Function, UML프로젝트 문서 쓰기: 요구사항·기능·함수·UML

In this lesson you write the four design documents for your project: Requirement, Feature, Function and UML. The four documents do not describe different programs; they look at the same program from four directions. The requirement answers what must hold, the feature what the user sees, the function what the code promises, and UML how they connect. Today's shared example is the study logger from earlier in this chapter. On the lab pages you run study_logger_skeleton, a skeleton with only contracts, and study_logger_f1, which implements F1, and carry out the documents' checks yourself.

The class is 120 minutes with a 10-minute break in the middle. The first half covers three documents (requirement, feature, function), the second half UML and traceability, followed by a 46-minute lab in which you write the four documents for your own project.

Project guidance and document scope

The project uses only Python 3 and the standard library. Data is kept in a file and results are reported on the screen. Every project is checked on the same three points:

  • Does it refuse bad input?
  • Does it survive a missing file?
  • Is the file left unchanged after a failure?

The design covers the problem, the feature scope, the module structure and the data format. The four documents introduced today are a guide; the actual submission items and weights follow the syllabus.

The role of the four documents

DocumentQuestion it answersWhat it contains
DOC 1 · RequirementWhat must hold?The requirements, and a pass/fail criterion for each
DOC 2 · FeatureWhat does the user do?How to use it, and the results the user can observe
DOC 3 · FunctionWhich Python function does it?Inputs, return value and failure, as a contract
DOC 4 · UMLHow does it connect?Module relations, the order of calls, state changes

Linking requirements to implementation

A requirement is a condition to satisfy, and a feature is what the user does to satisfy it. A function is the code's promise, and a check decides whether that promise holds. UML sits under feature and function and shows the structure and flow that connect them.

Rule: use the same ID in every document. Then you can follow one requirement all the way to its code and its check.

Shared example: the study logger

There are three basic features: log one entry, reload the file, and show weekly totals per course. The result report prints one line per course, largest first, or, if the entry could not be saved, "Not saved" with the reason. Its duties are to refuse bad input, leave the file unchanged on failure, and survive a missing file.

DOC 1 · Requirement: the specification

The requirement document states what must hold, for whom, and how far. Each line must be something you can judge pass or fail.

  • Purpose and scope: who has what problem, what the program solves, and where it stops.
  • Requirement items: an ID, the statement, a priority (Must, Should, Could) and a check.
  • Functional requirements: log an entry, apply the input rules, report totals, keep the data.
  • Constraints: standard library only, input checked, file unchanged on failure.

Write only one condition per line. A check must be something a classmate can do at the keyboard.

Requirement example

These checks become the implementation stage's test_logic.py, and the testing stage's test list.

Matching requirements to checks

Give each requirement sentence an input condition and an observable result.

  • Input condition: exactly what is typed, or what the file holds before the run.
  • Observed result: what is printed, and what the file contains after the run.

A check that only works if its author stands beside you and explains it is not a check yet.

DOC 2 · Feature: the user-facing specification

The feature document describes the program as the user meets it: the command, the questions (prompts), and the results that come back.

FEAT-xx  <name>              basic | extension
purpose  one sentence
usage    command, prompts, allowed values
flow     step 1 ... step n, the normal path
result   what the user sees on success
errors   each failure and its message
serves   REQ-xx, REQ-yy
  • Identification: feature ID, name, purpose, and whether it is a basic feature or an extension.
  • How to use: the command, the prompts, the allowed values, the preconditions.
  • Behavior and result: the normal flow and the output the user checks.
  • Exceptions and links: bad input, failures, and the requirement IDs this feature serves.

Feature example: logging one entry

FEAT-01  Log one entry                     basic

         date YYYY-MM-DD, course, minutes > 0

The usage line is what you will actually type in the demo. Write it so that a stranger could follow it. List errors one by one, each with its message; a single line saying "handles errors" is not an error entry. The serves line is the traceability link back to the requirements.

A feature's normal path and error path

Define what the user sees on both the good day and the bad day. Both belong in the feature sheet.

  • Normal path: four steps, each with something the user can observe.
  • Input error: a sentence with the reason is printed, and nothing is written to the file.
  • File error: the cause is reported, nothing is left half-written, and the program ends cleanly.

DOC 3 · Function: Python function design

One function, one contract. The design document from your design stage already has the fields.

make_record(date: str, course: str,
            minutes_text: str) -> dict
module   logic.py       called by main()
I/O      none           pure   yes
returns  {"date", "course", "minutes": int}
fails    ValueError: empty course, or
         minutes not a whole number above 0
  • Signature: name, parameters with types, return type.
  • Inputs and results: allowed values and units, what success returns, and how failure shows.
  • Where it runs: which module it is in and who calls it, and whether it uses the keyboard, a file, or neither.
  • Failure and resources: whether it raises an exception or returns None, and who opens and closes the file.

Function example: make_record()

Write the contract in the docstring and the body under it, then add one call that shows the promise is kept.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))
python 90

The input is three strings from input(). Trimming and lower-casing the course happens here and only here. main() calls this function before anything is written. It returns one dict, with minutes as an int. On failure it raises ValueError with a reason, and main prints Not saved and writes nothing. The real implementation is in logic.py of study_logger_f1 (with the minutes check split out into parse_minutes()), and you can run the same call on the lab page.

Functions and modules: who does what

Once main() has asked the user, each module answers only one kind of question. None of them asks the user anything.

  • main.py asks, calls and prints. It holds no rules.
  • logic.py holds the rules and never touches the keyboard or the disk.
  • storage.py is the only module that opens data/study.csv.
  • report.py turns results into lines.

DOC 1 · 요구사항: 명세

요구사항 문서는 무엇이 성립해야 하는지, 누구를 위해, 어디까지인지를 적습니다. 각 줄은 합격 또는 불합격으로 판정할 수 있어야 합니다.

  • 목적과 범위: 누가 어떤 문제를 겪는지, 프로그램이 무엇을 해결하고 어디서 멈추는지.
  • 요구사항 항목: ID, 문장, 우선순위(Must, Should, Could), 검사.
  • 기능 요구사항: 한 건 기록, 입력 규칙 적용, 합계 보고, 데이터 보관.
  • 제약: 표준 라이브러리만 사용, 입력 검사, 실패 시 파일 불변.

한 줄에는 조건 하나만 씁니다. 검사는 같은 반 친구가 키보드 앞에서 할 수 있는 것이어야 합니다.

DOC 3 · 함수: 파이썬 함수 설계

함수 하나에 계약 하나입니다. 설계 단계에서 쓴 설계 문서에 이미 항목이 있습니다.

make_record(date: str, course: str,
            minutes_text: str) -> dict
module   logic.py       called by main()
I/O      none           pure   yes
returns  {"date", "course", "minutes": int}
fails    ValueError: empty course, or
         minutes not a whole number above 0
  • 시그니처: 이름, 자료형이 붙은 매개변수, 반환 자료형.
  • 입력과 결과: 허용되는 값과 단위, 성공하면 무엇을 반환하는지, 실패는 어떻게 드러나는지.
  • 실행 위치: 어느 모듈에 있고 누가 호출하는지, 키보드나 파일에 접근하는지 아니면 둘 다 하지 않는지.
  • 실패와 자원: 예외를 던지는지 None을 반환하는지, 파일은 누가 열고 닫는지.

함수 예: make_record()

계약은 docstring에, 본문은 그 아래에 씁니다. 그리고 약속이 지켜지는 것을 보여 주는 호출 하나를 붙입니다.

def make_record(date, course, minutes_text):
    """Return {"date": str, "course": str,
    "minutes": int}. The course is trimmed and
    lower-cased. Raises ValueError if course is
    empty or minutes_text is not a whole number
    above 0.
    """
    course = course.strip().lower()
    if not course:
        raise ValueError("course must not be empty")
    minutes = int(minutes_text)
    if minutes <= 0:
        raise ValueError("minutes must be positive")
    return {"date": date.strip(), "course": course,
            "minutes": minutes}

rec = make_record("2026-11-10", " Python ", "90")
print(rec["course"], repr(rec["minutes"]))
python 90

입력은 input()에서 온 문자열 세 개입니다. 과목의 공백 제거와 소문자 변환은 여기에서만 합니다. 이 함수는 무엇이든 쓰기 전에 main()이 호출합니다. 반환값은 dict 하나이고 minutes는 int입니다. 실패하면 이유를 담은 ValueError를 던지고, main은 Not saved를 출력하고 아무것도 쓰지 않습니다. study_logger_f1의 logic.py에 실제 구현이 있으며(분 검사는 parse_minutes()로 분리), 실습 페이지에서 같은 호출을 실행할 수 있습니다.

함수로 나누기

여섯 함수, 여섯 개의 단일 책임입니다. '제안서에서 설계로' 수업의 동사 테스트로 이름을 붙입니다.

함수계약
parse_minutes()분 문자열 → 양의 int, 아니면 ValueError
make_record()날짜, 과목, 분 → 기록 dict 하나
append_record()기록 하나 → data/study.csv에 한 행
load_records()파일 → 기록 목록, 파일이 없으면 []

규칙 함수 둘, 파일 함수 둘, 보고 함수 하나, 그리고 이들을 호출하는 main()입니다. 이름은 모두 동사+명사이고, 위 표의 한 줄이 계약 표의 한 행입니다. 함수를 설명하는 데 "그리고"가 필요하다면, 계약을 쓰기 전에 나눕니다.

함수와 모듈: 누가 무엇을 하는가

main()이 사용자에게 묻고 나면, 각 모듈은 한 종류의 질문에만 답합니다. 그중 어느 모듈도 사용자에게 무언가를 묻지 않습니다.

  • main.py는 묻고, 호출하고, 출력합니다. 규칙은 갖지 않습니다.
  • logic.py는 규칙을 갖고, 키보드나 디스크를 절대 건드리지 않습니다.
  • storage.py는 data/study.csv를 여는 유일한 모듈입니다.
  • report.py는 결과를 줄로 바꿉니다.

모듈 다이어그램의 화살표는 한 방향만 가리킵니다. 활동 다이어그램은 오류 분기를 포함한 단계를 보여 줍니다.

유스케이스 예

사용자와, 시스템이 제공하는 목표를 그립니다. 함수가 아니라 목표입니다. 행위자(actor)는 학생 한 명이고, 시스템 경계는 공부 기록기입니다. 목표는 세 가지입니다. 한 건 기록하기, 주간 합계 보기, 예전 기록 다시 찾기. 함수 이름은 여기에 나오지 않습니다. 호출 순서는 시퀀스 다이어그램의 몫입니다.

시퀀스 예: 한 번의 실행

정상 경로의 한 번 실행을, 시간이 위에서 아래로 흐르게 그립니다. 모든 화살표는 계약 표에 있는 호출입니다. main()은 logic을 먼저 호출하므로, 기록이 유효해지기 전에는 아무것도 쓰이지 않습니다. 돌아오는 화살표마다 데이터 모양 하나를 나릅니다. 기록, 기록 목록, 합계 dict, 줄 목록입니다. 실패 경로(ValueError)는 별도의 분기로 그리거나, 더 짧은 두 번째 다이어그램으로 그립니다.

상태 예: 기록 하나

상태 넷과 막다른 길 하나입니다. 각 전이는 표에 있는 함수입니다. 입력됨(typed) → make_record()가 검사함(checked) → append_record()가 저장함(saved) → weekly_totals()가 셈(counted). 빈 과목이나 잘못된 분이면 거절됨(rejected)으로 끝나고 "Not saved"가 나오며 아무것도 쓰이지 않습니다. 검사를 통과한 뒤에 파일 오류가 나도 보고하고, 반쯤 쓴 파일은 남기지 않습니다.

문서 간 추적성

요구사항 ID를 기능, 함수, 다이어그램, 테스트에 모두 적으면 아무것도 잃어버리지 않습니다. 예를 들어 REQ-02는 무엇이 성립해야 하는지(양수가 아닌 분은 거절)를 말합니다. FEAT-01은 그것을 사용자에게 보여 주고, parse_minutes()가 강제하고, 상태 다이어그램이 그리고, TEST-02가 증명합니다. 채점자나 프로젝트 막바지의 내가 이 사슬을 어느 방향으로든 따라갈 수 있습니다.

ACT 1 · Requirements and features

Requirement: observable conditions

Each REQ in the Requirement sheet links to SC IDs and has a check.

ACT 2 · Functions and tests

Contracts before bodies

Keep the values and failure rules that cross module boundaries consistent.

Quote = {date, code, name, market,
         previous_close: int, close: int,
         volume: int}
Analyzed row = Quote + {change_pct: float}
Summary = {count, up, down, flat, mean}
  • FUNC-01 parse_row(row): strings → a typed quote. ValueError on invalid fields.
  • FUNC-02 load_quotes(path): CSV → list. A missing file raises OSError.
  • FUNC-04 analyze(quotes, market): validated list → freshly made, sorted rows.
  • FUNC-05 summarize(rows): counts and mean. If empty, the mean is None.

Implement the smallest rule

Compute with full precision and round only in the report. The formula is (close − previous_close) / previous_close × 100. Reject a zero or negative price before dividing. A rise, a fall and a flat price are separate checks.

def change_pct(previous_close, close):
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    difference = close - previous_close
    return difference / previous_close * 100

assert change_pct(70000, 71400) == 2.0
assert change_pct(200000, 198000) == -1.0
assert change_pct(100, 100) == 0.0
print("Daily change checks passed.")

스냅숏 표본은 그 한계가 드러나 있을 때 쓸모가 있습니다. 제공된 가격과 거래량은 모두 수업용 가상 데이터입니다. 날짜 하나, 시장 라벨 둘, 예시 종목 다섯입니다. 평균(Mean)은 선택된 표본의 등락률을 같은 가중치로 평균한 값입니다. KOSPI/KOSDAQ 지수 수익률도 아니고 실시간 시세도 아닙니다.

입력 계약

반복문을 쓰기 전에 데이터를 먼저 정의합니다.

date,code,name,market,previous_close,close,volume
2026-11-05,005930,삼성전자,KOSPI,70000,71400,1000000
  • UTF-8 CSV이며 BOM이 있어도 받아들입니다. 헤더는 순서까지 정확해야 합니다.
  • 여섯 자리 종목 코드는 텍스트로 둡니다. 005930은 앞자리 0을 유지해야 합니다.
  • previous_close는 전 거래일 종가(원), close는 스냅숏 종가(원)이며 양의 정수입니다. volume은 거래된 주식 수로 0 이상의 정수입니다.
  • 날짜는 하나, 코드는 중복이 없어야 합니다. 두 종가는 같은 가격 기준을 씁니다.

ACT 1 · 요구사항과 기능

요구사항: 관찰 가능한 조건

요구사항 시트의 각 REQ는 SC ID와 연결되고 검사를 가집니다.

  • REQ-01: 유효한 CSV를 읽고 종목 코드를 보존한다.
  • REQ-02: 잘못된 값, 중복 코드, 섞인 날짜를 거절한다.
  • REQ-03: 일간 등락률을 계산하고, 필터하고, 정렬한다. 예: previous_close=70000, close=71400이면 +2%. KOSPI를 고르면 KOSPI 행만 나온다. 순서는 등락률 내림차순, 같으면 코드 오름차순.
  • REQ-04: 상승·하락·보합을 세고 표본 평균을 계산한다.
  • REQ-05: HTML에 날짜, 시장, 출처, 단위, 요약, 표를 보여 준다.
  • REQ-06: 파일·데이터 오류를 알리고, 실패하면 기존 HTML을 보존한다.

출력과 실패 정책도 제품의 일부입니다. 헤더만 있는 CSV는 유효한 빈 보고서(개수 0, 평균 N/A)를 만듭니다. CSV 파일이 없으면 성공한 빈 보고서가 아니라 오류입니다.

MVP 범위: Must, Should, Could

CSV → 분석 → HTML의 완전한 경로를 먼저 내놓습니다.

  • Must: 검증된 입력, 분석, 정적 HTML, 명확한 오류 처리.
  • Should: 브라우저에서 클릭하는 시장 필터.
  • Could: API 데이터, 기간 기록, 이동평균, 차트, 게시(publishing).

기존 수락 검사가 통과하기 전에는 새 Must를 추가하지 않습니다.

기능: 사용자의 세 가지 목표

python3 main.py --market KOSPI
python3 main.py --output docs/index.html

ACT 2 · 함수와 테스트

본문보다 계약 먼저

모듈 경계를 넘나드는 값과 실패 규칙을 일관되게 유지합니다.

Quote = {date, code, name, market,
         previous_close: int, close: int,
         volume: int}
Analyzed row = Quote + {change_pct: float}
Summary = {count, up, down, flat, mean}
  • FUNC-01 parse_row(row): 문자열 → 자료형이 있는 quote. 잘못된 필드는 ValueError.
  • FUNC-02 load_quotes(path): CSV → 목록. 파일이 없으면 OSError.
  • FUNC-04 analyze(quotes, market): 검증된 목록 → 새로 만든 정렬된 행.
  • FUNC-05 summarize(rows): 개수와 평균. 비어 있으면 평균은 None.

가장 작은 규칙 구현하기

계산은 전체 정밀도로 하고, 반올림은 보고서에서만 합니다. 공식은 (close − previous_close) / previous_close × 100입니다. 나누기 전에 0이나 음수 가격을 거절합니다. 상승, 하락, 보합은 각각 별도의 검사입니다.

def change_pct(previous_close, close):
    if previous_close <= 0 or close <= 0:
        raise ValueError("prices must be positive")
    difference = close - previous_close
    return difference / previous_close * 100

assert change_pct(70000, 71400) == 2.0
assert change_pct(200000, 198000) == -1.0
assert change_pct(100, 100) == 0.0
print("Daily change checks passed.")

모듈: 입출력은 가장자리에

모듈 다이어그램은 각 책임이 어디에 있는지 알려 줍니다.

  • main: 인자, 전체 조율, 메시지와 종료 코드.
  • storage: CSV 읽기와 원자적(atomic) HTML 쓰기. parse_row를 import합니다.
  • logic: 검증과 분석. report: escape된 HTML 문자열.

logic과 report는 파일을 열지도 사용자에게 묻지도 않습니다.

텍스트 변환은 한 번만 하고, 코드는 문자열로 둡니다.

import csv, io

          "005930,70000,71400\n")

              - int(row["previous_close"]))

csv.DictReader는 모든 필드를 문자열로 읽습니다. 어떤 행도 믿기 전에 헤더가 정확한지 검사합니다. parse_row가 가격과 거래량을 검증하고 변환합니다. 선택한 시장 밖의 행이라도 모든 행을 검증합니다.

필터, 정렬, 요약

계산은 HTML과 독립적으로 유지합니다. 섞인 날짜와 중복 코드는 필터하기 전에 거절합니다. 불러온 quote는 바꾸지 않고 새 dict를 반환합니다. 반올림하지 않은 등락률로 정렬하고, 값이 같으면 종목 코드로 정렬합니다. 행이 비면 평균은 None이고, 화면에서 N/A로 바꿉니다.

HTML은 결과를 보여 주는 뷰다

서식은 보여 주는 방식을 바꿀 뿐 계산을 바꾸면 안 됩니다. render_html은 문자열을 반환하고, 쓰기는 storage가 합니다. 종목 이름처럼 외부에서 온 텍스트에는 html.escape를 씁니다. 색깔뿐 아니라 부호와 숫자도 보여 줍니다. 날짜, 출처, 가상 데이터 표시, 단위를 넣습니다.

from html import escape
name = "<b>Example</b>"
change = 2.0
print(escape(name))
print(f"{change:+.2f}%")
&lt;b&gt;Example&lt;/b&gt;
+2.00%
